## Purpose

Определяет REST API, который отдаёт каталог согласованных конфигураций дверей с их допустимыми опциями размеров и цвета, и рассчитывает стоимость изделия по выбранной клиентом конфигурации и опциям.

## Requirements

### Requirement: Получение каталога конфигураций
Система ДОЛЖНА (SHALL) предоставлять эндпоинт, возвращающий все строки door_configuration. Для каждой конфигурации в ответе ДОЛЖНЫ (SHALL) присутствовать данные (id, code, name) её leaf_type вместе с данными (id, code, name) collection, которой принадлежит этот leaf_type, и, только если они заданы у этой конфигурации, — данные её frame_type, edge_type, door_casing_type и frame_extensions_type.

#### Scenario: Конфигурация только с полотном
- **WHEN** запрашивается каталог конфигураций и в базе есть door_configuration только со ссылкой на leaf_type (без frame_type, edge_type, door_casing_type, frame_extensions_type)
- **THEN** в ответе для этой конфигурации присутствуют данные leaf_type, а поля frame/edge/door_casing/frame_extensions отсутствуют или равны null

#### Scenario: Конфигурация с коробкой, добором и удлинителями
- **WHEN** запрашивается каталог конфигураций и в базе есть door_configuration со ссылками на leaf_type, frame_type, door_casing_type и frame_extensions_type
- **THEN** в ответе для этой конфигурации присутствуют данные всех четырёх связанных типов

#### Scenario: Пустой каталог
- **WHEN** запрашивается каталог конфигураций и в базе нет ни одной строки door_configuration
- **THEN** эндпоинт возвращает пустой список с кодом 200, а не ошибку

#### Scenario: Полотно всегда включает данные своей коллекции
- **WHEN** запрашивается каталог конфигураций и в базе есть door_configuration со ссылкой на leaf_type
- **THEN** в ответе для leaf-компонента этой конфигурации присутствуют данные (id, code, name) collection, которой принадлежит этот leaf_type

### Requirement: Состав каталога для frame-компонента включает список его позиций frame_post
Для frame-компонента каждой door_configuration в ответе каталога конфигураций система ДОЛЖНА (SHALL) включать список его записей frame_post — для каждой записи данные (id, code, name) её post_type, quantity, length (если задана) и retail_price/dealer_price.

#### Scenario: Короб с несколькими позициями возвращает все их данные в каталоге
- **WHEN** запрашивается каталог конфигураций и frame_type данной door_configuration имеет две записи frame_post
- **THEN** в ответе для frame-компонента этой конфигурации присутствует список из двух позиций с данными их post_type, quantity, length и ценами

#### Scenario: Короб без записей frame_post возвращает пустой список позиций
- **WHEN** запрашивается каталог конфигураций и frame_type данной door_configuration не имеет ни одной записи frame_post
- **THEN** в ответе для frame-компонента этой конфигурации список позиций пуст, запрос не завершается ошибкой

### Requirement: Допустимые опции размеров и цвета для каждого компонента конфигурации
Для каждого типа компонента, присутствующего в конкретной door_configuration (leaf_type и, если заданы, frame_type, edge_type, door_casing_type, frame_extensions_type), ответ каталога ДОЛЖЕН (SHALL) включать список допустимых для этого типа liner_dimension_option (id, тип размера, значение, признак стандартного размера) и список допустимых colour_option (id, цвет), сгруппированные по компоненту, к которому они относятся.

#### Scenario: Опции размеров и цвета относятся к своему компоненту
- **WHEN** запрашивается каталог конфигураций и у leaf_type данной конфигурации есть допустимые значения длины и высоты, а у её frame_type — допустимые цвета
- **THEN** в ответе значения длины/высоты перечислены как опции leaf-компонента этой конфигурации, а цвета — как опции frame-компонента, без смешения между компонентами

#### Scenario: Компонент без опций размера или цвета
- **WHEN** запрашивается каталог конфигураций и для edge_type данной конфигурации не заданы ни liner_dimension_option, ни colour_option
- **THEN** в ответе для edge-компонента этой конфигурации возвращаются пустые списки опций размеров и цветов, запрос не завершается ошибкой

### Requirement: Расчёт стоимости изделия по выбранной конфигурации
Система ДОЛЖНА (SHALL) предоставлять эндпоинт расчёта стоимости, принимающий id существующей door_configuration и, для каждого присутствующего в ней компонента (leaf, и если заданы — frame, edge, door_casing, frame_extensions), набор выбранных клиентом id опций: liner_dimension_option для тех измерений (длина/высота/толщина), для которых у этого компонента есть допустимые значения, и id colour_option, если у компонента есть допустимые цвета. Компонент, отсутствующий в выбранной конфигурации, не должен участвовать в запросе.

#### Scenario: Расчёт для конфигурации только с полотном
- **WHEN** отправляется запрос расчёта стоимости с id конфигурации, содержащей только leaf_type, и с выбранными для неё опциями размеров и цвета
- **THEN** эндпоинт возвращает стоимость, рассчитанную только по leaf-компоненту

#### Scenario: Несуществующая конфигурация
- **WHEN** отправляется запрос расчёта стоимости с id door_configuration, которого не существует
- **THEN** эндпоинт отвечает ошибкой 404 и не выполняет расчёт

#### Scenario: Опция не принадлежит компоненту конфигурации
- **WHEN** отправляется запрос расчёта стоимости, в котором id выбранной liner_dimension_option или colour_option ссылается на тип компонента, отличный от типа соответствующего компонента этой door_configuration (например, передан colour_option, принадлежащий frame_type, для leaf-компонента)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

### Requirement: Совместимость диапазона высоты кромки с высотой полотна
Если в запросе расчёта стоимости для edge-компонента выбрана liner_dimension_option оси «Высота» (диапазон [min_value, value], где отсутствие min_value означает открытую нижнюю границу), система ДОЛЖНА (SHALL) проверить, что это значение высоты полотна, выбранное клиентом для leaf-компонента той же конфигурации, находится внутри этого диапазона. Если высота полотна не выбрана клиентом, либо выбранный диапазон её не покрывает, эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт.

#### Scenario: Высота полотна внутри диапазона кромки — расчёт выполняется
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) попадает в диапазон [min_value, value] выбранной высоты кромки (edge)
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки

#### Scenario: Высота полотна вне диапазона кромки — 400
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) не попадает в диапазон [min_value, value] выбранной высоты кромки (edge)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Высота кромки выбрана без высоты полотна — 400
- **WHEN** отправляется запрос расчёта стоимости, в котором для edge-компонента выбрана liner_dimension_option оси «Высота», а для leaf-компонента высота не выбрана
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

### Requirement: Сопоставление наиболее специфичной цены компонента
Для каждого оцениваемого компонента, кроме frame (короб — см. «Стоимость короба как сумма цен его стоек»), система ДОЛЖНА (SHALL) рассматривать как подходящие только те строки configuration_price этого владельца (leaf_type/edge_type/door_casing_type/frame_extensions_type), у которых каждая непустая ссылка на length_option, height_option, thickness_option и colour_option совпадает с соответствующей опцией, выбранной клиентом для этого компонента; строки, ссылающиеся на ось размера или цвета, не совпадающую с выбором клиента, не подходят. Среди подходящих строк система ДОЛЖНА (SHALL) выбирать ту, у которой больше всего непустых ссылок (наиболее специфичную).

#### Scenario: Более специфичная цена побеждает менее специфичную
- **WHEN** для одного компонента подходят две строки configuration_price: одна ссылается только на length_option, совпадающий с выбором, другая — на тот же length_option и совпадающий colour_option
- **THEN** для расчёта используется вторая строка (с двумя совпавшими ссылками)

#### Scenario: Строка с несовпадающей осью не подходит
- **WHEN** для компонента есть строка configuration_price с непустым colour_option, отличным от выбранного клиентом colour_option
- **THEN** эта строка не рассматривается как подходящая для расчёта, даже если остальные её ссылки совпадают

### Requirement: Частичный расчёт при отсутствии цены компонента
Если для оцениваемого компонента не найдено ни одной подходящей строки configuration_price, либо несколько подходящих строк имеют одинаковую наивысшую специфичность (неоднозначное совпадение), система ДОЛЖНА (SHALL) исключить этот компонент из суммы и включить его в список некалькулируемых компонентов ответа, не прерывая расчёт по остальным компонентам ошибкой.

#### Scenario: Один из компонентов без цены
- **WHEN** отправляется запрос расчёта стоимости для конфигурации с полотном и коробкой, и для коробки с выбранными опциями не найдено подходящей строки configuration_price
- **THEN** эндпоинт отвечает кодом 200, итоговая сумма включает только стоимость полотна, а коробка указана в ответе как компонент без найденной цены

#### Scenario: Неоднозначное совпадение цены
- **WHEN** для одного компонента находятся две подходящие строки configuration_price с одинаковым (наибольшим) числом совпавших непустых ссылок
- **THEN** этот компонент считается некалькулируемым и исключается из суммы, как и в случае полного отсутствия подходящей цены

#### Scenario: Ни один компонент не оценён
- **WHEN** ни для одного из компонентов выбранной конфигурации не найдено подходящей строки configuration_price
- **THEN** эндпоинт отвечает кодом 200 с итоговой суммой, равной нулю, и списком всех компонентов конфигурации как некалькулируемых

### Requirement: Стоимость короба как сумма цен его стоек
Для frame-компонента выбранной конфигурации система ДОЛЖНА (SHALL) вычислять стоимость как сумму retail_price и отдельно сумму dealer_price всех записей frame_post, принадлежащих frame_type этой конфигурации, независимо от опций размера или цвета, переданных клиентом для этого компонента (у frame сейчас нет допустимых опций размера/цвета для выбора). Если у frame_type нет ни одной записи frame_post, frame-компонент ДОЛЖЕН (SHALL) считаться некалькулируемым — исключаться из общей суммы и включаться в список компонентов без найденной цены, как и для остальных компонентов при отсутствии подходящей цены.

#### Scenario: Короб из нескольких позиций суммируется
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type имеет две записи frame_post (например, незарезная стойка и комплект зарезных стоек)
- **THEN** стоимость frame-компонента равна сумме retail_price (и отдельно dealer_price) обеих записей frame_post

#### Scenario: Короб без записей frame_post остаётся некалькулируемым
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type не имеет ни одной записи frame_post
- **THEN** эндпоинт отвечает кодом 200, frame-компонент включается в разбивку как компонент без найденной цены, а итоговая сумма его не учитывает

### Requirement: Состав ответа расчёта стоимости
Ответ эндпоинта расчёта стоимости ДОЛЖЕН (SHALL) содержать итоговую розничную (retail) и дилерскую (dealer) цену изделия — суммы retail_price и dealer_price найденных строк configuration_price по всем оценённым компонентам, — а также разбивку по каждому компоненту конфигурации: найденную цену компонента (если найдена) либо отметку, что цена не найдена.

#### Scenario: Успешный расчёт по всем компонентам
- **WHEN** для всех компонентов выбранной конфигурации найдены подходящие строки configuration_price
- **THEN** ответ содержит итоговую retail- и dealer-цену, равную сумме цен по компонентам, и разбивку с ценой для каждого компонента
