## Purpose

Определяет REST API, который отдаёт каталог согласованных конфигураций дверей с их допустимыми опциями размеров и цвета, и рассчитывает стоимость изделия по выбранной клиентом конфигурации и опциям.

## Requirements

### Requirement: Получение каталога конфигураций
Система ДОЛЖНА (SHALL) предоставлять эндпоинт, возвращающий все строки door_configuration. Для каждой конфигурации в ответе ДОЛЖНЫ (SHALL) присутствовать данные (id, code, name) её leaf_type вместе с данными (id, code, name) collection, которой принадлежит этот leaf_type, и, только если они заданы у этой конфигурации, — данные её frame_type, edge_type, door_casing_type и frame_extensions_type.

#### Scenario: Конфигурация только с полотном
- **WHEN** запрашивается каталог конфигураций и в базе есть door_configuration только со ссылкой на leaf_type (без frame_type, edge_type, door_casing_type, frame_extensions_type)
- **THEN** в ответе для этой конфигурации присутствуют данные leaf_type, а поля frame/edge/door_casing/frame_extensions отсутствуют или равны null

#### Scenario: Конфигурация с коробкой, добором и удлинителями
- **WHEN** запрашивается каталог конфигураций и в базе есть door_configuration со ссылками на leaf_type, frame_type, door_casing_type и frame_extensions_type
- **THEN** в ответе для этой конфигурации присутствуют данные всех четырёх связанных типов

#### Scenario: Пустой каталог
- **WHEN** запрашивается каталог конфигураций и в базе нет ни одной строки door_configuration
- **THEN** эндпоинт возвращает пустой список с кодом 200, а не ошибку

#### Scenario: Полотно всегда включает данные своей коллекции
- **WHEN** запрашивается каталог конфигураций и в базе есть door_configuration со ссылкой на leaf_type
- **THEN** в ответе для leaf-компонента этой конфигурации присутствуют данные (id, code, name) collection, которой принадлежит этот leaf_type

### Requirement: Состав каталога для frame-компонента включает список его позиций frame_post
Для frame-компонента каждой door_configuration в ответе каталога конфигураций система ДОЛЖНА (SHALL) включать список его записей frame_post — для каждой записи данные (id, code, name) её post_type, quantity, length (если задана) и retail_price/dealer_price.

#### Scenario: Короб с несколькими позициями возвращает все их данные в каталоге
- **WHEN** запрашивается каталог конфигураций и frame_type данной door_configuration имеет две записи frame_post
- **THEN** в ответе для frame-компонента этой конфигурации присутствует список из двух позиций с данными их post_type, quantity, length и ценами

#### Scenario: Короб без записей frame_post возвращает пустой список позиций
- **WHEN** запрашивается каталог конфигураций и frame_type данной door_configuration не имеет ни одной записи frame_post
- **THEN** в ответе для frame-компонента этой конфигурации список позиций пуст, запрос не завершается ошибкой

### Requirement: Допустимые опции размеров и цвета для каждого компонента конфигурации
Для каждого типа компонента, присутствующего в конкретной door_configuration (leaf_type и, если заданы, frame_type, edge_type, door_casing_type, frame_extensions_type), ответ каталога ДОЛЖЕН (SHALL) включать список допустимых для этого типа liner_dimension_option (id, тип размера, значение, признак стандартного размера) и список допустимых colour_option (id, цвет), сгруппированные по компоненту, к которому они относятся.

#### Scenario: Опции размеров и цвета относятся к своему компоненту
- **WHEN** запрашивается каталог конфигураций и у leaf_type данной конфигурации есть допустимые значения длины и высоты, а у её frame_type — допустимые цвета
- **THEN** в ответе значения длины/высоты перечислены как опции leaf-компонента этой конфигурации, а цвета — как опции frame-компонента, без смешения между компонентами

#### Scenario: Компонент без опций размера или цвета
- **WHEN** запрашивается каталог конфигураций и для edge_type данной конфигурации не заданы ни liner_dimension_option, ни colour_option
- **THEN** в ответе для edge-компонента этой конфигурации возвращаются пустые списки опций размеров и цветов, запрос не завершается ошибкой

### Requirement: Расчёт стоимости изделия по выбранной конфигурации
Система ДОЛЖНА (SHALL) предоставлять эндпоинт расчёта стоимости, принимающий id существующей door_configuration и, для каждого присутствующего в ней компонента (leaf, и если заданы — frame, edge, door_casing, frame_extensions), набор выбранных клиентом id опций: liner_dimension_option для тех измерений (длина/высота/толщина), для которых у этого компонента есть допустимые значения, и id colour_option, если у компонента есть допустимые цвета. Компонент, отсутствующий в выбранной конфигурации, не должен участвовать в запросе. Независимо от компонентов конфигурации, запрос МОЖЕТ (MAY) дополнительно содержать список позиций фурнитуры (см. «Учёт фурнитуры в расчёте стоимости изделия») и список позиций декоративных элементов (см. «Учёт декоративных элементов в расчёте стоимости изделия») — оба списка не привязаны к door_configuration и допустимы для любой конфигурации, независимо друг от друга.

#### Scenario: Расчёт для конфигурации только с полотном
- **WHEN** отправляется запрос расчёта стоимости с id конфигурации, содержащей только leaf_type, и с выбранными для неё опциями размеров и цвета
- **THEN** эндпоинт возвращает стоимость, рассчитанную только по leaf-компоненту

#### Scenario: Несуществующая конфигурация
- **WHEN** отправляется запрос расчёта стоимости с id door_configuration, которого не существует
- **THEN** эндпоинт отвечает ошибкой 404 и не выполняет расчёт

#### Scenario: Опция не принадлежит компоненту конфигурации
- **WHEN** отправляется запрос расчёта стоимости, в котором id выбранной liner_dimension_option или colour_option ссылается на тип компонента, отличный от типа соответствующего компонента этой door_configuration (например, передан colour_option, принадлежащий frame_type, для leaf-компонента)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Расчёт с фурнитурой без выбранных опций компонентов
- **WHEN** отправляется запрос расчёта стоимости с id конфигурации и непустым списком позиций фурнитуры, но без выбранных опций ни одного компонента
- **THEN** эндпоинт выполняет расчёт как обычно, компоненты конфигурации считаются некалькулируемыми по общим правилам, а стоимость фурнитуры учитывается независимо от этого

#### Scenario: Расчёт с декоративными элементами без выбранных опций компонентов
- **WHEN** отправляется запрос расчёта стоимости с id конфигурации и непустым списком позиций декоративных элементов, но без выбранных опций ни одного компонента
- **THEN** эндпоинт выполняет расчёт как обычно, компоненты конфигурации считаются некалькулируемыми по общим правилам, а стоимость декоративных элементов учитывается независимо от этого

### Requirement: Совместимость диапазона высоты кромки с высотой полотна
Если в запросе расчёта стоимости для edge-компонента выбрана liner_dimension_option оси «Высота» (диапазон [min_value, value], где отсутствие min_value означает открытую нижнюю границу), система ДОЛЖНА (SHALL) проверить, что это значение высоты полотна, выбранное клиентом для leaf-компонента той же конфигурации, находится внутри этого диапазона. Если высота полотна не выбрана клиентом, либо выбранный диапазон её не покрывает, эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт.

#### Scenario: Высота полотна внутри диапазона кромки — расчёт выполняется
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) попадает в диапазон [min_value, value] выбранной высоты кромки (edge)
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки

#### Scenario: Высота полотна вне диапазона кромки — 400
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) не попадает в диапазон [min_value, value] выбранной высоты кромки (edge)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Высота кромки выбрана без высоты полотна — 400
- **WHEN** отправляется запрос расчёта стоимости, в котором для edge-компонента выбрана liner_dimension_option оси «Высота», а для leaf-компонента высота не выбрана
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

### Requirement: Совместимость диапазона высоты короба с высотой полотна
Если в запросе расчёта стоимости для frame-компонента, чей frame_type имеет код из набора кодов коробов с диапазонным ограничением высоты (на данный момент FT-002 «Компланар» и FT-003 «НЕО»), выбрана liner_dimension_option оси «Высота» (диапазон [min_value, max_value], где отсутствующая граница означает открытую с этой стороны границу, а при отсутствующем max_value верхней границей считается value), система ДОЛЖНА (SHALL) проверить, что значение высоты полотна, выбранное клиентом для leaf-компонента той же конфигурации, находится внутри этого диапазона. Если высота полотна не выбрана клиентом, либо выбранный диапазон её не покрывает, эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт. Для frame_type с кодом вне этого набора эта проверка не выполняется, даже если у него есть опции высоты. Правило действует одинаково независимо от leaf_type и от признака is_reverse конфигурации.

#### Scenario: Высота полотна внутри диапазона короба — расчёт выполняется
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) попадает в диапазон [min_value, max_value] выбранной высоты короба с frame_type кодом из набора (FT-002 или FT-003)
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки

#### Scenario: Высота полотна вне диапазона короба — 400
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) не попадает в диапазон [min_value, max_value] выбранной высоты короба с frame_type кодом из набора
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Высота короба выбрана без высоты полотна — 400
- **WHEN** отправляется запрос расчёта стоимости, в котором для frame-компонента с frame_type кодом из набора выбрана liner_dimension_option оси «Высота», а для leaf-компонента высота не выбрана
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Высота полотна в разрыве между диапазонами короба — 400
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) не попадает ни в один из непересекающихся диапазонов, заданных для опций высоты короба с frame_type кодом из набора, но выбрана одна из этих опций высоты
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Проверка не применяется к типам короба вне набора
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом вне набора (например, FT-001 «Фантом») выбрана liner_dimension_option оси «Высота», независимо от выбранной высоты полотна
- **THEN** эндпоинт выполняет расчёт как обычно, без проверки диапазона высоты полотна для этого компонента

#### Scenario: Диапазон высоты короба «Компланар» 2600–2850 покрыт, в отличие от короба «НЕО»
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна попадает в диапазон 2600–2850, и выбрана высота короба «Компланар» (FT-002), диапазон которой [2600, 2850]
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки — этот диапазон специфичен для данных короба «Компланар» и не совпадает с диапазонами, недоступными у короба «НЕО»

#### Scenario: Правило действует одинаково для обычной и реверсивной конфигурации
- **WHEN** отправляется запрос расчёта стоимости для door_configuration с is_reverse = true, чей frame_type имеет код из набора, и выбранная высота полотна не попадает в диапазон выбранной высоты короба
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт — так же, как и для обычной (не реверсивной) конфигурации с тем же frame_type

### Requirement: Обязательность высоты для короба с диапазонным ограничением
Если в запросе расчёта стоимости для frame-компонента, чей frame_type имеет код из набора кодов коробов с диапазонным ограничением высоты (FT-002, FT-003), не передан id liner_dimension_option оси «Высота» (heightOptionId отсутствует), эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт — высота для этих типов короба обязательна, а не опциональна, как для прочих типов короба. Это гарантирует, что для высоты полотна, не покрытой ни одним диапазоном такого короба, расчёт с этим коробом невозможен ни при каком запросе — в том числе при полном отсутствии выбранной высоты короба.

#### Scenario: Короб без выбранной высоты — 400
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом из набора (FT-002 или FT-003) не передан heightOptionId
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт, независимо от того, выбрана ли высота полотна

#### Scenario: Типы короба вне набора не требуют обязательной высоты
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом вне набора не передан heightOptionId
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки, связанной с отсутствием высоты

### Requirement: Совместимость диапазона длины добора «ТС» с высотой полотна
Если в запросе расчёта стоимости для frameExtensions-компонента, чей frame_extensions_type имеет код из набора кодов добора «ТС» (FET-004, FET-005, FET-006, FET-007), выбрана liner_dimension_option оси «Длина» (диапазон [min_value, max_value], где отсутствующая граница означает открытую с этой стороны границу, а при отсутствующем max_value верхней границей считается value), система ДОЛЖНА (SHALL) проверить, что значение высоты полотна, выбранное клиентом для leaf-компонента той же конфигурации, находится внутри этого диапазона. Если высота полотна не выбрана клиентом, либо выбранный диапазон её не покрывает, эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт. Для frame_extensions_type с кодом вне этого набора эта проверка не выполняется, даже если у него есть опции длины.

#### Scenario: Высота полотна внутри диапазона длины добора «ТС» — расчёт выполняется
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) попадает в диапазон [min_value, max_value] выбранной длины добора «ТС» (frameExtensions с frame_extensions_type кодом из набора FET-004–FET-007)
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки

#### Scenario: Высота полотна вне диапазона длины добора «ТС» — 400
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) не попадает в диапазон [min_value, max_value] выбранной длины добора «ТС»
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Длина добора «ТС» выбрана без высоты полотна — 400
- **WHEN** отправляется запрос расчёта стоимости, в котором для frameExtensions-компонента с frame_extensions_type кодом из набора FET-004–FET-007 выбрана liner_dimension_option оси «Длина», а для leaf-компонента высота не выбрана
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Высота полотна в разрыве между диапазонами длины добора «ТС» — 400
- **WHEN** отправляется запрос расчёта стоимости, где выбранная высота полотна (leaf) не попадает ни в один из непересекающихся диапазонов, заданных для опций длины добора «ТС», но выбрана одна из этих опций длины
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Проверка не применяется к добору «КОМПЛАНАР» и другим компонентам
- **WHEN** отправляется запрос расчёта стоимости, где для frameExtensions-компонента с frame_extensions_type кодом вне обоих наборов (добора «ТС» и добора «КОМПЛАНАР») выбрана liner_dimension_option оси «Длина», независимо от выбранной высоты полотна
- **THEN** эндпоинт выполняет расчёт как обычно, без проверки диапазона высоты полотна для этого компонента

### Requirement: Обязательность длины для добора «ТС»
Если в запросе расчёта стоимости для frameExtensions-компонента, чей frame_extensions_type имеет код из набора кодов добора «ТС» (FET-004, FET-005, FET-006, FET-007), не передан id liner_dimension_option оси «Длина» (lengthOptionId отсутствует), эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт — длина для этих типов добора обязательна, а не опциональна, как для прочих компонентов. Это гарантирует, что для высоты полотна, не покрытой ни одним диапазоном длины добора «ТС» (см. «Совместимость диапазона длины добора «ТС» с высотой полотна»), расчёт с этим добором невозможен ни при каком запросе — в том числе при полном отсутствии выбранной длины.

#### Scenario: Добор «ТС» без выбранной длины — 400
- **WHEN** отправляется запрос расчёта стоимости, где для frameExtensions-компонента с frame_extensions_type кодом из набора FET-004–FET-007 не передан lengthOptionId
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт, независимо от того, выбрана ли высота полотна

#### Scenario: Добор «КОМПЛАНАР» не требует обязательной длины
- **WHEN** отправляется запрос расчёта стоимости, где для frameExtensions-компонента с frame_extensions_type кодом вне обоих наборов (добора «ТС» и добора «КОМПЛАНАР») не передан lengthOptionId
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки, связанной с отсутствием длины

- **THEN** система ищет среди строк configuration_price с владельцем этим frame_type подходящую по выбранному цвету так же, как для leaf/edge/door_casing/frame_extensions

### Requirement: Частичный расчёт при отсутствии цены компонента
Если для оцениваемого компонента не найдено ни одной подходящей строки configuration_price, либо несколько подходящих строк имеют одинаковую наивысшую специфичность (неоднозначное совпадение), система ДОЛЖНА (SHALL) исключить этот компонент из суммы и включить его в список некалькулируемых компонентов ответа, не прерывая расчёт по остальным компонентам ошибкой.

#### Scenario: Один из компонентов без цены
- **WHEN** отправляется запрос расчёта стоимости для конфигурации с полотном и коробкой, и для коробки с выбранными опциями не найдено подходящей строки configuration_price
- **THEN** эндпоинт отвечает кодом 200, итоговая сумма включает только стоимость полотна, а коробка указана в ответе как компонент без найденной цены

#### Scenario: Неоднозначное совпадение цены
- **WHEN** для одного компонента находятся две подходящие строки configuration_price с одинаковым (наибольшим) числом совпавших непустых ссылок
- **THEN** этот компонент считается некалькулируемым и исключается из суммы, как и в случае полного отсутствия подходящей цены

#### Scenario: Ни один компонент не оценён
- **WHEN** ни для одного из компонентов выбранной конфигурации не найдено подходящей строки configuration_price
- **THEN** эндпоинт отвечает кодом 200 с итоговой суммой, равной нулю, и списком всех компонентов конфигурации как некалькулируемых

### Requirement: Наценка за нестандартную длину/высоту короба, наличника и добора
Для frame-, doorCasing- и frameExtensions-компонентов система ДОЛЖНА (SHALL) определять значение размера, использованное для этого компонента (для frame — выбранная высота: каталожная опция для короба «НЕО»/«Компланар» или значение, совпадающее с высотой полотна, для короба «Фантом»; для doorCasing/frameExtensions — выбранная каталожная опция длины, если она указана), и искать применимую строку pogonazh_surcharge_rule (см. pogonazh-surcharge-rules) для этого владельца (frame_type/door_casing_type/frame_extensions_type соответственно) — точечную (значение точно совпадает с value строки) либо диапазонную (значение попадает в диапазон min_value_exclusive/max_value_inclusive строки; на практике диапазонные строки встречаются только у короба «Фантом», не имеющего каталожной привязки значения). Если применимая строка найдена, её surcharge_percent ДОЛЖЕН (SHALL) быть применён к найденной цене компонента (после определения цены по configuration_price/frame_post, до умножения на количество для doorCasing/frameExtensions); если строка не найдена, либо размер для этого компонента не выбран/не применим, наценка не применяется. Эта наценка независима от наценок leaf-компонента (за нестандартный размер полотна, реверс, исполнение зеркала, вид остекления) и не влияет на них.

#### Scenario: Наценка применяется к коробу «НЕО»/«Компланар» за нестандартную высоту
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type «НЕО» или «Компланар» выбрана каталожная высота, для которой существует точечная строка pogonazh_surcharge_rule этого frame_type
- **THEN** к цене frame-компонента (сумме frame_post и, если применимо, цены цвета) применяется surcharge_percent этой строки

#### Scenario: Наценка применяется к коробу «Фантом» за нестандартную высоту полотна
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type «Фантом» значение высоты (совпадающее с высотой полотна) точно совпадает со значением точечной строки pogonazh_surcharge_rule этого frame_type
- **THEN** к цене frame-компонента применяется surcharge_percent этой строки

#### Scenario: Наценка применяется к коробу «Фантом» по диапазонному правилу
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type «Фантом» значение высоты (совпадающее с высотой полотна) не совпадает точно ни с одной точечной строкой pogonazh_surcharge_rule этого frame_type, но попадает в диапазон (min_value_exclusive, max_value_inclusive] диапазонной строки этого frame_type
- **THEN** к цене frame-компонента применяется surcharge_percent этой диапазонной строки

#### Scenario: Наценка применяется к наличнику или добору за нестандартную длину
- **WHEN** отправляется запрос расчёта стоимости, где для doorCasing- или frameExtensions-компонента выбрана каталожная опция длины, для которой существует точечная строка pogonazh_surcharge_rule этого door_casing_type/frame_extensions_type
- **THEN** к найденной цене этого компонента (до умножения на количество, см. «Количество наличника и добора в расчёте стоимости») применяется surcharge_percent этой строки

#### Scenario: Базовое значение — наценка не применяется
- **WHEN** отправляется запрос расчёта стоимости, где для frame-, doorCasing- или frameExtensions-компонента выбранное значение размера не совпадает ни с одной точечной строкой pogonazh_surcharge_rule этого владельца и не попадает в диапазон ни одной диапазонной строки
- **THEN** наценка за нестандартный погонаж не применяется, цена компонента вычисляется как раньше

#### Scenario: Наценка не зависит от наценок leaf-компонента
- **WHEN** отправляется запрос расчёта стоимости, где к цене frame-компонента применяется наценка за нестандартный погонаж, а к цене leaf-компонента — наценка за нестандартный размер полотна и/или надбавка за реверс
- **THEN** обе группы наценок применяются независимо, каждая только к своему компоненту

### Requirement: Стоимость короба как сумма цен его стоек
Для frame-компонента выбранной конфигурации система ДОЛЖНА (SHALL) вычислять базовую стоимость как сумму retail_price и отдельно сумму dealer_price всех записей frame_post, принадлежащих frame_type этой конфигурации (0, если ни одной записи frame_post нет). Если у этого frame_type задана хотя бы одна строка colour_option, стоимость короба ДОЛЖНА (SHALL) дополнительно зависеть от выбора цвета: если для colour_option, выбранного клиентом, находится ровно одна наиболее специфичная подходящая строка configuration_price с владельцем этим frame_type (см. «Сопоставление наиболее специфичной цены компонента»), её retail_price и dealer_price прибавляются к базовой сумме frame_post; если клиент не выбрал цвет, либо подходящая строка не найдена, либо совпадение неоднозначно, frame-компонент целиком ДОЛЖЕН (SHALL) считаться некалькулируемым — независимо от того, что сумма frame_post сама по себе была бы посчитана. Если у frame_type нет ни одной строки colour_option, калькулируемость короба зависит только от наличия записей frame_post, как раньше. К полученной таким образом сумме (frame_post плюс, если применимо, цена цвета) дополнительно применяется наценка за нестандартную высоту погонажа, если она применима (см. «Наценка за нестандартную длину/высоту короба, наличника и добора»).

#### Scenario: Короб из нескольких позиций суммируется
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type не имеет ни одной строки colour_option и имеет две записи frame_post (например, незарезная стойка и комплект зарезных стоек)
- **THEN** стоимость frame-компонента равна сумме retail_price (и отдельно dealer_price) обеих записей frame_post, с учётом наценки за нестандартный погонаж, если она применима

#### Scenario: Короб без записей frame_post остаётся некалькулируемым
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type не имеет ни одной строки colour_option и не имеет ни одной записи frame_post
- **THEN** эндпоинт отвечает кодом 200, frame-компонент включается в разбивку как компонент без найденной цены, а итоговая сумма его не учитывает

#### Scenario: Короб с выбранным цветом калькулируется по цене цвета
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type имеет строки colour_option и не имеет ни одной записи frame_post, и клиент выбрал colour_option, для которого находится ровно одна подходящая строка configuration_price
- **THEN** стоимость frame-компонента равна retail_price (и отдельно dealer_price) этой строки configuration_price, с учётом наценки за нестандартный погонаж, если она применима

#### Scenario: Короб с цветовыми опциями без выбора цвета остаётся некалькулируемым
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type имеет строки colour_option, и клиент не выбрал цвет для frame-компонента
- **THEN** frame-компонент считается некалькулируемым, даже если у этого frame_type есть записи frame_post, дающие положительную базовую сумму

#### Scenario: Короб с цветовыми опциями и неоднозначным или отсутствующим совпадением цвета остаётся некалькулируемым
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type имеет строки colour_option, и для выбранного клиентом colour_option не находится ни одной подходящей строки configuration_price либо находится несколько с одинаковой наивысшей специфичностью
- **THEN** frame-компонент считается некалькулируемым, как и для остальных компонентов при отсутствии однозначной цены

### Requirement: Состав ответа расчёта стоимости
Ответ эндпоинта расчёта стоимости ДОЛЖЕН (SHALL) содержать итоговую розничную (retail) и дилерскую (dealer) цену изделия — суммы retail_price и dealer_price найденных строк configuration_price по всем оценённым компонентам, плюс сумму стоимости всех позиций фурнитуры из запроса (см. «Учёт фурнитуры в расчёте стоимости изделия»), — а также разбивку по каждому компоненту конфигурации (найденную цену компонента, если найдена, либо отметку, что цена не найдена) и отдельную разбивку по каждой позиции фурнитуры из запроса.

#### Scenario: Успешный расчёт по всем компонентам
- **WHEN** для всех компонентов выбранной конфигурации найдены подходящие строки configuration_price
- **THEN** ответ содержит итоговую retail- и dealer-цену, равную сумме цен по компонентам, и разбивку с ценой для каждого компонента

#### Scenario: Итоговая цена включает стоимость фурнитуры
- **WHEN** запрос расчёта стоимости содержит одну или несколько позиций фурнитуры, помимо выбора компонентов конфигурации
- **THEN** итоговые retail- и dealer-цена ответа равны сумме цен компонентов конфигурации плюс сумма стоимости всех позиций фурнитуры, а разбивка ответа содержит отдельную строку для каждой позиции фурнитуры

### Requirement: Учёт фурнитуры в расчёте стоимости изделия
Запрос расчёта стоимости МОЖЕТ (MAY) содержать список независимых от door_configuration позиций фурнитуры; каждая позиция ДОЛЖНА (SHALL) указывать id существующего цветового варианта фурнитуры (hardware_option) и МОЖЕТ (MAY) указывать количество — положительное целое число единиц. Если количество не указано, система ДОЛЖНА (SHALL) считать его равным 1. Стоимость каждой позиции равна розничной и, отдельно, дилерской цене указанного варианта, умноженной на количество; сумма стоимости всех позиций фурнитуры ДОЛЖНА (SHALL) прибавляться к итоговой сумме, посчитанной по компонентам конфигурации (после применения к ним всех надбавок), как отдельное, последнее слагаемое. К фурнитуре никакие надбавки (за размер, реверс, исполнение зеркала и т.п.) не применяются. Список МОЖЕТ (MAY) содержать несколько позиций с одинаковым hardware_option — они не объединяются и учитываются как отдельные позиции. Указание hardware_option, которого не существует, ДОЛЖНО (SHALL) отклоняться ошибкой 400. Указанное количество ДОЛЖНО (SHALL) быть положительным целым числом; ноль или отрицательное значение отклоняются ошибкой 400.

#### Scenario: Одна позиция фурнитуры добавляется к итогу
- **WHEN** отправляется запрос расчёта стоимости с одной позицией фурнитуры (существующий hardware_option, количество 2)
- **THEN** итоговая retail- и dealer-цена ответа увеличена на розничную и дилерскую цену этого варианта, умноженную на 2, по сравнению с расчётом без этой позиции

#### Scenario: Количество по умолчанию равно 1
- **WHEN** отправляется запрос расчёта стоимости с позицией фурнитуры без указанного количества
- **THEN** позиция учитывается с количеством 1

#### Scenario: Несколько позиций фурнитуры суммируются независимо
- **WHEN** отправляется запрос расчёта стоимости с несколькими позициями фурнитуры, включая две позиции с одинаковым hardware_option, но разным количеством
- **THEN** итоговая сумма включает стоимость каждой позиции по отдельности, а разбивка ответа содержит отдельную строку для каждой из них

#### Scenario: Несуществующий вариант фурнитуры — 400
- **WHEN** отправляется запрос расчёта стоимости с позицией фурнитуры, чей id не соответствует ни одному hardware_option
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Нулевое или отрицательное количество фурнитуры недопустимо
- **WHEN** отправляется запрос расчёта стоимости с позицией фурнитуры, для которой указано количество, равное нулю или отрицательное
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Фурнитура не получает надбавок
- **WHEN** отправляется запрос расчёта стоимости для реверсивной конфигурации (is_reverse = true) с произвольным значением высоты полотна и с позицией фурнитуры
- **THEN** надбавка за реверс и надбавка за нестандартный размер применяются только к цене leaf-компонента, а стоимость позиции фурнитуры равна цене варианта, умноженной на количество, без каких-либо надбавок

### Requirement: Учёт декоративных элементов в расчёте стоимости изделия
Запрос расчёта стоимости МОЖЕТ (MAY) содержать список независимых от door_configuration позиций декоративных элементов; каждая позиция ДОЛЖНА (SHALL) указывать id существующего decorative_element_type (см. decorative-element-catalog) и МОЖЕТ (MAY) указывать количество — положительное целое число единиц. Если количество не указано, система ДОЛЖНА (SHALL) считать его равным 1. Стоимость каждой позиции равна розничной и, отдельно, дилерской цене указанного типа, умноженной на количество; сумма стоимости всех позиций декоративных элементов ДОЛЖНА (SHALL) прибавляться к итоговой сумме, посчитанной по компонентам конфигурации (после применения к ним всех надбавок) и по фурнитуре, как отдельное, последнее слагаемое. К декоративным элементам никакие надбавки не применяются, и их допустимость для выбранного leaf_type/коллекции (см. decorative-element-catalog, «Владение decorative_element_option») этим эндпоинтом не проверяется — список позиций принимается как есть, тем же принципом, что и фурнитура. Список МОЖЕТ (MAY) содержать несколько позиций с одинаковым decorative_element_type — они не объединяются и учитываются как отдельные позиции. Указание decorative_element_type, которого не существует, ДОЛЖНО (SHALL) отклоняться ошибкой 400. Указанное количество ДОЛЖНО (SHALL) быть положительным целым числом; ноль или отрицательное значение отклоняются ошибкой 400. Если у указанного leaf-компонента этой door_configuration определена длина полотна (выбранная либо произвольная — см. «Расчёт стоимости изделия по выбранной конфигурации»), для позиций декоративных элементов, чей decorative_element_type имеет строки decorative_element_width_option (см. decorative-element-catalog, «Ширина сандрика по диапазону длины полотна»), ширина в разбивке ДОЛЖНА (SHALL) резолвиться по этой длине; если длина полотна не определена или не попадает ни в один диапазон, ширина такой позиции остаётся неопределённой — расчёт стоимости от этого не зависит.

#### Scenario: Одна позиция декоративного элемента добавляется к итогу
- **WHEN** отправляется запрос расчёта стоимости с одной позицией декоративного элемента (существующий decorative_element_type, количество 2)
- **THEN** итоговая retail- и dealer-цена ответа увеличена на розничную и дилерскую цену этого типа, умноженную на 2, по сравнению с расчётом без этой позиции

#### Scenario: Количество по умолчанию равно 1
- **WHEN** отправляется запрос расчёта стоимости с позицией декоративного элемента без указанного количества
- **THEN** позиция учитывается с количеством 1

#### Scenario: Несколько позиций декоративных элементов суммируются независимо
- **WHEN** отправляется запрос расчёта стоимости с несколькими позициями декоративных элементов, включая две позиции с одинаковым decorative_element_type, но разным количеством
- **THEN** итоговая сумма включает стоимость каждой позиции по отдельности, а разбивка ответа содержит отдельную строку для каждой из них

#### Scenario: Несуществующий тип декоративного элемента — 400
- **WHEN** отправляется запрос расчёта стоимости с позицией декоративного элемента, чей id не соответствует ни одному decorative_element_type
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Нулевое или отрицательное количество декоративного элемента недопустимо
- **WHEN** отправляется запрос расчёта стоимости с позицией декоративного элемента, для которой указано количество, равное нулю или отрицательное
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Декоративные элементы не получают надбавок и не проверяются на допустимость для коллекции
- **WHEN** отправляется запрос расчёта стоимости для конфигурации с leaf_type коллекции «Фантом» и позицией плинтуса
- **THEN** позиция плинтуса учитывается в итоговой сумме по своей цене, умноженной на количество, без ошибки и без надбавок — проверка допустимости декоративного элемента для коллекции выполняется на фронтенде (см. door-configurator-ui), а не этим эндпоинтом

#### Scenario: Ширина сандрика резолвится по длине полотна конфигурации

### Requirement: Надбавка за реверс при расчёте стоимости полотна
Если выбранная конфигурация (door_configuration) отмечена как реверсивная (is_reverse = true), система ДОЛЖНА (SHALL), найдя подходящую строку configuration_price для leaf-компонента обычным образом, прибавить к найденным retail_price и dealer_price этого компонента надбавку за реверс. Надбавка применяется только к цене leaf-компонента и не влияет на цену короба (в т. ч. на сумму frame_post) и остальных компонентов конфигурации.

#### Scenario: Цена полотна включает надбавку при реверсивном коробе

- **THEN** стоимость leaf-компонента равна найденной цене с прибавленной надбавкой за реверс, а стоимость остальных компонентов конфигурации надбавка не затрагивает

#### Scenario: Надбавка не применяется при обычном коробе

- **THEN** стоимость leaf-компонента равна найденной цене без каких-либо надбавок

#### Scenario: Полотно без цены при реверсивном коробе остаётся некалькулируемым

- **THEN** leaf-компонент считается некалькулируемым, как и при обычном коробе

### Requirement: Произвольное значение длины и высоты полотна в запросе расчёта
Для leaf-компонента запрос расчёта стоимости ДОЛЖЕН (SHALL) допускать передачу произвольного значения длины и/или высоты в миллиметрах (customLengthValueMm/customHeightValueMm) вместо id каталожной liner_dimension_option (lengthOptionId/heightOptionId) для соответствующей оси. Для каждой оси (длина, высота) клиент МОЖЕТ (MAY) указать либо id каталожной опции, либо произвольное значение, но не оба одновременно. Произвольное значение высоты (customHeightValueMm, не длины) допустимо также для frame-компонента, чей frame_type имеет код из набора кодов коробов с высотой, зеркалирующей высоту полотна (на данный момент только FT-001 «Фантом», см. «Совпадение высоты короба «Фантом» с высотой полотна»); для всех прочих компонентов, отличных от leaf, и для длины любого компонента, отличного от leaf, произвольное значение по-прежнему недопустимо.

#### Scenario: Произвольное значение принимается вместо id опции

- **THEN** запрос обрабатывается, не возвращая ошибку валидации формата запроса

#### Scenario: Одновременное указание id опции и произвольного значения для одной оси недопустимо
- **WHEN** для одной и той же оси (например, длины) leaf-компонента одновременно указаны и lengthOptionId, и произвольное значение длины
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Произвольное значение для компонента, отличного от leaf, недопустимо
- **WHEN** произвольное значение длины или высоты указано для компонента, отличного от leaf, и отличного от frame-компонента с frame_type кодом из набора коробов с зеркалируемой высотой (например, для edge, doorCasing, frameExtensions, либо для короба «НЕО»/«Компланар»)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Произвольное значение высоты допустимо для короба «Фантом»
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом FT-001 указано произвольное значение высоты (customHeightValueMm)
- **THEN** запрос обрабатывается, не возвращая ошибку валидации формата запроса (совместимость этого значения с высотой полотна проверяется отдельным требованием «Совпадение высоты короба «Фантом» с высотой полотна»)

#### Scenario: Произвольное значение длины для короба «Фантом» недопустимо
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом FT-001 указано произвольное значение длины (customLengthValueMm)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт — у короба «Фантом» зеркалируется только высота, не длина

### Requirement: Совпадение высоты короба «Фантом» с высотой полотна
Если в запросе расчёта стоимости для frame-компонента, чей frame_type имеет код из набора кодов коробов с высотой, зеркалирующей высоту полотна (на данный момент только FT-001 «Фантом»), указано произвольное значение высоты (customHeightValueMm), система ДОЛЖНА (SHALL) проверить, что оно в точности равно значению высоты полотна, выбранному клиентом для leaf-компонента той же конфигурации (числовое равенство, а не диапазон, в отличие от коробов «НЕО»/«Компланар»). Если высота полотна не выбрана клиентом, либо указанное значение ей не равно, эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт. Для frame_type с кодом вне этого набора эта проверка не выполняется. У короба «Фантом» нет каталожных liner_dimension_option оси «Высота» — customHeightValueMm единственный способ задать его высоту.

#### Scenario: Высота короба «Фантом» равна высоте полотна — расчёт выполняется
- **WHEN** отправляется запрос расчёта стоимости, где значение высоты полотна (leaf) в точности равно указанному произвольному значению высоты короба «Фантом» (FT-001)
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки

#### Scenario: Высота короба «Фантом» не равна высоте полотна — 400
- **WHEN** отправляется запрос расчёта стоимости, где указанное произвольное значение высоты короба «Фантом» отличается от значения высоты полотна той же конфигурации
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Высота короба «Фантом» указана без высоты полотна — 400
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом FT-001 указано произвольное значение высоты, а для leaf-компонента высота не выбрана
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Проверка не применяется к другим коробам
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом вне набора (например, FT-002 «Компланар» или FT-003 «НЕО») указана высота, независимо от значения высоты полотна
- **THEN** эта проверка на точное равенство не выполняется для этого компонента (совместимость таких коробов проверяется требованием «Совместимость диапазона высоты короба с высотой полотна»)

### Requirement: Обязательность высоты короба «Фантом»
Если в запросе расчёта стоимости для frame-компонента, чей frame_type имеет код из набора кодов коробов с высотой, зеркалирующей высоту полотна (FT-001), не указано customHeightValueMm, эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт — высота для этого короба обязательна, а не опциональна. Поскольку у этого короба нет каталожных опций высоты, heightOptionId для него не может ссылаться на существующую строку (любое переданное значение отклоняется требованием «Опция не принадлежит компоненту конфигурации»); единственный способ задать высоту — обязательное customHeightValueMm.

#### Scenario: Короб «Фантом» без указанной высоты — 400
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом FT-001 не указано ни heightOptionId, ни customHeightValueMm
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт, независимо от того, выбрана ли высота полотна

#### Scenario: Другие короба не требуют customHeightValueMm
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type кодом вне набора (FT-002, FT-003 или без опций высоты) не указано customHeightValueMm
- **THEN** эндпоинт выполняет расчёт как обычно, без ошибки, связанной с отсутствием customHeightValueMm — обязательность высоты для этих коробов регулируется другими требованиями

### Requirement: Выбор исполнения зеркала в запросе расчёта
Для leaf-компонента запрос расчёта стоимости МОЖЕТ (MAY) указывать id выбранного исполнения зеркала — id строки mirror_finish_type (тот же id, что и в каталоге, и в ответе эндпоинта получения процентов надбавок; НЕ id строки mirror_finish_option). Указание исполнения зеркала для компонента, отличного от leaf, ДОЛЖНО (SHALL) отклоняться ошибкой 400. Указанный id ДОЛЖЕН (SHALL) ссылаться на mirror_finish_type, для которого существует строка mirror_finish_option, связывающая его с leaf_type данной door_configuration (т.е. исполнение допустимо для этого полотна); иначе — ошибка 400.

#### Scenario: Исполнение зеркала принимается для leaf-компонента
- **WHEN** отправляется запрос расчёта стоимости, где для leaf-компонента указан id исполнения зеркала (mirror_finish_type), допустимого для leaf_type этой конфигурации
- **THEN** запрос обрабатывается, не возвращая ошибку валидации формата запроса

#### Scenario: Исполнение зеркала для компонента, отличного от leaf, недопустимо
- **WHEN** исполнение зеркала указано для frame, edge, doorCasing или frameExtensions
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Исполнение зеркала, не принадлежащее полотну конфигурации, недопустимо
- **WHEN** указанный id исполнения зеркала (mirror_finish_type) существует, но для leaf_type данной door_configuration нет строки mirror_finish_option, связывающей его с этим исполнением
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Несуществующее исполнение зеркала недопустимо
- **WHEN** указанный id исполнения зеркала не существует ни в одной строке mirror_finish_type
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

### Requirement: Выбор вида остекления в запросе расчёта
Для leaf-компонента запрос расчёта стоимости МОЖЕТ (MAY) указывать id выбранного вида остекления — id строки glazing_type (тот же id, что и в каталоге, и в ответе эндпоинта получения процентов надбавок; НЕ id строки glazing_option). Указание вида остекления для компонента, отличного от leaf, ДОЛЖНО (SHALL) отклоняться ошибкой 400. Указанный id ДОЛЖЕН (SHALL) ссылаться на glazing_type, для которого существует строка glazing_option, связывающая его с leaf_type данной door_configuration (т.е. вид остекления допустим для этого полотна); иначе — ошибка 400.

#### Scenario: Вид остекления принимается для leaf-компонента
- **WHEN** отправляется запрос расчёта стоимости, где для leaf-компонента указан id вида остекления (glazing_type), допустимого для leaf_type этой конфигурации
- **THEN** запрос обрабатывается, не возвращая ошибку валидации формата запроса

#### Scenario: Вид остекления для компонента, отличного от leaf, недопустим
- **WHEN** вид остекления указан для frame, edge, doorCasing или frameExtensions
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Вид остекления, не принадлежащий полотну конфигурации, недопустим
- **WHEN** указанный id вида остекления (glazing_type) существует, но для leaf_type данной door_configuration нет строки glazing_option, связывающей его с этим видом остекления
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Несуществующий вид остекления недопустим
- **WHEN** указанный id вида остекления не существует ни в одной строке glazing_type
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

### Requirement: Разрешение произвольного значения размера полотна
Если для leaf-компонента указано произвольное значение длины или высоты, система ДОЛЖНА (SHALL) определить его статус в следующем порядке: (1) если значение совпадает с value одной из liner_dimension_option этого leaf_type для той же оси (стандартный каталожный размер) — считать наценку равной нулю, как при обычном выборе этой опции; (2) иначе, если для коллекции (collection) этого leaf_type задан collection_dimension_range для этой оси (см. door-collection-catalog) и значение выходит за пределы `[min_value, max_value]` этого диапазона — считать значение недопустимым немедленно, не переходя к поиску наценки; (3) иначе искать применимую точную строку dimension_surcharge_rule для той же оси (liner_dimension_type) и этого значения — сперва специфичную для конкретного leaf_type этого компонента, при её отсутствии — общую (не привязанную к leaf_type); если найдена обычная строка — применить её surcharge_percent как наценку к цене leaf-компонента; если найдена блокирующая строка (unavailable = true) — считать значение недопустимым; (4) для оси высоты, если точной строки не нашлось (ни обычной, ни блокирующей), пробовать каскадное правило (см. dimension-surcharge-rules, «Каскадная наценка для промежуточных значений сетки 50мм высоты полотна»); (5) иначе — считать значение недопустимым. Во всех случаях, когда значение считается недопустимым (шаги 2, 3 или 5), эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 с единым текстом «Данная нестандартная величина не поддерживается для данной модели», не выполняя расчёт.

#### Scenario: Значение совпадает со стандартным размером — наценки нет
- **WHEN** произвольное значение длины полотна совпадает со значением одной из его каталожных liner_dimension_option
- **THEN** расчёт выполняется без наценки за размер, как если бы клиент выбрал эту каталожную опцию

#### Scenario: Значение вне диапазона коллекции отклоняется до поиска наценки
- **WHEN** произвольное значение длины или высоты полотна выходит за пределы collection_dimension_range, заданного для коллекции этого leaf_type по соответствующей оси
- **THEN** эндпоинт отвечает ошибкой 400 с текстом «Данная нестандартная величина не поддерживается для данной модели», не выполняя расчёт и не обращаясь к dimension_surcharge_rule

#### Scenario: Значение совпадает с правилом наценки — надбавка применяется
- **WHEN** произвольное значение длины или высоты полотна совпадает со значением общей строки dimension_surcharge_rule (не привязанной к конкретному leaf_type) для соответствующей оси
- **THEN** к retail_price и dealer_price найденной цены leaf-компонента применяется surcharge_percent этого правила

#### Scenario: Значение совпадает с правилом наценки конкретной модели — надбавка применяется
- **WHEN** произвольное значение длины или высоты полотна совпадает со значением dimension_surcharge_rule для соответствующей оси, привязанной к leaf_type этого компонента
- **THEN** к retail_price и dealer_price найденной цены leaf-компонента применяется surcharge_percent этого правила, а не общего правила с тем же значением (если оно существует)

#### Scenario: Значение высоты вычисляется каскадным правилом — надбавка применяется
- **WHEN** произвольное значение высоты полотна не совпадает ни с одним каталожным размером, ни с одной точной строкой dimension_surcharge_rule, но применимо каскадное правило (см. dimension-surcharge-rules)
- **THEN** к retail_price и dealer_price найденной цены leaf-компонента применяется наценка, вычисленная каскадным правилом

#### Scenario: Неизвестное значение отклоняется
- **WHEN** произвольное значение длины или высоты полотна не совпадает ни с одним каталожным размером этого leaf_type, ни с одной применимой строкой dimension_surcharge_rule для соответствующей оси (ни общей, ни специфичной для этого leaf_type), и для оси высоты каскадное правило тоже не даёт результата (значение вне сетки 50мм, ниже 1900мм, либо спуск по сетке упирается в блокирующую строку)
- **THEN** эндпоинт отвечает ошибкой 400 с текстом «Данная нестандартная величина не поддерживается для данной модели», не выполняя расчёт

### Requirement: Последовательное применение наценок к цене полотна
Если для leaf-компонента применяется наценка за нестандартную длину, наценка за нестандартную высоту и/или надбавка за реверс (см. «Надбавка за реверс при расчёте стоимости полотна»), они ДОЛЖНЫ (SHALL) применяться к найденной базовой цене leaf-компонента последовательно, а не единым перемножением коэффициентов: (1) наценка за длину — к базовой цене, результат округляется; (2) наценка за высоту — к результату шага (1), результат округляется; (3) если конфигурация реверсивная — надбавка за реверс — к результату шага (2), результат округляется. Шаг, для которого наценка/надбавка не применяется (нет нестандартного размера по этой оси, конфигурация не реверсивная), пропускается, не изменяя результат предыдущего шага.

#### Scenario: Наценки применяются последовательно с округлением на каждом шаге
- **WHEN** отправляется запрос расчёта стоимости для реверсивной конфигурации (is_reverse = true), в котором для leaf-компонента указаны произвольные значения и длины, и высоты, совпадающие со строками dimension_surcharge_rule
- **THEN** итоговая цена leaf-компонента вычисляется как: сумма₁ = округление(базовая_цена × (1 + наценка_за_длину)); сумма₂ = округление(сумма₁ × (1 + наценка_за_высоту)); итог = округление(сумма₂ × (1 + надбавка_за_реверс))

#### Scenario: Надбавка за реверс применяется к уже округлённой цене с учётом наценки за размер
- **WHEN** отправляется запрос расчёта стоимости для реверсивной конфигурации, в котором для leaf-компонента указано произвольное значение только по одной оси (например, только длины), совпадающее с dimension_surcharge_rule
- **THEN** надбавка за реверс применяется к округлённому результату шага применения наценки за длину, а не к базовой цене leaf-компонента напрямую

### Requirement: Место наценки за исполнение зеркала в последовательности надбавок
Если для leaf-компонента выбрано исполнение зеркала, его наценка ДОЛЖНА (SHALL) применяться к цене leaf-компонента последовательно, вместе с уже существующими наценками (см. «Последовательное применение наценок к цене полотна»), в следующем порядке: (1) наценка за длину; (2) наценка за высоту; (3) наценка за исполнение зеркала; (4) надбавка за реверс (если конфигурация реверсивная) — каждый шаг применяется к результату предыдущего, с округлением после каждого шага. Шаг наценки за зеркало пропускается (не изменяет результат предыдущего шага), если исполнение зеркала не выбрано.

#### Scenario: Наценка за зеркало применяется после высоты и до реверса
- **WHEN** отправляется запрос расчёта стоимости для реверсивной конфигурации, в котором для leaf-компонента указаны произвольное значение высоты, совпадающее с dimension_surcharge_rule, и исполнение зеркала
- **THEN** итоговая цена leaf-компонента вычисляется как: сумма₁ = округление(базовая_цена × (1 + наценка_за_высоту)); сумма₂ = округление(сумма₁ × (1 + наценка_за_зеркало)); итог = округление(сумма₂ × (1 + надбавка_за_реверс))

#### Scenario: Без выбранного исполнения зеркала шаг пропускается
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента исполнение зеркала не указано
- **THEN** итоговая цена leaf-компонента вычисляется без шага наценки за зеркало, как и до появления этого требования

### Requirement: Место наценки за вид остекления в последовательности надбавок
Если для leaf-компонента выбран вид остекления, его наценка (surcharge_percent соответствующего glazing_type) ДОЛЖНА (SHALL) применяться к цене leaf-компонента последовательно, вместе с уже существующими надбавками (см. «Последовательное применение наценок к цене полотна», «Место наценки за исполнение зеркала в последовательности надбавок»), в следующем порядке: (1) наценка за длину; (2) наценка за высоту; (3) наценка за исполнение зеркала (если выбрано); (4) наценка за вид остекления (если выбран); (5) надбавка за реверс (если конфигурация реверсивная) — каждый шаг применяется к результату предыдущего, с округлением после каждого шага. Шаг наценки за вид остекления пропускается (не изменяет результат предыдущего шага), если вид остекления не выбран, а также если выбранный вид остекления — «Прозрачное» (его surcharge_percent равен нулю).

#### Scenario: Наценка за вид остекления применяется после исполнения зеркала и до реверса
- **WHEN** отправляется запрос расчёта стоимости для реверсивной конфигурации, в котором для leaf-компонента указаны произвольное значение высоты, совпадающее с dimension_surcharge_rule, и вид остекления с ненулевой наценкой
- **THEN** итоговая цена leaf-компонента вычисляется как: сумма₁ = округление(базовая_цена × (1 + наценка_за_высоту)); сумма₂ = округление(сумма₁ × (1 + наценка_за_остекление)); итог = округление(сумма₂ × (1 + надбавка_за_реверс))

#### Scenario: Без выбранного вида остекления шаг пропускается
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента вид остекления не указан
- **THEN** итоговая цена leaf-компонента вычисляется без шага наценки за остекление, как и до появления этого требования

#### Scenario: Базовое «Прозрачное» остекление не добавляет наценку
- **WHEN** для leaf-компонента указан id вида остекления «Прозрачное» (surcharge_percent = 0)
- **THEN** итоговая цена leaf-компонента вычисляется так же, как если бы вид остекления не был указан вовсе

### Requirement: Наценка за выбранный цвет полотна
Если для leaf-компонента выбран colour_option (фронтальный цвет), чей colour_type имеет ненулевой surcharge_percent, система ДОЛЖНА (SHALL) применить этот процент как наценку к цене leaf-компонента. Если для этого же leaf-компонента установлен признак двусторонней покраски (см. «Второй цвет и признак двусторонней покраски полотна в запросе расчёта») и указан задний colour_option, чей colour_type тоже имеет ненулевой surcharge_percent, система ДОЛЖНА (SHALL) сложить проценты наценки фронтального и заднего цвета и применить результат как единую наценку одним шагом — а не последовательно перемножать множители каждой стороны друг на друга. Если наценку даёт только одна из двух сторон (при двусторонней покраске), либо единственный выбранный цвет (без двусторонней покраски), наценка равна проценту этой стороны — без изменений по сравнению с прежним поведением. Если ни фронтальный, ни (при двусторонней покраске) задний цвет не дают наценки, либо цвет для leaf-компонента не выбран вовсе, шаг наценки за цвет пропускается, не изменяя цену.

#### Scenario: Выбран цвет с ненулевой наценкой
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента (без двусторонней покраски) выбран colour_option, ссылающийся на colour_type с surcharge_percent = 20 (например, «Другой цвет из коллекции RAL и NCS»)
- **THEN** к цене leaf-компонента применяется наценка 20%

#### Scenario: Выбран цвет без наценки
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента выбран colour_option, ссылающийся на colour_type с surcharge_percent = 0
- **THEN** цена leaf-компонента вычисляется без наценки за цвет, как и до появления этого требования

#### Scenario: Цвет не выбран
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента цвет не указан
- **THEN** цена leaf-компонента вычисляется без шага наценки за цвет

#### Scenario: Двусторонняя покраска — наценки за оба цвета суммируются, а не перемножаются
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента установлен признак двусторонней покраски, фронтальный цвет ссылается на colour_type с surcharge_percent = 20, а задний цвет — на другой colour_type, тоже с surcharge_percent = 20
- **THEN** к цене leaf-компонента на шаге наценки за цвет применяется единая наценка 40% (20% + 20%), а не 44%, которые дало бы последовательное умножение множителей 1.2 × 1.2

#### Scenario: Двусторонняя покраска — наценку даёт только одна сторона
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента установлен признак двусторонней покраски, фронтальный цвет ссылается на colour_type с surcharge_percent = 20, а задний цвет — на colour_type с surcharge_percent = 0
- **THEN** к цене leaf-компонента на шаге наценки за цвет применяется наценка 20%, как если бы двусторонняя покраска не была выбрана

#### Scenario: Двусторонняя покраска — ни одна сторона не даёт наценки
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента установлен признак двусторонней покраски, а оба выбранных цвета (фронтальный и задний) ссылаются на colour_type с surcharge_percent = 0
- **THEN** шаг наценки за цвет пропускается, не изменяя цену (надбавка за саму двустороннюю покраску, см. «Наценка за двустороннюю покраску полотна», при этом всё равно применяется)

### Requirement: Второй цвет и признак двусторонней покраски полотна в запросе расчёта
Для leaf-компонента запрос расчёта стоимости МОЖЕТ (MAY) указывать признак двусторонней покраски (булево значение) и, независимо от него, id второго (заднего) colour_option — в дополнение к уже существующему id цвета этого компонента (см. «Допустимые опции размеров и цвета для каждого компонента конфигурации»), который при этом трактуется как цвет фронтальной стороны. Задний цвет учитывается в расчёте (см. «Наценка за выбранный цвет полотна») только если признак двусторонней покраски установлен в true; если признак не установлен или равен false, а задний цвет указан, эндпоинт ДОЛЖЕН (SHALL) отклонить запрос ошибкой 400. Указание заднего цвета или признака двусторонней покраски для компонента, отличного от leaf, ДОЛЖНО (SHALL) отклоняться ошибкой 400. Указанный id заднего цвета, если он передан, ДОЛЖЕН (SHALL) ссылаться на colour_option, принадлежащий leaf_type данной door_configuration, — по тому же правилу, что и для фронтального цвета; иначе — ошибка 400. Признак двусторонней покраски, установленный без указанного заднего цвета, допустим: наценка за двустороннюю покраску (см. «Наценка за двустороннюю покраску полотна») всё равно применяется, а наценка за цвет учитывает только фронтальную сторону.

#### Scenario: Двусторонняя покраска с обоими цветами принимается
- **WHEN** отправляется запрос расчёта стоимости, где для leaf-компонента установлен признак двусторонней покраски, указан фронтальный цвет и задний цвет, оба принадлежащие leaf_type этой конфигурации
- **THEN** запрос обрабатывается, не возвращая ошибку валидации формата запроса

#### Scenario: Задний цвет без двусторонней покраски отклоняется
- **WHEN** отправляется запрос расчёта стоимости, где для leaf-компонента указан задний цвет, но признак двусторонней покраски не установлен (или равен false)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Двусторонняя покраска или задний цвет для компонента, отличного от leaf, недопустимы
- **WHEN** признак двусторонней покраски или задний цвет указаны для frame, edge, doorCasing или frameExtensions
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Задний цвет, не принадлежащий полотну конфигурации, недопустим
- **WHEN** отправляется запрос расчёта стоимости с установленным признаком двусторонней покраски, в котором id заднего цвета ссылается на colour_option, принадлежащий типу компонента, отличному от leaf_type этой конфигурации (либо не существует)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Двусторонняя покраска без указанного заднего цвета допустима
- **WHEN** отправляется запрос расчёта стоимости, где для leaf-компонента установлен признак двусторонней покраски, указан только фронтальный цвет (или цвет не указан вовсе), а задний цвет не передан
- **THEN** запрос обрабатывается: наценка за цвет учитывает только фронтальную сторону, а надбавка за двустороннюю покраску применяется

### Requirement: Наценка за двустороннюю покраску полотна
Если для leaf-компонента установлен признак двусторонней покраски (см. «Второй цвет и признак двусторонней покраски полотна в запросе расчёта») в true, система ДОЛЖНА (SHALL) применить к цене leaf-компонента дополнительную надбавку 50% — независимо от того, выбраны ли цвета (фронтальный и/или задний) и дают ли они собственную наценку за цвет (см. «Наценка за выбранный цвет полотна»). Эта надбавка не отменяет и не заменяет наценку за выбранный цвет — обе применяются одновременно, если применимы. Если признак двусторонней покраски не установлен (или false), шаг этой надбавки пропускается, не изменяя цену.

#### Scenario: Двусторонняя покраска без выбранных цветов всё равно даёт надбавку
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента установлен признак двусторонней покраски, а фронтальный и задний цвет не выбраны
- **THEN** к цене leaf-компонента применяется надбавка 50%

#### Scenario: Надбавка за двустороннюю покраску сочетается с наценкой за цвет
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента установлен признак двусторонней покраски и выбран фронтальный цвет с ненулевой наценкой
- **THEN** к цене leaf-компонента применяются и наценка за цвет, и надбавка 50% за двустороннюю покраску — ни одна из них не отменяет другую

#### Scenario: Без двусторонней покраски надбавка не применяется
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента признак двусторонней покраски не установлен
- **THEN** цена leaf-компонента вычисляется без шага надбавки за двустороннюю покраску, как и до появления этого требования

### Requirement: Место наценки за цвет в последовательности надбавок
Наценка за выбранный цвет полотна (см. «Наценка за выбранный цвет полотна») ДОЛЖНА (SHALL) применяться к цене leaf-компонента последовательно, вместе с уже существующими наценками (см. «Последовательное применение наценок к цене полотна», «Место наценки за исполнение зеркала в последовательности надбавок», «Место наценки за вид остекления в последовательности надбавок»), в следующем порядке: (1) наценка за длину; (2) наценка за высоту; (3) наценка за цвет (если применяется); (4) наценка за исполнение зеркала (если выбрано); (5) наценка за вид остекления (если выбран); (6) надбавка за реверс (если конфигурация реверсивная) — каждый шаг применяется к результату предыдущего, с округлением после каждого шага.

#### Scenario: Наценка за цвет применяется после высоты и до исполнения зеркала
- **WHEN** отправляется запрос расчёта стоимости для реверсивной конфигурации, в котором для leaf-компонента указаны произвольное значение высоты, совпадающее с dimension_surcharge_rule, цвет с ненулевой наценкой и исполнение зеркала
- **THEN** итоговая цена leaf-компонента вычисляется как: сумма₁ = округление(базовая_цена × (1 + наценка_за_высоту)); сумма₂ = округление(сумма₁ × (1 + наценка_за_цвет)); сумма₃ = округление(сумма₂ × (1 + наценка_за_зеркало)); итог = округление(сумма₃ × (1 + надбавка_за_реверс))

### Requirement: Место надбавки за двустороннюю покраску в последовательности надбавок
Надбавка за двустороннюю покраску полотна (см. «Наценка за двустороннюю покраску полотна») ДОЛЖНА (SHALL) применяться к цене leaf-компонента последовательно, вместе с уже существующими наценками (см. «Последовательное применение наценок к цене полотна», «Место наценки за исполнение зеркала в последовательности надбавок», «Место наценки за вид остекления в последовательности надбавок», «Место наценки за цвет в последовательности надбавок»), в следующем порядке: (1) наценка за длину; (2) наценка за высоту; (3) наценка за цвет (если применяется — с учётом суммирования по фронтальной и задней стороне при двусторонней покраске, см. «Наценка за выбранный цвет полотна»); (4) надбавка за двустороннюю покраску (если применяется); (5) наценка за исполнение зеркала (если выбрано); (6) наценка за вид остекления (если выбран); (7) надбавка за реверс (если конфигурация реверсивная) — каждый шаг применяется к результату предыдущего, с округлением после каждого шага.

#### Scenario: Надбавка за двустороннюю покраску применяется после цвета и до исполнения зеркала
- **WHEN** отправляется запрос расчёта стоимости для реверсивной конфигурации, в котором для leaf-компонента указаны цвет с ненулевой наценкой, признак двусторонней покраски и исполнение зеркала
- **THEN** итоговая цена leaf-компонента вычисляется как: сумма₁ = округление(базовая_цена × (1 + наценка_за_цвет)); сумма₂ = округление(сумма₁ × (1 + 0.5)); сумма₃ = округление(сумма₂ × (1 + наценка_за_зеркало)); итог = округление(сумма₃ × (1 + надбавка_за_реверс))

### Requirement: Признак реверса в каталоге конфигураций
Ответ каталога конфигураций ДОЛЖЕН (SHALL) включать для каждой door_configuration признак is_reverse этой конфигурации.

#### Scenario: Реверсивная конфигурация помечена в каталоге
- **WHEN** запрашивается каталог конфигураций и в базе есть door_configuration с is_reverse = true
- **THEN** в ответе для этой конфигурации присутствует признак реверса со значением true

#### Scenario: Обычная конфигурация помечена в каталоге
- **WHEN** запрашивается каталог конфигураций и в базе есть door_configuration с is_reverse = false
- **THEN** в ответе для этой конфигурации присутствует признак реверса со значением false

### Requirement: Признак «Четверть» в каталоге конфигураций

### Requirement: Получение процентов надбавок к цене полотна
Система ДОЛЖНА (SHALL) предоставлять read-only эндпоинт, возвращающий все правила наценки за нестандартный размер полотна (тип размера, значение в мм, id модели полотна — если правило привязано к конкретному leaf_type, иначе null, процент наценки — по одной записи на строку dimension_surcharge_rule) вместе с процентом надбавки за реверс, применяемым при расчёте стоимости, и все правила наценки за нестандартную длину/высоту погонажа (владелец — frame_type/door_casing_type/frame_extensions_type, значение в мм либо, для диапазонных правил, границы диапазона, процент наценки — по одной записи на строку pogonazh_surcharge_rule, см. pogonazh-surcharge-rules). Эндпоинт не принимает параметров и не зависит от конкретной door_configuration. Существующий эндпоинт расчёта стоимости (`POST /api/door-configurations/{id}/price`) этим требованием не затрагивается — контракт его запроса не меняется (об изменении контракта ответа см. «Базовая цена компонента в ответе расчёта стоимости»).

#### Scenario: Возвращаются все правила наценки за размер и надбавка за реверс

- **THEN** ответ содержит все строки dimension_surcharge_rule (тип размера, значение, id модели полотна или null, процент) и процент надбавки за реверс, используемый расчётом стоимости

#### Scenario: Правило, привязанное к конкретной модели, возвращается с её id

- **THEN** возвращённый процент надбавки за реверс равен проценту, который `POST /api/door-configurations/{id}/price` фактически применяет к цене полотна реверсивной конфигурации

#### Scenario: Возвращаются все правила наценки за погонаж

- **THEN** ответ дополнительно содержит все строки pogonazh_surcharge_rule (владелец, значение либо границы диапазона, процент), наряду с уже существующими полями

- **THEN** в соответствующем элементе списка правил наценки за погонаж value равен null, а заданные границы диапазона возвращаются в отдельных полях ответа

#### Scenario: Пустой справочник наценок за погонаж не считается ошибкой

### Requirement: Базовая цена компонента в ответе расчёта стоимости
Каждый оценённый (priced = true) компонент в разбивке ответа эндпоинта расчёта стоимости (`POST /api/door-configurations/{id}/price`) ДОЛЖЕН (SHALL), в дополнение к существующим полям, содержать базовую розничную и дилерскую цену этого компонента — цену найденной строки configuration_price/frame_post до применения наценки за нестандартный размер полотна, надбавки за реверс (leaf) и наценки за нестандартную длину/высоту погонажа (frame/doorCasing/frameExtensions, см. «Наценка за нестандартную длину/высоту короба, наличника и добора»). Для компонентов, к которым ни одна из применимых им наценок не применяется, базовая цена компонента совпадает с его итоговой ценой. Некалькулируемые (priced = false) компоненты не содержат базовой цены. Это расширение контракта ответа аддитивно, на уровне объекта компонента: ранее существовавшие поля не меняются и не удаляются, контракт запроса не меняется, итоговые суммы (`totalRetailPrice`/`totalDealerPrice`) не меняются.

#### Scenario: Базовая цена компонента равна итоговой при отсутствии надбавок
- **WHEN** отправляется запрос расчёта стоимости, для которого ни одна надбавка (за размер полотна, за реверс, за нестандартный погонаж) не применяется к оцененному компоненту
- **THEN** базовая розничная и дилерская цена этого компонента в ответе равны его итоговой розничной и дилерской цене

#### Scenario: Базовая цена leaf-компонента меньше итоговой при применённых надбавках
- **WHEN** отправляется запрос расчёта стоимости, для которого к цене leaf-компонента применяется хотя бы одна надбавка (за нестандартный размер и/или за реверс)
- **THEN** базовая розничная и дилерская цена leaf-компонента в ответе меньше его итоговой розничной и дилерской цены ровно на сумму применённых к нему надбавок

#### Scenario: Базовая цена короба, наличника или добора меньше итоговой при применённой наценке за нестандартный погонаж
- **WHEN** отправляется запрос расчёта стоимости, для которого к цене frame-, doorCasing- или frameExtensions-компонента применяется наценка за нестандартную длину/высоту погонажа
- **THEN** базовая розничная и дилерская цена этого компонента в ответе меньше его итоговой розничной и дилерской цены ровно на сумму применённой наценки

#### Scenario: Базовая цена компонентов, к которым надбавки не применяются, всегда совпадает с их итоговой ценой
- **WHEN** отправляется запрос расчёта стоимости для конфигурации с edge-компонентом (кромкой) — единственным компонентом, к которому никакая наценка никогда не применяется
- **THEN** базовая цена edge-компонента в ответе совпадает с его итоговой ценой, независимо от того, применены ли какие-либо наценки к другим компонентам той же конфигурации

### Requirement: Количество наличника и добора в расчёте стоимости
Для компонентов doorCasing (наличник) и frameExtensions (добор) запрос расчёта стоимости МОЖЕТ (MAY) указывать количество — положительное целое число. Если количество не указано, система ДОЛЖНА (SHALL) считать его равным 1 (текущее поведение сохраняется). Если найдена подходящая строка configuration_price для этого компонента, система ДОЛЖНА (SHALL) сначала применить к её цене наценку за нестандартную длину погонажа, если она применима (см. «Наценка за нестандартную длину/высоту короба, наличника и добора»), а затем умножить результат на указанное количество — итоговые retail_price и dealer_price равны этому произведению; базовая цена компонента (см. «Базовая цена компонента в ответе расчёта стоимости») равна цене найденной строки (без наценки за погонаж), умноженной на то же количество. Указание количества для компонента, отличного от doorCasing и frameExtensions, ДОЛЖНО (SHALL) отклоняться ошибкой 400. Указанное количество ДОЛЖНО (SHALL) быть положительным целым числом; ноль, отрицательное значение отклоняются ошибкой 400.

#### Scenario: Количество не указано — цена как за одну единицу
- **WHEN** отправляется запрос расчёта стоимости для наличника или добора без указания количества
- **THEN** цена этого компонента равна найденной цене configuration_price (с наценкой за нестандартный погонаж, если она применима) без дополнительного умножения

#### Scenario: Указанное количество умножает цену компонента
- **WHEN** отправляется запрос расчёта стоимости, где для наличника или добора указано количество N, найдена подходящая строка configuration_price и применима наценка за нестандартную длину погонажа
- **THEN** итоговая retail_price и dealer_price этого компонента равны (retail_price/dealer_price найденной строки, увеличенным на наценку за погонаж), умноженным на N

#### Scenario: Количество для компонента, отличного от наличника и добора, недопустимо
- **WHEN** отправляется запрос расчёта стоимости, где количество указано для leaf, frame или edge
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Нулевое или отрицательное количество недопустимо
- **WHEN** отправляется запрос расчёта стоимости, где для наличника или добора указано количество, равное нулю или отрицательное
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Количество не влияет на компонент без найденной цены
- **WHEN** отправляется запрос расчёта стоимости, где для наличника или добора указано количество, но подходящая строка configuration_price не найдена
- **THEN** компонент считается некалькулируемым, как и без указания количества

### Requirement: Наценка за выбранную толщину полотна
Если для leaf-компонента выбрана каталожная опция толщины (id `liner_dimension_option` для оси «ТОЛЩИНА»), для значения которой существует применимая строка `dimension_surcharge_rule` (сперва специфичная для leaf_type этого компонента, при её отсутствии — общая), система ДОЛЖНА (SHALL) применить её `surcharge_percent` как наценку к цене leaf-компонента. Если для значения выбранной опции толщины нет ни специфичной, ни общей строки `dimension_surcharge_rule` (в том числе для стандартной толщины 44 мм), либо толщина не выбрана вовсе, шаг наценки за толщину пропускается, не изменяя цену — это не считается ошибкой, в отличие от произвольного (нестандартного) значения длины/высоты: у толщины нет режима произвольного значения, выбор всегда идёт по id существующей каталожной опции, поэтому отсутствие правила наценки для неё означает лишь «наценки нет», а не «недопустимое значение».

#### Scenario: Выбрана толщина с наценкой
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента выбрана опция толщины, для значения которой есть dimension_surcharge_rule с surcharge_percent = 20
- **THEN** к цене leaf-компонента применяется наценка 20%

#### Scenario: Выбрана толщина без наценки
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента выбрана опция толщины, для значения которой нет ни одной строки dimension_surcharge_rule (например, стандартная толщина 44 мм)
- **THEN** цена leaf-компонента вычисляется без наценки за толщину, как и до появления этого требования

#### Scenario: Толщина не выбрана
- **WHEN** отправляется запрос расчёта стоимости, в котором для leaf-компонента толщина не указана
- **THEN** цена leaf-компонента вычисляется без шага наценки за толщину

### Requirement: Место наценки за толщину полотна в последовательности надбавок
Наценка за выбранную толщину полотна (см. «Наценка за выбранную толщину полотна») ДОЛЖНА (SHALL) применяться к цене leaf-компонента последовательно, вместе с уже существующими наценками (см. «Последовательное применение наценок к цене полотна», «Место наценки за цвет в последовательности надбавок», «Место надбавки за двустороннюю покраску в последовательности надбавок», «Место наценки за исполнение зеркала в последовательности надбавок», «Место наценки за вид остекления в последовательности надбавок»), в следующем порядке: (1) наценка за длину; (2) наценка за высоту; (3) наценка за толщину (если применяется); (4) наценка за цвет (если применяется); (5) надбавка за двустороннюю покраску (если применяется); (6) наценка за исполнение зеркала (если выбрано); (7) наценка за вид остекления (если выбран); (8) надбавка за реверс (если конфигурация реверсивная) — каждый шаг применяется к результату предыдущего, с округлением после каждого шага.

#### Scenario: Наценка за толщину применяется после высоты и до цвета
- **WHEN** отправляется запрос расчёта стоимости для реверсивной конфигурации, в котором для leaf-компонента указаны произвольное значение высоты, совпадающее с dimension_surcharge_rule, опция толщины с наценкой 20% и цвет с ненулевой наценкой
- **THEN** итоговая цена leaf-компонента вычисляется как: сумма₁ = округление(базовая_цена × (1 + наценка_за_высоту)); сумма₂ = округление(сумма₁ × (1 + 0.2)); сумма₃ = округление(сумма₂ × (1 + наценка_за_цвет)); итог = округление(сумма₃ × (1 + надбавка_за_реверс))

### Requirement: Толщина полотна 59 мм требует исполнение «с четвертью»
Толщина полотна 59 мм (см. door-configuration-catalog, «Опция толщины полотна 59 мм по коллекциям») физически изготавливается только с четвертью по периметру полотна. Эта связь не выражена в каталоге `door_configuration` (толщина выбирается клиентом независимо от строки каталога) — она ДОЛЖНА (SHALL) проверяться на уровне запроса расчёта стоимости: если для leaf-компонента выбрана опция толщины со значением 59 мм, и атрибут «Четверть», действующий для этого расчёта, точно определён (см. ниже) и равен false, эндпоинт ДОЛЖЕН (SHALL) отвечать ошибкой 400 и не выполнять расчёт. Атрибут «Четверть» для этой проверки определяется: при расчёте по `door_configuration` — значением `hasQuarter` самой конфигурации (всегда точно известно); при расчёте отдельного полотна или выгрузке спецификации — по явно переданному id вида кромки (`edgeTypeId`), если он передан (кромка «Прямая» ⇒ «Четверть» = false, кромка «С четвертью» ⇒ «Четверть» = true); если кромка не передана, атрибут считается неопределённым, и эта проверка НЕ ДОЛЖНА (SHALL NOT) блокировать запрос.

#### Scenario: Толщина 59 мм с конфигурацией без четверти отклоняется
- **WHEN** запрашивается расчёт стоимости по `door_configuration`, для которой атрибут «Четверть» = false, и для leaf-компонента выбрана опция толщины со значением 59 мм
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Толщина 59 мм с конфигурацией с четвертью допустима
- **WHEN** запрашивается расчёт стоимости по `door_configuration`, для которой атрибут «Четверть» = true, и для leaf-компонента выбрана опция толщины со значением 59 мм
- **THEN** расчёт выполняется без ошибки, наценка за толщину применяется как обычно

#### Scenario: Толщина 59 мм при расчёте отдельного полотна с явной кромкой «Прямая» отклоняется
- **WHEN** запрашивается расчёт стоимости отдельного полотна с явно переданным id вида кромки «Прямая» и опцией толщины со значением 59 мм
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Толщина 59 мм при расчёте отдельного полотна без указанной кромки не блокируется
- **WHEN** запрашивается расчёт стоимости отдельного полотна с опцией толщины со значением 59 мм, но без указанного id вида кромки
- **THEN** запрос не отклоняется этой проверкой (атрибут «Четверть» для него не определён)

### Requirement: Наценка за атрибут «Четверть» полотна
Если атрибут «Четверть», действующий для расчёта (см. «Толщина полотна 59 мм требует исполнение «с четвертью»» — тот же способ определения: `hasQuarter` конфигурации, либо по явно переданной кромке, либо неопределён), точно равен true для leaf-компонента, к его цене ДОЛЖНА (SHALL) применяться наценка 10% — но ТОЛЬКО если она не подразумевается уже применённой другой наценкой, которая сама по себе требует «Четверть» = true: наценкой за реверс (см. «Надбавка за реверс при расчёте стоимости полотна») или наценкой за толщину 59 мм (см. «Толщина полотна 59 мм требует исполнение «с четвертью»»). Если применяется хотя бы одна из этих двух наценок, наценка за «Четверть» саму по себе ДОЛЖНА (SHALL) быть пропущена — иначе клиент заплатил бы дважды за один и тот же факт. Если атрибут «Четверть» не определён (неизвестен) или равен false, наценка не применяется.

#### Scenario: Наценка применяется, когда «Четверть» выбрана без реверса и без толщины 59 мм
- **WHEN** запрашивается расчёт стоимости, в котором атрибут «Четверть» для leaf-компонента точно равен true, конфигурация не реверсивная, и толщина полотна не выбрана (или выбрана стандартная — не 59 мм)
- **THEN** к цене leaf-компонента применяется наценка 10%

#### Scenario: Наценка не применяется вместе с наценкой за реверс
- **WHEN** запрашивается расчёт стоимости по реверсивной `door_configuration` (атрибут «Четверть» = true как следствие реверса)
- **THEN** к цене leaf-компонента применяется только надбавка за реверс; отдельная наценка за «Четверть» не добавляется — итоговая надбавка не задваивается

#### Scenario: Наценка не применяется вместе с наценкой за толщину 59 мм
- **WHEN** запрашивается расчёт стоимости, в котором для leaf-компонента выбрана толщина 59 мм (что требует и подтверждает «Четверть» = true)
- **THEN** к цене leaf-компонента применяется только наценка за толщину; отдельная наценка за «Четверть» не добавляется

#### Scenario: Наценка не применяется, если «Четверть» ложна
- **WHEN** запрашивается расчёт стоимости, в котором атрибут «Четверть» для leaf-компонента точно равен false
- **THEN** наценка за «Четверть» не применяется

### Requirement: Наценка за «Четверть» в ответе эндпоинта процентов надбавок
Ответ эндпоинта получения процентов надбавок (`GET /api/pricing-surcharges`) ДОЛЖЕН (SHALL), в дополнение к существующим полям, содержать процент наценки за атрибут «Четверть», применяемый при расчёте стоимости (см. «Наценка за атрибут «Четверть» полотна»).

#### Scenario: Возвращается процент наценки за «Четверть»
- **WHEN** запрашивается эндпоинт получения процентов надбавок
- **THEN** ответ содержит процент наценки за «Четверть» (10%), наряду с уже существующими полями

#### Scenario: Значение совпадает с фактически применяемым при расчёте
- **WHEN** запрашивается эндпоинт получения процентов надбавок
- **THEN** возвращённый процент наценки за «Четверть» равен проценту, который расчёт стоимости фактически применяет к цене leaf-компонента, когда «Четверть» истинна сама по себе

### Requirement: Место наценки за «Четверть» в последовательности надбавок
Наценка за атрибут «Четверть» (см. «Наценка за атрибут «Четверть» полотна») ДОЛЖНА (SHALL) применяться к цене leaf-компонента последовательно, вместе с уже существующими наценками (см. «Последовательное применение наценок к цене полотна» и все последующие «Место наценки за X в последовательности надбавок»), в следующем порядке: (1) наценка за длину; (2) наценка за высоту; (3) наценка за толщину (если применяется); (4) наценка за «Четверть» (если применяется — с учётом её неприменения при уже применённой наценке за толщину, см. выше); (5) наценка за цвет (если применяется); (6) надбавка за двустороннюю покраску (если применяется); (7) наценка за исполнение зеркала (если выбрано); (8) наценка за вид остекления (если выбран); (9) надбавка за реверс (если конфигурация реверсивная — с учётом того, что наценка за «Четверть» на шаге 4 в этом случае уже не применена, см. выше) — каждый шаг применяется к результату предыдущего, с округлением после каждого шага.

#### Scenario: Наценка за «Четверть» применяется после толщины и до цвета
- **WHEN** запрашивается расчёт стоимости, в котором для leaf-компонента атрибут «Четверть» точно равен true (без реверса и без толщины 59 мм), указано произвольное значение высоты, совпадающее с dimension_surcharge_rule, и выбран цвет с ненулевой наценкой
- **THEN** итоговая цена leaf-компонента вычисляется как: сумма₁ = округление(базовая_цена × (1 + наценка_за_высоту)); сумма₂ = округление(сумма₁ × (1 + 0.1)); итог = округление(сумма₂ × (1 + наценка_за_цвет))

### Requirement: Прайс-лист в каталоге конфигураций
Для leaf-компонента каждой door_configuration в ответе каталога конфигураций система ДОЛЖНА (SHALL) включать прайс-лист (id, code, name — название файла), которому принадлежит коллекция этого leaf_type. Для остальных компонентов (frame, edge, doorCasing, frameExtensions) поле прайс-листа НЕ ДОЛЖНО (SHALL NOT) заполняться (null/отсутствует).

#### Scenario: Leaf-компонент содержит прайс-лист своей коллекции
- **WHEN** запрашивается каталог конфигураций и коллекция leaf_type конфигурации принадлежит price_list `PL-001`
- **THEN** в leaf-компоненте этой конфигурации присутствует прайс-лист с code `PL-001` и name `hausdoors_emal_i_shpon_rf_07_09_2026`

#### Scenario: Остальные компоненты не содержат прайс-лист
- **WHEN** запрашивается каталог конфигураций
- **THEN** у компонентов frame, edge, doorCasing и frameExtensions поле прайс-листа не заполнено
