# order-export-api Specification

## Purpose

Определяет REST API для выгрузки в один Excel-файл сразу всех позиций заказа, собранных в корзине (см. order-cart-ui), — единым листом, повторяющим структуру таблицы позиций на экране корзины (строка конфигурации, сразу под ней — детализация по компонентам), переиспользуя ту же расчётную логику, что и выгрузка одиночной спецификации (см. door-configuration-export).

## Requirements

### Requirement: Эндпоинт выгрузки заказа целиком
Система ДОЛЖНА (SHALL) предоставлять эндпоинт `POST /api/specification/export-order`, принимающий непустой список позиций заказа. Каждая позиция ДОЛЖНА (SHALL) содержать: то же тело, что принимает `POST /api/specification/export` (см. door-configuration-export, «Эндпоинт выгрузки спецификации») — id `leaf_type` с опциями и опционально кромку, короб, наличник, добор, декоративные элементы, фурнитуру; количество (целое число, не меньше 1); отображаемое наименование позиции (используется в строке конфигурации на листе заказа, см. «Строка конфигурации на листе заказа»); список тегов атрибутов конфигурации (`attribute_tags`, опциональный, по умолчанию пустой список — те же теги, что показаны у позиции в столбце «Конфигурация» на экране корзины, см. order-cart-ui, «Теги атрибутов конфигурации»; используется в строке конфигурации на листе заказа, без пересчёта на backend). Валидация каждой позиции ДОЛЖНА (SHALL) следовать тем же правилам, что и у `POST /api/specification/export` (см. door-configuration-export, «Эндпоинт выгрузки спецификации») — 404 для несуществующего `leaf_type`, 400 для недопустимых id опций; `attribute_tags` не валидируется по каталогу — это отображаемые данные, переданные с фронтенда, тем же принципом, что и `displayName`.

#### Scenario: Пустой список позиций отклоняется
- **WHEN** отправляется запрос с пустым списком позиций
- **THEN** эндпоинт отвечает ошибкой 400 и не генерирует файл

#### Scenario: Невалидная позиция в списке отклоняет весь запрос
- **WHEN** список содержит несколько позиций, и хотя бы одна из них ссылается на несуществующий `leaf_type` или недопустимую опцию
- **THEN** эндпоинт отвечает той же ошибкой (404 или 400 в зависимости от причины), что и `POST /api/specification/export` для этой позиции, и не генерирует файл — частичная выгрузка (без невалидной позиции) не выполняется

#### Scenario: Количество меньше 1 отклоняется
- **WHEN** у одной из позиций указано количество 0 или отрицательное
- **THEN** эндпоинт отвечает ошибкой 400 и не генерирует файл

#### Scenario: Позиция без тегов атрибутов принимается как обычно
- **WHEN** позиция заказа не содержит поле `attribute_tags` вовсе (например, запрос отправлен клиентом, ещё не обновлённым под это изменение)
- **THEN** эндпоинт обрабатывает позицию как обычно, считая список тегов пустым, без ошибки

### Requirement: Формат ответа выгрузки заказа
Ответ эндпоинта выгрузки заказа ДОЛЖЕН (SHALL) быть файлом в формате `.xlsx` (`Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`) с заголовком `Content-Disposition: attachment`, тем же соглашением об имени файла, что и у выгрузки одиночной спецификации (`Заказ-от-<дата>.xlsx`, см. door-configuration-export, «Формат ответа»).

#### Scenario: Ответ помечен как вложение
- **WHEN** запрос выгрузки заказа выполнен успешно
- **THEN** ответ содержит заголовок `Content-Disposition: attachment` с именем файла вида `Заказ-от-<дата>.xlsx` и тело в формате `.xlsx`

### Requirement: Единый лист заказа
Файл заказа ДОЛЖЕН (SHALL) состоять из одного листа «Заказ» (а не из отдельных листов на позицию) с общей строкой заголовков колонок «№», «Конфигурация», «Параметры», «Цена за ед., ₽», «Количество», «Сумма, ₽» — тот же набор столбцов, что и в таблице позиций на экране корзины (см. order-cart-ui, «Таблица позиций корзины»), кроме столбца «Действия» (кнопки «Посмотреть»/«Удалить» неприменимы к статичному файлу). Далее, в том же порядке, в котором позиции переданы в запросе, ДОЛЖЕН (SHALL) идти блок на каждую позицию: строка конфигурации (см. «Строка конфигурации на листе заказа»), сразу под ней — детализация по компонентам (см. «Блок детализации под строкой конфигурации») со строкой «Итого» под ней (см. «Итоговая строка детализации»), которая же служит разделителем перед следующей позицией. Последней строкой листа, после блоков всех позиций, ДОЛЖНА (SHALL) идти строка «Итого по заказу» (см. «Итог по заказу»).

#### Scenario: Файл содержит один лист «Заказ» с общим заголовком
- **WHEN** запрошена выгрузка заказа из нескольких позиций
- **THEN** файл содержит ровно один лист с именем «Заказ», отдельных листов на каждую позицию нет; первая строка листа — заголовки «№», «Конфигурация», «Параметры», «Цена за ед., ₽», «Количество», «Сумма, ₽»

### Requirement: Строка конфигурации на листе заказа
Для каждой позиции заказа лист ДОЛЖЕН (SHALL) содержать строку конфигурации со значениями: порядковый номер; в столбце «Конфигурация» — отображаемое наименование позиции, а сразу после него, в той же ячейке, — теги атрибутов конфигурации этой позиции (`attribute_tags` из запроса), если они не пусты, через « — » после наименования и через ", " между собой (например, «Вертикаль 01 — РЕВЕРС, ЧЕТВЕРТЬ»); если список тегов пуст, ячейка содержит только наименование, без « — »; параметры полотна — длина × высота × толщина через « × », без единиц измерения (столбец «Параметры», тот же формат, что и `dimensionsLabel` в order-cart-ui, «Таблица позиций корзины»); итоговая розничная цена за единицу — сумма цен всех компонентов этой позиции (столбец «Цена за ед.»); количество позиции (столбец «Количество»); сумма по позиции — цена за единицу × количество (столбец «Сумма»). Ячейка столбца «Конфигурация» НЕ ДОЛЖНА (SHALL NOT) выделяться жирным текстом — ни наименование, ни добавленные теги; порядковый номер в столбце «№» по-прежнему выделяется жирным, как и раньше.

#### Scenario: Строка конфигурации содержит цену за единицу и сумму с учётом количества
- **WHEN** позиция заказа имеет итоговую розничную цену за единицу 85545 и количество 2
- **THEN** строка конфигурации этой позиции показывает «Цена за ед.» 85545, «Количество» 2 и «Сумма» 171090

#### Scenario: Теги добавляются в ячейку наименования через тире
- **WHEN** позиция заказа имеет наименование «Вертикаль 01» и теги атрибутов «РЕВЕРС», «ЧЕТВЕРТЬ»
- **THEN** столбец «Конфигурация» этой строки показывает «Вертикаль 01 — РЕВЕРС, ЧЕТВЕРТЬ»

#### Scenario: Позиция без применимых тегов показывает только наименование
- **WHEN** позиция заказа не имеет применимых тегов атрибутов (пустой список)
- **THEN** столбец «Конфигурация» этой строки показывает только наименование, без «—» и без тегов

#### Scenario: Наименование не выделяется жирным
- **WHEN** отображается строка конфигурации любой позиции заказа
- **THEN** текст в столбце «Конфигурация» (наименование и, если есть, теги) не выделен жирным начертанием; порядковый номер в столбце «№» остаётся жирным

### Requirement: Блок детализации под строкой конфигурации
Сразу под строкой каждой конфигурации лист ДОЛЖЕН (SHALL) содержать свою строку заголовков «Элемент», «Наименование», «Размеры», «Цвет», «Кол-во», «Цена дилер, ₽», «Цена клиенту, ₽», «Сумма дилер, ₽», «Сумма клиенту, ₽» и построчную детализацию по компонентам этой конфигурации (полотно, кромка, короб, наличник, добор, декоративные элементы, фурнитура — какие из них присутствуют) — тот же состав данных, что и в раскрываемой детализации позиции корзины на экране (см. order-cart-ui, «Разворачиваемая детализация позиции корзины»): «Цена дилер»/«Цена клиенту» — цена за одну единицу компонента, «Сумма дилер»/«Сумма клиенту» — с учётом количества строки (для большинства строк, где количество компонента равно 1, совпадает с ценой за единицу). Короб ДОЛЖЕН (SHALL) показываться ровно одной строкой на весь короб — его позиции состава (frame_post) отдельными строками НЕ ДОЛЖНЫ (SHALL NOT) выводиться (тем же принципом, что и в order-cart-ui, «Разворачиваемая детализация позиции корзины» — цена строки «Короб» уже включает их сумму целиком). Каждая позиция декоративного элемента ДОЛЖНА (SHALL) показываться отдельной строкой «Декоративные элементы» (без объединения одинаковых типов), со столбцом «Размеры», содержащим длину типа в мм, а если у типа дополнительно заданы ширина (width_mm) и/или толщина (thickness_mm) — объединённые с длиной через ` × ` в порядке длина-ширина-толщина (тем же способом, что и у прочих компонентов, см. door-configuration-export, «Содержимое строки спецификации»), и пустым столбцом «Цвет». Компонент без найденной цены ДОЛЖЕН (SHALL) показывать прочерк («—») в ценовых столбцах вместо числа, не пропуская саму строку (тем же принципом, что и в door-configuration-export, «Ненайденная цена отображается прочерком»).

#### Scenario: Детализация содержит строку на каждый присутствующий компонент
- **WHEN** позиция заказа содержит полотно, кромку и один комплект фурнитуры
- **THEN** под строкой конфигурации этой позиции идёт строка заголовков детализации и три строки — «Полотно», «Кромка», «Фурнитура» — с наименованием, размерами (где применимо), цветом (где применимо), количеством и ценами/суммами дилер и клиенту

#### Scenario: Цена за единицу и сумма компонента с количеством больше 1
- **WHEN** в детализации позиции наличник имеет цену дилер за единицу 8280 и количество 3
- **THEN** строка «Наличник» показывает «Цена дилер» 8280 и «Сумма дилер» 24840

#### Scenario: Короб показан одной строкой без состава
- **WHEN** позиция заказа содержит короб, чей список позиций frame_post из каталога содержит несколько записей
- **THEN** детализация этой позиции содержит ровно одну строку «Короб» с суммарной ценой; отдельных строк на каждую позицию его состава нет

#### Scenario: Компонент без найденной цены показывает прочерк
- **WHEN** в детализации позиции цена одного из компонентов не найдена
- **THEN** его строка показывает «—» в столбцах «Цена дилер», «Цена клиенту», «Сумма дилер», «Сумма клиенту», сама строка при этом не пропускается

#### Scenario: Детализация содержит строку декоративного элемента между наличником/добором и фурнитурой
- **WHEN** позиция заказа содержит наличник, одну позицию декоративного элемента и один комплект фурнитуры
- **THEN** под строкой конфигурации этой позиции строки детализации идут в порядке: «Наличник», «Декоративные элементы», «Фурнитура»

#### Scenario: Несколько позиций декоративных элементов показаны отдельными строками
- **WHEN** позиция заказа содержит две позиции декоративных элементов с разными типами
- **THEN** детализация содержит две отдельные строки «Декоративные элементы», каждая со своим наименованием, размерами в столбце «Размеры» и ценой/суммой

#### Scenario: Позиция декоративного элемента с шириной и толщиной показывает объединённые размеры
- **WHEN** позиция заказа содержит декоративный элемент, у типа которого заданы length_mm, width_mm и thickness_mm (например, «Блок А» — 90/90/30)
- **THEN** столбец «Размеры» его строки в детализации содержит `90 × 90 × 30` — длину, ширину и толщину, объединённые через ` × `

### Requirement: Итоговая строка детализации
Сразу под последней строкой детализации каждой конфигурации лист ДОЛЖЕН (SHALL) содержать строку «Итого» со значениями в столбцах «Сумма дилер» и «Сумма клиенту» — суммой соответствующих столбцов по всем строкам детализации этой позиции (компонент без найденной цены, см. «Компонент без найденной цены показывает прочерк», участвует в сумме как 0, не прерывая и не исключаясь из суммирования). Эта строка ДОЛЖНА (SHALL) быть единственным разделителем перед строкой конфигурации следующей позиции — отдельной пустой строки-разделителя после неё быть не должно.

#### Scenario: Итоговая строка суммирует детализацию позиции
- **WHEN** детализация позиции состоит из строк с суммой дилер 8280 и 34000, и суммой клиенту 12000 и 55000
- **THEN** строка «Итого» под детализацией этой позиции показывает сумму дилер 42280 и сумму клиенту 67000

#### Scenario: Итоговая строка сразу предшествует следующей конфигурации
- **WHEN** заказ состоит из нескольких позиций
- **THEN** строка конфигурации каждой следующей позиции (кроме первой) идёт сразу за итоговой строкой детализации предыдущей — без дополнительной пустой строки между ними

### Requirement: Итог по заказу
Последняя строка листа ДОЛЖНА (SHALL) содержать ровно три заполненные, идущие подряд ячейки: «Итого по заказу» (текст выделен жирным), рядом с ней — дилерская сумма по заказу (сумма итоговой дилерской цены каждой позиции с учётом её количества), рядом с дилерской суммой — клиентская (розничная) сумма по заказу (сумма столбца «Сумма» по всем позициям, см. «Строка конфигурации на листе заказа») — тем же принципом, что и «Итого по заказу» под таблицей позиций на экране корзины (см. order-cart-ui, «Сводка и итог по заказу»). Значения сумм НЕ ДОЛЖНЫ (SHALL NOT) выделяться жирным — жирным выделен только текст «Итого по заказу».

#### Scenario: Итог по заказу — сумма сумм всех позиций
- **WHEN** заказ состоит из двух позиций с суммой 2000 и 1000
- **THEN** последняя строка листа показывает клиентскую сумму 3000 третьей из трёх заполненных ячеек этой строки

#### Scenario: Дилерский итог показан рядом с клиентским
- **WHEN** заказ состоит из двух позиций с дилерской ценой за единицу 900 (количество 2) и 1000 (количество 1)
- **THEN** та же итоговая строка листа показывает дилерскую сумму по заказу 2800 второй из трёх заполненных ячеек этой строки, перед клиентской суммой

#### Scenario: Итоговая строка содержит ровно три заполненные ячейки
- **WHEN** заказ состоит из двух позиций с клиентской суммой 2000 и 1000, и дилерской суммой 1800 и 900
- **THEN** последняя строка листа содержит три подряд идущие заполненные ячейки: «Итого по заказу», 2700 (дилерская сумма), 3000 (клиентская сумма) — и никаких других заполненных ячеек в этой строке

#### Scenario: Только текст «Итого по заказу» выделен жирным
- **WHEN** отображается последняя строка листа
- **THEN** ячейка с текстом «Итого по заказу» выделена жирным, а ячейки с суммами — нет

### Requirement: Переиспользование расчёта позиции заказа
Расчёт цены и построчной детализации каждой позиции заказа ДОЛЖЕН (SHALL) использовать ту же расчётную логику, что и `POST /api/specification/export` (`DoorConfigurationPricingService.resolveSpecificationComponents`) — без отдельной, дублирующей реализации расчёта или собственных правил округления/надбавок для выгрузки заказа.

#### Scenario: Изменение правил расчёта одинаково влияет на обе выгрузки
- **WHEN** правило расчёта цены или надбавки меняется на уровне `DoorConfigurationPricingService`
- **THEN** это изменение одинаково отражается и в выгрузке одиночной спецификации, и в детализации каждой позиции выгрузки заказа — без необходимости менять код выгрузки заказа отдельно
