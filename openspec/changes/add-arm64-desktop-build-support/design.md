## Context

Существующий desktop-pipeline (`jlink` + `jpackage`, Gradle-таски `desktopFxLibs`/`desktopJlinkRuntime`/`desktopAppImage` в `backend/build.gradle`, см. архивный change `add-desktop-app-packaging`) собран и проверен на Intel Mac (x86_64). Плагин `org.openjfx.javafxplugin` уже сам определяет архитектуру и подставляет нужный classifier JavaFX-jar'ов (`mac` для Intel, `mac-aarch64` для Apple Silicon — у OpenJFX эта пара названа несимметрично: Intel не имеет суффикса вообще). Сам `jlink`/`jpackage` тоже неявно "поддерживают" любую архитектуру — они просто используют архитектуру той JDK, из которой запущены. Проблема не в поддержке arm64 как таковой, а в том, что выходные артефакты (директории `build/desktop/*`, имя `.dmg`) сейчас никак не помечены архитектурой — если тот же checkout когда-либо соберётся на другой машине (или JDK на Apple Silicon machine окажется под Rosetta), результат будет неотличим от x86_64-сборки по имени файла, и слишком легко перепутать/затереть.

## Goals / Non-Goals

**Goals:**
- Тот же `./gradlew desktopAppImage`, без дополнительных флагов, при запуске на Apple Silicon Mac собирает нативный arm64 `.dmg`, чьё имя явно отличается от x86_64-варианта.
- Автоматическая проверка (Gradle-таск), что итоговый бинарник внутри `.app` действительно нужной архитектуры — страхует от случая, когда на Apple Silicon Mac Gradle-toolchain незаметно резолвится в x86_64-JDK под Rosetta (такое возможно, если рядом установлены обе JDK, как сейчас на машине разработки).
- Документация: что нужно поставить на чистый Apple Silicon Mac, чтобы сборка прошла с первого раза.

**Non-Goals:**
- Сама сборка arm64 `.dmg` не выполняется в рамках этого изменения — физически нет доступа к Apple Silicon-машине из среды, где ведётся разработка; изменение готовит код и проверяется на существующей Intel-машине (имя файла, определение архитектуры, verification-таск — с подставным/ожидаемым значением архитектуры).
- Universal2-бинарник (один `.dmg`, нативно работающий на обеих архитектурах) — сложнее на порядок (ручная сборка universal JRE через `lipo`, `jpackage` не умеет это из коробки), отдельное решение при реальной необходимости.
- CI/автоматическая сборка на push/релиз — у репозитория нет GitHub-remote на данный момент.

## Decisions

### Определение архитектуры: `System.getProperty("os.arch")`, нормализованное в Gradle
`org.openjfx.javafxplugin` уже использует этот же сигнал для выбора classifier'а зависимостей — переиспользуем тот же источник истины вместо параллельного механизма. Нормализация: `aarch64` → `aarch64`, `x86_64`/`amd64` → `x86_64` (на случай отличий в написании между JVM-вендорами). Значение вычисляется один раз в `build.gradle` и используется во всех именах выходных путей.

Alternative — Gradle-свойство типа `-Pdesktop.arch=...` для ручного указания: отклонено для этой итерации — кросс-сборка всё равно невозможна (jlink берёт архитектуру реальной JDK), поэтому ручное указание архитектуры создавало бы только иллюзию контроля и риск несоответствия факту.

### Именование выходных артефактов: явный суффикс архитектуры, не classifier OpenJFX
Все выходные пути desktop-сборки (`build/desktop/<arch>/runtime`, `.../fxlibs`, `.../app-lib`, `.../dmg`) и имя `.dmg`/`.app` получают суффикс `x86_64` или `aarch64`. Сознательно НЕ переиспользуется несимметричная пара OpenJFX (`mac`/`mac-aarch64`) — она специфична для их публикации артефактов, а в наших собственных именах файлов симметричные явные лейблы (`x86_64`/`aarch64`) понятнее конечному пользователю, который выбирает `.dmg` под свой Mac.

Вынесение под-путей `build/desktop/<arch>/...` (а не только суффикс в имени `.dmg`) — так, чтобы `desktopJlinkRuntime`/`desktopAppImage` естественно оставались корректными (Gradle up-to-date checks) при гипотетическом запуске обеих архитектур из одного и того же checkout в разное время (например, через сетевой диск между двумя Mac) — маловероятный, но дешёвый в подстраховке сценарий.

### Проверка архитектуры результата: отдельный Gradle-таск на `file`
Новый таск (условно `desktopVerifyArch`) запускает `file` на бинарнике `Contents/MacOS/<AppName>` внутри собранного `.app` и сверяет вывод (`Mach-O 64-bit executable arm64` / `x86_64`) с ожидаемой архитектурой сборки. Ловит конкретный реальный риск: на Apple Silicon Mac с установленными двумя JDK (нативной arm64 и Intel-версией под Rosetta — ровно так сейчас настроена машина разработки) Gradle toolchain может незаметно зарезолвиться не в ту JDK, и в результате получится x86_64-сборка, которая по внешним признакам (имя файла с "правильным" на первый взгляд суффиксом, если суффикс не пересчитывать пере-проверкой) будет выглядеть как arm64. Автоматическая проверка после `jpackage` устраняет этот риск.

## Risks / Trade-offs

- **[Риск]** Реальная arm64-сборка не может быть выполнена и проверена в рамках этого изменения — код и verification-таск проверяются только логически/на Intel-машине (ожидаемое значение архитектуры). → **Митигация**: после реализации — ручная проверка на настоящем Apple Silicon Mac как последний шаг (задача в tasks.md), значение "готово" для этого изменения зависит от такой проверки.
- **[Риск]** Смена схемы именования `.dmg` — любые внешние ссылки/скрипты/документация со старым именем файла перестанут работать. → **Митигация**: единственная известная ссылка на старое имя — переписка с пользователем в этом чате, не файл в репозитории; `grep` по репозиторию перед реализацией на всякий случай.
- **[Trade-off]** Без universal2-бинарника пользователю нужно самому выбрать правильный `.dmg` под свою архитектуру (см. изменённый Requirement в specs) — осознанно принято, universal2 сильно дороже в реализации ради разовой распространяемой утилиты.

## Migration Plan

Не влияет на уже собранные/распространённые x86_64-`.dmg` — они не переименовываются постфактум, изменение касается только будущих сборок. Никакого отката не требуется: если arm64-сборка на реальной машине не удастся, x86_64-путь остаётся полностью рабочим без изменений в поведении.
