## Context

Сейчас единственный способ запуска — `./gradlew bootRun` с backend, обращающимся к PostgreSQL (`docker-compose.yml`, порт 5434), и отдельно поднятым Vite dev-сервером или собранным SPA, отдаваемым откуда-то ещё. См. proposal.md — Why и What Changes для мотивации и общего списка изменений.

По итогам пробной сборки (задача 1.1 в tasks.md, прогон полной цепочки миграций против H2 в режиме `MODE=PostgreSQL`) подтверждено:
- Синтаксис `значение::numeric` (явные касты в raw SQL `insert`, встречается в нескольких changeset'ах, например `0025-vertikal-edge-configurations.yaml`, `0053-fantom-post-colours.yaml`, `0058-dimension-surcharge-rules.yaml`) — работает под H2 без изменений.
- **Функциональные и partial unique-индексы не поддерживаются H2** и требуют переписывания. Обнаружено 13 таких SQL-выражений в 3 changeset'ах: `CREATE UNIQUE INDEX ... (COALESCE(col, 0), ...)` в `0006-door-configuration-catalog.yaml` (1 индекс), `0008-configuration-price.yaml` (1 индекс) и `0054-rework-reverse-mechanism.yaml` (1 индекс); `CREATE UNIQUE INDEX ... WHERE col IS NOT NULL` (partial index) — 10 индексов в `0006-door-configuration-catalog.yaml`. H2 отклоняет оба паттерна с ошибкой синтаксиса (проверено напрямую через JDBC) — ни функциональные индексы, ни `WHERE`-условие в `CREATE INDEX` не поддерживаются. Другого postgres-специфичного синтаксиса (`jsonb`, `SERIAL`, `gen_random_uuid()` и т.п.) не обнаружено.

Пробная сборка JavaFX WebView (задача 1.4) дополнительно выявила: колонка `value` (используется в `LinerDimensionOption.value` и `DimensionSurchargeRule.value`) — зарезервированное слово в H2. Полный прогон Liquibase-миграций (задача 1.1) эту проблему не поймал, так как реально дошёл только до первого падения на функциональном индексе (см. ниже) — до changeset'ов с `value` дело не дошло. По итогам задачи 2.3 выяснилось, что единой формы квотирования для JPA-маппинга не существует (Liquibase квотирует `value` на H2 в ВЕРХНЕМ регистре при `createTable`, а на PostgreSQL не квотирует вообще — одна аннотация `@Column` не может совпасть с обоими); кроме того, минимум 18 уже применённых changeset-файлов используют `value` без кавычек в raw SQL (`INSERT`, `CREATE INDEX`), что похоронило бы любой точечный JPA-фикс в рантайме. Итоговое решение — см. Decisions, "Зарезервированное слово `value` в H2".

## Goals / Non-Goals

**Goals:**
- Один установщик `.dmg` для macOS, дающий рабочее приложение без внешних зависимостей (Java, СУБД).
- Общий кодовый путь backend/frontend между серверным (PostgreSQL) и десктоп (H2) профилями — без форка кода, только конфигурация через Spring-профиль.
- Пробная сборка (`jlink` + `jpackage`) как первый шаг реализации — чтобы получить реальные цифры по размеру/памяти до того, как вкладываться в остальную работу.

**Non-Goals:**
- Windows/Linux сборки — только macOS в этой итерации.
- Полностью автоматическое обновление (скачивание и тихая установка) — только уведомление со ссылкой.
- Синхронизация данных между несколькими устройствами одного пользователя — приложение однопользовательское, данные локальны на одной машине.
- Сохранение многопользовательского / сетевого режима в desktop-сборке — десктоп-профиль рассчитан на одного локального пользователя.

## Decisions

### Обёртка UI: JavaFX WebView, а не Electron/Tauri
Проект уже написан на Java/Spring + React; JavaFX WebView не добавляет вторую технологическую экосистему (Node/Rust), использует существующий backend-процесс напрямую (тот же JVM) и не тянет Chromium (~150+ МБ, как в Electron). Alternative — Electron: отклонён, так как требует полностью отдельный Node.js-рантайм и раздувает дистрибутив. Alternative — Tauri: отклонён по той же причине (Rust toolchain, отдельная сборка) при отсутствии выигрыша, раз JVM и так обязательна для backend.

Компромисс: движок WebView — встроенный WebKit, версия которого зависит от версии JavaFX, а не от системного браузера; возможна более медленная поддержка новых веб-фич. Проверяется на этапе пробной сборки — нужно убедиться, что используемые компоненты Ant Design корректно рендерятся.

### Упаковка backend: `jlink` + `jpackage`, без Electron/установщиков на базе Node
Стандартный инструмент JDK (доступен с Java 14, у проекта Java 21 — ничего дополнительно ставить не нужно). Даёт нативный `.dmg` со встроенным урезанным JRE. Alternative — install4j (платный, с готовым автообновлением): отклонён для первой итерации, так как автообновление не входит в цели (Non-Goals); может быть пересмотрено отдельным изменением, если понадобится полноценный auto-update.

### БД для desktop-профиля: H2 в PostgreSQL-совместимом режиме (`MODE=PostgreSQL`)
H2 — pure-Java библиотека (~2.5-3 МБ), работает in-process в той же JVM, не требует отдельного бинарника и процесса (в отличие от embedded PostgreSQL, ~130-160 МБ и +100-150 МБ RAM — см. оценку в обсуждении к proposal). Совместимый режим PostgreSQL у H2 поддерживает синтаксис `значение::тип`, который уже встречается в нескольких Liquibase changeset'ах — это подтверждено пробной сборкой. Alternative — SQLite: отклонён, так как не имеет режима совместимости с PostgreSQL-синтаксисом и потребовал бы больше правок существующих changeset'ов. Alternative — embedded PostgreSQL: отклонён из-за веса (см. Impact в proposal.md).

Активируется через отдельный Spring-профиль (например, `desktop`) с собственным `application-desktop.yml` (JDBC URL на файл H2 в пользовательском каталоге ОС, `spring.liquibase` — та же цепочка changelog'ов). Существующий профиль по умолчанию с PostgreSQL не меняется.

### Функциональные и partial unique-индексы: generated-колонки + раздельные changelog-файлы через Liquibase `context`
`COALESCE(col, 0)` в списке колонок индекса и `WHERE col IS NOT NULL` (partial unique index) — стандартные в PostgreSQL способы сделать "уникально, если непустое", но H2 не поддерживает ни функциональные индексы, ни `WHERE`-условие в `CREATE INDEX`. Решено использовать **сгенерированные колонки** — но не единым ANSI-SQL-синтаксисом, как предполагалось изначально: `GENERATED ALWAYS AS (...) STORED` — PostgreSQL требует `STORED`, а H2 его не принимает вообще (синтаксическая ошибка). Пришлось разделить SQL по диалекту:
- `COALESCE(x, 0)` → колонка `x_norm GENERATED ALWAYS AS (COALESCE(x, 0))` (H2, без `STORED`) / `... STORED` (PostgreSQL), индекс по `x_norm`.
- `WHERE x IS NOT NULL` (partial unique по `x`, `y`) → колонка вида `x_key GENERATED ALWAYS AS (CASE WHEN x IS NOT NULL THEN x ELSE -id END)` (та же разница по `STORED`) — использует PK строки как sentinel, чтобы строки с `x IS NULL` никогда не конфликтовали друг с другом — обычный unique-индекс по (`x_key`, `y`).

Отдельная, более серьёзная находка: Liquibase останавливает **всю** цепочку миграций на первом упавшем changeset'е. Проблемные changeset'ы (`0006-3` и далее) — один из самых первых в цепочке (из 60+). План "новые changeset'ы в конец, старые не трогать" технически не мог сработать — на чистой H2 Liquibase падал на `0006-3` и никогда не доходил до новых changeset'ов в конце файла.

Реализованное решение (без единой правки уже применённых/заархивированных changeset'ов — пользователь явно это потребовал): раздельные changelog-файлы, переключаемые атрибутом `context` на уровне `include` (это правка структуры master-файла, не содержимого/checksum самих changeset'ов):
- Новая директория `backend/src/main/resources/db/changelog/changes-desktop-overrides/` с файлами `0006-door-configuration-catalog.yaml`, `0008-configuration-price.yaml`, `0054-rework-reverse-mechanism.yaml` — полные копии одноимённых оригиналов с тем же набором changeset'ов (та же структура таблиц, check-констрейнты, data-changesets), только проблемные unique-индексы пересобраны через generated-колонки в H2-варианте.
- В `db.changelog-master.yaml`: у трёх исходных `include` добавлен `context: "!desktop"`, сразу за каждым — параллельный `include` override-файла с `context: "desktop"`.
- В `application.yml` добавлено `spring.liquibase.contexts: "!desktop"` — обязательно: без явного `contexts` Liquibase не фильтрует по контексту вообще и пытается выполнить changeset'ы с обоими тегами. Профиль `desktop` (задача 2.1) должен задавать `contexts: desktop`.

Итог: единого changelog без ветвления по диалекту, как предполагалось в первой версии дизайна, добиться не удалось — Liquibase этого не позволяет при таком ограничении (не трогать применённые changeset'ы). Ветвление локализовано на 3 файлах через `context`, остальные ~57 файлов общие для обоих профилей.

Проверено: полный прогон на чистой H2 (задача 2.4) — 226 changeset'ов выполнено, 28 отфильтровано, plus smoke-запросы через реальные repository-методы. Повторно проверено на реальном локальном PostgreSQL (`./gradlew bootRun`) — 0 новых changeset'ов, 28 отфильтровано, приложение стартует штатно, существующая БД не пострадала.

### Зарезервированное слово `value` в H2: `NON_KEYWORDS=VALUE` на уровне JDBC URL
`value` — зарезервированное слово в H2 (не в PostgreSQL). Точечный JPA-фикс (квотирование в `@Column`) оказался невозможен: Liquibase квотирует `value` на H2 в ВЕРХНЕМ регистре при `createTable`, а на PostgreSQL не квотирует вообще — одна аннотация не может совпасть сразу с обоими. Кроме того, минимум 18 уже применённых changeset-файлов (`0007`, `0058` и другие) содержат `value` без кавычек в raw SQL (`INSERT`, `CREATE INDEX`) — переписывать все ради H2 потребовало бы правки применённых changeset'ов.

Решение — параметр JDBC URL `NON_KEYWORDS=VALUE` для H2-датасорса: сообщает парсеру H2, что "value" не зарезервировано, снимает конфликт для всех raw-SQL changeset'ов без единой правки кода или changeset'ов. Требует также убрать `DATABASE_TO_LOWER=TRUE` из URL, если он был — при нём регистр unquoted-идентификаторов не совпадает с тем, что реально создаёт Liquibase для этой колонки. Должно войти в JDBC URL профиля `desktop` (задача 2.1). Проверено тем же полным прогоном на H2 (задача 2.4), включая ORM-запросы к обеим таблицам.

### Расположение данных: стандартный пользовательский каталог ОС
Файл БД H2 и любые локальные настройки хранятся в `~/Library/Application Support/FurnitureCalculator/` (macOS), а не внутри `.app`-бандла — так переустановка/обновление `.app` (полная перезапись бандла) не затрагивает данные пользователя.

### Идентификация версий: стабильный bundle ID + macOS CFBundleVersion
`jpackage` конфигурируется с постоянным `--mac-package-identifier` между сборками, а `CFBundleVersion` берётся из версии Gradle-проекта. При установке новой `.dmg` поверх старой, при одинаковом identifier и большей версии, Finder/Installer заменяют бандл в `/Applications` (пользователь просто перетаскивает новую иконку — см. proposal.md).

### Проверка обновлений: пассивная проверка версии при старте
При старте приложение делает один HTTP-запрос к простому статическому источнику (например, JSON-файл на GitHub Releases с полем `latestVersion` и `downloadUrl`) и сравнивает с текущей версией. При ошибке сети/таймауте — проверка молча пропускается, приложение стартует как обычно (см. спецификацию, Requirement: Уведомление о доступном обновлении). Никакой инфраструктуры сервера для этого поднимать не требуется.

## Migration Plan

Это новая, отдельная сборочная цепочка — она не заменяет существующий серверный профиль с PostgreSQL и `docker-compose.yml`, а добавляется параллельно. Отката существующего поведения не требуется: если desktop-сборка не нужна, ей просто не пользуются, серверный профиль работает как прежде.

Порядок реализации (детализируется в tasks.md):
1. Пробная сборка (`jlink` + `jpackage`) с текущим backend и H2 — чтобы получить реальные цифры по размеру/памяти и убедиться, что миграции проходят на H2.
2. Профиль `desktop` (конфигурация datasource, проверка прохождения Liquibase на H2).
3. Обёртка JavaFX WebView вокруг backend + фронтенда.
4. Настройка стабильного bundle ID и путей хранения данных пользователя.
5. Механизм проверки версии и уведомления.
