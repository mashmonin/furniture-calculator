## Context

См. proposal.md — Why/What Changes. Ключевые факты из текущей кодовой базы:

- `LinerDimensionOption` — плоская сущность (`id`, `linerDimensionType`, `value` (BigDecimal, NOT NULL), `standard`, и ровно один nullable FK-владелец среди leaf/frame/edge/doorCasing/frameExtensions). Значение `value` сейчас всегда трактуется как одна точка (600 мм длины, 2000 мм высоты и т.п.).
- `DoorConfigurationPricingService.addComponentIfPresent` обрабатывает компоненты последовательно в порядке `leaf → frame → edge → doorCasing → frameExtensions` (см. `COMPONENT_ORDER`/`calculate`); `validatedDimensionOption(componentName, type, optionId)` сейчас проверяет только принадлежность опции своему компоненту (`belongsToLeaf`), не имея доступа к выбору соседних компонентов. Frame уже обрабатывается особым образом (`type instanceof FrameType` → своя ветка `framePostPrice`, см. archived change `add-frame-post-catalog`) — есть прецедент точечного спецкейса для одного типа компонента внутри общего цикла.
- Frontend (`App.tsx`) на шаге «2. Выберите опции» рендерит карточки компонентов независимо друг от друга (`COMPONENT_ORDER.map`), каждая со своими группами «Длина/Высота/Толщина/Цвет» через универсальный `OptionGroup`, без какой-либо связи между компонентами. Выбор опций хранится в `selection: Record<ComponentKey, ComponentSelectionDto>`; `updateSelection(key, patch)` обновляет только один компонент за раз.
- Ось «Высота» определяется кодом `liner_dimension_type.code = 'DT-002'` (константа `HEIGHT_TYPE_CODE` уже используется в `App.tsx`).
- Данных для edge (диапазоны высоты, цвета, цены) в БД сейчас нет вообще — этот change вводит только механизм, не данные (см. proposal.md → Impact).

## Goals / Non-Goals

**Goals:**
- Дать `liner_dimension_option` возможность описывать диапазон, а не только точку, не ломая существующие точечные оси (длина/высота/толщина полотна, короба и т.д.).
- Гарантировать на бэкенде, что расчёт стоимости не даст цену по несовместимой паре «высота кромки — высота полотна».
- В UI не дать пользователю физически выбрать несовместимую пару: скрыть/отфильтровать группу «Высота» кромки до и после выбора высоты полотна.

**Non-Goals:**
- Не наполняем реальные диапазоны, цвета и цены для ET-001/ET-002 в этом изменении — только механизм (см. proposal.md → Impact). Наполнение данных — последующий шаг, когда пользователь даст конкретные значения.
- Не обобщаем «диапазонность» на другие оси/компоненты (длина, толщина, доборы и т.п.) — правило совместимости диапазона вводится точечно только для оси «Высота» edge-компонента, по аналогии с тем, как frame получил свою отдельную ветку расчёта в прошлом change, а не общий механизм для всех компонентов.
- Не meняем структуру `configuration_price`/алгоритм «наиболее специфичной цены» — цвет кромки по-прежнему подбирается тем же существующим механизмом; новая проверка — дополнительный барьер перед расчётом, а не замена алгоритма подбора цены.

## Decisions

### min_value — nullable-столбец на liner_dimension_option, а не отдельная таблица
Рассматривался вариант вынести диапазоны в отдельную таблицу (по аналогии с тем, как `frame_post` вынесен из `configuration_price`). Отклонён: диапазон высоты кромки — это всё та же ось `liner_dimension_type = ВЫСОТА`, тот же owner-паттерн (ровно один справочник-владелец), та же роль в каталоге (`dimensionOptions` компонента) и в `ComponentSelectionDto` (`heightOptionId`) — никакой новой структуры не требуется, только дополнительное поле для интерпретации `value` как границы диапазона. Как и `frame_post.length`, `min_value` добавляется простым `addColumn` (nullable), без изменения существующих constraint'ов (`NOT NULL` на `value` остаётся, `UNIQUE(owner, type, value)` не трогается — `min_value` не входит в уникальность, поскольку у диапазона всегда одна одна и та же верхняя граница `value`, определяющая позицию в списке).

### Проверка диапазона — новая явная ветка в DoorConfigurationPricingService, а не расширение validatedDimensionOption
`validatedDimensionOption` — общая функция для 4 осей × 5 компонентов, её изменение под один частный случай (edge + высота) усложнило бы сигнатуру для всех остальных вызовов. Вместо этого: `calculate()` сохраняет валидированную высоту leaf-компонента (`LinerDimensionOption`, уже вычисляется в текущем порядке `leaf` первым) в локальную переменную и передаёт её единственным дополнительным параметром в обработку edge-компонента, где выполняется новая проверка «leaf-высота внутри [min_value, value] edge-опции». Компонент leaf по-прежнему обрабатывается как раньше — специальной логики для него не добавляется, только для edge (аналог уже существующего спецкейса `if (type instanceof FrameType)`).

### Порядок компонентов в запросе гарантирует, что leaf обработан раньше edge
`COMPONENT_ORDER = [leaf, frame, edge, doorCasing, frameExtensions]` уже фиксирован и не меняется этим change — leaf всегда валидируется до edge, поэтому его высота доступна к моменту проверки edge без необходимости менять порядок или делать два прохода по компонентам.

### Frontend: фильтрация — вычисляемое значение внутри `App.tsx`, без нового запроса к backend
Высота полотна и допустимые высоты кромки уже приходят в одном ответе каталога (`DoorConfigurationDto.leaf.dimensionOptions` / `.edge.dimensionOptions`) — фильтрация делается на уже загруженных данных (`leafHeightValue = leaf.dimensionOptions.find(o => o.id === selection.leaf.heightOptionId)?.value`), без дополнительных сетевых запросов.

### Сброс выбора высоты кромки при смене высоты полотна
Поскольку допустимость опции высоты кромки зависит от опции высоты полотна, при изменении `selection.leaf.heightOptionId` нужно сбрасывать `selection.edge.heightOptionId` (и, соответственно, скрытый ранее результат расчёта, если он был показан) — расширение существующей функции `updateSelection` точечно для этого случая (единственная известная на сегодня кросс-компонентная зависимость внутри шага «2. Выберите опции»).

## Risks / Trade-offs

- **[Риск] Без данных ET-001/ET-002 эта функциональность не проявится в интерфейсе** (у edge пока нет ни одной door_configuration, поэтому шаг «Кромка» вообще не появляется в каскаде — см. предыдущий ответ по кромке в БД) → Смягчение: это ожидаемо, механизм и данные разделены по проекту (Non-Goals); значимость проверяется юнит/интеграционными тестами с синтетическими данными, а не через UI до тех пор, пока не будут даны реальные диапазоны и цены.
- **[Trade-off] Спецкейс только для edge + высоты, не общий механизм** — если в будущем похожая диапазонная зависимость понадобится для другой оси/компонента, потребуется либо дублировать паттерн, либо позже обобщить. Осознанно принято: сейчас есть только один такой случай, обобщение раньше времени было бы overengineering.
- **[Риск] Фронтенд и бэкенд независимо реализуют одну и ту же формулу совместимости диапазона** (`min_value ⩽ high ⩽ value`) → Смягчение: формула тривиальна и одинаково описана в specs обеих capability (`door-configuration-api` и `door-configurator-ui`) как эталон; расхождение будет заметно по интеграционным тестам (фронт покажет опцию, которую бэкенд отклонит, или наоборот).
