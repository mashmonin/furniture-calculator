## Context

См. proposal.md — Why. Таблицы уже существуют и применены (`0001-item-schema.yaml`); это изменение только добавляет столбцы поверх них через новый additive changeset, ничего в `0001-item-schema.yaml` не трогает.

В обсуждении перед написанием этого изменения рассматривались альтернативы структуре справочников:
- **varchar прямо на потребителе** (например, `item.item_type` строкой вместо FK на `item_type`) — отклонено: теряется ссылочная целостность (опечатки не ловятся БД, переименование значения — массовый `UPDATE` по потребителям), и уже действующее требование спецификации «защита справочников от удаления» (`item-configuration-schema`) перестаёт что-либо защищать.
- **Единая таблица `dictionary`** с колонкой-категорией вместо семи отдельных `_type` таблиц — отклонено: FK на такую таблицу не гарантирует БД-уровнем, что сослались на строку нужной категории (нужен составной ключ `(id, category)`, что возвращает сложность обратно), и типизация «под категорию» (например, отдельная колонка для дименшена или hex для цвета) в общей таблице не помещается без деградации в generic-колонки.
- **`binding_object_id` на `liner_dimensions`/`colours`**, разворачивающий связь так, что размер/цвет принадлежит одному конкретному объекту — отклонено: ломает уже реализованную и специфицированную переиспользуемость (`liner_dimensions`/`colours` — общие таблицы значений, на одну строку могут ссылаться несколько компонентов), и представляет собой полиморфную связь, которую нельзя выразить одной FK-колонкой.

## Goals / Non-Goals

**Goals:**
- Дать всем семи справочным таблицам (`item_type`, `leaf_type`, `mirror_type`, `leaf_side`, `frame_type`, `liner_dimension_type`, `colour_type`) единообразную пару столбцов `name`/`code`, достаточную для их наполнения данными.
- Дать `liner_dimensions` и `colours` минимальный набор столбцов, необходимый, чтобы строка размера/цвета что-то содержательное описывала.

**Non-Goals:**
- JPA-сущности, репозитории, сервисы, REST-эндпоинты, начальные данные справочников — не в этом изменении (аналогично `add-item-schema`).
- Изменение уже применённого `0001-item-schema.yaml` — новые столбцы идут отдельным changeset-файлом.
- `item`, `leaf`, `frame`, `edge`, `door_casing`, `frame_extensions`, `leaf_mirror` новых столбцов не получают — их тип и описательные данные уже полностью выражены существующими `*_type_id`, `liner_dimensions_id`, `colours_id` FK.

## Decisions

### Единообразная пара `name`/`code` для всех семи справочников
`name VARCHAR(255) NOT NULL`, `code VARCHAR(255) NOT NULL`, уникальный индекс на `code` в пределах таблицы. Одинаковая форма для всех семи таблиц — сознательный выбор ради прикладного слоя: в будущем прикладном изменении это позволяет описать все справочники одним общим `@MappedSuperclass` (`id`, `name`, `code`) и одним generic `@NoRepositoryBean`-репозиторием, так что каждая конкретная `_type`-сущность в Java сводится к пустому классу-наследнику вместо полноценного дублирующегося CRUD-слоя на 15 (в перспективе) справочников. Здесь это только ориентир на будущее — код не пишется в рамках этого изменения.

### `liner_dimensions.value` + `liner_dimensions.is_standard`, без отдельной колонки типа
`value DECIMAL NOT NULL`, `is_standard BOOLEAN NOT NULL`. Тип размера уже выражен существующим `liner_dimension_type_id` — отдельная `dimension_type varchar` дублировала бы его и создавала два источника истины для одного и того же факта.

### `colours.name` (обязательно) + `colours.ral_code` (опционально)
`name VARCHAR(255) NOT NULL`, `ral_code VARCHAR(255)` без `NOT NULL`. Название обязательно, каталожный код — нет: не у каждого цвета обязательно есть присвоенный RAL/каталожный код на момент внесения.

### Организация changeset'ов
Новый файл `backend/src/main/resources/db/changelog/changes/0002-item-attribute-columns.yaml`, подключаемый из `db.changelog-master.yaml` после `0001-item-schema.yaml`. Один changeset на таблицу (`addColumn`), без зависимостей между собой (все таблицы уже существуют) — порядок внутри файла не критичен, но сохраняется тот же, что и в `0001`, для читаемости.

## Risks / Trade-offs

- **`code` как `VARCHAR` без ссылки на фиксированный набор значений** → возможны опечатки при заполнении справочников вручную. Смягчение: `UNIQUE` хотя бы предотвращает дубликаты; более строгая валидация (например, регэксп формата кода) — решение прикладного слоя, не схемы.
- **`NOT NULL` на новых столбцах справочников** → если в справочных таблицах уже есть строки (сейчас нет — `add-item-schema` оставил их пустыми) без `name`/`code`, `addColumn` с `NOT NULL` без `defaultValue` упадёт. Риска нет при пустых таблицах на момент применения; если к моменту применения появятся строки — потребуется `defaultValue` или предварительный backfill.
