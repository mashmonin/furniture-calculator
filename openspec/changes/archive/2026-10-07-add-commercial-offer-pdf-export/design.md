## Context

Выгрузка заказа в Excel (`OrderExportService`, Apache POI) уже умеет по списку `OrderLineExportRequestDto` разворачивать позиции в компоненты с розничной/дилерской ценой. Фронтенд хранит корзину в `localStorage` и отправляет её целиком в теле запроса; сохранение файла унифицировано в `saveBlob` (в desktop-оболочке JavaFX WebView — через мост «Сохранить как»). Папка `DoorImages/` в корне репозитория сейчас не отслеживается git: `Вертикаль/<1..7>/<цвет>/<hash>.jpg.webp` и `Лайт/<модель>/<цвет>/<имя>.jpg.webp` (38 файлов, 37 WebP + 1 JPEG, ~0,7 МБ). Образец оформления — `zakaz_….pdf` (HAUSDOORS): одна страница на заказ, логотип, строки номера/даты, изображение двери, характеристики, итоговая цена. Отдельного файла-шаблона нет; первоначально брался другой образец («Я-КОНЦЕПТ», с обложкой и контактами), заменён по решению пользователя. См. proposal.md — мотивация и объём.

## Goals / Non-Goals

**Goals:**
- Одинаковая работа в браузере и в desktop-сборках (macOS/Windows) без зависимости от ОС-шрифтов.
- Переиспользовать расчёт компонентов и цен из экспорта заказа — цифры в КП совпадают с Excel и корзиной.
- Подбор картинки по модели и цвету без изменений схемы БД.

**Non-Goals:**
- Тексты-описания моделей/покрытий (правая колонка «Описание модели» образца), обложка и страница контактов, реквизиты клиента, форма ввода «помещение/имя клиента», колонки «Открывание» и «Рекомендации по проемам» — не в этой версии.
- Загрузка/управление изображениями через UI; добавление картинок для всех моделей (только то, что лежит в `DoorImages`).
- Изменение формата Excel-выгрузки.

## Decisions

**1. PDF генерируется на backend, а не на фронтенде.** Backend уже владеет расчётом, ресурсами и упаковкой в desktop-дистрибутив; клиент получает готовый `Blob` и отдаёт его в существующий `saveBlob`. Альтернатива — jsPDF/pdfmake в браузере: пришлось бы тащить на фронт шрифты и все картинки (или отдельные эндпоинты для них) и дублировать форматирование цен.

**2. Библиотека — OpenPDF (`com.github.librepdf:openpdf`) с встроенным TTF-шрифтом.** Вёрстка страниц (шапка и страница позиции) строится программно: `PdfPTable` для таблицы с повтором заголовка при переносе, `Image` для картинок. Шрифт (семейство с кириллицей и «₽», например PT Sans/Roboto с открытой лицензией) лежит в ресурсах и подключается через `BaseFont.createFont(..., IDENTITY_H, EMBEDDED)` — без AWT/системных шрифтов (на Homebrew-JDK AWT-шрифты уже ломали экспорт Excel, см. комментарий в `build.gradle`). Альтернатива — HTML → PDF (openhtmltopdf): удобнее верстать, но тяжелее зависимости (PDFBox, Batik) и больше размер дистрибутива; пересмотреть, если программная вёрстка окажется неудобной.

**3. WebP-декодирование — `com.twelvemonkeys.imageio:imageio-webp`.** JDK не читает WebP; плагин подключается через ServiceLoader `ImageIO`, картинка перекодируется в PNG/JPEG в памяти перед вставкой в PDF. Альтернатива — заранее сконвертировать файлы в JPEG и положить в ресурсы: убирает зависимость, но усложняет добавление новых картинок (пользователь кладёт те, что у него есть, — WebP). Если плагин не заработает в jlink-сборке desktop, fallback — конвертация при сборке.

**4. Каталог изображений переезжает в `backend/src/main/resources/commercial-offer/door-images/` и отслеживается git.** Так файлы попадают в jar и в desktop-дистрибутив без изменений `jpackage`-конфигурации. Структура папок сохраняется: `<коллекция>/<модель>/<цвет>/<файл>`. Файл внутри папки цвета берётся единственный (имя-хэш не используется для сопоставления). Поиск — по ресурсному пути через `PathMatchingResourcePatternResolver`.

**5. Сопоставление «позиция → картинка»** выполняется на backend по данным запроса: `leafTypeId` → тип полотна (код, наименование, коллекция), `leaf.colourOptionId` → название цвета (`colour_type.name`). Правило нормализации: коллекция = папка первого уровня (регистр и пробелы нормализуются); для «Вертикаль» папка модели — номер из наименования типа без ведущих нулей («Вертикаль 01» → `1`); для «Эмаль Лайт» папка модели — наименование типа как есть («MONO MN 01»); папка цвета — название цвета как есть. Точные имена типов/коллекций в каталоге сверяются на этапе реализации и фиксируются тестом по реальным данным; несовпадение → «картинки нет» (fallback — страница без изображения, не ошибка). Данные для сопоставления — только каталог, схема БД не меняется.

**6. Состав таблицы.** Строки компонентов строятся из того же разворота компонентов, что и в Excel-заказе (`OrderExportService`/`SpecificationComponents`), но выводятся только розничные цена и сумма. Логика разворота выносится в общий метод (или используется напрямую), чтобы не копировать расчёт. Размер полотна в формате «высота*ширина» (по образцу «2400*800»), мм.

**7. Фирменные ассеты:** логотип HAUSDOORS (PNG, вырезан из образца `zakaz_….pdf` — векторного оригинала нет) и шрифт лежат в `commercial-offer/`. Шапка (логотип, номер, дата, линии) рисуется page-event'ом на каждой странице; номер заказа — момент выгрузки `ггммддччмм` (как в образце), он же в имени файла `КП-<номер>.pdf`; сервис возвращает номер вместе с содержимым PDF.

**8. Фронтенд:** метод `exportOffer(lines)` в `api/doorConfigurations.ts` (зеркало `exportOrder`, `Accept: application/pdf`), кнопка в `CartScreen.tsx` по образцу Excel-кнопки: `loading`, блок ошибки, имя файла из `Content-Disposition`, сохранение через `saveBlob`. Только компоненты `antd`.

## Risks / Trade-offs

- [WebP-плагин не работает в jlink/jpackage-сборке] → проверить сборку desktop на этапе реализации; fallback — конвертировать картинки в JPEG при сборке/в репозитории.
- [Не совпадают названия цветов/моделей в каталоге и в папках] → тест на реальных данных каталога, список «цвет есть, картинки нет» в логе (debug); страница без картинки — штатный сценарий.
- [Размер дистрибутива растёт на ~1 МБ картинок + шрифт] → приемлемо.
- [Нет оригинала логотипа] → растровый логотип вырезан из образца; при печати проверить качество, при необходимости запросить оригинал.
- [Программная вёрстка хуже передаёт «красоту» образца] → сверка с образцом на этапе apply, при необходимости переход на HTML → PDF (см. решение 2).

## Migration Plan

Миграций БД нет. Порядок: перенос `DoorImages` в ресурсы → зависимости → сервис генерации → эндпоинт → фронтенд. Откат — удаление эндпоинта и кнопки; Excel-выгрузка не затрагивается.
