## Why

Для части справочных записей полные наименования слишком длинные и громоздкие для компактных мест интерфейса (селекты, чипы, разбивка стоимости). Нужно универсальное, необязательное «краткое наименование», которое можно заполнять итеративно — начиная с двух значений `edge_type` и трёх значений `mirror_finish_type`, — не создавая при этом отдельный нестандартный контракт для каждого справочника.

## What Changes

- Добавить в общий контракт справочных типов (`CatalogType` и всё, что через него отдаётся как `ReferenceDto`: `edge_type`, `door_casing_type`, `frame_extensions_type`, `post_type`, `frame_type`, `hardware_category`, `hardware_type`, `liner_dimension_type`, `colour_type`, `leaf_type`, `leaf_collection`) необязательное поле «краткое наименование» (`short_name` / `shortName`).
- Добавить необязательное поле «краткое наименование» отдельно для `mirror_finish_type` (не входит в `CatalogType`) и прокинуть его в ответ `GET /api/pricing-surcharges`, а также в список допустимых исполнений зеркала полотна в каталоге конфигураций.
- Заполнить краткие наименования для конкретных значений:
  - `edge_type`: «ПРЯМАЯ КРОМКА ПО ПЕРИМЕТРУ ПОЛОТНА» → «Прямая», «КРОМКА ДЛЯ ПОЛОТНА С ЧЕТВЕРТЬЮ ПО ПЕРИМЕТРУ» → «С четвертью».
  - `mirror_finish_type`: «Глухое плоское полотно с зеркалом с одной стороны» → «Базовое», «Глухое плоское полотно с зеркалом с фацетом с одной стороны» → «С фацетом», «Глухое плоское полотно с зеркалом серое/бронза с одной стороны» → «Серое/бронза».
  - Для всех остальных справочных строк (все прочие значения перечисленных таблиц) краткое наименование остаётся пустым (`NULL`) — заполнение остальных значений выполняется отдельными изменениями в будущем.
- Поле необязательное на уровне API: когда краткое наименование не задано, соответствующее поле в ответе — `null`, полное наименование (`name`) продолжает возвращаться как обычно.

## Capabilities

### New Capabilities
- `catalog-reference-short-name`: общий контракт «краткого наименования» для справочных типов, реализующих `CatalogType`, — необязательное поле в структуре типа и в `ReferenceDto`, плюс конкретные значения для `edge_type`.

### Modified Capabilities
- `door-configuration-catalog`: структура `mirror_finish_type` получает необязательное краткое наименование; список допустимых исполнений зеркала полотна в каталоге конфигураций дополнительно возвращает краткое наименование, когда оно задано.
- `door-configuration-api`: ответ `GET /api/pricing-surcharges` дополнительно содержит краткое наименование каждого исполнения зеркала, когда оно задано.

## Impact

- **БД**: новые Liquibase changeset'ы — колонка `short_name VARCHAR NULL` в таблицах `edge_type`, `door_casing_type`, `frame_extensions_type`, `post_type`, `frame_type`, `hardware_category`, `hardware_type`, `liner_dimension_type`, `colour_type`, `leaf_type`, `leaf_collection` и отдельно в `mirror_finish_type`; заполнение колонки для перечисленных выше пяти значений.
- **Backend**: интерфейс `CatalogType` (+ 11 реализующих его сущностей), `ReferenceDto`, `MirrorFinishSurchargeDto`, точка сборки списка исполнений зеркала в `DoorConfigurationCatalogService` (`toDto(MirrorFinishOption)`), `PricingSurchargesService`.
- **Frontend**: типы ответов, соответствующие `ReferenceDto` и `MirrorFinishSurchargeDto`, и места отображения кратких наименований (там, где сейчас показывается `name` для этих справочников) — конкретные экраны определяются на этапе `design`/`tasks`.
