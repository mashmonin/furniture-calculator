## Context

Название прайс-листа сейчас — константа `PRICE_LIST_LABEL = 'Прайс-лист: hausdoors_emal_i_shpon_rf_13_07_2026'` в `App.tsx` (показывается в шапке только на экране конфигуратора); в корзине отдельный тег `ЭМАЛЬ И ШПОН` — тоже константа (не меняется). В БД: `collection` (9 записей, `LC-001..LC-009`) → `leaf_type`; фурнитура: `hardware_category` (6) → `hardware_type` (17) → `hardware_option` (55). Каталог дверей отдаётся `GET /api/door-configurations` как список `DoorConfigurationDto`, у каждого компонента `ComponentCatalogDto` есть `collection` (`ReferenceDto`); каталог фурнитуры — `GET /api/hardware-catalog`, тип — `HardwareTypeDto(type, unit, options)`. Названия источников — имена файлов; новая фурнитура новых файлов не пересекается со старой.

## Goals / Non-Goals

**Goals:**
- Хранить источник (имя файла прайса) в БД и связать его с коллекциями и типами фурнитуры.
- Отдавать источник через API и показывать в шапке сервиса.

**Non-Goals:**
- Таблица сервисов, фильтрация каталога по источнику, выбор источника пользователем.
- Источник в корзине и экспорте заказа.
- Источник у декоративных элементов, версионирование и история прайс-листов.
- Загрузка/импорт файла прайса.

## Decisions

1. **Таблица `price_list`** (`id`, `code` уникальный `PL-001`…, `name` — имя файла). Имя `price_list`, а не «source»: в предметной области это прайс-лист, подпись в UI «Прайс-лист: …». Начальная запись `PL-001` = `hausdoors_emal_i_shpon_rf_07_09_2026` (не `13_07_2026`; новое название вместо старого в UI).
2. **Источник дверей — на `collection`, не на `door_configuration`/компонентах.** Конфигурация и модель полотна наследуют источник через коллекцию (`collection.price_list_id`). Альтернативы (на каждом типе компонента или на каждой строке `door_configuration`) — тяжёлые миграции и обновления данных при каждом новом прайсе без выгоды при принципе «один сервис = один источник».
3. **Источник фурнитуры — на `hardware_type`.** Не на категории (категория может смешивать источники, когда новый файл добавляет позицию в существующую категорию) и не на `hardware_option` (цвета одного типа всегда из одного файла, дублирование). Для новых файлов источник задаётся одной константой в `INSERT` типов.
4. **Миграция без процедурной логики**, переносимая на H2: создать таблицу, вставить `PL-001`, добавить колонки как nullable, заполнить `UPDATE`, затем `NOT NULL` и внешний ключ. Новый changeset, существующие не редактируются; для desktop override не нужен, если используется только переносимый SQL (проверить тестами).
5. **API: поле `priceList` (`{id, code, name}`).** В `ComponentCatalogDto` заполняется только для leaf-компонента (по аналогии с диапазонами размеров коллекции), у остальных компонентов `null`. В `HardwareTypeDto` — у каждого типа. Добавление полей обратно-совместимо. Альтернатива — отдельный эндпоинт `/api/price-lists`: лишний запрос и необходимость знать, какой источник относится к сервису.
6. **Frontend: подпись из каталога.** Шапка показывает «Прайс-лист: » + `priceList.name` leaf-компонента загруженных конфигураций (по принципу «один сервис = один источник» значение одно). Пока каталог не загружен или пуст — подпись не показывается. Константа `PRICE_LIST_LABEL` удаляется; префикс «Прайс-лист: » остаётся на фронтенде.

## Risks / Trade-offs

- [Если в одном сервисе окажутся коллекции из разных файлов, одной подписи недостаточно] → вне scope по принципу «один сервис = один источник»; при нарушении фронтенд берёт источник первой конфигурации — зафиксировать в комментарии; при появлении такого сценария — отдельный change.
- [Название источника меняется с `13_07_2026` на `07_09_2026`] → это сознательное решение пользователя; единственное место с прежним названием — константа и комментарий на фронтенде, они заменяются.
- [Колонка `NOT NULL` + заполнение: порядок шагов в миграции] → один changeset в правильном порядке; проверка на PostgreSQL и H2 (десктопные тесты).
- [Декоративные элементы остаются без источника] → зафиксировано в Non-Goals; добавить отдельным change при необходимости.
