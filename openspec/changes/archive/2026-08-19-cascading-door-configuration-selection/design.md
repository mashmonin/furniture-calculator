## Context

`GET /api/door-configurations` уже отдаёт весь каталог как плоский список `DoorConfigurationDto[]` (frontend/src/api/types.ts), где у каждой конфигурации есть `leaf: ComponentCatalogDto` (всегда) и `frame/edge/doorCasing/frameExtensions: ComponentCatalogDto | null`. Каждый `ComponentCatalogDto` несёт `type: ReferenceDto` (id/code/name конкретного *_type) и списки `dimensionOptions`/`colourOptions`. См. proposal.md - Why/What Changes.

Текущий `App.tsx` хранит этот список в `configurations` и рендерит их как `Radio.Group` с меткой `configurationLabel()`. Это заменяется каскадной фильтрацией того же массива, без изменений на backend.

## Goals / Non-Goals

**Goals:**
- Заменить шаг 1 на последовательность из до пяти шагов (leaf, frame, doorCasing, edge, frameExtensions), каждый — вычисляемый клиентский фильтр по уже загруженному `configurations`.
- Довести каскадный выбор до единственной `DoorConfigurationDto`, после чего шаги 2–3 работают как сейчас без изменений их кода.

**Non-Goals:**
- Изменение backend API или БД — не требуется, т.к. весь необходимый для фильтрации состав уже есть в ответе каталога.
- Изменение формата запроса/ответа расчёта стоимости (`PricingRequestDto`/`PricingResponseDto`).
- Изменение порядка/состава осей размеров и цвета внутри уже выбранного компонента (шаг 2) — не трогается.

## Decisions

### Порядок шагов каскада: leaf → frame → doorCasing → edge → frameExtensions
Явно задан в proposal.md по требованию пользователя (полотно → короб → наличник, кромка и удлинители — аналогично). Наличник и удлинители по действующему ограничению БД (`chk_door_configuration_casing_extensions_require_frame`) требуют заданного короба, поэтому в любом случае должны идти не раньше frame; помещаем оба после doorCasing, так как явного требования по их взаимному порядку нет, а doorCasing явно назван пользователем раньше.

### Фильтрация — чистая клиентская функция от списка выборов
Вместо пяти независимых `useState` полей вводится единый стейт `cascadeSelection: Partial<Record<ComponentKey, number>>` (id выбранного `type` на каждом пройденном шаге). Для каждого шага `key` в `COMPONENT_ORDER`:
1. `candidates` = `configurations`, отфильтрованные по всем уже выбранным в `cascadeSelection` ключам (`configuration[selectedKey]?.type.id === cascadeSelection[selectedKey]`), включая шаги перед `key`, но не включая сам `key`.
2. `availableTypes` = уникальные по `id` значения `candidates.map(c => c[key]?.type)`, отбросив `null`/`undefined`.
3. Если `availableTypes.length === 0` — шаг `key` пропускается (компонент неприменим для текущего частичного выбора).
4. Значение для `key` считается выбранным только если оно явно присутствует в `manualSelection[key]` (пользователь кликнул по варианту). Даже когда `availableTypes.length === 1`, шаг не выбирается сам за себя и не пропускается — вычисление останавливается на этом `key` до явного клика.
5. Шаг всегда показывается как группа кнопок (`OptionGroup`, один вариант на элемент `availableTypes`, в том числе когда вариант всего один) — так пользователь одинаково видит и явно выбирает каждый шаг каскада, вне зависимости от числа доступных вариантов.

**История решения:** первая версия при единственном варианте автоматически выбирала его и сразу показывала следующий шаг — либо как неинтерактивную строку текста, либо как подсвеченную «выбранную» кнопку. Оба варианта отклонены по прямой обратной связи пользователя: неинтерактивная строка не читалась как часть того же набора шагов и выглядела как баг/недоступность; подсвеченная, но не кликабельная по сути кнопка выглядела «залипшей» без возможности осознанного выбора. Итоговое решение — не автовыбирать вообще: пользователь обязан кликнуть по варианту, даже если он единственный.

Эта функция пересчитывается на каждом рендере из `configurations` + `cascadeSelection` (без мемоизации на первом проходе — каталог небольшой), что проще и надёжнее, чем поддерживать производный стейт вручную.

**Альтернатива (отклонена):** держать на backend отдельный эндпоинт вида `GET /api/door-configurations/options?leaf=..&frame=..`, вычисляющий доступные следующие варианты. Отклонено, т.к. весь каталог и так помещается в один ответ, который уже загружается целиком для шага 2 (там нужны `dimensionOptions`/`colourOptions` всех компонентов выбранной конфигурации) — вводить сетевой round-trip на каждый шаг ради данных, которые уже есть на клиенте, не даёт выигрыша и усложняет backend.

### Итоговая конфигурация
После того как для каждого `key` из `COMPONENT_ORDER` шаг либо пройден (пользователь явно выбрал вариант), либо пропущен (неприменим), `candidates` в этот момент содержит ровно одну конфигурацию — она и становится `selectedConfiguration`, как раньше используемым шагами 2 и 3 без изменений их логики. Это гарантируется тем, что `door_configuration` имеет уникальный индекс `uk_door_configuration_combination` по полному набору `(leaf_type_id, frame_type_id, edge_type_id, door_casing_type_id, frame_extensions_type_id)` — пройдя все пять осей, невозможно получить более одной строки.

### Сброс при изменении раннего шага
Изменение выбора на шаге `key` очищает `cascadeSelection` для всех шагов, идущих в `COMPONENT_ORDER` после `key` (аналогично текущему сбросу опций размера/цвета при смене конфигурации). Опции размеров/цвета (шаг 2) и результат расчёта (шаг 3) сбрасываются всегда при любом изменении `cascadeSelection`, а не только когда итоговая конфигурация меняется — это проще в реализации и достаточно для UX (промежуточное состояние каскада не должно нести устаревший результат расчёта).

## Risks / Trade-offs

- [Пересчёт кандидатов на каждом рендере линеен по размеру каталога] → каталог — это согласованные конфигурации дверей одного магазина, ожидаемый размер — десятки-сотни строк; пересчёт тривиален, отдельная оптимизация не нужна.
- [Требование явного клика даже при единственном варианте добавляет пользователю лишний шаг по сравнению с автовыбором] → сознательный компромисс по прямой обратной связи пользователя: предсказуемость и однообразие («каждый шаг выбирается кликом») важнее экономии одного клика на шагах с единственным вариантом.
