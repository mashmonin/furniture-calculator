## Why

Сейчас пользователь конфигуратора видит на первом шаге плоский список готовых сочетаний door_configuration (например «ВЕРТИКАЛЬ 06 · КОМПЛАНАР · Эво») и должен сразу узнать и выбрать целую готовую конфигурацию кликом — по сути, найти нужное сочетание в каталоге. Это неудобно: пользователь думает моделями компонентов («хочу Вертикаль 01, с коробом Комплланар и наличником Авеню»), а не заучивает состав каждой строки каталога. Нужен пошаговый подбор: сначала модель полотна, затем короб — только из тех, что доступны для выбранной модели, затем наличник — только из доступных для выбранной пары модель+короб, и так далее.

## What Changes

- Замена шага 1 конфигуратора (плоский список готовых конфигураций) на последовательность каскадных шагов выбора по типам компонентов: полотно → короб → наличник → кромка → удлинители.
- На каждом шаге, кроме первого, набор доступных вариантов вычисляется как множество значений компонента среди door_configuration, уже согласованных с выбором на предыдущих шагах (а не полный справочник типа).
- Если для текущего частичного выбора у следующего компонента есть только один допустимый вариант, он выбирается автоматически, без лишнего клика пользователя.
- Если очередной компонент не применим ни к одной из подходящих конфигураций (например, для полотна без короба нет ни коробов, ни наличников, ни удлинителей), соответствующий шаг не отображается.
- Как только каскадный выбор однозначно определяет одну строку door_configuration, конфигуратор переходит к уже существующему шагу выбора опций размеров/цвета по компонентам и расчёту стоимости — эта часть поведения не меняется.
- Источник данных не меняется: используется тот же эндпоинт `GET /api/door-configurations`, отдающий весь каталог целиком; каскадная фильтрация выполняется на фронтенде над уже загруженным списком. Новые backend-эндпоинты не вводятся.

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `door-configurator-ui`: требования «Загрузка и отображение каталога конфигураций» и «Выбор конфигурации» заменяются требованиями пошагового каскадного выбора компонентов конфигурации; требования «Динамический выбор опций компонентов» и «Расчёт стоимости по текущему выбору» сохраняются без изменений (применяются после того, как каскадный выбор определил конкретную конфигурацию).

## Impact

- `frontend/src/App.tsx`: шаг 1 переписывается с `Radio.Group` по всему каталогу на последовательность каскадных групп выбора по компонентам; логика сведения частичного выбора к конкретной door_configuration — новый код на фронтенде.
- Backend (`DoorConfigurationController`, `DoorConfigurationCatalogService`, эндпоинт `GET /api/door-configurations`) и схема БД не меняются.
