## Context

Исходные данные — ER-диаграмма в нотации Chen (PlantUML) с 17 сущностями; у каждой пустое тело атрибутов (`entity item {}`), и каждая связь нарисована как обычная `-N-` без маркера кардинальности на любом конце:

```
item -N- item_type
item -N- leaf
item -N- frame
item -N- edge
leaf -N- leaf_type
leaf -N- leaf_mirror
leaf -N- liner_dimensions
leaf -N- colours
leaf_mirror -N- mirror_type
leaf_mirror -N- leaf_side
leaf_mirror -N- liner_dimensions
frame -N- frame_type
frame -N- liner_dimensions
frame -N- colours
frame -N- door_casing
frame -N- frame_extensions
door_casing -N- liner_dimensions
door_casing -N- colours
frame_extensions -N- liner_dimensions
frame_extensions -N- colours
edge -N- liner_dimensions
edge -N- colours
liner_dimensions -N- liner_dimension_type
colours -N- colour_type
```

(В исходнике `entity frame {}` также объявлена дважды; считается одной сущностью — повторное объявление, а не две разные.)

Поскольку `-N-` не задаёт направление, первая задача этого документа — разрешить каждую связь в конкретную кардинальность, прежде чем она станет внешним ключом. О том, зачем эта схема нужна сейчас, см. proposal.md.

## Goals / Non-Goals

**Goals:**
- Превратить каждую сущность и связь диаграммы в таблицы PostgreSQL и внешние ключи, применяемые через Liquibase.
- Разрешить неоднозначные связи `-N-` диаграммы в явную, согласованную, проверяемую модель кардинальности (ниже), чтобы ревьюеры могли поправить её здесь, а не после того, как таблицы уже созданы.

**Non-Goals:**
- Столбцы-атрибуты. Каждая сущность в исходной диаграмме пустая; это изменение не добавляет описательных столбцов (названий, кодов, значений размеров, hex-цветов, цен и т. д.) сверх первичных и внешних ключей. Атрибуты добавляются последующим изменением, когда поля каждой сущности будут определены.
- JPA-сущности, репозитории, сервисы или REST-эндпоинты — только Liquibase changeset'ы.
- Начальные/справочные данные для справочных таблиц (`item_type`, `leaf_type`, `mirror_type`, `leaf_side`, `frame_type`, `liner_dimension_type`, `colour_type`) — пустые таблицы, заполняются позже.

## Decisions

### Интерпретация кардинальности (ключевое решение — пожалуйста, подтвердите)

Каждая связь в исходнике соответствует одной из двух форм:

1. **Форма справочника** (`X -N- X_type`): много строк `X` ссылаются на одну строку `X_type`. Однозначно — `X_type` явно является справочной таблицей.
2. **Структурная форма** (например, `item -N- leaf`, `frame -N- door_casing`): нет справочного именования, чтобы определить направление.

Для каждой структурной связи в этом дизайне сущность-**контейнер** помещена на сторону «один», а сущность-**компонент** — на сторону «много», внешний ключ — на компоненте:

| Родитель (1) | Потомок (N) | Столбец FK |
|---|---|---|
| item | leaf | `leaf.item_id` |
| item | frame | `frame.item_id` |
| item | edge | `edge.item_id` |
| leaf | leaf_mirror | `leaf_mirror.leaf_id` |
| frame | door_casing | `door_casing.frame_id` |
| frame | frame_extensions | `frame_extensions.frame_id` |

Обоснование: item (например, дверь) естественным образом состоит из своих полотен (leaf), коробки/коробок (frame) и кромок (edge); frame естественным образом состоит из добора (door_casing) и удлинителей (frame_extensions). Чтение диаграммы в обратную сторону (например, одно полотно, общее для многих item) не соответствует домену и ничем в диаграмме не подтверждается — это то же самое чтение «контейнер владеет компонентом», применённое единообразно, а не частный случай.

`liner_dimensions` и `colours` — это общие таблицы значений: они находятся на стороне «один» в каждой связи с компонентом (leaf, leaf_mirror, frame, door_casing, frame_extensions, edge), поэтому несколько компонентов могут ссылаться на одну и ту же строку размеров/цвета (`leaf.dimensions_id`, `frame.dimensions_id` и т. д. — все FK со значением NOT NULL к `liner_dimensions`/`colours`). Это отражает форму справочника и оставляет каждую связь диаграммы разрешённой одинаковым образом: много-ссылающихся-сущностей → одна-сущность-на-которую-ссылаются.

**Это предположение, а не факт, который можно восстановить из диаграммы.** Если предполагаемая кардинальность где-либо в таблице выше отличается (например, у frame должен быть ровно один item, или у leaf должно быть разрешено не более одного mirror, а не несколько), сообщите об этом до `/opsx:apply` — это изменит и `specs/item-configuration-schema/spec.md`, и Liquibase changeset'ы в `tasks.md`.

### Первичные ключи
`BIGINT GENERATED ALWAYS AS IDENTITY` с именем `id` в каждой таблице. Соответствует целевой СУБД проекта (PostgreSQL) и избегает накладных расходов UUID там, где на эти ID пока ничего не ссылается извне.

### Именование внешних ключей и поведение ON DELETE
- Столбцы FK: `<referenced_entity_singular>_id` (например, `leaf.item_id`, `leaf.leaf_type_id`).
- FK композиции (item→leaf/frame/edge, leaf→leaf_mirror, frame→door_casing/frame_extensions): `ON DELETE CASCADE` — удаление контейнера удаляет его компоненты.
- Справочные FK (→ item_type, leaf_type, mirror_type, leaf_side, frame_type, liner_dimension_type, colour_type) и FK на общие значения (→ liner_dimensions, colours): `ON DELETE RESTRICT` — соответствует требованию спецификации «защита справочников от удаления»; используемую строку типа или общих размеров/цвета нельзя удалить из-под ссылающихся на неё строк.

### Организация таблиц и changeset'ов
Один файл Liquibase changelog, `backend/src/main/resources/db/changelog/changes/0001-item-schema.yaml`, подключаемый из `db.changelog-master.yaml`. Внутри — один `changeSet` на таблицу, в порядке, при котором таблицы, на которые ссылаются, создаются раньше таблиц, которые на них ссылаются:
1. Справочные таблицы без зависимостей: `item_type`, `leaf_type`, `mirror_type`, `leaf_side`, `frame_type`, `liner_dimension_type`, `colour_type`.
2. Таблицы общих значений: `liner_dimensions`, `colours` (каждая зависит от своей `_type`-таблицы).
3. `item` (зависит от `item_type`).
4. `leaf`, `frame`, `edge` (каждая зависит от `item`, своей `_type`-таблицы, где применимо, и `liner_dimensions`/`colours`).
5. `leaf_mirror` (зависит от `leaf`, `mirror_type`, `leaf_side`, `liner_dimensions`).
6. `door_casing`, `frame_extensions` (каждая зависит от `frame`, `liner_dimensions`, `colours`).

Один changeset на таблицу (а не один changeset на всю схему) делает откат и ревью более гранулярными, что соответствует конвенции Liquibase.

## Risks / Trade-offs

- **Неверное направление кардинальности** → таблицу выше можно проверить сейчас, до того как появится хоть одна таблица; исправление её после `/opsx:apply` означает правку/откат changeset'ов вместо правки markdown-таблицы. Смягчение: явное подтверждение запрашивается перед apply.
- **Справочные таблицы выпускаются пустыми, без строк** → не с чем сопоставлять (join), пока данные атрибутов не добавлены последующим изменением. Приемлемо, поскольку это изменение по замыслу — только схема (см. Non-Goals).
- **Все справочные/значимые связи обязательны (`NOT NULL` FK)** → например, leaf нельзя сохранить без уже существующих dimensions и colour. Это соответствует диаграмме (показаны все связи, ни одна не отмечена как опциональная), но потребует от прикладного слоя создавать/выбирать эти строки перед вставкой leaf. Если что-то из этого должно быть опциональным — это тоже нужно решить в рамках подтверждения кардинальности выше.

## Migration Plan

Только аддитивно — новые таблицы, без изменений существующей схемы (master changelog сейчас пуст). Применение — это единый `liquibase update` (или `./gradlew bootRun`, который запускает Liquibase при старте) к новой или существующей базе `furniture_calculator`. Откат — `liquibase rollback-count 1` на каждый changeset, либо удаление таблиц в обратном порядке зависимостей — риска потери данных нет, поскольку сейчас таблиц не существует.
