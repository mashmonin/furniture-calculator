## Context

Наценка за цвет полотна сейчас — один множитель (`colourSurchargeMultiplier` в `DoorConfigurationPricingService`), выведенный из единственного `colourOptionId` в `ComponentSelectionDto`. Надбавки к цене полотна применяются строго последовательно, шаг за шагом, с округлением после каждого шага (`applySequentialSurcharges`); порядок шагов — контракт, задокументированный по частям в `door-configuration-api` («Место наценки за N в последовательности надбавок»). Надбавка за реверс (10%, единственная надбавка, которая не зависит от выбора клиента, а только от булевого признака) — константа в коде (`REVERSE_SURCHARGE_MULTIPLIER`), не строка в БД, отданная фронту через `GET /api/pricing-surcharges` как вычисляемое поле. Два места в бэкенде резолвят выбор компонента одинаковым способом (`addComponentIfPresent` в `DoorConfigurationPricingService`, общий для расчёта по `door_configuration` и для этапного расчёта отдельного полотна) — значит новую логику цвета/двусторонней покраски достаточно реализовать один раз в этом общем месте. См. proposal.md — «Why» и «What Changes» для мотивации; ответы на уточняющие вопросы (только `leaf`; 50%-я надбавка — отдельный последовательный шаг, как реверс) уже приняты и не пересматриваются здесь.

## Goals / Non-Goals

**Goals:**
- Добавить возможность указать для полотна два цвета (фронтальный/задний) и признак двусторонней покраски в едином контракте выбора компонента, без дублирования валидации между расчётом по конфигурации и этапным расчётом полотна.
- Реализовать формулу наценки за цвет (сумма процентов двух сторон, без каскадного перемножения) и отдельную 50%-ю надбавку за двустороннюю покраску, встроив их в существующую последовательную цепочку наценок в правильном месте.
- Прокинуть новые поля через выгрузку спецификации (второй цвет в ячейке, надбавка в разделе) и через фронтенд (переключатель, два списка, разбивка).

**Non-Goals:**
- Не затрагивает короб, кромку, наличник, добор — двусторонность и второй цвет только у `leaf`.
- Не вводит новых таблиц/колонок в БД — второй цвет ссылается на уже существующий `colour_option`, процент 50% — константа в коде.
- Не меняет UI других компонентов (`ряд кнопок` для цвета короба/кромки/наличника/добора не трогаем).

## Decisions

### 1. Контракт запроса: новые поля в `ComponentSelectionDto`, а не новый DTO
Добавляем два поля в существующий `ComponentSelectionDto`: `Long backColourOptionId` и `Boolean doubleSidedPainting`. Существующее поле `colourOptionId` остаётся как есть и трактуется как фронтальный цвет при `doubleSidedPainting = true`. Оба поля валидны только когда резолвится `LeafType` — как и `mirrorFinishTypeId`/`glazingTypeId` сейчас (см. `resolveMirrorFinishMultiplier`/`resolveGlazingMultiplier` — тот же паттерн «поле общее для DTO, но 400 для не-leaf компонента»).
- Альтернатива (отклонена): отдельный `LeafSelectionDto` с явными `frontColourOptionId`/`backColourOptionId` вместо общего `colourOptionId`. Отклонено — потребовало бы переименовывать/дублировать поле во всех вызывающих местах (frame/edge/doorCasing/frameExtensions тоже используют `colourOptionId`) ради поля, нужного только одному типу компонента; существующий паттерн (общий DTO + серверная валидация «только для leaf») уже решает эту задачу для mirrorFinish/glazing.
- Валидация: `backColourOptionId != null` при `doubleSidedPainting != true` → 400 (см. спеку). `doubleSidedPainting = true` без `backColourOptionId` — допустимо (наценка за цвет считает только фронтальную сторону, надбавка за двустороннюю покраску всё равно применяется).

### 2. Наценка за цвет: суммирование процентов, а не перемножение множителей, до пересчёта в единый множитель
`colourSurchargeMultiplier` возвращает множитель `1 + (frontPercent [+ backPercent, если doubleSidedPainting]) / 100` — т.е. складываются проценты (`BigDecimal`), а не перемножаются готовые множители `(1+p1/100)×(1+p2/100)`. Это даёт ровно 40% для двух сторон по 20%, а не 44%, как того требует proposal.md. Реализуется как небольшое изменение существующего метода: вместо одного `colourOption.getColourType().getSurchargePercent()` — сумма процента фронтального и (если применимо) заднего `colourOption`.
- Альтернатива (отклонена): применять наценку каждой стороны отдельным шагом цепочки (front-цвет → back-цвет как два последовательных шага). Отклонено явно требованием proposal.md («не последовательно, а просто умножается на 2») и решением пользователя не суммировать это с двусторонней покраской в один шаг — цвет остаётся одним шагом, как и до этого изменения, просто с другой формулой процента.

### 3. Надбавка за двустороннюю покраску: константа в коде, отдельный шаг цепочки, по аналогии с реверсом
Новая константа `DOUBLE_SIDED_PAINTING_SURCHARGE_MULTIPLIER = 1.50` рядом с `REVERSE_SURCHARGE_MULTIPLIER`. Новый шаг в `applySequentialSurcharges`/`applyPercentMultiplier`, применяемый сразу после шага цвета и до шага исполнения зеркала (порядок задокументирован в специфике door-configuration-api, «Место надбавки за двустороннюю покраску в последовательности надбавок»). `reverseSurchargePercent()`-подобный метод `doubleSidedPaintingSurchargePercent()` добавляется в `DoorConfigurationPricingService` и пробрасывается в `PricingSurchargesDto` через `PricingSurchargesService` — так же, как сегодня `reverseSurchargePercent`.
- Почему после цвета и до зеркала, а не в конце (рядом с реверсом): это единственное место, явно не специфицированное в исходном запросе; размещение рядом с шагом цвета логически группирует обе «покрасочные» надбавки, не меняя относительный порядок уже существующих шагов (зеркало/остекление/реверс остаются в прежней взаимной последовательности, просто сдвинуты на один шаг). Порядок — детерминированная часть контракта (см. существующий принцип «наценки применяются строго последовательно, с округлением после каждого шага»), поэтому решение зафиксировано в спеке, а не оставлено на усмотрение реализации.

### 4. Разбивка (`LeafPriceSurcharge`) и спецификация: новая строка-надбавка, вторая колонка цвета
`leafPriceSurcharges` получает новую строку «За двустороннюю покраску» (`addSurchargeIfApplied` с уже готовым множителем — паттерн не меняется). Для экспорта строки полотна (`SpecificationExportService`) `ResolvedComponent.colourOption` заменяется на пару `frontColourOption`/`backColourOption` (второе поле `null` вне leaf или без двусторонней покраски); форматирование ячейки цвета («Фронт / Зад» через ` / `) — единственное новое форматирование, локальное для этого сервиса.

### 5. Фронтенд: локальное состояние полотна, а не новый шаг каскада
Переключатель «Двустороннее» и второй цвет — состояние конкретного полотна (как текущий `colourOptionId` в `selection.leaf`), а не отдельный шаг каскада уровня всего потока (в отличие от «Реверс», который сужает согласованные `door_configuration`). Он не должен вызывать пересчёт каскада — только локально переключает состав полей группы «Цвет» этого полотна и то, что отправляется в запрос. Технически: `selection.leaf` получает `doubleSidedPainting?: boolean` и `backColourOptionId?: number`; `colourOptionId` остаётся фронтальным цветом. UI — `antd Switch` рядом с `antd Select` (как сегодня), при включении второй `Select` в том же ряду (`antd Row`/`Space`), оба со своим `onChange`/очисткой, повторно использующие тот же список вариантов колонки цвета, что и сегодняшний одиночный список.

## Risks / Trade-offs

- [Смешение семантики `colourOptionId`: «единственный цвет» vs «фронтальный цвет» в зависимости от `doubleSidedPainting`] → Митигируется явной валидацией на бэкенде (see Decision 1) и явными сценариями в specs; альтернатива с раздельными полями была явно взвешена и отклонена как непропорционально инвазивная.
- [Порядок нового шага в последовательности наценок — решение, не зафиксированное в исходном запросе пользователя] → Задокументировано explicit в специфике (door-configuration-api) и здесь (Decision 3), с обоснованием; расхождение с ожиданием пользователя обнаружится на этапе ревью спеков/задач, до кода.
- [Общая формула суммирования процентов цвета (а не хардкод «двух конкретных RAL/NCS цветов») меняет поведение для любых будущих `colour_type` с ненулевым процентом, а не только для «Другой цвет из RAL и NCS»] → Согласуется с текущим состоянием БД (единственный ненулевой `colour_type` — «Другой цвет из коллекции RAL и NCS», см. changelog 0102/0103): для текущих данных поведение совпадает с примером из proposal.md; для новых цветов с ненулевым процентом в будущем — предсказуемо обобщается, без специального кода под конкретный `colour_type`.
