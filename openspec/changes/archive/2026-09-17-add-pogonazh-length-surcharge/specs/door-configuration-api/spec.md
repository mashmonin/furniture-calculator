## ADDED Requirements

### Requirement: Наценка за нестандартную длину/высоту короба, наличника и добора
Для frame-, doorCasing- и frameExtensions-компонентов система ДОЛЖНА (SHALL) определять значение размера, использованное для этого компонента (для frame — выбранная высота: каталожная опция для короба «НЕО»/«Компланар» или значение, совпадающее с высотой полотна, для короба «Фантом»; для doorCasing/frameExtensions — выбранная каталожная опция длины, если она указана), и искать строку pogonazh_surcharge_rule (см. pogonazh-surcharge-rules) для этого владельца (frame_type/door_casing_type/frame_extensions_type соответственно) и этого значения. Если строка найдена, её surcharge_percent ДОЛЖЕН (SHALL) быть применён к найденной цене компонента (после определения цены по configuration_price/frame_post, до умножения на количество для doorCasing/frameExtensions); если строка не найдена, либо размер для этого компонента не выбран/не применим, наценка не применяется. Эта наценка независима от наценок leaf-компонента (за нестандартный размер полотна, реверс, исполнение зеркала, вид остекления) и не влияет на них.

#### Scenario: Наценка применяется к коробу «НЕО»/«Компланар» за нестандартную высоту
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type «НЕО» или «Компланар» выбрана каталожная высота, для которой существует строка pogonazh_surcharge_rule этого frame_type
- **THEN** к цене frame-компонента (сумме frame_post и, если применимо, цены цвета) применяется surcharge_percent этой строки

#### Scenario: Наценка применяется к коробу «Фантом» за нестандартную высоту полотна
- **WHEN** отправляется запрос расчёта стоимости, где для frame-компонента с frame_type «Фантом» значение высоты (совпадающее с высотой полотна) совпадает со значением строки pogonazh_surcharge_rule этого frame_type
- **THEN** к цене frame-компонента применяется surcharge_percent этой строки

#### Scenario: Наценка применяется к наличнику или добору за нестандартную длину
- **WHEN** отправляется запрос расчёта стоимости, где для doorCasing- или frameExtensions-компонента выбрана каталожная опция длины, для которой существует строка pogonazh_surcharge_rule этого door_casing_type/frame_extensions_type
- **THEN** к найденной цене этого компонента (до умножения на количество, см. «Количество наличника и добора в расчёте стоимости») применяется surcharge_percent этой строки

#### Scenario: Базовое значение — наценка не применяется
- **WHEN** отправляется запрос расчёта стоимости, где для frame-, doorCasing- или frameExtensions-компонента выбранное значение размера не совпадает ни с одной строкой pogonazh_surcharge_rule этого владельца
- **THEN** наценка за нестандартный погонаж не применяется, цена компонента вычисляется как раньше

#### Scenario: Наценка не зависит от наценок leaf-компонента
- **WHEN** отправляется запрос расчёта стоимости, где к цене frame-компонента применяется наценка за нестандартный погонаж, а к цене leaf-компонента — наценка за нестандартный размер полотна и/или надбавка за реверс
- **THEN** обе группы наценок применяются независимо, каждая только к своему компоненту

## MODIFIED Requirements

### Requirement: Базовая цена компонента в ответе расчёта стоимости
Каждый оценённый (priced = true) компонент в разбивке ответа эндпоинта расчёта стоимости (`POST /api/door-configurations/{id}/price`) ДОЛЖЕН (SHALL), в дополнение к существующим полям, содержать базовую розничную и дилерскую цену этого компонента — цену найденной строки configuration_price/frame_post до применения наценки за нестандартный размер полотна, надбавки за реверс (leaf) и наценки за нестандартную длину/высоту погонажа (frame/doorCasing/frameExtensions, см. «Наценка за нестандартную длину/высоту короба, наличника и добора»). Для компонентов, к которым ни одна из применимых им наценок не применяется, базовая цена компонента совпадает с его итоговой ценой. Некалькулируемые (priced = false) компоненты не содержат базовой цены. Это расширение контракта ответа аддитивно, на уровне объекта компонента: ранее существовавшие поля не меняются и не удаляются, контракт запроса не меняется, итоговые суммы (`totalRetailPrice`/`totalDealerPrice`) не меняются.

#### Scenario: Базовая цена компонента равна итоговой при отсутствии надбавок
- **WHEN** отправляется запрос расчёта стоимости, для которого ни одна надбавка (за размер полотна, за реверс, за нестандартный погонаж) не применяется к оцененному компоненту
- **THEN** базовая розничная и дилерская цена этого компонента в ответе равны его итоговой розничной и дилерской цене

#### Scenario: Базовая цена leaf-компонента меньше итоговой при применённых надбавках
- **WHEN** отправляется запрос расчёта стоимости, для которого к цене leaf-компонента применяется хотя бы одна надбавка (за нестандартный размер и/или за реверс)
- **THEN** базовая розничная и дилерская цена leaf-компонента в ответе меньше его итоговой розничной и дилерской цены ровно на сумму применённых к нему надбавок

#### Scenario: Базовая цена короба, наличника или добора меньше итоговой при применённой наценке за нестандартный погонаж
- **WHEN** отправляется запрос расчёта стоимости, для которого к цене frame-, doorCasing- или frameExtensions-компонента применяется наценка за нестандартную длину/высоту погонажа
- **THEN** базовая розничная и дилерская цена этого компонента в ответе меньше его итоговой розничной и дилерской цены ровно на сумму применённой наценки

#### Scenario: Базовая цена компонентов, к которым надбавки не применяются, всегда совпадает с их итоговой ценой
- **WHEN** отправляется запрос расчёта стоимости для конфигурации с edge-компонентом (кромкой) — единственным компонентом, к которому никакая наценка никогда не применяется
- **THEN** базовая цена edge-компонента в ответе совпадает с его итоговой ценой, независимо от того, применены ли какие-либо наценки к другим компонентам той же конфигурации

### Requirement: Количество наличника и добора в расчёте стоимости
Для компонентов doorCasing (наличник) и frameExtensions (добор) запрос расчёта стоимости МОЖЕТ (MAY) указывать количество — положительное целое число. Если количество не указано, система ДОЛЖНА (SHALL) считать его равным 1 (текущее поведение сохраняется). Если найдена подходящая строка configuration_price для этого компонента, система ДОЛЖНА (SHALL) сначала применить к её цене наценку за нестандартную длину погонажа, если она применима (см. «Наценка за нестандартную длину/высоту короба, наличника и добора»), а затем умножить результат на указанное количество — итоговые retail_price и dealer_price равны этому произведению; базовая цена компонента (см. «Базовая цена компонента в ответе расчёта стоимости») равна цене найденной строки (без наценки за погонаж), умноженной на то же количество. Указание количества для компонента, отличного от doorCasing и frameExtensions, ДОЛЖНО (SHALL) отклоняться ошибкой 400. Указанное количество ДОЛЖНО (SHALL) быть положительным целым числом; ноль, отрицательное значение отклоняются ошибкой 400.

#### Scenario: Количество не указано — цена как за одну единицу
- **WHEN** отправляется запрос расчёта стоимости для наличника или добора без указания количества
- **THEN** цена этого компонента равна найденной цене configuration_price (с наценкой за нестандартный погонаж, если она применима) без дополнительного умножения

#### Scenario: Указанное количество умножает цену компонента
- **WHEN** отправляется запрос расчёта стоимости, где для наличника или добора указано количество N, найдена подходящая строка configuration_price и применима наценка за нестандартную длину погонажа
- **THEN** итоговая retail_price и dealer_price этого компонента равны (retail_price/dealer_price найденной строки, увеличенным на наценку за погонаж), умноженным на N

#### Scenario: Количество для компонента, отличного от наличника и добора, недопустимо
- **WHEN** отправляется запрос расчёта стоимости, где количество указано для leaf, frame или edge
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Нулевое или отрицательное количество недопустимо
- **WHEN** отправляется запрос расчёта стоимости, где для наличника или добора указано количество, равное нулю или отрицательное
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Количество не влияет на компонент без найденной цены
- **WHEN** отправляется запрос расчёта стоимости, где для наличника или добора указано количество, но подходящая строка configuration_price не найдена
- **THEN** компонент считается некалькулируемым, как и без указания количества

### Requirement: Получение процентов надбавок к цене полотна
Система ДОЛЖНА (SHALL) предоставлять read-only эндпоинт, возвращающий все правила наценки за нестандартный размер полотна (тип размера, значение в мм, процент наценки — по одной записи на строку dimension_surcharge_rule) вместе с процентом надбавки за реверс, применяемым при расчёте стоимости, и все правила наценки за нестандартную длину/высоту погонажа (владелец — frame_type/door_casing_type/frame_extensions_type, значение в мм, процент наценки — по одной записи на строку pogonazh_surcharge_rule, см. pogonazh-surcharge-rules). Эндпоинт не принимает параметров и не зависит от конкретной door_configuration. Существующий эндпоинт расчёта стоимости (`POST /api/door-configurations/{id}/price`) этим требованием не затрагивается — контракт его запроса не меняется (об изменении контракта ответа см. «Базовая цена компонента в ответе расчёта стоимости»).

#### Scenario: Возвращаются все правила наценки за размер и надбавка за реверс
- **WHEN** запрашивается эндпоинт получения процентов надбавок
- **THEN** ответ содержит все строки dimension_surcharge_rule (тип размера, значение, процент) и процент надбавки за реверс, используемый расчётом стоимости

#### Scenario: Пустой справочник наценок за размер не считается ошибкой
- **WHEN** запрашивается эндпоинт получения процентов надбавок и в базе нет ни одной строки dimension_surcharge_rule
- **THEN** эндпоинт возвращает код 200 с пустым списком наценок за размер и процентом надбавки за реверс

#### Scenario: Значение надбавки за реверс совпадает с фактически применяемым при расчёте
- **WHEN** запрашивается эндпоинт получения процентов надбавок
- **THEN** возвращённый процент надбавки за реверс равен проценту, который `POST /api/door-configurations/{id}/price` фактически применяет к цене полотна реверсивной конфигурации

#### Scenario: Возвращаются все правила наценки за погонаж
- **WHEN** запрашивается эндпоинт получения процентов надбавок
- **THEN** ответ дополнительно содержит все строки pogonazh_surcharge_rule (владелец, значение, процент), наряду с уже существующими полями

#### Scenario: Пустой справочник наценок за погонаж не считается ошибкой
- **WHEN** запрашивается эндпоинт получения процентов надбавок и в базе нет ни одной строки pogonazh_surcharge_rule
- **THEN** эндпоинт возвращает код 200 с пустым списком наценок за погонаж, не влияя на остальные поля ответа

### Requirement: Стоимость короба как сумма цен его стоек
Для frame-компонента выбранной конфигурации система ДОЛЖНА (SHALL) вычислять базовую стоимость как сумму retail_price и отдельно сумму dealer_price всех записей frame_post, принадлежащих frame_type этой конфигурации (0, если ни одной записи frame_post нет). Если у этого frame_type задана хотя бы одна строка colour_option, стоимость короба ДОЛЖНА (SHALL) дополнительно зависеть от выбора цвета: если для colour_option, выбранного клиентом, находится ровно одна наиболее специфичная подходящая строка configuration_price с владельцем этим frame_type (см. «Сопоставление наиболее специфичной цены компонента»), её retail_price и dealer_price прибавляются к базовой сумме frame_post; если клиент не выбрал цвет, либо подходящая строка не найдена, либо совпадение неоднозначно, frame-компонент целиком ДОЛЖЕН (SHALL) считаться некалькулируемым — независимо от того, что сумма frame_post сама по себе была бы посчитана. Если у frame_type нет ни одной строки colour_option, калькулируемость короба зависит только от наличия записей frame_post, как раньше. К полученной таким образом сумме (frame_post плюс, если применимо, цена цвета) дополнительно применяется наценка за нестандартную высоту погонажа, если она применима (см. «Наценка за нестандартную длину/высоту короба, наличника и добора»).

#### Scenario: Короб из нескольких позиций суммируется
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type не имеет ни одной строки colour_option и имеет две записи frame_post (например, незарезная стойка и комплект зарезных стоек)
- **THEN** стоимость frame-компонента равна сумме retail_price (и отдельно dealer_price) обеих записей frame_post, с учётом наценки за нестандартный погонаж, если она применима

#### Scenario: Короб без записей frame_post остаётся некалькулируемым
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type не имеет ни одной строки colour_option и не имеет ни одной записи frame_post
- **THEN** эндпоинт отвечает кодом 200, frame-компонент включается в разбивку как компонент без найденной цены, а итоговая сумма его не учитывает

#### Scenario: Короб с выбранным цветом калькулируется по цене цвета
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type имеет строки colour_option и не имеет ни одной записи frame_post, и клиент выбрал colour_option, для которого находится ровно одна подходящая строка configuration_price
- **THEN** стоимость frame-компонента равна retail_price (и отдельно dealer_price) этой строки configuration_price, с учётом наценки за нестандартный погонаж, если она применима

#### Scenario: Короб с цветовыми опциями без выбора цвета остаётся некалькулируемым
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type имеет строки colour_option, и клиент не выбрал цвет для frame-компонента
- **THEN** frame-компонент считается некалькулируемым, даже если у этого frame_type есть записи frame_post, дающие положительную базовую сумму

#### Scenario: Короб с цветовыми опциями и неоднозначным или отсутствующим совпадением цвета остаётся некалькулируемым
- **WHEN** отправляется запрос расчёта стоимости для конфигурации, чей frame_type имеет строки colour_option, и для выбранного клиентом colour_option не находится ни одной подходящей строки configuration_price либо находится несколько с одинаковой наивысшей специфичностью
- **THEN** frame-компонент считается некалькулируемым, как и для остальных компонентов при отсутствии однозначной цены
