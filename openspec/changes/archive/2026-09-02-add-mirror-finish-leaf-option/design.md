## Context

См. `proposal.md` — «Why» и «What Changes». Ключевые факты о текущей реализации, определяющие подход:

- `App.tsx` (см. change `redesign-door-configurator-flow`): `resolveReverseStep(configurations, reverseSelection)` вычисляет `reverseStep`/`resolvedReverse` над ПОЛНЫМ `configurations`, до вычисления `collectionOptions`; `collectionFilteredConfigurations` строится из `reverseFilteredConfigurations`. Реверс — не тип-компонент (`ComponentKey`), а отдельный булев признак самой строки `door_configuration` (колонка `is_reverse`), поэтому вычисляется отдельной функцией, а не через `CASCADE_ORDER`/`applyCascadeStep`.
- `DoorConfigurationPricingService.applySequentialSurcharges(price, leafDimensionSurcharge, applyReverseSurcharge)` применяет наценки строго последовательно с округлением после каждого шага: длина → высота → (если `applyReverseSurcharge`) реверс. Каждый шаг — вызов `applyPercentMultiplier`, которая округляет `HALF_UP` до целого, если множитель ≠ 1 (см. change `add-dimension-surcharge-rules`).
- `ComponentCatalogDto` (leaf/frame/edge/doorCasing/frameExtensions) уже содержит generic-поля `dimensionOptions`/`colourOptions`, заполняемые только там, где они реально существуют для этого владельца (`liner_dimension_option`/`colour_option` — полиморфное владение с ровно одной непустой ссылкой среди leaf_type/frame_type/edge_type/door_casing_type/frame_extensions_type).
- `GET /api/pricing-surcharges` (`PricingSurchargesDto`: `reverseSurchargePercent`, `dimensionSurchargeRules`) — единственный источник процентов для клиентской разбивки надбавок; сама разбивка вычисляется на фронтенде из уже загруженных данных, не из ответа `calculate()` (см. change `redesign-door-configurator-flow`, решение «Разбивка процентов на фронтенде вычисляется локально»).
- Коллекции в БД: 9 строк (`collection`), из них ровно 6 совпадают с перечисленными в запросе (Элегант LC-003, Гармония LC-004, Свобода LC-005, Геометрия LC-006, Сияние LC-007, Сибирь LC-008); Вертикаль (LC-001), Атмосфера (LC-002), Фантом (LC-009) — зеркало не поддерживают. Всего 31 leaf_type в 6 подходящих коллекциях.
- Пользователь явно подтвердил (при уточнении): выбор исполнения зеркала должен буквально стоять в одной строке с переключателем «Реверс», до выбора коллекции, и сужать каталог по аналогии с реверсом.

## Goals / Non-Goals

**Goals:**
- Три исполнения зеркала с фиксированными процентами (30/40/50%), выбираемые для leaf-компонента конфигураций 6 названных коллекций.
- Наценка применяется в математике `calculate()` строго между наценкой за высоту и надбавкой за реверс.
- Выбор исполнения зеркала — независимый от реверса переключатель «Нужно зеркало» в одном ряду с ним, плюс появляющийся при включении список конкретных исполнений; выключенный переключатель не сужает каталог, включённый — сужает (сначала до полотен, поддерживающих хотя бы одно исполнение, затем — при выборе конкретного — до него).

**Non-Goals:**
- Не меняется контракт запроса существующих полей `calculate()`, не меняется математика уже существующих наценок (длина/высота/реверс) — только добавляется новый шаг между высотой и реверсом.
- Не вводится наценка за зеркало для компонентов, отличных от leaf (короб/кромка/наличник/добор зеркала не имеют).
- Не варьируется процент наценки по коллекции/модели полотна — как и в `dimension_surcharge_rule`, наценка зависит только от выбранного исполнения зеркала, одинаково для любого допустившего его leaf_type.
- Не переносится в движок бизнес-правил (Drools) — тот же принцип «временно», что уже применяется к надбавке за реверс.

## Decisions

**Процент наценки хранится прямо на `mirror_finish_type`, а не в отдельной rule-таблице по аналогии с `dimension_surcharge_rule`.**
`dimension_surcharge_rule` вынесена отдельно от `liner_dimension_type`, потому что `liner_dimension_type` — независимый справочник осей размера, используемый много где помимо наценок, а наценка зависит ещё и от конкретного *значения* размера (много правил на один тип оси). Для зеркала исполнение и наценка — одно и то же понятие один-к-одному (три исполнения — три процента, никакой дополнительной оси-значения нет, и справочник `mirror_finish_type` не используется ни для чего, кроме этой наценки) — заводить отдельную rule-таблицу поверх такого справочника было бы лишним слоем без смысловой разницы.

**Владение — прямой FK `mirror_finish_option.leaf_type_id`, а не полиморфная схема `liner_dimension_option`/`colour_option` (leaf_type/frame_type/edge_type/door_casing_type/frame_extensions_type, ровно одна ссылка).**
Исполнение зеркала — по определению свойство только полотна («зеркало устанавливается на одну из сторон [полотна]»); ни для короба, ни для кромки, ни для наличника/добора зеркальное исполнение физически не имеет смысла и не запрашивалось. Полиморфная схема существующих option-таблиц оправдана тем, что размеры и цвета РЕАЛЬНО применимы к разным типам компонентов; вводить пять взаимоисключающих nullable-колонок ради типа, которому подходит только один из пяти владельцев, — не оправданная общность (см. общий принцип проекта не проектировать под гипотетические будущие требования).

**Каталог, запрос расчёта и `GET /api/pricing-surcharges` ссылаются на `mirror_finish_type.id` — глобальный, а не на `mirror_finish_option.id` — leaf-специфичный.**
Первая версия дизайна выбрала `mirror_finish_option.id` для запроса, по прямой аналогии с `colourOptionId`/`lengthOptionId` (те действительно ссылаются на владеющую строку, потому что цена ищется через конкретную `configuration_price`, привязанную к конкретной строке опции). У зеркала наценка не зависит от владеющей строки — только от `mirror_finish_type`, глобально одна и та же для любого допустившего его полотна (см. решение выше про `dimension_surcharge_rule`-подобную природу). Обнаружено при реализации: `mirror_finish_option.id` — leaf-специфичный (разный для каждого полотна, даже для одного и того же исполнения), а `GET /api/pricing-surcharges` неизбежно отдаёт проценты по `mirror_finish_type` (глобально, вне контекста конкретного полотна) — фронтенду было бы нечем сопоставить выбранный `mirror_finish_option.id` с процентом из справочника надбавок без дополнительного джойна через название (ненадёжно) или ещё одного запроса. Использование `mirror_finish_type.id` везде — в каталоге (`ComponentCatalogDto.mirrorFinishOptions`), в запросе (`ComponentSelectionDto.mirrorFinishTypeId`) и в `GET /api/pricing-surcharges` (`mirrorFinishSurcharges`) — даёt фронтенду одно общее пространство id без дополнительных запросов или сопоставления по имени. Владение (какие leaf_type допускают какой mirror_finish_type) по-прежнему проверяется через `mirror_finish_option` на backend — просто не выдаётся клиенту как отдельный id.

**Выбор исполнения зеркала — два отдельных пред-коллекционных псевдо-шага: переключатель «Нужно зеркало» (boolean, по образцу «Реверс») и появляющийся при его включении список конкретных исполнений, а не единый OptionGroup с псевдо-вариантом «Без зеркала».**
Первая версия реализации использовала один `OptionGroup` с тремя реальными исполнениями плюс синтетическим вариантом «Без зеркала» (аналогично `NONE_OPTION_ID` у типов компонентов), отображаемым сразу рядом с переключателем «Реверс». Промежуточная версия (после первого уточнения пользователя) добавляла последовательную зависимость — зеркало показывалось только после того, как реверс явно отвечен. Пользователь в итоге явно потребовал третий вариант: два независимых `Switch` в одном ряду («Реверс» и «Нужно зеркало», ни один не блокирует и не зависит от другого) — а сам список из трёх конкретных исполнений зеркала показывается отдельным шагом ниже, только когда «Нужно зеркало» включён. Реализовано двумя state: `mirrorFinishEnabled: boolean` (сам переключатель, аналог `reverseSelection`) и `mirrorFinishTypeId: number | undefined` (выбор внутри появившегося списка, сбрасывается при выключении переключателя).

**Сужение candidates по зеркалу — двухуровневое: включение переключателя «Нужно зеркало» само по себе уже сужает (до leaf_type с непустым `mirrorFinishOptions`), выбор конкретного исполнения сужает дальше.**
В отличие от промежуточной версии, где «Без зеркала» как отдельный вариант списка НЕ сужал candidates (а конкретное исполнение — сужало), в переключательной модели сам факт включения «Нужно зеркало» — это уже осмысленный фильтр («покажи мне только полотна, которые вообще поддерживают зеркало»), поэтому `filterByMirrorFinish(configurations, mirrorFinishEnabled, mirrorFinishTypeId)`: выключено → без сужения; включено без выбранного исполнения → сужение до leaf_type с хотя бы одним исполнением; включено с выбранным исполнением → сужение до этого конкретного исполнения. Выключение переключателя сбрасывает `mirrorFinishTypeId` обратно в `undefined`.

**Кандидаты, чтобы понять, какая `door_configuration` "поддерживает" исполнение зеркала, определяются через `leaf.mirrorFinishOptions` в уже загруженном каталоге (`GET /api/door-configurations`), а не отдельным запросом.**
Тот же принцип, что уже применяется к `collectionOptions`/`CASCADE_ORDER` — единственный источник данных для сужения кандидатов это initial `GET /api/door-configurations` (см. «Загрузка каталога конфигураций»), no дополнительных запросов на этом этапе. `mirrorFinishOptions` — новое generic-поле `ComponentCatalogDto`, заполняется только для leaf (аналогично тому, как `colourOptions` уже заполняется избирательно).

**Наценка за зеркало не хранится как отдельное generic-поле `LeafDimensionSurcharge`, а как отдельный параметр `applySequentialSurcharges`.**
`LeafDimensionSurcharge` (lengthMultiplier/heightMultiplier) — по названию и структуре специфична для осей *размера*; зеркало не ось размера (нет `liner_dimension_type`, значение не числовое). Добавление третьего мультипликатора прямо в `applySequentialSurcharges` как отдельный параметр (`mirrorFinishMultiplier`) яснее показывает, что это независимый третий шаг последовательности, а не третья ось той же природы, что длина/высота.

**На фронтенде выбор исполнения зеркала хранится в отдельных top-level state (`mirrorFinishEnabled`, `mirrorFinishTypeId`), а не внутри `selection.leaf`, и подмешивается в `selection.leaf` только при сборке запроса в `handleCalculate`.**
Обнаружено при реализации группы 5: `handleCascadeStepChange('leaf', …)` целиком очищает `selection.leaf` при смене конкретной модели полотна на уже суженном списке кандидатов (сброс опций изменённого и всех последующих по каскаду шагов — существующее и корректное поведение для длины/высоты/толщины/цвета, которые действительно зависят от выбранной модели полотна). Если бы `mirrorFinishTypeId` хранился внутри `selection.leaf`, этот же сброс стирал бы уже сделанный выбор зеркала при выборе конкретной модели полотна — притом что кандидаты для этого шага и так уже сужены до полотен, поддерживающих выбранное зеркало, то есть стирать выбор незачем и вредно с точки зрения UX. Реверс и зеркало — пред-коллекционные пседво-шаги, логически «до» `selection` вообще; хранение зеркала отдельным state (аналогично `reverseSelection`) освобождает его от зависимости на сбросы каскада `selection.leaf` и симметрично тому, что реверс уже не часть `selection`.

## Risks / Trade-offs

- **[Risk]** Пред-коллекционное сужение по зеркалу — если у пользователя выбраны одновременно реверс=true и конкретное исполнение зеркала, а среди 6 подходящих коллекций не все имеют реверс-исполнение, список коллекций может схлопнуться сильнее, чем ожидает пользователь (пересечение двух независимых фильтров). → Это уже предусмотренное и подтверждённое пользователем поведение (та же механика, что уже работает для одного реверса); риск — не архитектурный, а обычная бизнес-логика сужения, консистентная с остальным потоком.
- **[Trade-off]** Сужение по зеркалу двухуровневое (сам переключатель уже сужает, конкретное исполнение сужает ещё раз) — асимметрично по сравнению с «без короба»/«без кромки», где сужение происходит только при выборе конкретного значения. → Явно задокументировано отдельным пунктом Decisions и отдельными сценариями в specs.
- **[Risk]** 93 строки `mirror_finish_option` (3 исполнения × 31 leaf_type) заполняются одним миграционным SQL через `JOIN collection`/`leaf_type` по кодам коллекций — ошибка в списке кодов молча исключит/добавит лишние leaf_type. → Явно перечислить коды коллекций (`LC-003`..`LC-008`) в SQL и проверить количество вставленных строк вручную перед архивированием (см. tasks.md).

## Migration Plan

1. **БД**: новый Liquibase changeset — таблицы `mirror_finish_type` (id, name, surcharge_percent) и `mirror_finish_option` (id, mirror_finish_type_id FK, leaf_type_id FK, unique по паре); 3 строки `mirror_finish_type`; `INSERT` в `mirror_finish_option` — `CROSS JOIN` трёх исполнений на все `leaf_type`, чей `collection.code IN ('LC-003','LC-004','LC-005','LC-006','LC-007','LC-008')`. Прогнать локально, проверить количество строк (3 × 31 = 93) и что leaf_type вне этих 6 коллекций не затронуты.
2. **Backend**: `MirrorFinishType`/`MirrorFinishOption` (domain) + репозитории (`MirrorFinishTypeRepository.findAll()`, `MirrorFinishOptionRepository.findByLeafTypeId(Long)`, `findByMirrorFinishTypeIdAndLeafTypeId(Long, Long)`); `ComponentCatalogDto` — новое generic-поле `mirrorFinishOptions: List<ReferenceDto>`, заполняется в `DoorConfigurationCatalogService.buildLeafComponent` (пустой список во всех остальных builder-методах); `ComponentSelectionDto` — новое поле `mirrorFinishTypeId`; `DoorConfigurationPricingService` — валидация (только для leaf; должен принадлежать leaf_type конфигурации — иначе 400) и `applySequentialSurcharges` — новый параметр `mirrorFinishMultiplier`, применяемый между высотой и реверсом; `PricingSurchargesDto`/`PricingSurchargesService` — новое поле со списком `mirror_finish_type` (id, name, surchargePercent).
3. **Frontend**: `App.tsx` — `resolveMirrorFinishStep`, аналогичная `resolveReverseStep`, вычисляется над `reverseFilteredConfigurations`; `filterByMirrorFinish(configurations, mirrorFinishEnabled, mirrorFinishTypeId)` — двухуровневое сужение (см. Decisions); UI — `Switch` «Нужно зеркало» в той же строке, что и переключатель «Реверс» (оба независимы), и отдельный `OptionGroup` со списком конкретных исполнений, показываемый только когда переключатель включён; изменение любого из двух (переключателя или конкретного исполнения) сбрасывает всё последующее (коллекция и далее), реверс и зеркало не сбрасывают друг друга; выбор хранится в отдельных top-level state `mirrorFinishEnabled`/`mirrorFinishTypeId` (не в `selection.leaf` — см. Decisions) и подмешивается в `selection.leaf.mirrorFinishTypeId` только при сборке запроса; разбивка надбавок дополняется строкой за зеркало (по аналогии с шириной/высотой/реверсом, используя загруженные проценты `mirror_finish_type`). `api/types.ts` — новые поля.
4. **Проверка**: точечный прогон новых/изменённых backend-тестов (без полного `./gradlew test` — по умолчанию не запускать без явной просьбы пользователя, см. session-конвенцию); `npm run build`/`lint`; ручная проверка — включение «Нужно зеркало» сужает список коллекций до 6 названных и показывает список конкретных исполнений; выключенный переключатель не сужает; наценка встаёт между высотой и реверсом (конкретный числовой пример); разбивка надбавок показывает строку за зеркало.

Откат — по конвенции проекта: новые компенсирующие changeset'ы, не редактирование уже применённых.
