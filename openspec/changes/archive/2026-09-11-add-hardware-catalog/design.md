## Context

См. proposal.md — «Why»/«What Changes» для мотивации и общего описания. Здесь — как это устроено технически.

Существующий каталог конфигураций дверей построен вокруг иерархии «компонент конфигурации (leaf/frame/edge/doorCasing/frameExtensions) → тип компонента → цена», где тип компонента реализует `CatalogType` (id/code/name), а цена ищется по наиболее специфичной подходящей строке `configuration_price` с учётом владельца-типа. Фурнитура структурно не вписывается в эту модель: она не принадлежит `door_configuration`, не участвует в поиске цены «по владельцу» и никогда не получает надбавок (за размер, реверс, исполнение зеркала). Поэтому для неё нужна отдельная, более простая иерархия и отдельный путь расчёта, независимый от `DoorConfigurationPricingService`, кроме финального сложения сумм.

## Goals / Non-Goals

**Goals:**
- Простая трёхуровневая справочная иерархия: категория фурнитуры → тип фурнитуры → цветовой вариант (с ценами).
- Одна позиция расчёта = один цветовой вариант + количество единиц; в одном расчёте — произвольный список таких позиций.
- Стоимость фурнитуры добавляется к итогу после расчёта стоимости компонентов двери, без взаимодействия с существующими надбавками.

**Non-Goals:**
- Ограничение доступности фурнитуры по типу двери/коллекции/полотну — каталог глобальный (см. proposal.md), эта версия не вводит связи фурнитуры с `door_configuration` или её компонентами.
- Надбавки/наценки, применяемые к фурнитуре (за размер, реверс и т.п.) — фурнитура всегда учитывается по цене цветового варианта × количество.
- Нормализация/дедупликация похожих названий цветов между разными типами фурнитуры (см. «Decisions» ниже).

## Decisions

### Три новые таблицы, без переиспользования существующих типов компонентов
`hardware_category` (категория, напр. «Замки, цилиндры»), `hardware_type` (конкретное изделие внутри категории, напр. «AGB защелка магнитная под завертку WC 96 мм», с единицей измерения — «шт»/«компл»), `hardware_option` (цветовой вариант конкретного типа с розничной и дилерской ценой). `hardware_category` и `hardware_type` реализуют существующий интерфейс `CatalogType` (id/code/name) для переиспользования `ReferenceDto`; `hardware_option` — не реализует его, так как ему помимо (id/code) нужны цвет и обе цены, для чего заводится отдельный DTO.

Альтернатива — переиспользовать существующий паттерн «владелец-полиморфизм» (как `LeafType`/`FrameType`/…) — отвергнута: фурнитура не принадлежит `door_configuration` и не имеет диапазонов размеров/надбавок, поэтому общий с компонентами двери путь расчёта только усложнил бы обе модели.

### Цвет — обычное текстовое поле `hardware_option`, а не отдельный справочник
В исходных данных цвета одного типа фурнитуры не переиспользуются другими типами, а похожие по смыслу названия у разных производителей записаны по-разному (например, «хром матовый» и «никель (хром матовый)», «латунь» и «латунь матовая»/«латунь полированная»). Общий справочник цветов потребовал бы решения об объединении таких названий, не дающего практической пользы (нет сквозного поведения, которое зависело бы от одного и того же цвета у разных типов). Решение: хранить название цвета как обычную строку на `hardware_option`, ровно как в исходных данных, без попытки нормализации. Это же снимает вопрос о слиянии похожих названий — они не сравниваются друг с другом.

### Расчёт фурнитуры — по id варианта, без поиска «наиболее подходящей цены»
В отличие от компонентов двери (где цена ищется по совпадению владельца/цвета/размера с возможной некалькулируемостью), у позиции фурнитуры цена всегда однозначно определена по `hardwareOptionId` — она хранится прямо на найденной строке. Несуществующий `hardwareOptionId` — ошибка запроса (400), а не «компонент без цены» — так как в отличие от опций компонента, у фурнитуры нет какого-то конкретного заведомо связанного родителя, за который она отвечает, поэтому не выбор конкретного варианта означает вообще отсутствие позиции в запросе, а не позицию с ненайденной ценой.

### Список позиций фурнитуры и формула суммы
Запрос расчёта получает необязательный список позиций `{ hardwareOptionId, quantity }` (quantity по умолчанию 1, как для наличника/добора — см. «Количество наличника и добора» и связанное серверное требование в door-configuration-api). Один и тот же `hardwareOptionId` МОЖЕТ повторяться в списке несколькими отдельными позициями (не объединяются автоматически) — это проще как для реализации, так и для UI (каждая карточка выбора — независимая позиция), и не создаёт двусмысленности в разбивке ответа. Сумма по фурнитуре = Σ(retail_price/dealer_price варианта × quantity) по всем позициям списка; она прибавляется к итоговым `totalRetailPrice`/`totalDealerPrice`, посчитанным по компонентам двери, как последний шаг — уже после надбавок, применённых к компонентам.

### Отдельный контроллер каталога
`GET /api/hardware-catalog` — самостоятельный эндпоинт (не расширение `GET /api/door-configurations`), возвращающий полное дерево категория → типы → варианты с ценами. Он не зависит от выбранной конфигурации (см. Non-Goals), поэтому не требует параметров.

## Migration Plan

Новые Liquibase changelog'и (следующий свободный номер на момент реализации — начиная с 0076, точную нумерацию и разбивку по файлам зафиксировать в tasks.md):
1. Схема: три таблицы (`hardware_category`, `hardware_type`, `hardware_option`) с FK и уникальными индексами на `code`.
2. Начальные данные — отдельными changelog'ами по каждой категории источника (Замки/цилиндры; Петли Италия; Петли Armadillo; Дополнительная фурнитура; Крепление плинтуса; Ручки для раздвижных дверей), чтобы каждый набор данных был отдельным атомарным changeset'ом и было легко расширять каталог позже.

Откат — стандартный для Liquibase (`rollback` на changeset), новые таблицы не связаны внешними ключами с существующими — откат не влияет на другие данные.

## Risks / Trade-offs

- [Явные дубликаты названий цветов между типами не нормализуются] → сознательный trade-off (см. Decisions); при необходимости кросс-типового отчёта по цветам потребуется отдельная последующая доработка.
- [Повтор одного `hardwareOptionId` в списке позиций расчёта] → трактуется как две независимые позиции с одинаковой ценой варианта, суммируется корректно; в ответе они также идут двумя отдельными строками разбивки.
- [Рост списка типов/вариантов фурнитуры со временем] → плоская модель категория/тип/вариант легко расширяется новыми changelog'ами без миграции существующих данных.
