## Context

См. proposal.md — «Why»/«What Changes» для мотивации. Здесь — как это устроено технически.

`DoorConfigurationPricingService.calculate(doorConfigurationId, request)` сегодня: находит `DoorConfiguration` по id, затем для каждого присутствующего в ней компонента вызывает приватный `addComponentIfPresent(...)`, который ищет цену в `configuration_price` по владельцу-типу (`leaf_type_id`/`frame_type_id`/…) и выбранным клиентом опциям — независимо от того, к какой именно `door_configuration` принадлежит этот тип. То есть подбор цены для leaf уже не зависит от `door_configuration` как таковой — она нужна только чтобы (1) получить конкретный `LeafType` по id и (2) узнать `is_reverse` для надбавки за реверс. Фурнитура (`priceHardwareSelections`) уже полностью независима от `door_configuration` и просто прибавляется к итогу.

## Goals / Non-Goals

**Goals:**
- Дать возможность посчитать стоимость одного полотна (с его надбавками за размер/исполнение зеркала) и, опционально, позиций фурнитуры — без необходимости, чтобы существовала подходящая согласованная `door_configuration`, и без выбора короба/кромки/наличника/добора.
- Переиспользовать существующий код подбора цены компонента (`addComponentIfPresent` и всё, что он использует) — не дублировать бизнес-правила поиска цены и надбавок.
- Не менять поведение существующего эндпоинта `POST /api/door-configurations/{id}/price`.

**Non-Goals:**
- Расчёт произвольных сочетаний компонентов (например, полотно + короб без согласованной `door_configuration`) — только полотно (+ фурнитура). Короб/кромка/наличник/добор по-прежнему требуют согласованной конфигурации.

## Decisions

### Новый эндпоинт, а не расширение существующего
`POST /api/leaf-types/{leafTypeId}/price` — отдельный эндпоинт, а не изменение сигнатуры `POST /api/door-configurations/{id}/price`: у пути `{id}` там иная семантика (id согласованной конфигурации, обязателен для поиска `is_reverse` и присутствующих компонентов), и делать его опциональным/перегруженным усложнило бы контракт без выгоды. Новый путь принимает `leaf_type_id` напрямую.

### Общий request/response с существующим эндпоинтом, плюс явный признак реверса
Тело запроса — существующий `PricingRequestDto` (поле `leaf` для опций полотна, `hardware` — для фурнитуры; поля `frame`/`edge`/`doorCasing`/`frameExtensions`, если переданы, эндпоинтом игнорируются, так как у отдельного полотна этих компонентов нет), дополненный новым полем `isReverse` (булево, по умолчанию/при отсутствии — false). У отдельного полотна нет `door_configuration.is_reverse`, откуда обычно берётся признак реверса, поэтому клиент передаёт его явно. Поле игнорируется существующим эндпоинтом `calculate()` — там реверс по-прежнему определяется исключительно `door_configuration.is_reverse`, чтобы не открывать лазейку переопределить его клиентом. Ответ — существующий `PricingResponseDto` (тот же формат: итоговые суммы, `components` — список из одной записи `"leaf"`, `hardware` — как обычно). Переиспользование форматов означает, что фронтенду не нужен отдельный код рендеринга результата — тот же компонент отображения работает для обоих эндпоинтов.

### Реализация — переиспользование addComponentIfPresent, без дублирования итогов/фурнитуры
`DoorConfigurationPricingService` получает новый публичный метод `calculateForLeaf(Long leafTypeId, PricingRequestDto request)`:
1. Находит `LeafType` по id (404, если не найден — аналогично поиску `DoorConfiguration`).
2. Вызывает тот же `addComponentIfPresent(components, "leaf", leafType, leafSelection, null, applyReverseSurcharge)` — `leafHeightValue = null` (не используется веткой leaf), `applyReverseSurcharge = Boolean.TRUE.equals(request.isReverse())`.
3. Считает итоговые суммы и добавляет фурнитуру — этот код (суммирование `components`, вызов `priceHardwareSelections`, сложение итогов) выносится из `calculate()` в приватный общий метод `finalizeResponse(components, request)`, чтобы не дублировать его в `calculateForLeaf()`.

Валидация полотна (принадлежность `colourOptionId`/`lengthOptionId`/`heightOptionId`/`thicknessOptionId` этому `leafType`, произвольные размеры и надбавки за них, исполнение зеркала, отказ в количестве) отрабатывает без изменений — она уже параметризована типом-владельцем, а не `door_configuration`.

### Фронтенд: приоритет между двумя способами расчёта и источник признака реверса
Пока `selectedConfiguration` (согласованная конкретная `door_configuration`) не определена, но тип полотна уже определён (первый шаг каскада разрешён), автоматический расчёт (см. change redesign-configurator-layout) использует новый эндпоинт с id этого `leaf_type`, текущими опциями полотна и фурнитуры и значением `isReverse`, равным текущему состоянию переключателя «Реверс» (`resolvedReverse`) — того же переключателя, что фильтрует кандидатов door_configuration на более ранних шагах каскада. Как только каскад определяет конкретную `door_configuration`, автоматический расчёт переключается на существующий эндпоинт (с учётом короба и т.д., и с реверсом уже из самой конфигурации), даже если до этого показывалась цена только полотна — таким образом, при дальнейшем выборе короба/наличника/добора отображаемая цена не «застревает» на варианте «только полотно».

## Risks / Trade-offs

- [Пользователь видит цену «только полотна», затем она увеличивается/меняется, когда он выбирает короб и другие компоненты] → ожидаемое и понятное поведение (аналог «предварительный расчёт по мере заполнения»), явно описано в specs, не требует отдельного предупреждения в UI.
- [Дублирование пути валидации между `calculate()` и `calculateForLeaf()`] → минимизировано переносом общего кода (`addComponentIfPresent`, `finalizeResponse`) в переиспользуемые методы; оба публичных метода остаются тонкими обёртками.
