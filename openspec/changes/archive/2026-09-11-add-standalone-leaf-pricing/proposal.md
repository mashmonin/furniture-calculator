## Why

Сейчас расчёт стоимости возможен только по id уже согласованной строки `door_configuration` — а такая строка существует лишь для комбинаций компонентов, заранее одобренных производителем. Для большинства моделей полотна, у которых в каталоге есть варианты короба/наличника/добора, не существует отдельной строки «только полотно, без короба» — поэтому менеджер не может получить цену на одно полотно (с его надбавками за нестандартный размер, исполнение зеркала), пока не пройдёт весь каскад выбора короба и обрамления, хотя клиенту может быть нужна именно цена одного полотна.

## What Changes

- Новый способ расчёта стоимости полотна отдельно от `door_configuration`: по id `leaf_type` — с учётом надбавок за нестандартный размер, исполнение зеркала и реверс, без короба/кромки/наличника/добора и без необходимости, чтобы существовала подходящая согласованная конфигурация.
- Поскольку у отдельного полотна нет `door_configuration.is_reverse`, признак реверса для этого расчёта клиент передаёт явно в запросе; на существующий расчёт по `door_configuration` этот признак не влияет — там реверс по-прежнему определяется самой конфигурацией.
- Существующий расчёт по `door_configuration` (`POST /api/door-configurations/{id}/price`) не меняется и продолжает обслуживать полные и частичные (кромка/короб/наличник/добор) согласованные комбинации, включая надбавку за реверс.
- UI конфигуратора: пока каскад ещё не определил конкретную согласованную `door_configuration` (короб/наличник/добор не выбраны или не применимы), но тип полотна уже определён, sticky-панель показывает цену, рассчитанную новым способом — только по полотну. Как только каскад определяет конкретную `door_configuration`, расчёт переключается на существующий способ (с учётом короба и др.), как и раньше.

## Capabilities

### New Capabilities
- `leaf-standalone-pricing`: расчёт стоимости одного полотна (с его надбавками) по id `leaf_type`, независимо от `door_configuration`.

### Modified Capabilities
- `door-configurator-ui`: автоматический расчёт стоимости использует новый способ (только полотно) до того, как каскад определит конкретную `door_configuration`, и переключается на существующий способ после этого.

## Impact

- Backend: новый эндпоинт (например, `POST /api/leaf-types/{id}/price`) и сервис/метод, переиспользующий существующую логику надбавок полотна (`DoorConfigurationPricingService` либо выделенная его часть) без изменения существующего эндпоинта `door-configurations/{id}/price`.
- Frontend: `App.tsx` — выбор между новым и существующим способом расчёта в зависимости от того, определена ли уже конкретная `door_configuration`; новый вызов API.
- API: новый публичный REST-эндпоинт; существующие эндпоинты и их контракт не меняются (обратная совместимость).
