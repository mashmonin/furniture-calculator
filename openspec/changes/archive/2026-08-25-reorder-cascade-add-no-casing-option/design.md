## Context

См. proposal.md — Why/What Changes. Ключевые факты из текущей кодовой базы:

- `App.tsx`: `CASCADE_ORDER: ComponentKey[] = ['leaf', 'frame', 'doorCasing', 'edge', 'frameExtensions']` управляет порядком шага «1. Соберите конфигурацию» (`buildCascadeSteps` итерирует этот массив и на каждом шаге сужает кандидатов `door_configuration`). Порядок — просто константа-массив; сам алгоритм сужения (`buildCascadeSteps`) от конкретного порядка не зависит, кроме того, что каждый следующий шаг сужается по уже выбранным предыдущим.
- `COMPONENT_ORDER: ComponentKey[] = ['leaf', 'frame', 'edge', 'doorCasing', 'frameExtensions']` — отдельная константа для шага «2. Выберите опции» и порядка обработки компонентов в `DoorConfigurationPricingService.calculate` на бэкенде; она фиксирована решением из `link-edge-height-to-leaf-height` (leaf должен быть обработан раньше edge для проверки высоты) и этим изменением не трогается.
- Механизм «явный вариант без компонента» (`hasNoneOption`, `NONE_OPTION_LABELS`) уже реализован универсально для всех 5 типов компонентов и не требует изменений в коде — ему нужны только данные (`door_configuration` без ссылки на `door_casing_type_id`).
- `door_casing_type_id` в `door_configuration` уже nullable (см. `0006-door-configuration-catalog.yaml`, chk-ограничение требует только `frame_type_id IS NOT NULL`, если `door_casing_type_id` задан) — никаких изменений схемы не требуется.
- Текущие данные: КОМПЛАНАР (FT-002) — 378 строк `door_configuration`, все с заданным `door_casing_type_id`, 189 уникальных комбинаций (leaf_type, edge_type, frame_extensions_type). НЕО (FT-003) — 270 строк, все с наличником, 135 уникальных комбинаций.

## Goals / Non-Goals

**Goals:**
- Сделать «Без наличника» видимым и выбираемым в каскаде для коробов КОМПЛАНАР и НЕО — без изменения кода фронта (данные единственный недостающий элемент).
- Переставить кромку на второй шаг каскада (сразу после полотна), не трогая порядок обработки компонентов на шаге «2. Выберите опции» и в расчёте стоимости (`COMPONENT_ORDER` остаётся прежним).

**Non-Goals:**
- Не меняем `COMPONENT_ORDER`/бэкенд-логику расчёта стоимости — leaf по-прежнему обрабатывается первым, эта гарантия не связана с порядком каскада выбора типов.
- Не добавляем «без наличника» для короба КОМПЛАНАР РЕВЕРС (FT-004) — там такие строки уже существуют (13 из 26, см. `add-reverse-leaf-catalog`).
- Не меняем сами типы наличников/цены — только добавляем отсутствующую комбинацию «без наличника» для уже существующих сочетаний полотно+короб+кромка+добор.

## Decisions

### Новые door_configuration — зеркалирование существующих комбинаций, а не полный CROSS JOIN
Для каждой уникальной существующей комбинации `(leaf_type_id, frame_type_id, edge_type_id, frame_extensions_type_id)` короба КОМПЛАНАР/НЕО, у которой сейчас задан `door_casing_type_id`, вставляется одна дополнительная строка с `door_casing_type_id = NULL` (`INSERT ... SELECT DISTINCT ... FROM door_configuration WHERE door_casing_type_id IS NOT NULL`). Альтернатива — полный `CROSS JOIN` по leaf × frame × edge × extensions, как в некоторых прошлых миграциях (например, `0020`) — отклонена: она заново перебирает все допустимые оси и может случайно ввести комбинации, которых не было в исходных 378/270 строках (например, edge_type без реального совместимого leaf), тогда как зеркалирование по `DISTINCT` гарантированно копирует только уже подтверждённые фабрикой сочетания, лишь снимая наличник.

### Порядок каскада — обычная перестановка элементов массива
`CASCADE_ORDER` меняется с `['leaf', 'frame', 'doorCasing', 'edge', 'frameExtensions']` на `['leaf', 'edge', 'frame', 'doorCasing', 'frameExtensions']`. `buildCascadeSteps` уже реализован общим циклом без предположений о конкретных позициях компонентов — перестановка безопасна и не требует изменений в самой функции, только в константе и сопроводительном комментарии (который сейчас объясняет старый порядок и должен быть переписан).

### door-configurator-ui как единственная затронутая capability
`door-configuration-catalog`/`door-configuration-api` не меняются: наличник как необязательный компонент `door_configuration` уже полностью описан существующими требованиями (структура/уникальность `door_configuration`, «Частичный расчёт при отсутствии цены компонента» и т.д.), новые строки без `door_casing_type_id` — это данные в рамках уже действующего контракта, а не новое поведение API. Delta-спека нужна только для `door-configurator-ui`, где явно зафиксирован порядок шагов каскада.

## Risks / Trade-offs

- **[Trade-off] Увеличение door_configuration примерно вдвое для КОМПЛАНАР/НЕО** (378→567, 270→405) → Осознанно: тот же паттерн уже применялся для отдельных наличников/доборов в предыдущих миграциях этого проекта; каталожная таблица рассчитана на такой рост (уже 688+ строк на момент этого изменения).
- **[Риск] Перестановка каскада меняет наблюдаемое поведение UI** (пользователи, привыкшие к прежнему порядку клика, увидят кромку раньше короба) → Это осознанный запрос пользователя, а не побочный эффект; зафиксировано явным MODIFIED-требованием в `door-configurator-ui`.

## Migration Plan

Новый Liquibase changeset (следующий по порядку номер после `0029`) — чисто аддитивный `INSERT`, без изменения существующих строк или схемы. Откат — стандартный для таких миграций в проекте: ручной `DELETE` затронутых строк по тому же предикату (`door_casing_type_id IS NULL AND frame_type_id IN (FT-002, FT-003) AND` совпадение по остальным ссылкам с уже существующей строкой), если потребуется; в проекте нет автоматизированного отката миграций (см. существующие changeset'ы — все аддитивные).
