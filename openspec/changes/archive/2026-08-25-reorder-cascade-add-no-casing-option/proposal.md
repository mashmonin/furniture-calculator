## Why

Пользователь запросил два изменения в каскадном подборе конфигурации на фронте: (1) возможность выбрать «Без наличника» и (2) шаг выбора кромки должен идти раньше шагов короба, наличника и добора.

По (1): механизм явного варианта «без этого компонента» уже реализован в каскаде универсально (см. `door-configurator-ui` — «Каскадный выбор компонента конфигурации», «Часть конфигураций без компонента предлагает явный вариант «без»») и уже покрывает наличник. Проверка в БД показала, что для коробов КОМПЛАНАР (FT-002, 378 строк) и НЕО (FT-003, 270 строк) нет ни одной `door_configuration` без `door_casing_type_id` — поэтому вариант «Без наличника» физически не может появиться, хотя код его отображает при наличии подходящих данных (для короба КОМПЛАНАР РЕВЕРС такие строки уже есть, см. `add-reverse-leaf-catalog`). Значит, нужна не правка вёрстки, а новые данные `door_configuration`.

По (2): текущий порядок шагов каскада — полотно → короб → наличник → кромка → удлинители (см. `door-configurator-ui` — «Каскадный выбор компонента конфигурации»). Пользователь хочет: полотно → кромка → короб → наличник → удлинители.

## What Changes

- Добавить в БД для каждой уже существующей уникальной комбинации (leaf_type, frame_type, edge_type, frame_extensions_type) короба КОМПЛАНАР (FT-002) и НЕО (FT-003), для которой сейчас задан `door_casing_type`, зеркальную `door_configuration`-строку с `door_casing_type_id = NULL` — тем самым делая явный вариант «Без наличника» доступным на этих коробах (данные, а не код: сам механизм уже реализован).
- Изменить порядок шагов каскадного выбора компонентов на фронте: полотно (leaf) → **кромка (edge)** → короб (frame) → наличник (doorCasing) → удлинители (frameExtensions) — было: полотно → короб → наличник → кромка → удлинители.
- Порядок обработки компонентов в запросе расчёта стоимости (`COMPONENT_ORDER`, шаг «2. Выберите опции») НЕ меняется — leaf должен оставаться первым для проверки высоты кромки (см. `link-edge-height-to-leaf-height`), это уже обеспечено и не зависит от порядка каскада выбора типов.

## Capabilities

### Modified Capabilities
- `door-configurator-ui`: порядок шагов каскадного выбора компонентов меняется (кромка перемещается сразу после полотна, перед коробом).

## Impact

- **База данных**: новая Liquibase-миграция — `INSERT ... SELECT DISTINCT` новых `door_configuration` с `door_casing_type_id = NULL` для существующих комбинаций короба КОМПЛАНАР и НЕО (≈189 + 135 = 324 новые строки).
- **Frontend**: изменение константы `CASCADE_ORDER` в `App.tsx` (и сопровождающего комментария) — реестр смены порядка, без изменения общей логики `buildCascadeSteps`, которая уже не зависит от конкретного порядка массива.
- **Backend**: изменений не требуется — вариант «без наличника» уже полностью поддержан существующим кодом каталога и расчёта цены (наличник — необязательный компонент `door_configuration`).
