## Context

Каталог фурнитуры (`hardware_category` → `hardware_type` → `hardware_option`, у типа `brand` и `price_list_id`, у варианта `article`) уже отдаётся целиком через `GET /api/hardware-catalog`; конфигуратор каждого сервиса фильтрует его по прайс-листу сервиса (`hardwareCatalogForPriceList`). Расчёт и выгрузки (`resolveSpecificationComponents`, Excel, КП) принимают `hardware: [{hardwareOptionId, quantity}]` и не проверяют принадлежность варианта прайс-листу. Позиция корзины (`CartItem`) хранит `exportRequest` (в т.ч. `hardware`), `pricingSnapshot` (цены, включая `hardware`) и `detailRows` (строки детализации, в т.ч. «Фурнитура»), построенные конфигуратором (`buildCartItemContent`) и обновляемые его живой синхронизацией. Сервисы описаны в `services.ts` по принципу «сервис = прайс-лист» и все отображаются конфигуратором. Источник данных — `~/Downloads/prays_list_furnitura_tsfo_01_02_2026.xls`: листы «HAUSDOORS» (~140 строк, колонки: фото, артикул, наименование, цвет, дилер, розница), «Fantom» (~110, те же колонки, разделы-заголовки), «Vantage» (~830, колонки: фото, артикул, наименование=цвет, дилер, розница; часть строк без цвета; в хвосте строк есть лишний числовой столбец — не используется). См. proposal.md — мотивация.

## Goals / Non-Goals

**Goals:**
- Экран «Фурнитура» с каталогом из файла и добавлением к дверям из корзины, с корректной ценой, детализацией и выгрузками.
- Не потерять фурнитуру при редактировании двери в конфигураторе.

**Non-Goals:**
- Фото, описания, правило кратности 2 для петель, автоподбор фурнитуры к двери.
- Отдельные позиции фурнитуры в корзине без двери.
- Изменение API и схемы БД.

## Decisions

**1. Фурнитура принадлежит позиции двери, не отдельной позиции корзины** (решение пользователя). Добавление меняет `exportRequest.hardware`, `pricingSnapshot` и `detailRows` существующей позиции. Расчёт — существующим эндпоинтом расчёта списка фурнитуры (`calculateHardwarePrice`, `hardware-standalone-pricing`) по полному списку фурнитуры позиции; новая цена за единицу = прежняя − прежняя сумма фурнитуры + новая сумма фурнитуры (полотно и компоненты не пересчитываются). Строки «Фурнитура» детализации строятся тем же кодом, что в конфигураторе: общая функция в `cart.ts`, которую используют и `buildCartItemContent`, и экран сервиса. Альтернатива — перерасчёт всей двери через конфигуратор: тяжелее и требует загруженного каталога конфигураций.

**2. Данные — Liquibase-миграции, сгенерированные разовым скриптом из xls.** Только переносимый SQL (PostgreSQL и H2), по образцу `0126-emal-layt-hardware.yaml`: changeSet прайс-листа `PL-003`, категории, типы, цветовые варианты. Файл — старый `.xls`, генератор читает его (xlrd/POI) и пишет YAML; скрипт в репозиторий не кладётся (как в предыдущих изменениях с прайсами), результат проверяется тестом по числу строк. Коды: `HWG-0xx`, `HWT-xxx` продолжают существующие нумерации.

**3. Правила нормализации.**
- Категория = раздел файла в пределах листа, с брендом в названии, чтобы разделы разных брендов не сливались («Ручки дверные ЦАМ — Vantage»); если на листе раздел один — заголовок листа.
- HAUSDOORS и Fantom: тип = наименование без цвета, цветовые варианты с одинаковым наименованием объединяются в один тип (как в «Эмаль лайт»); цвет — из колонки «Цвет».
- Vantage: колонка «наименование» содержит цвет, а модель задаёт артикул, поэтому один артикул = один тип «Vantage <артикул>» с одним вариантом; строки без цвета получают цвет «Без цвета».
- Артикулы сохраняются дословно (лишние пробелы по краям убираются); дубли строк с одним артикулом в одном разделе не создаются; дилерская цена — первая, розничная — вторая.

**4. Экран сервиса — отдельный компонент, а не конфигуратор.** «Фурнитура» в `services.ts` помечается видом (`kind: 'hardware'`) и рендерится новым `HardwareServiceScreen` вместо `ConfiguratorScreen`; в меню — тот же механизм пунктов, что у остальных сервисов. Экран получает корзину и колбэк обновления позиции (`updateCartItem`) из `App.tsx` и сам не хранит корзину. Раскладка: сверху — горизонтальная лента дверей (antd `Card` с выбором), под ней — каталог с выбором «бренд → модель → цвет» (см. решение 8). Только компоненты `antd`.

**5. Конфигуратор не теряет «чужую» фурнитуру.** При загрузке позиции (`loadRequest`) варианты `hardware`, которых нет в каталоге прайс-листа сервиса, не отбрасываются обратным поиском, а сохраняются в отдельном состоянии `foreignHardware` (с названием, цветом и ценой из полного каталога). Они добавляются в `hardwareSelections` расчёта и в `exportRequest.hardware`, показываются неизменяемыми строками в блоке «Фурнитура». Для этого каталог для поиска названий загружается целиком (он уже кэшируется `fetchHardwareCatalog`), а в блоке выбора остаётся отфильтрованный. Альтернатива — показывать фурнитуру PL-003 во всех сервисах: загромождает блок выбора ~1000 позициями.

**6. Фильтрация каталога сервиса «Фурнитура»** — на фронтенде по `priceList.code === 'PL-003'`, как у других сервисов; каталог не меняется и не требует новых параметров API.

**7. Уточнения при реализации.** (а) Фурнитура других прайс-листов уже не терялась в `hardwareLines` конфигуратора (обратный поиск оставляет такую строку без категории/типа), поэтому «сквозная» часть решения 5 свелась к показу: строки определяются как «вариант отсутствует в каталоге сервиса» и выводятся неизменяемыми (с названием из каталога целиком), без отдельного состояния `foreignHardware`. (б) Если дверь, которой сервис «Фурнитура» меняет фурнитуру, сейчас открыта в конфигураторе (режим редактирования), режим завершается — иначе живая синхронизация перезаписала бы позицию устаревшим списком фурнитуры конфигуратора.

**8. Доработки после первого просмотра экрана.** (а) Двери — горизонтальная лента карточек над каталогом (а не боковая колонка). (б) Каталог ведёт выбор шагами «бренд → модель → цвет» (бренд — переключатель, модели — список выбранного бренда, цвета — список выбранной модели с кнопкой «Добавить»), вместо плоской таблицы на ~1050 строк; раздел и поиск — дополнительные фильтры списка моделей. (в) Фурнитура других прайс-листов в списке фурнитуры двери показывается без редактирования и удаления (определяется по принадлежности варианта `PL-003`); весь список (включая её) передаётся в расчёт при каждом изменении, поэтому она не теряется из позиции и цены.

**9. Вторая серия доработок.** Бренд — выпадающий список (`Select`); фильтр раздела подписан «Элемент»; управление количеством в каталоге убрано («Добавить» = +1, количество правится у фурнитуры двери); название прайс-листа вынесено в шапку приложения (название берётся из каталога фурнитуры в `App.tsx`); названия категорий PL-003 очищены от префикса бренда отдельным changeSet'ом `0128` (бренд уже выбран и хранится в `hardware_type.brand`; правка `0127` не годится — он уже применён). В названиях категорий разных брендов теперь возможны совпадения («Накладки на цилиндр»): категории различаются кодом, на экране фильтруются по бренду.

**10.** Выбор цвета — отдельный выпадающий список «Цвет» в строке фильтров рядом с «Бренд», «Элемент» и поиском, список моделей — на всю ширину, под ним строка выбранной модели (цвет, цена дилер, цена розница, кнопка «+») (вместо списка цветов с кнопкой «Добавить» у каждого).

**11.** Блоки «Двери из корзины» и «Каталог фурнитуры» — антд `Collapse` (серые аккордеоны, как блоки конфигуратора), оба раскрыты по умолчанию и сворачиваются независимо.

**12.** Карточка двери: модель, теги, цвет, размеры и количество — каждое с новой строки; фурнитура других прайс-листов (из конфигуратора) в карточке не показывается вовсе (решение 8в уточнено: она не редактируется и не отображается, но сохраняется в позиции и цене).

**13.** В строке каждой модели списка выводятся цвета и цены дилер/розница (цена — значение или диапазон, если у цветов модели цены различаются); точные значения выбранного цвета остаются в строке выбранной модели под списком.

**14.** Каталог — плоский список записей «модель + один цвет + цены дилер/розница» (одна запись = один цветовой вариант) вместо каскада модель → цвет: фильтры бренд / «Элемент» / поиск сверху, кнопка «+» в каждой строке, без отдельного выбора цвета и без блока «Выбранная модель» (решения 8–13 в части выбора цвета и строки выбранной модели заменены этим).

**15.** Рядом с «Элемент» добавлен фильтр «Цвет» (цвета выбранных бренда и элемента, «Все цвета» по умолчанию); он сужает список записей и сбрасывается при смене бренда или элемента.

**16.** Поиск оставлен в строке фильтров («Бренд», «Элемент», «Цвет», поиск); в строке записи колонка «Цвет» сжимаемая и сдвинута левее, цены уже, а кнопка «+» не сжимается — чтобы она не выходила за границы списка.

**17.** В карточке двери блок фурнитуры отделён от характеристик двери отступом 12 px сверху и снизу и тонкой линией; между строками фурнитуры — 8 px.

**18.** Теги атрибутов в карточке двери — цветные метки сразу после названия модели (как в корзине), а не отдельной строкой; карта цветов тегов вынесена из `CartScreen.tsx` в `cart.ts` (`ATTRIBUTE_TAG_COLORS`) и общая для обоих экранов.

**19.** Блок характеристик двери в карточке имеет фиксированную минимальную высоту (150 px, константа `CONFIG_BLOCK_MIN_HEIGHT`), чтобы разделитель перед фурнитурой был на одном уровне у всех карточек; если модель с тегами переносится на несколько строк и блок вырастает, разделитель у такой карточки окажется ниже.

**20.** Блок «Двери из корзины» переименован в «Позиции из корзины»; в карточке позиции у фурнитуры убрано поле количества (остаётся удаление), количество растёт повторным «+» в каталоге.

## Risks / Trade-offs

- [Каталог вырастает с ~40 до ~1100 вариантов, грузится в каждый сервис] → запрос один и кэшируется; фильтрация по прайс-листу — на клиенте; при проблемах с производительностью добавить параметр фильтра на сервере отдельным изменением.
- [Нормализация названий и группировка по типам расходится с файлом (особенно Vantage — ~700 типов по одной позиции)] → правила зафиксированы выше; тест на полноту (каждая строка файла → вариант с артикулом и ценами); каталог ищется по тексту и артикулу.
- [Позиции корзины в `localStorage` без `foreignHardware`] → поле не хранится в позиции, а восстанавливается из `exportRequest.hardware` и каталога при загрузке; старые позиции работают как раньше.
- [Живая синхронизация конфигуратора перезаписывает `exportRequest.hardware`] → она включает сохранённую «чужую» фурнитуру (решение 5); покрывается тестом сценария «добавили ручку → открыли в конфигураторе → сменили цвет».
- [Разные цены/округления между расчётом фурнитуры и расчётом двери] → используется тот же backend-расчёт (`HardwarePriceDto`), итог пересчитывается только в части фурнитуры.
- [Файл — `.xls` с датой действия цен 01.02.2026] → дата в названии прайс-листа; обновление цен — отдельным changeset'ом, существующие не правятся.

## Migration Plan

Только данные: changeSet'ы добавляются в master changelog, откат — удаление добавленных строк в обратном порядке. Схема не меняется; позиции корзин пользователей остаются совместимыми.
