## Context

Каталог фурнитуры (`HardwareOption`) имеет необязательный артикул (change `add-emal-layt-hardware`/`add-hardware-service`); прайс-лист PL-003 «Фурнитура» содержит 1052 цветовых варианта с уникальными артикулами. Фото ручек лежат вне репозитория: `~/Downloads/foto_ruchek_po_artikulam/` — 1037 файлов (249 PNG, 207 JPG, ~27 МБ; размеры от ~300×120 до 800×800) и `список.csv` (468 строк: папка; лист; раздел; артикул; наименование; файл; привязка). Проверено по данным: все 468 артикулов CSV есть в миграции 0127; у 5 строк (Vantage, «нет фото») файла нет; имя каждого файла = артикул с заменой `/` на `_`; неиспользуемых файлов нет. Для моделей, где фото общее на все цвета, в папке уже лежат копии под каждый артикул. Для картинок дверей КП уже принят подход «файлы в ресурсах + индекс по именам» (`DoorImageCatalog`), см. архив `add-commercial-offer-pdf-export`, решение 4.

## Goals / Non-Goals

**Goals:**
- Фото каждой из 1037 позиций доступно в приложении (web и desktop одинаково) и показывается в списке сервиса «Фурнитура».
- Добавление/замена фото — положить файл в папку ресурсов, без миграций.

**Non-Goals:**
- Фото для петель, фиксаторов и прочих позиций без файла; загрузка фото из UI; фото в корзине, Excel и КП (можно отдельным change).
- Увеличение фото по клику / галерея.
- Хранение фото в БД.

## Decisions

**1. Файлы в ресурсах backend, не в БД.** `backend/src/main/resources/hardware-images/<артикул с «/»→«_»>.webp`. Те же причины, что у картинок дверей: попадают в jar и desktop-дистрибутив без изменений `jpackage`, версионируются в git, одинаково работают на PostgreSQL и H2, миграции не нужны. Альтернатива — `bytea`/BLOB в `hardware_option`: усложняет схему и дампы, а редактирования фото из UI нет.

**2. Привязка по имени файла, без новой колонки.** Артикул уже есть в БД, правило `/`→`_` покрывает все 1037 файлов без исключений. Отдельный индекс-файл (CSV) или колонка `image_file` дали бы лишнюю сущность для синхронизации. Альтернатива — колонка `hardware_option.image_file` через Liquibase: явнее, но требует миграции данных на 463 строк и правки при каждом новом фото. `список.csv` в репозиторий не переносится (в нём пути и служебные пометки).

**3. Подготовка файлов — разово, при переносе: масштаб до 480 px по большей стороне и конвертация в WebP (cwebp, качество ~85).** Миниатюра в строке списка — десятки пикселей, 800×800 PNG избыточны; ожидаемый размер набора ~8 МБ вместо 27 МБ. WebP читают все целевые браузеры и JavaFX WebView desktop-оболочки на macOS (проверить в задачах); сервер отдаёт байты как есть, без декодирования. Исходники остаются у пользователя в Downloads. Альтернатива — класть как есть: раздувает дистрибутив в разы.

**4. Каталог изображений — компонент `HardwareImageCatalog`:** при первом обращении сканирует `classpath*:hardware-images/*` (`PathMatchingResourcePatternResolver`, как `DoorImageCatalog`), строит множество имён файлов; имена сравниваются в NFC. `HardwareCatalogService` при сборке `HardwareOptionDto` проверяет наличие файла для артикула и, если есть, заполняет `imageUrl = "/api/hardware-images/" + URL-кодированное имя`. Артикулы содержат пробелы и кириллицы нет, но нужен `UriUtils`-кодинг.

**5. Эндпоинт `GET /api/hardware-images/{file}`** (новый контроллер): имя берётся только из индекса каталога (запрос вне индекса → 404), поэтому обход каталога невозможен по построению; `Content-Type: image/webp`, `Cache-Control: max-age=86400` (файлы меняются только релизом). Альтернатива — отдавать как статику Spring (`static/`): тогда путь не под `/api` и нужно отдельно настраивать прокси Vite и desktop; свой контроллер проще и тестируется MockMvc.

**6. Frontend.** В `HardwareServiceScreen.tsx` в `List.Item` слева — компонент `Image` из `antd` (`width/height` фиксированные, `preview={false}`, `loading="lazy"`, `fallback` и `placeholder` — нейтральная заглушка того же размера; для записей без `imageUrl` рендерится та же заглушка (`Avatar`/`Image` без `src`)). Тип `HardwareOptionDto` в `api/` получает `imageUrl: string | null`; `records` переносят его из варианта.

## Risks / Trade-offs

- Переименование артикула в БД молча «отвязывает» фото → тест в backend проверяет, что для всех артикулов с файлом в каталоге изображений он находится среди артикулов миграций (и наоборот — ни один файл не осиротел).
- Качество после уменьшения до 480 px / WebP для мелких деталей ручек → просмотреть выборку после конвертации; при необходимости поднять порог размера.
- WebP в JavaFX WebView desktop-оболочки → проверить запуском; запасной вариант — JPEG.
- 15 позиций без файла остаются с заглушкой → ожидаемо, отражено в спеках; в БД у 8 «новинок» артикул длиннее, чем в файле-списке (суффикс «новинка(…)»), поэтому файл копируется под артикул БД.

## Migration Plan

Миграций БД нет. Порядок: подготовка и перенос файлов → каталог изображений и поле `imageUrl` → эндпоинт → фронтенд → тесты. Откат — удаление поля, эндпоинта и папки ресурсов; каталог и расчёты не затрагиваются.
