## Context

Три независимых, но объединённых в один change уточнения (см. proposal.md — «Why»). Ключевые факты, установленные исследованием перед написанием:

- **«Комплект зарезных стоек»**: `post_type.name` в БД уже равно ровно «Комплект зарезных стоек» — суффикс «, длина 2170» нигде не хранится как единая строка, он собирается на фронте (`frontend/src/App.tsx`) из отдельных `postType.name` + `post.quantity` + `post.length`. Единственные два живых `frame_post` с этим `post_type` (frame_type «Комплланар» и «Нео») оба имеют `length = 2170`. Правка — чисто фронтенд, без миграций.
- **Наличники КОМПЛАНАР РЕВЕРС**: `door_casing_type.short_name` — колонка существует (добавлена в `0084-catalog-type-short-name.yaml`), но ни для одной строки `door_casing_type` ещё не заполнена ни одной миграцией. Прецедент заполнения — `0086`/`0087`/`0088` (`edge_type`/`mirror_finish_type`/`frame_extensions_type`), а формулировка в спеке — уже существующий раздел «Краткие наименования доборов ТС и КОМПЛАНАР» в `catalog-reference-short-name`.
- **Кромка ↔ реверс**: сейчас каждая строка `door_configuration`, где применима кромка, симметрично продублирована для обоих `edge_type` (`ET-001` прямая, `ET-002` с четвертью) — это видно по паттерну `CROSS JOIN edge_type et ... WHERE et.code IN ('ET-001','ET-002')`, повторяющемуся во всех миграциях, добавлявших кромку по коллекциям, и сохраняющемуся при копировании строк в реверсивные (`is_reverse = true`) через `0054`/`0056`/`0057`/`0059`. Нарушающих правило комбинаций может быть от нескольких десятков до нескольких сотен строк — точное число зависит от текущего состояния БД.

## Goals / Non-Goals

**Goals:**
- Убрать вводящую в заблуждение длину у позиции «Комплект зарезных стоек» в карточке короба.
- Задать краткие наименования трём наличникам КОМПЛАНАР РЕВЕРС.
- Обеспечить, чтобы прямая кромка предлагалась только для обычных конфигураций, а кромка с четвертью — только для реверсивных, убрав из каталога нарушающие это комбинации.

**Non-Goals:**
- Не вводить database-level ограничение (CHECK/trigger), предотвращающее появление таких комбинаций в будущем — PostgreSQL не поддерживает CHECK-ограничения, ссылающиеся на другие таблицы (а `edge_type_id` в `door_configuration` — это FK на отдельную таблицу `edge_type`, не enum), поэтому единственный практичный способ — согласованность на уровне данных, как и для прочих комбинаторных правил этого каталога (например, «доборы КОМПЛАНАР требуют короба Компланар» тоже не закреплено отдельным constraint'ом, только миграциями).
- Не меняем backend-код и API-контракты — каталог и так отдаёт только то, что есть в таблице `door_configuration`; фронтенд-каскад и без правок покажет только оставшиеся после удаления комбинации.
- Не переносим короткие наименования на неревeрсивные тёзки («Авеню»/«Аура»/«Ария») — явно не запрошено, остаются `null`.

## Decisions

### Удаление несовместимых строк — прямой DELETE по подзапросу, без CHECK-ограничения
Новый changeset выполняет:
```sql
DELETE FROM door_configuration
WHERE edge_type_id = (SELECT id FROM edge_type WHERE code = 'ET-001') AND is_reverse = true;

DELETE FROM door_configuration
WHERE edge_type_id = (SELECT id FROM edge_type WHERE code = 'ET-002') AND is_reverse = false;
```
Альтернатива — ограничение на уровне схемы (CHECK/trigger) — отклонена: PostgreSQL CHECK-ограничения не могут ссылаться на другие таблицы (нет способа сослаться на `edge_type.code` из CHECK на `door_configuration` без хардкода конкретного `id`, который генерируется автоинкрементом и неизвестен на момент написания миграции). Триггер возможен технически, но не соответствует стилю этого каталога — ни одно из уже существующих комбинаторных правил (например, casing/extensions требуют заданного frame_type) не закреплено триггером, все поддерживаются исключительно дисциплиной миграций.

### Никаких изменений в `configuration_price`
`configuration_price` ссылается на конкретный `leaf_type`/`frame_type`/`edge_type`/... напрямую, а не на `door_configuration.id` — удаление строк `door_configuration` не затрагивает цены кромки (`ET-001`/`ET-002` продолжают существовать как справочные строки, только сама комбинация с «неправильным» `is_reverse` перестаёт быть предлагаемой в каталоге).

### Верификация перед удалением — обязательный шаг apply, не часть самой миграции
Поскольку точное число и распределение затрагиваемых строк не определено статическим анализом миграций (требует живой БД), в tasks.md явно вынесен шаг «выполнить SELECT COUNT(...) до и после DELETE, вручную сверить, что ни одна пара leaf_type+frame_type не потеряла все свои door_configuration строки для одного из значений is_reverse» — до объявления задачи выполненной.

## Risks / Trade-offs

- **[Риск]** DELETE необратим через обычный откат приложения (это не soft-delete). → Стандартная практика этого проекта для каталожных миграций (см. `0054-5/6/7`, `0058` и др. — уже существующие DELETE-миграции); откат — через восстановление БД из бэкапа/повторного применения миграций с нуля, не специфично для этого change.
- **[Риск]** Возможна редкая комбинация leaf_type/frame_type, где исторически была задана только «неправильная» кромка (например, только `ET-002` для `is_reverse = false`) — тогда после удаления эта пара лишится кромки полностью, а не просто сузится до одного варианта. → Проверяется явным SQL-шагом в tasks.md перед завершением задачи; по паттерну миграций (см. design.md, Context) такое не ожидается, но не гарантировано статическим анализом.
- **[Риск]** Правка отображения «Комплект зарезных стоек» через сравнение по `postType.name` — хрупко (сломается, если наименование когда-нибудь переименуют). → Согласуется с уже существующим в этом файле паттерном (`FRAME_KIT_WITHOUT_POSTS_DESCRIPTION`) — тот же компромисс, тот же файл, тот же стиль.

## Migration Plan

1. Новый Liquibase changeset: `door_casing_type.short_name` для `DCT-005/007/009`.
2. Новый Liquibase changeset: удаление несовместимых по кромке/реверсу строк `door_configuration` (после ручной SQL-проверки количества затрагиваемых строк на локальной БД).
3. `frontend/src/App.tsx`: не показывать `length` для позиции короба с `postType.name === 'Комплект зарезных стоек'`.
4. Откат — обычный git-ревёрт кода; откат данных — через пересоздание БД из миграций (Liquibase down не используется в этом проекте, только новые миграции вперёд).
