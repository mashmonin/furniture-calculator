## Context

Короб — `frame_type` (`FT-001` ФАНТОМ, `FT-002` КОМПЛАНАР, `FT-003` НЕО); его стоимость — сумма `retail_price`/`dealer_price` всех строк `frame_post` этого короба (+ цена цвета, если у короба есть цвета; у «NEO 75» цветов нет). У «НЕО» одна пара позиций (стойка незарезная 2 027/3 549 и комплект зарезных стоек 4 027/7 047, длина 2170), а высоту 2400/2700 дают процентные наценки погонажа (`pogonazh_surcharge_rule`, например 2400 → +30 %). Высота короба — `liner_dimension_option` оси «ВЫСОТА» с диапазоном `[min_value, max_value]` высоты полотна (у «НЕО»: 2170 для 1900–2100, 2400 для 2150–2250 и 2300, …); коды `FT-002`, `FT-003` входят в набор `HEIGHT_RANGE_FRAME_TYPE_CODES` (backend и frontend), для них высота короба подбирается по высоте полотна, а расчёт без выбранной высоты отклоняется. В `frame_post` уникален `(frame_type_id, post_type_id)`, привязки к высоте нет; frontend позиции короба не использует, выгрузка спецификации берёт позиции из расчёта.

Для «NEO 75» цены заданы явно по двум высотам (отличаются от цен «НЕО» ≈ на 13 %, а не на +30 % погонажа), поэтому процентными наценками их выразить нельзя. Принято трактовать «длина полотна/короба» из запроса как высоту (DT-002): в проекте «длина» полотна — это ширина.

## Goals / Non-Goals

**Goals:**
- Завести короб «NEO 75» с явными ценами по двум высотам и конфигурациями для шести моделей «Эмаль Лайт».

**Non-Goals:**
- Реверс, четверть, кромки, наличники, добор, цвета короба для «Эмаль Лайт».
- «NEO 75» для других коллекций; изменение цен/позиций существующих коробов.

## Decisions

1. **Привязка позиции к высоте: `frame_post.height_option_id`.** Необязательная ссылка на `liner_dimension_option` (опция высоты этого же короба). Позиция без привязки действует при любой высоте (поведение существующих коробов не меняется); позиция с привязкой — только при выборе этой опции. Стоимость короба = сумма позиций без привязки и позиций, привязанных к выбранной опции высоты. Альтернативы: (а) два отдельных `frame_type` (NEO 75 «2170» и «2400») — ломают понятие «один короб» и подбор по высоте полотна; (б) процентные наценки — не воспроизводят цены прайса; (в) цена короба в `configuration_price` — этот механизм у короба используется только для цвета.
2. **Уникальность.** Прежний `UNIQUE (frame_type_id, post_type_id)` заменяется уникальностью `(frame_type_id, post_type_id, COALESCE(height_option_id, 0))` — отсутствие привязки считается отдельным значением. Простой `UNIQUE (…, height_option_id)` не годится: NULL считались бы различными, и для позиций без высоты пропала бы уникальность. Как и в остальных таблицах проекта: на PostgreSQL — индекс по выражению (`changes/0119-…`), на H2 — тот же приём через generated-колонку `height_option_norm` и обычный unique-индекс (`changes-desktop-overrides/0119-…`, контексты `!desktop`/`desktop` в master). Первоначально планировалась generated-колонка на обеих БД; индекс по выражению на PostgreSQL проще и соответствует существующим индексам (`uk_configuration_price_combination`). Проверено на обеих БД: повтор позиции с той же высотой и повтор позиции без привязки отклоняются.
3. **Данные «NEO 75».** `FT-004`; опции высоты короба: 2170 с диапазоном высоты полотна [2000; 2000] и 2400 с диапазоном [2100; 2300] (стандартные). Позиции: для каждой из двух высот — «Стойка незарезная» (qty 1, length NULL) и «Комплект зарезных стоек» (qty 2, length = 2170/2400). Итого 4 строки `frame_post` с привязкой к высоте. Цены — из `proposal.md`; первая цифра в прайсе — дилерская. «Стойки с фрезеровкой под петли» из запроса — это существующий `PT-002` («Комплект зарезных стоек»), новый тип позиции не заводится.
4. **Никаких процентных надбавок.** Правила `pogonazh_surcharge_rule` привязаны к конкретному коробу (`frame_type_id`); для `FT-004` ни одного правила не заводится, поэтому множитель погонажа всегда равен 1 (проверено по коду: без правила `resolvePogonazhSurchargeMultiplier` возвращает 1). Цены короба равны сумме явных цен позиций, выбранных по высоте. Правила для `FT-004` в будущем добавлять нельзя без отдельного решения; защитой служит тест (нет строк `pogonazh_surcharge_rule` у `FT-004`, базовая и итоговая цена короба совпадают). Нестандартные размеры у «Эмаль Лайт» запрещены, так что их наценки тоже не возникают.
5. **Диапазонные правила.** `FT-004` добавляется в `HEIGHT_RANGE_FRAME_TYPE_CODES` (backend и frontend): высота короба подбирается по высоте полотна, отсутствие высоты отклоняется, как у «НЕО». Для «Эмаль Лайт» высоты полотна — только 2000/2100/2200/2300, все покрыты диапазонами.
6. **Конфигурации.** Для каждой из шести моделей одна `door_configuration` (`LT-046…LT-051` × `FT-004`), `is_reverse = false`, `has_quarter = false`, без кромки/наличника/добора; конфигурация «только полотно» сохраняется (вариант «без короба»).
7. **API.** `FramePostDto` получает `heightOptionId` (null для существующих коробов); обратно-совместимое добавление. Расчёт и список позиций выбирают позиции, подходящие к выбранной высоте.

## Risks / Trade-offs

- [Изменение расчёта стоимости короба затрагивает все короба] → у существующих позиций `height_option_id` = NULL, они суммируются как раньше; регрессия проверяется существующими тестами цены короба.
- [Уникальность через generated-колонку и override для H2] → проверить миграцию на PostgreSQL и H2 (десктопные тесты); при несовместимости — решение по образцу `0006`/`0105` override.
- [Прайс «возможный»] → цены заведены отдельным changeset'ом, обновляются новым.
- [Не покрыты реверс/четверть/кромка] → сознательно: добавятся отдельными изменениями; без них у «Эмаль Лайт» доступны только «без короба» и «NEO 75» в базовом исполнении.

## Migration Plan

Новый Liquibase: колонка и ограничение `frame_post` (PostgreSQL + H2-override), затем данные «NEO 75». Откат — удаление данных и колонки, возврат прежнего уникального ограничения.

- Нужны ли «NEO 75» реверс, четверть и кромка — решается отдельным изменением по прайсу.
