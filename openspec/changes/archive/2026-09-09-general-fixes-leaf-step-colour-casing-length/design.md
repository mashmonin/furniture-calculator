## Context

См. proposal.md — «Why» и «What Changes». Три пункта независимы друг от друга технически (разные файлы/слои), объединены только тем, что были поданы одним пользовательским запросом. Ключевые факты о текущем состоянии:

1. **Поля «Другое значение длины/высоты (мм)» полотна** — обычные `antd InputNumber` (`frontend/src/App.tsx`, рендерятся только при `step.key === 'leaf'`, сразу после групп «Длина» и «Высота» соответственно), сейчас без явного `step` (по умолчанию у `InputNumber` шаг равен 1).
2. **Группа «Цвет»** для всех компонентов рендерится единообразно через `OptionGroup` (`frontend/src/components/OptionGroup.tsx`) — обёртка над `antd Radio.Group`/`Radio.Button`, рендерящая ряд кнопок; компонент уже реализует «не более одного выбора» и скрытие при пустом списке опций. `OptionGroup` используется не только для «Цвет», но и для «Длина»/«Высота»/«Толщина», а также для выбора типа компонента на каждом шаге каскада и для коллекции/исполнения зеркала — эти использования не меняются.
3. **Наличник (`door_casing_type`) и его единственная опция размера.** Во всех миграциях, где вообще заводится собственный размер наличника (`0010`, `0012`, `0029`, `0035`, `0040` — суммарно все 9 существующих `door_casing_type`: `DCT-001`–`DCT-009`), это одна и та же схема: `INSERT INTO liner_dimension_option (..., door_casing_type_id) SELECT dt.id, 2100, true, dct.id ... WHERE dt.code = 'DT-002'`, и `configuration_price` для наличника ссылается через `height_option_id`. Ни одна строка `liner_dimension_option` с `door_casing_type_id IS NOT NULL` и `liner_dimension_type_id` = id `DT-001` сегодня не существует.
4. **Ни бэкенд, ни фронтенд нигде не жёстко привязывают наличник к оси «Высота».** Бэкенд: в общей (не-`FrameType`) ветке `addComponentIfPresent` `lengthOption`/`heightOption` вычисляются одинаково для любого типа компонента (`LeafType` — особый случай только для `heightOption`, которая принудительно `null`), передаются в `findMostSpecificPrice` и сопоставляются с `configuration_price.length_option_id`/`height_option_id` независимо друг от друга; никакого `instanceof DoorCasingType`-ветвления, аналогичного `EdgeType`/`FrameType`, нет. Фронтенд: группы «Длина» и «Высота» для `doorCasing` (в отличие от `edge`/`frame`, у которых есть специальные хелперы `edgeHeightOptions`/`frameHeightRangeOptions`) рендерятся через обычный `component.dimensionOptions.filter((option) => option.dimensionType.code === LENGTH_TYPE_CODE / HEIGHT_TYPE_CODE)`. Это значит, что на какой бы оси ни лежали данные наличника в каталоге — в такой группе он и появится, без дополнительного кода.

## Goals / Non-Goals

**Goals:**
- Шаг `+50` для полей «Другое значение» длины/высоты полотна.
- Выпадающий список с единственным выбором для цвета полотна, без изменения поведения цвета у прочих компонентов.
- Перенести единственный параметр размера наличника с оси «Высота» на ось «Длина» во всех существующих `door_casing_type`, чисто на уровне данных каталога.

**Non-Goals:**
- Не меняется механизм валидации диапазонов (`validateHeightWithinLeafRange`) и не создаётся новой проверки для наличника — у наличника как не было, так и не появляется диапазонного ограничения по высоте полотна (в отличие от кромки/короба/добора «ТС»), просто теперь единственная опция его размера классифицирована как длина.
- Не меняется цена наличника — миграция переносит ссылку `configuration_price` на другую колонку (`length_option_id` вместо `height_option_id`), но не сами значения `retail_price`/`dealer_price`.
- Не вводится общий «выпадающий список» для цвета всех компонентов — только для полотна, по прямому запросу.
- Не меняется механизм «количество» и его отображение для наличника/добора.

## Decisions

### 1. Шаг `InputNumber` — прямое добавление пропа

`<InputNumber min={1} step={50} ... />` для обоих полей полотна (`customLengthValueMm`, `customHeightValueMm`). Больше нигде `step` не добавляется — поле «Количество» (`doorCasing`/`frameExtensions`) явно вне запроса пользователя и по смыслу (целые единицы товара) не должно шагать по 50.

### 2. `OptionGroup` получает необязательный `variant`, а не отдельный компонент

`OptionGroup` дополняется пропом `variant?: 'buttons' | 'select'` (по умолчанию `'buttons'`, поведение не меняется для всех существующих вызовов). При `variant === 'select'` вместо `Radio.Group`/`Radio.Button` рендерится `antd Select` (`allowClear`, `style={{ minWidth: 200 }}`) с теми же `options`/`selectedId`/`onChange`. Единственный новый вызов с `variant="select"` — группа «Цвет» при `step.key === 'leaf'`; для всех остальных групп (включая «Цвет» прочих компонентов) `variant` не передаётся.

**Альтернатива (отклонена):** отдельный компонент `ColourSelect` рядом с `OptionGroup`, дублирующий логику скрытия при пустом списке и заголовка. Отклонено — логика идентична `OptionGroup` (label, пустой список → не рендерить, ровно один выбор), различается только то, каким элементом antd она рендерится; расширение существующего компонента пропом меньше дублирует код и не создаёт второй источник правды для формы данных `SelectableOption`.

**Альтернатива (отклонена):** сделать `select` вариантом по умолчанию для «Цвет» у всех компонентов, а не только полотна. Отклонено — прямо противоречит запросу пользователя («цвет полотна»); у остальных компонентов при типичном малом числе цветов ряд кнопок остаётся не менее удобным, и это не в объёме этой задачи.

### 3. Перенос оси наличника — миграция данных, без кода

Поскольку (см. Context, п. 4) ни бэкенд, ни фронтенд не завязаны на конкретную ось наличника, перенос выполняется одной парой обобщённых `UPDATE` (не по каждому `door_casing_type` отдельно, в отличие от `INSERT`-миграций-прецедентов 0010/0012/0029/0035/0040, которые заводили каждый `door_casing_type` отдельными вставками при появлении новых коллекций):

```sql
UPDATE liner_dimension_option
SET liner_dimension_type_id = (SELECT id FROM liner_dimension_type WHERE code = 'DT-001')
WHERE door_casing_type_id IS NOT NULL
  AND liner_dimension_type_id = (SELECT id FROM liner_dimension_type WHERE code = 'DT-002');

UPDATE configuration_price
SET length_option_id = height_option_id, height_option_id = NULL
WHERE door_casing_type_id IS NOT NULL AND height_option_id IS NOT NULL;
```

Это безопасно относительно уникальных индексов: `uk_liner_dimension_option_door_casing_type (door_casing_type_id, liner_dimension_type_id, value)` — конфликта нет, т.к. ни у одного `door_casing_type` сегодня нет строки на оси `DT-001`; `uk_configuration_price_combination` (включает `COALESCE(length_option_id,0)`/`COALESCE(height_option_id,0)`) — конфликта нет, т.к. ни одна строка `configuration_price` наличника сегодня не ссылается на `length_option_id`.

После этой миграции фронтенд автоматически (без изменения кода) перестаёт показывать группу «Высота» для наличника (список опций для этой оси станет пустым → `OptionGroup` не рендерится) и начинает показывать группу «Длина» с тем же значением 2100 мм; клиент будет посылать выбор как `lengthOptionId` вместо `heightOptionId` — бэкенд уже одинаково обрабатывает оба поля для наличника.

**Альтернатива (отклонена):** оставить данные на оси «Высота» и просто переименовать отображаемую подпись группы на «Длина» для `doorCasing` на фронтенде. Отклонено — это разошлось бы с осью, которую хранит и матчит бэкенд/каталог (`liner_dimension_type`/`dimensionType.code`), создав несоответствие между отображаемой подписью и фактической семантикой данных; будущие правки (например, диапазонные ограничения по аналогии с кромкой/коробом/добором «ТС», если наличник когда-нибудь их получит) унаследовали бы эту путаницу.

## Risks / Trade-offs

- **[Риск]** `UPDATE ... WHERE door_casing_type_id IS NOT NULL` в новой миграции меняет данные, вставленные пятью разными более ранними миграциями (0010, 0012, 0029, 0035, 0040). → Это не редактирование самих changeset'ов (их SQL не трогается) — новый changeset с `UPDATE`, что соответствует правилу проекта «не редактировать применённые changeset'ы, только новые»; сам приём уже использован в `link-dobor-ts-length-to-leaf-height` (миграция 0067) для аналогичного переноса `length_option_id`.
- **[Риск]** Любой будущий `door_casing_type`, заведённый по старому паттерну (`dt.code = 'DT-002'`, копипастой из 0010/0012/0029/0035/0040), после этой миграции снова окажется на оси «Высота». → Вне объёма этой задачи (существующие данные, не паттерн вставки будущих); можно отметить в комментарии миграции для будущих авторов.
- **[Риск]** `antd Select` при большом количестве опций и отсутствии `showSearch` может быть неудобен для поиска по названию цвета. → Не входит в текущий запрос («выпадающий список с единственным выбором»); `showSearch` можно добавить отдельным изменением по запросу, если понадобится.

## Migration Plan

1. Frontend: `step={50}` на `InputNumber` длины и высоты полотна.
2. Frontend: `OptionGroup` — добавить проп `variant`; группа «Цвет» полотна — `variant="select"`.
3. Liquibase-миграция: перенос оси наличника (`liner_dimension_option`) и ссылки в `configuration_price` (Decision 3).
4. Проверка: `npm run build` (типы/сборка); backend-тесты не запускаются (см. ограничение пользователя в предыдущей сессии — тесты сейчас сломаны; ни один существующий тест не зависит от оси наличника, см. proposal.md Impact); ручная проверка в браузере — шаг `+50` на полях полотна, выпадающий список цвета полотна, наличник в группе «Длина» с прежним значением.

Откат — стандартный: новая миграция — новый changeset, откат через Liquibase `rollback` при необходимости; frontend-правки откатываются обычным git-ревертом.
