## Context

`pogonazh_surcharge_rule` (см. pogonazh-surcharge-rules) сейчас — чисто точечная модель: одна строка = один владелец + одно конкретное значение `value` (наценка применяется только при точном совпадении). Для короба «НЕО»/«Компланар», наличника и добора это достаточно, потому что их размер всегда выбирается из каталожной опции `liner_dimension_option` — конечного списка значений. Короб «Фантом» (frame_type FT-001) — исключение: его высота не выбирается из каталога, а копирует высоту полотна, которая вводится как свободное число (`InputNumber` на фронтенде, `customHeightValueMm` в DTO) без ограничения сверху (см. `HEIGHT_MIRROR_FRAME_TYPE_CODES` в `DoorConfigurationPricingService`, изначально введено в change `mirror-fantom-frame-height-to-leaf-height`). Это разработанное поведение: короб «Фантом» физически обязан повторять высоту полотна в точности, поэтому его высота никогда «снэпится» к ближайшей каталожной опции, в отличие от «НЕО»/«Компланар» (там для этого именно и используются диапазоны `min_value`/`max_value` в `liner_dimension_option`, которые пере переводят произвольный ввод в дискретную каталожную точку — см. `frameHeightRangeOptions`/`dimensionRangeCoversLeafHeight` на фронтенде).

Новое требование фабрики — наценка 70%/100% на ЛЮБУЮ высоту полотна выше 2400 мм (двумя тирами: `(2400, 2700]` → 70%, `(2700, ∞)` → 100%), а не только на несколько заранее перечисленных точек. Перечислять точки заранее (как это было сделано для 2050–2400 в предыдущих changes) здесь не работает: у диапазона `(2700, ∞)` нет верхней границы, а высота — произвольное число, а не значение из фиксированного списка.

## Goals / Non-Goals

**Goals:**
- Позволить `pogonazh_surcharge_rule` описывать наценку как диапазон значений (не только точку), без изменения смысла уже существующих точечных строк.
- Не трогать `liner_dimension_option`/механизм «снэпа к каталожной опции» — он сознательно не применяется к «Фантому», и это не меняется.
- Сохранить обратную совместимость: все существующие точечные строки и весь код, который их читает (backend-резолвер, `GET /api/pricing-surcharges`, фронтенд), продолжают работать без изменений там, где диапазоны не используются.

**Non-Goals:**
- Не вводим общий механизм диапазонов для ВСЕХ владельцев `pogonazh_surcharge_rule` — у короба «НЕО»/«Компланар», наличника и добора значение всегда приходит из конечного каталога, точечная модель для них остаётся достаточной и unchanged.
- Не проверяем на уровне БД отсутствие перекрывающихся диапазонов у одного владельца (см. «Risks»).

## Decisions

### Диапазон — как дополнительные nullable-колонки в `pogonazh_surcharge_rule`, а не отдельная таблица
Добавляем `min_value_exclusive` (нижняя граница, не включая) и `max_value_inclusive` (верхняя граница, включая) — обе nullable, обе NULL для существующих точечных строк. `value` становится nullable: точечная строка задаёт `value` (границы NULL), диапазонная — задаёт хотя бы одну из границ (`value` NULL). CHECK-констрейнт (по аналогии с уже существующим «single owner» констрейнтом в этой же таблице) гарантирует, что строка — точка либо диапазон, но не и то, и другое, и не ни то, ни другое:
```
(CASE WHEN value IS NOT NULL THEN 1 ELSE 0 END) +
(CASE WHEN min_value_exclusive IS NOT NULL OR max_value_inclusive IS NOT NULL THEN 1 ELSE 0 END) = 1
```
**Альтернатива (отклонена)**: отдельная таблица `pogonazh_surcharge_range_rule`. Отклонена — это дублирует «single owner» констрейнт и весь резолв-код почти без выгоды, а диапазоны нужны только одному владельцу из трёх.

**Альтернатива (отклонена)**: заранее перечислить точки диапазона (как раньше для 2050–2400) — например, добавить точки 2500/2600/2700 на 70% и «условную» точку 3000 на 100%. Отклонена по прямому запросу пользователя: верхний диапазон не ограничен сверху, а привязка к конкретным точкам скрывает эту границу и даёт неверный результат для промежуточных значений (например, 2550 мм или 2900 мм).

### Границы — «нижняя не включая, верхняя включая» (не унифицируем с семантикой `liner_dimension_option`)
`liner_dimension_option.min_value`/`max_value` инклюзивны с обеих сторон (`min <= x <= max`, см. `dimensionRangeCoversLeafHeight`). Для `pogonazh_surcharge_rule` нижняя граница сделана **исключающей**, чтобы соседние тиры (`2400` точка на 50%, `(2400, 2700]` диапазон на 70%) не пересекались и не требовали дополнительной логики приоритета: `2400` попадает только в точечное правило (50%), `2400.01`–`2700` — только в диапазонное (70%). Верхняя граница включающая, поэтому `2700` попадает в тир 70%, а не 100%; строка `(2700, ∞)` не имеет `max_value_inclusive` (NULL = без ограничения).

### Резолвер — читает все строки владельца и матчит в памяти, а не два SQL-запроса
`PogonazhSurchargeRuleRepository` получает `findByFrameTypeId(Long)` (все строки владельца, обычно 1–8 штук), а `DoorConfigurationPricingService.resolvePogonazhSurchargeMultiplier(FrameType, BigDecimal)` сначала ищет точное совпадение по `value`, затем — диапазонную строку, где `(minValueExclusive == null || heightValue.compareTo(minValueExclusive) > 0) && (maxValueInclusive == null || heightValue.compareTo(maxValueInclusive) <= 0)`. `doorCasingType`/`frameExtensionsType`-варианты резолвера не меняются (у них диапазонных строк не бывает, точечный `findByXIdAndValue` остаётся).

### DTO и фронтенд — те же поля, что и в модели: `value` nullable + границы диапазона
`PogonazhSurchargeRuleDto` получает `minValueExclusive`/`maxValueInclusive` (nullable), `value` становится nullable. Фронтенд (`pogonazhSurchargePercent` в `App.tsx`) сначала ищет точное совпадение `rule.value === matchedValue` (как сейчас), а если не найдено — ищет диапазонное правило того же владельца с тем же условием, что и на backend. Дублирование этой логики между backend и frontend — та же ситуация, что уже существует для наценки за размер полотна (`dimensionRangeCoversLeafHeight` тоже задан отдельно на фронтенде) — не вводим общий контракт валидации специально для этого change.

## Risks / Trade-offs

- **Перекрывающиеся или дублирующиеся диапазоны не проверяются на уровне БД** → уникальный индекс `(owner_key, value)` не работает при `value IS NULL` (диапазонные строки). Митигация: только 2 диапазонные строки заводятся этим change (обе для одного владельца, не пересекаются по построению — `2400 < x <= 2700` и `x > 2700`), правильность — на ревью миграции, не на констрейнте.
- **Дублирование условия матчинга диапазона между Java (backend) и TypeScript (frontend)** → риск, что при будущем изменении границ поправят только одну сторону. Митигация: то же уже принятое в проекте решение для похожей логики (`dimensionRangeCoversLeafHeight`), новый риск не вводится, а не устраняется отдельно в рамках этого change.
- **Расширение до диапазонов усложняет модель `pogonazh_surcharge_rule` для будущих читателей** (два взаимоисключающих способа задать правило вместо одного). Митигация: CHECK-констрейнт делает недопустимые комбинации невозможными на уровне БД, а не только по конвенции.
