## Why

Фабрика продолжает уточнять наценку за нестандартную длину/высоту погонажа (см. предыдущий change `increase-pogonazh-surcharge-for-2700-and-fantom-2350-2400`, который ввёл тир 50%): для более длинных значений, требующих ещё большего расхода материала, нужны более высокие тиры — 70% и 100%. Дополнительно для короба «Фантом» (высота — свободное числовое поле, а не выбор из каталога) требуется наценка на весь диапазон значений выше 2400 мм, а не только на отдельные заранее перечисленные точки — точечная модель `pogonazh_surcharge_rule` (владелец + одно конкретное значение) для этого не годится, отсюда and расширение модели диапазонами.

## What Changes

- **Точечные тиры 70% (без изменения модели)** — повышаются существующие строки `pogonazh_surcharge_rule` с 30% до 70%, где это уже заведено в каталоге длин:
  - Короб «Компланар» (`frame_type` FT-002), `value = 3000` мм.
  - Наличник «Эво» (`door_casing_type` DCT-001), `value = 3000` мм. *(У наличников «Авеню»/«Авеню РЕВЕРС»/«Аура»/«Аура РЕВЕРС» упомянутых в исходном запросе 3000 мм нет в каталоге длин (максимум 2700 мм) — наценка 70% на 3000 мм физически неприменима, эти типы не затрагиваются.)*
  - Добор «Компланар» (`frame_extensions_type` FET-008/009/010, `value = 3000`; FET-011/012/013, `value = 2950`). *(Добор «Нео»/«ТС» (FET-004..007) не имеет длин 2950/3000 в каталоге (максимум 2700 мм) — не затрагивается, хотя в исходном запросе упомянут «Компланар/Нео».)*
- **Диапазонные тиры для короба «Фантом» (`frame_type` FT-001) — расширение модели `pogonazh_surcharge_rule`**:
  - `pogonazh_surcharge_rule` дополняется опциональными полями диапазона `min_value_exclusive`/`max_value_inclusive` (обе NULL = точечное правило по `value`, как сейчас; иначе — диапазонное правило, `value` для такой строки NULL). Правило матчится, если `min_value_exclusive` не задан или высота строго больше него, и `max_value_inclusive` не задан или высота меньше-либо-равна ему.
  - Новая диапазонная строка: `2400 < value ≤ 2700` → наценка 70%.
  - Новая диапазонная строка: `value > 2700` (без верхней границы) → наценка 100%. Это тот же случай, что в исходном запросе назван «Стоевая короба врезная» — отдельного владельца/frame_type с таким названием нет, это просто разговорное название конструкции короба «Фантом» при высоте выше 2700 мм.
  - Существующие точечные строки (2050/2150/2200/2250/2300 @ 30%, 2350/2400 @ 50%) не меняются — диапазон начинается строго после 2400, поэтому не пересекается с ними.
- **Наценка 30% по умолчанию перестаёт быть "хвостом"**: после этого изменения для короба/наличника/добора (кроме собственных базовых значений короба «Фантом» ниже 2400 мм, которые в это изменение не входят) 30% остаётся только на `value = 2400` — остальные заведённые длины (2700/2950/3000 и диапазоны выше 2400 для «Фантома») получили явный более высокий тир (50%/70%/100%).
- **Backend**: `DoorConfigurationPricingService`/`PogonazhSurchargeRuleRepository` — резолв наценки для `frame_type` учитывает и точечные, и диапазонные строки (диапазонные — только у владельцев без каталожных `liner_dimension_option`, на практике только «Фантом»). `GET /api/pricing-surcharges` (`PogonazhSurchargeRuleDto`) дополнительно отдаёт `minValueExclusive`/`maxValueInclusive` для диапазонных строк (nullable `value`). **BREAKING** (аддитивное расширение контракта ответа, не ломающее существующие поля): элементы `pogonazhSurchargeRules` теперь могут иметь `value = null` при заданном диапазоне.
- **Frontend**: разбивка наценки за погонаж (`App.tsx`) для короба «Фантом» ищет подходящее правило не только по точному совпадению `value`, но и по попаданию высоты в диапазон `(minValueExclusive, maxValueInclusive]`.
## Capabilities

### Modified Capabilities
- `pogonazh-surcharge-rules`: `pogonazh_surcharge_rule` дополняется опциональными полями диапазона (`min_value_exclusive`/`max_value_inclusive`) как альтернативой точечному `value` для владельцев без каталожной привязки значения (короб «Фантом»); добавляются тиры наценки 70% (value=3000/2950 у ряда владельцев) и диапазонные тиры 70%/100% для «Фантома» выше 2400 мм.
- `door-configuration-api`: `GET /api/pricing-surcharges` дополнительно отдаёт границы диапазона для диапазонных правил наценки за погонаж; `value` элемента `pogonazhSurchargeRules` теперь может быть `null`.
- `door-configurator-ui`: разбивка наценки за погонаж для короба «Фантом» учитывает диапазонные правила, а не только точное совпадение значения.

## Impact

- Backend: новый Liquibase changelog (`ALTER TABLE pogonazh_surcharge_rule` — новые nullable-колонки, релаксация `value` до nullable, новый CHECK-констрейнт «точка либо диапазон», UPDATE существующих точечных строк на 70%, INSERT новых диапазонных строк для FT-001); новый метод(ы) в `PogonazhSurchargeRuleRepository` для диапазонного поиска у `frame_type`; правка `DoorConfigurationPricingService.resolvePogonazhSurchargeMultiplier(FrameType, BigDecimal)`; расширение `PogonazhSurchargeRuleDto`.
- Frontend: расширение типа `PogonazhSurchargeRuleDto` в `api/types.ts`, правка `pogonazhSurchargePercent()` в `App.tsx` для диапазонного матчинга.
- Desktop (H2): `ALTER TABLE ... ADD COLUMN` и `CHECK` constraint — чистый DDL без partial/functional индексов, совместим с H2 напрямую (desktop-override не потребуется, как и для 0095); UPDATE/INSERT данных тоже нейтральны к диалекту.
- Ограничение (осознанно не устраняется в этом change): для диапазонных строк уникальность/непересечение диапазонов не проверяется на уровне БД (unique-индекс по (owner, value) не действует при value=NULL) — контроль за отсутствием перекрывающихся диапазонов остаётся на ревью миграций.
