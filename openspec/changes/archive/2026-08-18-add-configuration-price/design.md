## Context

См. proposal.md — Why. Продолжение `add-door-configuration-catalog` (0006): `door_configuration`, `liner_dimension_option`, `colour_option` уже реализованы и работают, используют единый паттерн владения — 5 nullable FK-колонок (leaf_type_id/frame_type_id/edge_type_id/door_casing_type_id/frame_extensions_type_id) + CHECK "ровно один" — и уникальные индексы через `COALESCE` (см. design.md того изменения). В системе ровно 3 `liner_dimension_type` (ДЛИНА, ВЫСОТА, ТОЛЩИНА), заданы с 0001-item-schema.yaml.

## Goals / Non-Goals

**Goals:**
- Цена привязана к конкретной комбинации значений (не к типу компонента целиком).
- Одна структура для всех пяти типов компонентов.
- Ссылки на размер/цвет — на уже существующие каталожные строки (`liner_dimension_option`, `colour_option`), без дублирования value/name.

**Non-Goals:**
- Проверка на уровне СУБД, что `length_option`/`height_option`/`thickness_option`/`colour_option` в строке цены принадлежат тому же типу-владельцу, что и сама строка цены (см. Risks — сознательно не реализуется).
- Расчёт цены всей двери из цен компонентов — эта логика не проектируется здесь.
- Наполнение реальными ценами и единица измерения.
- Java-слой приложения — кода пока нет, меняется только схема БД.

## Decisions

**Три отдельные nullable-колонки (length_option_id/height_option_id/thickness_option_id) вместо обобщённой связи "N произвольных liner_dimension_option".**
Почему: в системе фиксированно и устойчиво 3 вида размера (ДЛИНА/ВЫСОТА/ТОЛЩИНА, с 0001) — их не нужно моделировать как открытый список. Явные именованные роли проще читать и проверять (`length_option_id` однозначно про длину), чем связывающая таблица "price ↔ N liner_dimension_option" с неограниченной мощностью, которая для этой предметной области избыточна.

**Ссылка на colour_option, а не на colour_type напрямую.**
Цена должна существовать только для уже разрешённого этому типу компонента цвета — использование `colour_option` (а не `colour_type`) делает это ограничение структурным: нельзя сослаться на цвет, который каталог не считает допустимым для этого типа. Аналогично для размеров — ссылка на `liner_dimension_option`, а не на `value` напрямую.

**Не проверять на уровне БД согласованность "length_option принадлежит тому же leaf_type, что и сама строка price".**
CHECK-констрейнт в PostgreSQL не может обращаться к данным другой строки/таблицы; для этого нужен триггер. Триггер здесь — заметно возросшая сложность ради одного инварианта, который проще держать на уровне данных/будущего приложения (при вставке явно выбирать `length_option` того же типа, что и владелец цены). Явно вынесено в риски ниже.

**Уникальность через COALESCE — тот же приём, что и в 0006.**
```sql
CREATE UNIQUE INDEX uk_configuration_price_combination ON configuration_price (
  COALESCE(leaf_type_id, 0), COALESCE(frame_type_id, 0), COALESCE(edge_type_id, 0),
  COALESCE(door_casing_type_id, 0), COALESCE(frame_extensions_type_id, 0),
  COALESCE(length_option_id, 0), COALESCE(height_option_id, 0), COALESCE(thickness_option_id, 0),
  COALESCE(colour_option_id, 0)
)
```
(Владельческие колонки тоже через COALESCE здесь, а не как в 0006 через "leaf_type_id, COALESCE(...)" — в 0006 первая колонка `leaf_type_id` была обязательной (NOT NULL) и поэтому не нуждалась в COALESCE; здесь ни один из пяти владельцев не обязателен сам по себе, обязательно только то, что один из них заполнен — CHECK single-owner это гарантирует отдельно, а уникальный индекс просто должен одинаково обрабатывать NULL по всем пяти.)

## Risks / Trade-offs

- **[Риск]** Ничто на уровне БД не мешает вставить `configuration_price` с `length_option_id`, который на самом деле принадлежит другому типу компонента (не тому, что владелец этой цены) → **Митигация**: осознанный компромисс (см. Decisions) — при появлении Java-слоя проверка переносится в сервисный код; добавление триггера — возможное отдельное изменение, если проблема проявится на практике.
- **[Риск]** 9 nullable-колонок (5 владельцев + 3 размера + 1 цвет) в одной таблице — читать структуру сложнее, чем плоскую таблицу → **Митигация**: паттерн уже принят и обкатан в проекте (0003, 0006), комментарии в миграции и этот design.md документируют намерение.
