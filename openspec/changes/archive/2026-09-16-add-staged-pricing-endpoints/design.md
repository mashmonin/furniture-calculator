## Context

См. proposal.md — «Why»/«What Changes» для мотивации и списка эндпоинтов. Ключевые технические факты, установленные исследованием перед написанием этого change:

- `door_configuration` — плоская таблица валидных комбинаций (leaf × frame × edge × doorCasing × frameExtensions, все кроме leaf — опциональны), с уникальным индексом по полному кортежу (см. `openspec/specs/door-configuration-catalog/spec.md`, «Уникальность door_configuration»). Это не набор независимо нормализованных списков опций, соединяемых на лету.
- `edge_type` комбинаторно независим от `frame_type`/`door_casing_type`/`frame_extensions_type`: seed-миграции (например, `0025-vertikal-edge-configurations.yaml`) CROSS JOIN'ят уже существующие строки `door_configuration` (с любым `frame_type`, включая `NULL`) с видами кромки — один и тот же короб встречается с разными кромками и наоборот.
- `DoorConfigurationPricingService.addComponentIfPresent` уже считает `leaf`, `frame`, `edge`, `doorCasing`, `frameExtensions` полностью независимо друг от друга — единственная общая величина между ними — `leafHeightValue`, используемая только для проверок диапазона (короб «НЕО»/«Компланар», точное совпадение у «Фантом», длина наличника/добора). Наценка за реверс применяется только к `leaf`. Это уже подтверждает, что разбиение общего расчёта на этапные эндпоинты не требует распутывания перекрёстных ценовых зависимостей — только явной передачи `leafHeightValue` между этапами.
- Сейчас `FrameType`, `EdgeType`, `DoorCasingType`, `FrameExtensionsType` резолвятся исключительно через уже загруженный `DoorConfiguration` (`configuration.getFrameType()` и т.п.) — отдельных репозиториев для поиска этих сущностей по id нет (есть только `LeafTypeRepository`, используемый `calculateForLeaf`).
- Прецедент валидации «id ссылается на допустимую для этого владельца сущность» уже есть: `MirrorFinishOptionRepository.findByMirrorFinishTypeIdAndLeafTypeId` и `GlazingOptionRepository.findByGlazingTypeIdAndLeafTypeId` — оба не различают «id не существует вовсе» и «существует, но недопустим для этого владельца», возвращая в обоих случаях 400 с одним и тем же сообщением.

## Goals / Non-Goals

**Goals:**
- Три независимых эндпоинта для трёх этапов фронтенда, каждый — без необходимости заранее знать финальную согласованную `door_configuration`.
- Переиспользовать существующую ценовую логику (`addComponentIfPresent`, наценки, `priceHardwareSelections`) без дублирования.
- Валидировать межтиповые связи (leaf↔edge, frame↔doorCasing, frame↔frameExtensions) тем же способом, что уже применяется для leaf↔mirror_finish_type и leaf↔glazing_type.

**Non-Goals:**
- Четвёртый суммирующий эндпоинт — явно исключён (см. proposal.md).
- Миграция фронтенда на новые эндпоинты — отдельный будущий change.
- Изменение существующего `POST /api/door-configurations/{id}/price` — не трогается.
- Полная сквозная валидация «эта комбинация leaf+edge+frame+doorCasing+frameExtensions целиком существует как одна строка door_configuration» — каждый этап проверяет только свою пару типов (leaf↔edge, либо frame↔doorCasing и frame↔frameExtensions), как и существующая проверка mirror_finish/glazing. Полную сквозную согласованность каскада по-прежнему обеспечивает фронтенд (он никогда не предлагает пользователю комбинацию, не ведущую к валидной строке каталога).

## Decisions

### Кромка — расширение существующего `POST /api/leaf-types/{id}/price`, а не новый эндпоинт
Этот эндпоинт уже покрывает «Полотно» (реверс, размеры, цвет, зеркало, остекление) — кромка логически тот же этап, а не отдельная сущность. Расширение аддитивно: новое поле `edgeTypeId` и заполнение уже существующего (но пока игнорируемого этим эндпоинтом) поля `edge` в `PricingRequestDto` — старые клиенты, не передающие `edgeTypeId`, получают прежнее поведение один в один.

Альтернатива — отдельный эндпоинт `POST /api/leaf-types/{id}/price/edge` или включение кромки только в новый «короб»-эндпоинт — отклонена: кромка физически и по смыслу относится к полотну (так её уже группирует фронтенд), а не к коробу, и раздувает набор эндпоинтов без выгоды.

### Новый эндпоинт короба и обрамления ключуется по `frame_type_id`, не по `door_configuration_id`
`POST /api/frame-types/{id}/price`, по аналогии с `POST /api/leaf-types/{id}/price`. На этапе «Короб и обрамление» согласованная `door_configuration` ещё не определена (кромка уже выбрана на предыдущем этапе, но короб/наличник/добор — только на этом), а `frame_type_id` — единственный id, который клиент точно знает к этому моменту (наличник/добор — производные от него через каталог, как и раньше выбираются кликом в UI).

### `leafHeightValue` передаётся эндпоинту явно, а не вычисляется из опций полотна
Раз этот эндпоинт не получает выбор полотна, а высота полотна нужна только для диапазонных проверок (короб/наличник/добор), клиент передаёт уже известное ему значение (оно уже есть в состоянии фронтенда после этапа «Полотно»). Это то же значение, что фронтенд сегодня использует локально для тех же целей (сужение каскада по высоте).

### `isReverse` в запросе короба и обрамления не нужен
Наценка за реверс в текущей логике применяется только к `leaf` (см. Context) — короб/наличник/добор её никогда не получают. Реверс влияет только на то, какие типы вообще доступны в каталоге, а это уже разрешено на фронтенде до вызова (клиент передаёт только валидные для выбранного реверса id).

### Валидация межтиповых связей — новые методы существования на `DoorConfigurationRepository`
`existsByLeafTypeIdAndEdgeTypeId`, `existsByFrameTypeIdAndDoorCasingTypeId`, `existsByFrameTypeIdAndFrameExtensionsTypeId` — производные Spring Data запросы, по аналогии с существующим паттерном owned-lookup у `MirrorFinishOptionRepository`/`GlazingOptionRepository` (см. Context). Не различают «id не существует» и «существует, но недопустим для этой пары» — один и тот же код 400, то же решение, что уже принято для зеркала/остекления.

### Новые репозитории `FrameTypeRepository`, `EdgeTypeRepository`, `DoorCasingTypeRepository`, `FrameExtensionsTypeRepository`
Нужны для резолва `frameTypeId` (обязательный path-параметр нового эндпоинта, 404 при отсутствии, по образцу `LeafTypeRepository` в `calculateForLeaf`) и `edgeTypeId`/`doorCasingTypeId`/`frameExtensionsTypeId` (опциональные id в теле запроса, нужен сам объект типа для передачи в уже существующий `addComponentIfPresent`/`validatedColourOption`/`validatedDimensionOption`, которые работают с любым `CatalogType`).

### Новые минимальные DTO для двух новых эндпоинтов вместо переиспользования `PricingRequestDto`/`PricingResponseDto`
Для эндпоинта короба/обрамления и эндпоинта фурнитуры — новые узкие DTO (`FrameGroupPricingRequestDto`/`ResponseDto`, `HardwarePricingRequestDto`/`ResponseDto`) без полей, не относящихся к этому этапу. Это часть заявленной цели change («техническая доработка API» — привести контракт в соответствие с реальным разделением ответственности), в отличие от `PricingRequestDto`, который уже переиспользуется между `calculate()` и `calculateForLeaf()` с молчаливо игнорируемыми полями — этот паттерн не расширяется на новые эндпоинты, а оставляется только в существующем коде.

## Risks / Trade-offs

- **[Риск]** Клиент может передать валидную по отдельности пару (leaf+edge на одном этапе, frame+doorCasing на другом), которые вместе не образуют ни одной реальной строки `door_configuration` (например, эта конкретная кромка никогда не сочеталась в каталоге именно с этим коробом). → Не смягчается на уровне этих двух эндпоинтов (они физически не видят друг друга в рамках одного запроса) — это принятое ограничение (см. Non-Goals); ответственность остаётся на фронтенде, как и сегодня для mirror_finish/glazing относительно leaf.
- **[Риск]** Рассинхронизация между новыми этапными эндпоинтами и существующим `calculate()` при будущих изменениях бизнес-правил (кто-то поправит проверку диапазона высоты в одном месте и забудет в другом). → Оба пути используют один и тот же `addComponentIfPresent`/`validateHeightWithinLeafRange`/`requireHeightMirrorsLeaf` и т.д. — нет дублирования самой бизнес-логики, только новые тонкие точки входа.
- **[Риск]** Четыре новых репозитория ради простого поиска по id — минимальный, но реальный прирост поверхности кода. → Каждый — однострочный `JpaRepository<T, Long>` без кастомной логики, симметрично уже существующему `LeafTypeRepository`.

## Migration Plan

1. Backend: новые репозитории → новые методы `DoorConfigurationRepository` → новые DTO → расширение `PricingRequestDto`/`calculateForLeaf` (кромка) → новый `calculateForFrameGroup` + `FrameGroupPricingController` → новый `calculateHardware` + `HardwarePricingController`.
2. Тесты на новую логику точечно (`./gradlew test --tests`), без полного прогона (см. заметку в CLAUDE.md/памяти проекта).
3. Откат — обычный git-ревёрт; новые эндпоинты аддитивны, существующие не меняются (кроме аддитивного расширения `POST /api/leaf-types/{id}/price`, обратно совместимого).
