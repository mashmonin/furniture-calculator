## Why

Сейчас для нестандартной длины/высоты полотна можно ввести любое значение — годным его делает (или не делает) только наличие правила наценки (`dimension_surcharge_rule`, включая каскад) для конкретного значения; физического верхнего/нижнего предела, отражающего реальные производственные возможности серии, в системе нет. Фабрика по каждой серии полотна прямо назвала диапазон длины/высоты, который она физически способна произвести — это факт каталога («что вообще можно сделать»), а не бизнес-правило наценки («сколько это стоит»), и их не стоит смешивать в одной таблице. Клиент также не видит заранее, какой диапазон вообще допустим для выбранной модели, и при вводе недопустимого значения получает техническое сообщение («фабрика не производит полотно с размером X мм для этой оси»), а не понятную клиенту формулировку.

## What Changes

- **Новый каталожный справочник `collection_dimension_range`** — по одной строке на (коллекция полотна, ось размера: длина/высота), с `min_value`/`max_value`. Это каталожный факт о производственных возможностях серии, отдельный от `dimension_surcharge_rule`/`pogonazh_surcharge_rule` (которые остаются про наценку, а не про допустимость). Ровно один диапазон на пару (коллекция, ось).
- **Обязательный порядок проверки нестандартного размера полотна**: (1) совпадение со стандартной каталожной опцией — наценки нет, как сейчас; (2) если для коллекции этого полотна задан диапазон для этой оси — значение вне `[min_value, max_value]` отклоняется немедленно, до любой попытки найти наценку; (3) если диапазон допускает значение (или диапазон для этой коллекции/оси не задан — см. Impact) — наценка ищется как раньше (`dimension_surcharge_rule`, включая каскад для высоты).
- **Единый понятный текст ошибки** для обоих случаев отказа (значение вне диапазона серии ИЛИ внутри диапазона, но без применимого правила наценки) — заменяет текущее «фабрика не производит полотно с размером X мм для этой оси» на «Данная нестандартная величина не поддерживается для данной модели».
- **Каталог отдаёт диапазон клиенту заранее**: `GET /api/door-configurations` — `ComponentCatalogDto` полотна дополняется списком диапазонов (по одной записи на ось, если для коллекции этой модели она задана).
- **Frontend подсвечивает диапазон** рядом с полем нестандартного значения длины/высоты полотна (например: «Доступно: 1900–2900 мм»), используя данные, уже загруженные с каталогом (не константа в коде фронтенда — значения различаются по сериям и должны совпадать с тем, что реально проверяет backend). При отклонении запроса backend с новым текстом ошибки — этот же текст показывается клиенту.

## Capabilities

### Modified Capabilities
- `door-collection-catalog`: добавляется структура `collection_dimension_range` — диапазон допустимой нестандартной длины/высоты полотна по коллекции и оси размера.
- `door-configuration-api`: резолв наценки за нестандартный размер полотна дополняется проверкой диапазона серии (перед поиском наценки); текст ошибки для недопустимого значения размера полотна меняется на единый понятный текст.
- `door-configuration-catalog`: каталог компонентов (`GET /api/door-configurations`) дополнительно отдаёт диапазоны допустимой нестандартной длины/высоты для leaf-компонента (по аналогии с уже отдаваемыми исполнениями зеркала/типом полотна).
- `door-configurator-ui`: рядом с полем нестандартного значения длины/высоты полотна показывается допустимый диапазон (если он задан для коллекции); текст ошибки при отклонённом запросе показывается клиенту как есть (уже понятный).

## Impact

- Backend: новый Liquibase changelog (`CREATE TABLE collection_dimension_range` — FK на `collection` и `liner_dimension_type`, `min_value`/`max_value`, уникальность (collection_id, liner_dimension_type_id), CHECK `min_value <= max_value`); новая domain-сущность и репозиторий; правка `DoorConfigurationPricingService.resolveAxisSurchargeMultiplier` (проверка диапазона перед поиском наценки, единый текст ошибки для обоих случаев отказа); расширение `ComponentCatalogDto` (новое поле, заполняется только для полотна — по аналогии с `mirrorFinishOptions`/`glazingOptions`/`panelType`, у остальных компонентов всегда пустой список) — меняются все 3 места создания `ComponentCatalogDto` (`buildLeafComponent`, `buildFrameComponent`, `buildComponent`), так как это Java `record` с позиционным конструктором.
- Frontend: расширение типа `ComponentCatalogDto` в `api/types.ts`; новый текст-подсказка рядом с полями нестандартной длины/высоты полотна в `App.tsx`.
- **Сид-данные диапазонов включены в этот change** (уточнение по ходу реализации — изначально планировались отдельным последующим change, но реальные числа фабрика передала до архивации этого change, поэтому вошли сюда же, отдельным Liquibase changelog `0100-collection-dimension-range-seed-data.yaml`, а не правкой уже применённого `0099`): высота 1900–2950мм одинакова для всех 9 коллекций; ширина (длина, ось «ДЛИНА») — 600–1000мм для «Вертикаль», «Атмосфера», «Элегант», «Свобода», 400–1000мм для «Гармония», «Геометрия», «Сияние», «Сибирь», «Фантом».
- **Явное поведение при отсутствии диапазона для коллекции/оси**: до тех пор, пока диапазон для конкретной (коллекция, ось) не заведён, проверка диапазона для неё пропускается — резолв работает как сегодня (через `dimension_surcharge_rule`/каскад), без изменения поведения. Это осознанный выбор, чтобы ввод механизма не стал скрытым breaking change для всех уже работающих серий разом.
