## Context

Сейчас произвольная длина/высота полотна валидируется только через `dimension_surcharge_rule` (точные строки + каскад для высоты, см. предыдущие changes) — это справочник наценки, не каталога: отсутствие строки означает «попробовать каскад» либо «недопустимо», но никак не отражает физический предел конкретной серии полотна. Пользователь прямо попросил разделить два разных по смыслу факта: «что фабрика физически может произвести» (каталог, по сериям, значения стабильны и меняются редко) и «сколько это стоит» (наценка, уже существующий гибкий механизм). Числовых порогов по конкретным сериям на момент этого change нет — вводится только механизм.

`ComponentCatalogDto` — Java `record` с позиционным конструктором, три места создания (`buildComponent`, `buildFrameComponent`, `buildLeafComponent` в `DoorConfigurationCatalogService`) — уже сложившийся паттерн для «поле только у leaf, у остальных пустое/null» (`mirrorFinishOptions`, `panelType`, `glazingOptions`).

## Goals / Non-Goals

**Goals:**
- Отдельная каталожная таблица диапазона допустимой нестандартной длины/высоты по коллекции — не смешивается со строками наценки.
- Проверка диапазона происходит раньше поиска наценки и не зависит от того, найдётся ли наценка (диапазон — про допустимость, а не про цену).
- Единый понятный текст ошибки для любого случая недопустимого значения (вне диапазона серии ИЛИ без применимого правила наценки).
- Фронтенд показывает диапазон, полученный с backend, а не захардкоженное число.

**Non-Goals:**
- Не заводим сид-данные диапазонов в этом change (числа фабрика ещё не передала) — таблица остаётся пустой до отдельного будущего change.
- Не меняем сам каскадный алгоритм наценки за высоту — диапазон работает как независимая проверка раньше него, а не как его параметр.
- Не трогаем диапазоны короба/наличника/добора (`liner_dimension_option.min_value/max_value`) — это другой, уже существующий механизм для другой цели (привязка опции короба к диапазону высоты полотна), не смешиваем.

## Decisions

### Отдельная каталожная таблица `collection_dimension_range`, а не расширение `dimension_surcharge_rule`
Ровно то разделение, которое запросил пользователь: «может ли фабрика это сделать» — каталог (`collection` → `door-collection-catalog`), «сколько это стоит» — наценка (`dimension_surcharge_rule` → `dimension-surcharge-rules`). Отдельная таблица с FK на `collection` и `liner_dimension_type`, `min_value`/`max_value`, уникальность (collection_id, liner_dimension_type_id), CHECK `min_value <= max_value`. Без generated-колонок/partial-индексов — прямой DDL, как 0096/0098 (проверить на H2 всё равно перед тем, как считать это окончательным — см. tasks.md).

### Диапазон — по коллекции (серии), не по конкретной модели (leaf_type)
Пользователь явно подтвердил: порог общий на серию. `leaf_type.collection_id` уже есть и обязателен (`NOT NULL`) — резолверу и сборке каталога достаточно `leafType.getCollection().getId()`, дополнительных данных на `leaf_type` заводить не нужно.

### Отсутствие диапазона для (коллекция, ось) = проверка пропускается, а не запрещает всё
Так как это change не содержит сид-данных, любая другая трактовка («нет строки — запрещено») сделала бы ВСЕ нестандартные размеры недоступными сразу после мержа — то есть являлась бы скрытым breaking change для уже работающей функциональности. Проверка диапазона добавляется как дополнительный (опциональный) шаг: есть диапазон для этой (коллекция, ось) — проверяем; нет — ведём себя как сегодня (наценка по `dimension_surcharge_rule`/каскаду решает всё).

### Диапазон проверяется до поиска наценки, а не вместо него
Диапазон отвечает на вопрос «допустимо ли значение физически», наценка — «какой процент», это независимые проверки в фиксированном порядке: каталожный размер → диапазон коллекции (если задан) → точная наценка → каскад (для высоты) → отказ. Если значение вне диапазона — дальше идти незачем, к наценке не обращаемся вообще (не только не находим, а не пытаемся).

### `ComponentCatalogDto` — новое поле `dimensionRanges`, только у leaf
Новый `record DimensionRangeDto(ReferenceDto dimensionType, BigDecimal minValue, BigDecimal maxValue)` — по аналогии с уже существующими `minValue`/`maxValue` в `LinerDimensionOptionDto` (тот же нейминг). `ComponentCatalogDto` получает `List<DimensionRangeDto> dimensionRanges` — заполняется в `buildLeafComponent` (по одной записи на ось, для которой у коллекции этого leaf_type есть `collection_dimension_range`), везде остальные передают `List.of()`. Так как это позиционный `record`, придётся поправить оба других места создания (`buildComponent`, `buildFrameComponent`) — тот же паттерн, что уже применялся для `mirrorFinishOptions`/`glazingOptions`/`panelType`.

### Единый текст ошибки для ЛЮБОГО отказа по размеру полотна
И «вне диапазона коллекции», и «внутри диапазона, но нет применимого правила наценки» превращаются в один и тот же текст — «Данная нестандартная величина не поддерживается для данной модели» — с точки зрения клиента оба случая означают одно и то же: «так нельзя». Технически разные причины отказа не нужно различать в тексте (различаются только по месту в коде, откуда брошено исключение).

## Risks / Trade-offs

- **Молчаливая деградация функциональности без сид-данных не происходит** (см. Decision «Отсутствие диапазона — проверка пропускается»), но по той же причине само появление этого change ничего не меняет для пользователя, пока фабрика не передаст числа и они не будут заведены отдельным change — это осознанно, а не недоработка.
- **`ComponentCatalogDto` — публичный контракт ответа `GET /api/door-configurations`, аддитивное расширение** (новое поле, а не удаление/переименование существующих) — не ломает уже работающий фронтенд, но требует одновременного обновления backend/frontend типов (как и раньше при похожих расширениях).
- **Диапазон не привязан к конкретному значению каталожной длины/высоты**, только к оси в целом — если у коллекции когда-нибудь появится опция, которая физически лежит внутри диапазона, но сама по себе нежелательна, для этого понадобится отдельный механизм (не входит в этот change).
