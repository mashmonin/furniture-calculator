## Context

`ConfiguratorScreen`'s «Живая синхронизация» `useEffect` (см. `frontend/src/ConfiguratorScreen.tsx`, комментарий «Живая синхронизация открытой из корзины позиции») вызывает `buildCartItemContent()` и, только если результат не `null`, зовёт `onSyncEditedItem(editingItemId, content)` → `App.syncEditedCartItem`, которая делает `{ ...item, ...content }`. `buildCartItemContent()` требует выбранной модели полотна и готового `pricingResult` (`if (leafTypeId === undefined || !pricingResult || !leafComponent) { return null }`), поэтому пока эти условия не выполнены, синхронизация не пишет ничего — включая теги атрибутов, которые вычисляются внутри той же функции из `resolvedReverse`/`resolvedPanelType`/`resolvedMirrorFinishNeeded`/`resolvedHasQuarter`/`leafThicknessValue`/`selection.leaf.doubleSidedPainting`.

Переключатели «Реверс», «Четверть» и «Тип полотна» (`handleReverseChange`/`handleHasQuarterChange`/`handlePanelTypeChange`/`handleMirrorFinishNeededChange`) при изменении сбрасывают `selectedCollectionId`/`cascadeSelection`/`selection` — значит `leafTypeId` временно становится `undefined`, `buildCartItemContent()` возвращает `null`, и вся позиция корзины (включая теги) замирает на предыдущем снимке до повторного выбора модели.

При этом четыре из шести составляющих `resolveReverseStep`/`resolveHasQuarterStep`/`resolvePanelTypeStep`/`resolveMirrorFinishNeededStep` (строки ~1081–1113 в `ConfiguratorScreen.tsx`) вычисляются из каталога и состояния переключателей ДО того, как модель полотна вообще выбрана — то есть уже доступны в момент, когда `buildCartItemContent()` ещё возвращает `null`.

## Goals / Non-Goals

**Goals:**
- «РЕВЕРС», «ЧЕТВЕРТЬ», «ОСТЕКЛЕНИЕ», «ЗЕРКАЛО» у открытой из корзины позиции отражают текущее состояние соответствующих переключателей немедленно — без ожидания повторного выбора модели полотна и новой цены.
- «ТОЛЩИНА 59»/«ДВУСТОРОННЯЯ» никогда не показывают устаревшее значение — либо текущее (когда модель выбрана и известна), либо не показываются вовсе (когда неизвестна).
- Не трогать остальную синхронизацию (цена, детализация, наименование, параметры) — она по-прежнему ждёт полной валидной конфигурации, это подтверждённое пользователем поведение (см. proposal.md).

**Non-Goals:**
- Не пытаться сохранить «Толщина 59»/«Двусторонняя» на время переходного состояния каким-либо приближением (например, последним известным значением) — пользователь явно выбрал показывать только то, что действительно вычислимо прямо сейчас.
- Не меняется структура `CartItem`/`CartItemContent`/`localStorage` — `attributeTags` остаётся тем же полем `string[]`, просто получает дополнительный, более ранний путь обновления.
- Не трогается поведение при изменениях, не сбрасывающих каскад (цвет, кромка, короб, декоративные элементы, фурнитура) — там `buildCartItemContent()` и так успешно возвращает полный результат сразу, дополнительный путь для них не нужен.

## Decisions

**Отдельный, более ранний вычисляемый список «кросс-модельных» тегов вместо изменения гейта `buildCartItemContent`.** Альтернатива — ослабить условие `if (leafTypeId === undefined || !pricingResult || !leafComponent) return null`, чтобы `buildCartItemContent()` возвращала частичный результат без цены/детализации. Отклонено: это расползлось бы по всей функции (каждое поле результата пришлось бы делать optional и разбираться, что показывать вместо него в `CartScreen`), тогда как нужны только теги. Вместо этого — маленькая чистая функция уровня компонента (например, `cascadeIndependentAttributeTags()`), использующая только `resolvedReverse`/`resolvedHasQuarter`/`resolvedPanelType`/`resolvedMirrorFinishNeeded` (уже вычислены к моменту, когда модель ещё не выбрана), возвращающая ровно те теги, что не зависят от выбранной модели.

**Новый колбэк `onSyncEditedItemTags(id, tags)` рядом с `onSyncEditedItem`, а не расширение существующего.** `App.syncEditedCartItem` заменяет весь `CartItemContent` (`{ ...item, ...content }`) — переиспользовать его для частичного обновления одного поля означало бы либо пропускать через него неполный/фиктивный `CartItemContent` (хрупко, легко случайно затереть другие поля `undefined`), либо явно мержить только `attributeTags`. Отдельная маленькая функция `syncEditedCartItemTags(id, tags)` в `App.tsx`, делающая `{ ...item, attributeTags: tags }`, — самый явный вариант, без риска задеть остальные поля.

**Условие показа «Толщина 59»/«Двусторонняя»: скрывать, пока модель не переизбрана.** Рассматривался вариант «оставлять последнее известное значение до пересчёта» — отклонён пользователем явно (см. проясняющий вопрос в /opsx:propose): показ старого значения — та же самая ошибка, которую чинит этот change, просто для двух конкретных тегов вместо всех шести. Раз для этих двух тегов недостающие данные (выбранная модель) сейчас объективно отсутствуют, единственный не вводящий в заблуждение вариант — не показывать их, пока модель не выбрана заново.

**Триггер синхронизации тегов — тот же набор зависимостей, что уже есть у эффекта «Живая синхронизация», плюс сам список тегов.** Не нужен отдельный `useEffect` с полностью новым списком зависимостей: тегов-синхронизация может быть частью того же эффекта (вызывается безусловно, до или вместо гейта `if (content)`), либо соседним эффектом с подмножеством тех же зависимостей (`editingItemId`, `resolvedReverse`, `resolvedHasQuarter`, `resolvedPanelType`, `resolvedMirrorFinishNeeded`) — конкретная реализация (один эффект или два) оставлена на этап реализации (tasks.md), это не влияет на наблюдаемое поведение.

## Risks / Trade-offs

[Два независимых пути записи в один и тот же `CartItem.attributeTags` (частичный — только теги, и полный — из `buildCartItemContent()`) могут разойтись в порядке выполнения между рендерами] → оба пути детерминированно вычисляют одно и то же значение тегов из одного и того же состояния конфигуратора на момент вызова; когда `buildCartItemContent()` успешно возвращает результат, его `attributeTags` уже включает все шесть тегов (включая «Толщина 59»/«Двусторонняя») и полностью перезаписывает то, что записал частичный путь — расхождения не возникает, частичный путь только заполняет паузу до этого момента.

[Дополнительная запись в `localStorage` при каждом переключении «Реверс»/«Четверть»/«Тип полотна», даже если модель потом не будет переизбрана] → та же цена, что уже платится существующей синхронизацией при каждом изменении конфигурации (`saveCart` уже вызывается на каждое изменение, пока открыт режим редактирования) — не новый паттерн, просто на один дополнительный (частичный) вызов больше в переходный период.
