## Context

См. proposal.md - Why. Сейчас leaf_type (`backend/.../domain/LeafType.java`) не хранит информацию о конструктивном типе полотна. Единственный существующий механизм, пересекающийся по смыслу, — `mirror_finish_type`/`mirror_finish_option` (наценка-исполнение зеркала поверх leaf_type), который этим change не меняется.

## Goals / Non-Goals

**Goals:**
- Дать leaf_type обязательный атрибут «тип полотна» с тремя значениями: глухое / остеклённое / с зеркалом.
- Корректно заполнить его для существующих данных без ручного вмешательства.
- Отдать значение в каталоге конфигураций для leaf-компонента.

**Non-Goals:**
- Наценка или иная функциональная логика для остеклённых полотен.
- Отдельный справочник видов остекления (аналог mirror_finish_type).
- Изменение существующих таблиц/API mirror_finish_type, mirror_finish_option.
- Отображение или фильтрация по типу полотна во frontend.

## Decisions

- **Представление в БД**: новая колонка `panel_type` типа `varchar` в таблице `leaf_type`, NOT NULL, с `CHECK (panel_type IN ('BLIND', 'GLAZED', 'MIRRORED'))` — тот же стиль ограничения набора значений, что уже используется в схеме (см. `chk_*_single_owner` constraints в существующих changelog'ах). Отдельная справочная таблица не вводится, так как набор значений фиксирован, мал и не имеет собственных атрибутов (в отличие от mirror_finish_type, где у каждого исполнения есть наценка) — заводить для него полноценный CatalogType было бы избыточно.
  - Альтернатива (отклонена): отдельная таблица `leaf_panel_type` по образцу других справочников (`CatalogType`) — избыточна, пока значение не обрастает собственными атрибутами.
- **Java-представление**: поле `panelType` в `LeafType` с Java enum `LeafPanelType { BLIND, GLAZED, MIRRORED }`, замаппленным через `@Enumerated(EnumType.STRING)` — первый enum в domain-слое проекта, но это стандартный и наименее многословный способ представить фиксированный набор значений с проверкой на этапе компиляции; альтернатива (голая String-константа) отклонена как менее безопасная без явного выигрыша.
- **Backfill существующих данных**: в одном changeset — добавить колонку без default, затем `UPDATE leaf_type SET panel_type = 'MIRRORED' WHERE id IN (SELECT DISTINCT leaf_type_id FROM mirror_finish_option)`, затем `UPDATE leaf_type SET panel_type = 'BLIND' WHERE panel_type IS NULL` (остеклённых моделей сейчас нет), затем `ALTER COLUMN panel_type SET NOT NULL`. Порядок гарантирует отсутствие NULL на момент применения ограничения.
- **Место в API-ответе**: поле добавляется в leaf-часть `ComponentCatalogDto` (или в саму `ReferenceDto` leaf_type, если так проще сохранить симметрию с существующими полями id/code/name/shortName) — заполняется только для leaf-компонента, как и другие leaf-специфичные поля (например, список исполнений зеркала).

## Risks / Trade-offs

- [Первый enum в domain-слое, где раньше везде были справочные таблицы или простые строки] → осознанное отклонение от предыдущего паттерна, обосновано выше; если позже потребуется добавить атрибуты к значению (например, наценку за остекление), тип можно будет мигрировать в полноценный CatalogType-справочник отдельным change, не меняя внешний контракт API (тот же список из трёх строк, просто из другого источника).
- [Backfill полагается на текущее состояние mirror_finish_option на момент применения миграции] → миграция детерминирована и идемпотентна (основана на данных, а не на ручном списке id), запускается один раз при выкатке этого change.

## Migration Plan

1. Liquibase changeset: добавить колонку `panel_type` (nullable), выполнить backfill-UPDATE'ы по правилу выше, затем установить NOT NULL и CHECK constraint.
2. Обновить `LeafType`, добавить enum `LeafPanelType`, обновить `ComponentCatalogDto`/маппинг в `DoorConfigurationCatalogService`.
3. Откат: отдельный down-changeset, удаляющий constraint и колонку (данные mirror_finish_option не затрагиваются и не требуют отката).
