## Why

Система различает модели полотна (leaf_type) только по коллекции и коду, но не по конструктивному типу самого полотна. Фабрика классифицирует полотна как глухие (сплошные), остеклённые (со вставкой из стекла) и с зеркалом (зеркальное исполнение на одной из сторон). Сейчас «зеркало» существует только как необязательная наценка-исполнение поверх любого подходящего leaf_type (`mirror_finish_type`/`mirror_finish_option`), а понятия «глухое» и «остеклённое» как конструктивного типа полотна в системе нет вовсе — это мешает вести и в дальнейшем расширять каталог полотен по их фактической конструкции.

## What Changes

- Добавить у leaf_type атрибут «тип полотна» (panel_type) с тремя взаимоисключающими значениями: глухое, остеклённое, с зеркалом. Атрибут обязателен для каждой строки leaf_type.
- Значение — чистая классификация: этим изменением не вводится ни отдельный справочник видов остекления, ни наценка за остекление, ни какая-либо иная функциональная логика (расчёт стоимости, валидация запроса) для типа полотна. Наценка и детализация остекления (если понадобятся) — предмет отдельного будущего change, по аналогии с тем, как раньше отдельным change добавлялась наценка за исполнение зеркала.
- Отношение к существующему `mirror_finish_type`/`mirror_finish_option` не меняется: эти таблицы и их API остаются как есть. Значение «с зеркалом» у нового атрибута — производное от существующих данных (проставляется тем leaf_type, у которых уже есть хотя бы одна строка mirror_finish_option), а не новый параллельный механизм.
- Первоначальное заполнение (backfill): всем существующим leaf_type, для которых нет ни одной строки mirror_finish_option, атрибут проставляется как «глухое» — остеклённых моделей в каталоге сейчас нет, признак «остеклённое» появится только тогда, когда в каталог будет добавлена соответствующая модель полотна.
- Тип полотна отдаётся в ответе каталога конфигураций (`GET /api/door-configurations`) для leaf-компонента — аналогично тому, как уже отдаются данные коллекции и допустимые исполнения зеркала.
- Frontend и расчёт стоимости этим изменением не затрагиваются — отображение типа полотна в интерфейсе конфигуратора остаётся вне рамок (может быть добавлено отдельным change).

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `door-configuration-catalog`: у leaf_type появляется обязательный атрибут «тип полотна» (глухое / остеклённое / с зеркалом); ответ каталога конфигураций дополняется этим атрибутом для leaf-компонента.

## Impact

- **БД**: новый Liquibase changeset — новая колонка `panel_type` в таблице `leaf_type` (обязательная, с ограничением на набор допустимых значений) + миграция данных: для leaf_type без строк `mirror_finish_option` — значение «глухое», для leaf_type со строками `mirror_finish_option` — значение «с зеркалом».
- **Backend**: сущность `LeafType` — новое поле panel_type; `ComponentCatalogDto` (или его leaf-часть) — новое поле с типом полотна, заполняется для leaf-компонента.
- **Frontend**: изменений нет.
- Наценка за остекление, справочник видов остекления и отображение типа полотна в UI — вне рамок этого change.
