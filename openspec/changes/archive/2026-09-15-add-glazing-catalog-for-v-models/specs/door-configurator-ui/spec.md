## ADDED Requirements

### Requirement: Выбор вида остекления
Система ДОЛЖНА (SHALL) отображать выпадающий список «Вид остекления» только тогда, когда выбранный тип полотна — «Остеклённое» (см. «Сужение каскада по типу полотна») — в одном ряду с каскадным шагом выбора модели полотна («Полотно»), там же, где для типа «Зеркальное» отображается выбор исполнения зеркала (см. «Выбор конкретного исполнения зеркала»). Варианты списка — все виды остекления (glazing_type), встречающиеся хотя бы в одной строке glazing_option среди согласованных door_configuration. Выбор конкретного вида остекления НЕ ДОЛЖЕН (SHALL NOT) сужать согласованные door_configuration и НЕ ДОЛЖЕН (SHALL NOT) передаваться в запрос расчёта стоимости — это только отображение справочных значений и локальный выбор пользователя.

#### Scenario: Список появляется рядом с выбором модели полотна, ничего не выбрано по умолчанию
- **WHEN** клиент выбирает тип полотна «Остеклённое»
- **THEN** в одном ряду с шагом выбора модели полотна («Полотно») появляется выпадающий список «Вид остекления» со всеми видами, встречающимися среди согласованных door_configuration, и ни один вариант не выбран

#### Scenario: Список — выпадающий, а не ряд кнопок
- **WHEN** отображается список «Вид остекления»
- **THEN** он показывается выпадающим списком (как «Коллекция» или «Цвет»), а не рядом кнопок-сегментов (как «Исполнение с зеркалом»)

#### Scenario: Выбор вида остекления не сужает каталог
- **WHEN** выбран тип полотна «Остеклённое» и клиент выбирает конкретный вид остекления
- **THEN** шаг выбора коллекции и все последующие шаги продолжают показывать полный набор, согласованный с типом полотна «Остеклённое» — сужения по выбранному виду остекления не происходит

#### Scenario: Выбор вида остекления не сбрасывает уже сделанный выбор
- **WHEN** клиент уже выбрал коллекцию, модель полотна и, возможно, опции размеров/цвета, а затем выбирает (или меняет) вид остекления
- **THEN** ранее выбранные коллекция, модель полотна и введённые опции сохраняются без изменений — в отличие от смены типа полотна или коллекции, выбор вида остекления не запускает сброс каскада (см. также «Выбор конкретного исполнения зеркала», где по той же причине больше не сбрасывается каскад)

#### Scenario: Вид остекления не передаётся в запрос расчёта
- **WHEN** клиент выбрал конкретный вид остекления и активирует расчёт стоимости
- **THEN** запрос расчёта отправляется без указания вида остекления для leaf-компонента

#### Scenario: Список скрыт для остальных типов полотна
- **WHEN** выбранный тип полотна — «Глухое» или «Зеркальное»
- **THEN** выпадающий список «Вид остекления» не отображается

### Requirement: Выбор конкретного исполнения зеркала
Система ДОЛЖНА (SHALL) отображать шаг выбора конкретного исполнения зеркала только тогда, когда выбранный тип полотна — «Зеркальное» (см. «Сужение каскада по типу полотна») — в одном ряду с каскадным шагом выбора модели полотна («Полотно»), рядом с ним, а не отдельным блоком в другом месте потока. Варианты этого шага — все исполнения зеркала (mirror_finish_type), встречающиеся хотя бы в одной строке mirror_finish_option среди согласованных door_configuration; никакого отдельного варианта «без зеркала» в этом шаге нет — выбор любого другого типа полотна уже покрывает этот случай. Выбор конкретного исполнения зеркала НЕ ДОЛЖЕН (SHALL NOT) сужать согласованные door_configuration и НЕ ДОЛЖЕН (SHALL NOT) сбрасывать уже сделанный выбор коллекции, модели полотна или введённых опций — он используется только в запросе расчёта стоимости (наценка за исполнение).

#### Scenario: Шаг появляется с вариантами, ничего не выбрано по умолчанию
- **WHEN** клиент выбирает тип полотна «Зеркальное»
- **THEN** в одном ряду с шагом выбора модели полотна («Полотно») появляется шаг выбора исполнения зеркала со всеми исполнениями, встречающимися среди согласованных door_configuration, и ни один вариант не выбран

#### Scenario: Выбор исполнения не сужает каталог
- **WHEN** выбран тип полотна «Зеркальное» и клиент выбирает конкретное исполнение зеркала
- **THEN** шаг выбора коллекции и все последующие шаги продолжают показывать полный набор, согласованный с типом полотна «Зеркальное» — сужения по выбранному исполнению не происходит

#### Scenario: Изменение исполнения зеркала не сбрасывает уже сделанный выбор
- **WHEN** клиент уже выбрал коллекцию, модель полотна и, возможно, опции размеров/цвета, а затем выбирает или меняет исполнение зеркала
- **THEN** ранее выбранные коллекция, модель полотна и введённые опции сохраняются без изменений

#### Scenario: Выбранное исполнение зеркала передаётся в запрос расчёта
- **WHEN** клиент выбрал конкретное исполнение зеркала и активирует расчёт стоимости
- **THEN** в запрос расчёта стоимости для leaf-компонента передаётся id выбранного исполнения зеркала

#### Scenario: Тип полотна, отличный от «Зеркальное», не передаёт исполнение зеркала в запрос расчёта
- **WHEN** выбранный тип полотна — «Глухое» или «С остеклением», и активируется расчёт стоимости
- **THEN** запрос расчёта отправляется без указания исполнения зеркала для leaf-компонента

## REMOVED Requirements

### Requirement: Выбор исполнения зеркала
**Reason**: две из пяти сценариев этого требования утверждали поведение, которое либо никогда не было реализовано (сужение каталога по выбранному исполнению зеркала отпало при переходе на сужение по «Тип полотна», см. change `filter-by-leaf-panel-type`, но спецификация не была обновлена), либо оказалось нежелательной регрессией (сброс уже выбранной модели полотна и опций при каждой смене исполнения — по обратной связи пользователя, тот же баг, что и у вида остекления). Заменено требованием «Выбор конкретного исполнения зеркала» в этом же change, отражающим фактическое и исправленное поведение.
**Migration**: наблюдаемое поведение выбора исполнения зеркала становится мягче — выбор больше не сужает список коллекций (он никогда фактически не сужал) и не сбрасывает уже сделанный выбор модели/опций (раньше сбрасывал — это было исправлено как баг). Передача исполнения в запрос расчёта стоимости не меняется.
