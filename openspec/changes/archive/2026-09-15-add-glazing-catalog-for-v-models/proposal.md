## Why

Change `add-leaf-panel-type` ввёл тип полотна «остеклённое» как значение в перечислении, но реальных остеклённых моделей в каталоге до сих пор нет (0 leaf_type с этим типом), а справочника видов остекления никогда не существовало — это было сознательно отложено. Теперь нужно ввести первую партию реальных остеклённых моделей: 12 конкретных моделей полотна из коллекций Гармония, Геометрия, Свобода и Элегант (все с суффиксом V/G в названии — витражные модели) сейчас классифицированы как «Зеркальное» только потому, что для них исторически заведены исполнения зеркала наравне со всей коллекцией; по факту это остеклённые модели, и их нужно переклассифицировать.

## What Changes

- Добавить справочник видов остекления (`glazing_type`) — шесть вариантов: «Прозрачное», «Прозрачное серое», «Прозрачное бронза», «Сатинированное», «Сатинированное серое», «Сатинированное бронзовое». Без наценки к цене полотна (решение по предыдущему обсуждению — наценка, если понадобится, добавляется отдельным change, как это в своё время было сделано для зеркала).
- Добавить таблицу владения `glazing_option` (какие leaf_type допускают какие виды остекления) — по образцу `mirror_finish_option`.
- Для 12 конкретных моделей — ГЕОМЕТРИЯ 01V, ГЕОМЕТРИЯ 02V, СВОБОДА 01V, СВОБОДА 02V, СВОБОДА 021V, СВОБОДА 01G, ГАРМОНИЯ 01V, ГАРМОНИЯ 02V, ГАРМОНИЯ 021V, ЭЛЕГАНТ 01V, ЭЛЕГАНТ 02V, ЭЛЕГАНТ 021V — завести строки `glazing_option` на все шесть видов остекления (72 строки) и сменить их `panel_type` на «остеклённое».
- **BREAKING (данные каталога)**: у этих же 12 моделей удаляются все строки `mirror_finish_option` (36 строк, по 3 исполнения на модель) — по правилу «leaf_type имеет ровно один тип полотна» модель не может одновременно быть «Зеркальное» и «Остеклённое». Это подтверждённое решение: эти 12 моделей перестают быть доступны с зеркалом и становятся доступны с остеклением.
- Каталог конфигураций (`GET /api/door-configurations`) отдаёт для leaf-компонента список допустимых видов остекления — аналогично тому, как уже отдаются допустимые исполнения зеркала.
- **Дополнено по обратной связи после первой реализации**: вид остекления отображается на фронте — выпадающим списком (`Select`), в том же ряду, где сейчас отображается выбор исполнения зеркала (рядом с шагом выбора модели полотна «Полотно»); раскрывается только когда выбранный тип полотна — «Остеклённое». В отличие от исполнения зеркала, выбор конкретного вида остекления НЕ сужает каталог и НЕ передаётся в запрос расчёта стоимости — backend пока не принимает его (наценки за остекление нет, см. Impact); это осталось вне рамок.
- **Вне рамок этого change**: выбор конкретного вида остекления в запросе расчёта стоимости и наценка за остекление — backend для этого не дорабатывается; сам вид остекления на фронте только отображается и локально выбирается.
- **Попутно исправлен баг (по той же обратной связи)**: выбор вида остекления был по ошибке скопирован с поведения «Исполнение с зеркалом» и сбрасывал уже выбранную модель полотна/коллекцию/опции при каждой смене — убрано. При проверке выяснилось, что тот же самый сброс годами жил и в самом выборе исполнения зеркала (`handleMirrorFinishTypeChange`), хотя реального сужения каталога по исполнению зеркала в коде нет и не было со времён `filter-by-leaf-panel-type` — исправлено там же, и соответствующее требование спецификации приведено в соответствие с фактическим поведением.

### New Capabilities

(нет)

### Modified Capabilities

- `door-configuration-catalog`: новые сущности `glazing_type` (шесть видов остекления, без наценки) и `glazing_option` (владение — какие leaf_type допускают какие виды остекления); каталог конфигураций отдаёт допустимые виды остекления для leaf-компонента; 12 конкретных leaf_type (коды перечислены в спецификации) переклассифицируются с «Зеркальное» на «Остеклённое», их строки `mirror_finish_option` удаляются.
- `door-configurator-ui`: выпадающий список «Вид остекления» отображается в одном ряду с выбором модели полотна («Полотно»), только когда выбранный тип полотна — «Остеклённое»; выбор — чисто локальный, не сужает каталог и не передаётся в запрос расчёта стоимости. Требование «Выбор исполнения зеркала» заменено на «Выбор конкретного исполнения зеркала»: убраны неверные утверждения о сужении каталога (никогда не было реализовано) и сбросе выбора модели/опций (был баг, исправлено).

## Impact

- **БД**: новый Liquibase changeset — таблицы `glazing_type` (id, name) и `glazing_option` (id, glazing_type_id, leaf_type_id, unique по паре) + данные: 6 видов остекления; 72 строки `glazing_option` (12 моделей × 6 видов); удаление 36 строк `mirror_finish_option` для этих 12 моделей; `UPDATE leaf_type SET panel_type = 'GLAZED'` для них же.
- **Backend**: новые сущности `GlazingType`/`GlazingOption` + репозиторий; `ComponentCatalogDto` — новое поле со списком допустимых видов остекления (заполняется только для leaf, по образцу `mirrorFinishOptions`); `DoorConfigurationCatalogService` — заполнение этого поля. Попутно исправлена уже существовавшая проблема производительности этого сервиса (N+1 запросы на каждую из тысяч строк `door_configuration` вместо одного раза на уникальный `leaf_type`/`frame_type`/... — без дедупликации каталог отдавался за 35–67 с); чистый рефактор без изменения контракта API, отдельного change не потребовал.
- **Frontend**: `api/types.ts` — новое поле `glazingOptions` в `ComponentCatalogDto`; `App.tsx` — `resolveGlazingStep` (по образцу `resolveMirrorFinishStep`), состояние `glazingTypeId`, выпадающий список «Вид остекления» рядом с шагом «Полотно», видимый только при типе полотна «Остеклённое». Существующий переключатель «Тип полотна» уже умел показывать и сужать по значению «С остеклением» (см. `filter-by-leaf-panel-type`) — это не менялось.
