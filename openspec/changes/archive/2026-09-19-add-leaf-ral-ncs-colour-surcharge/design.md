## Context

`ColourType` (`colour_type`) сейчас — чисто справочная сущность (`id`, `name`, `code`, опционально `short_name`), без какого-либо влияния на цену: она участвует только в подборе наиболее специфичной строки `configuration_price` (см. `findMostSpecificPrice`). `ColourOption` связывает `colour_type` с ровно одним владельцем (`leaf_type`/`frame_type`/`edge_type`/`door_casing_type`/`frame_extensions_type`); в запросе расчёта клиент передаёт `colourOptionId` (id строки `colour_option`), а не id `colour_type` напрямую.

Это структурно отличается от `mirror_finish_type`/`glazing_type`, у которых уже есть `surcharge_percent`, и клиент в запросе расчёта передаёт id самого типа (`mirrorFinishTypeId`/`glazingTypeId`), а не id строки владения. Наценка для них резолвится через `resolveMirrorFinishMultiplier`/`resolveGlazingMultiplier` (см. `DoorConfigurationPricingService`) и попадает в `applySequentialSurcharges` (текущий порядок: длина → высота → зеркало → остекление → реверс → [отдельно, на компонентах погонажа] погонаж).

## Goals / Non-Goals

**Goals:**
- Добавить `surcharge_percent` в `colour_type`, не меняя существующий контракт запроса расчёта (цвет по-прежнему выбирается через `colourOptionId`).
- Применить наценку за цвет к цене leaf-компонента, встроив её в уже существующую последовательную цепочку наценок.
- Отдать проценты наценки по цветам через `GET /api/pricing-surcharges`, чтобы фронтенд не пересчитывал их из итоговой цены.

**Non-Goals:**
- Не меняется контракт запроса расчёта стоимости (`colourOptionId` остаётся id `colour_option`, новых полей запроса не вводится).
- Наценка не вводится как отдельная таблица правил (по аналогии с `dimension_surcharge_rule`/`pogonazh_surcharge_rule`) — используется тот же паттерн «процент как атрибут типа», что у `mirror_finish_type`/`glazing_type`, так как наценка привязана к конкретному значению цвета, а не к диапазону/владельцу.
- Не вводится новый раздел/формат в `SpecificationExportService` сверх уже существующего механизма: наценка за цвет добавляется в тот же список `leafPriceSurcharges`, что уже используют зеркало и остекление (при реализации выяснилось, что они ТАМ уже фигурируют — см. секцию «Надбавки» выгрузки — это уточнение исходного предположения, а не новый функционал).

## Decisions

### Наценка резолвится из уже загруженного colourOption, без нового параметра запроса
В отличие от зеркала/остекления (новые request-поля `mirrorFinishTypeId`/`glazingTypeId`, валидируемые через `resolveMirrorFinishMultiplier`/`resolveGlazingMultiplier`), цвет уже полностью резолвится существующим кодом (`validatedColourOption`) для получения `ColourOption`. Новый шаг просто читает `colourOption.getColourType().getSurchargePercent()` у уже полученного объекта — без дополнительного запроса к репозиторию и без изменения `ComponentSelectionDto`/`ColourOptionDto`/валидации владения.

Альтернатива (отклонена): ввести отдельный `colourTypeId` в запрос, как у зеркала/остекления. Отклонено — это дублировало бы уже существующий канал выбора цвета (`colourOptionId`) и потребовало бы двух независимых полей для одного и того же выбора.

### Место в последовательности наценок: сразу после высоты, до зеркала и остекления
Цвет — более базовый атрибут полотна (выбирается почти всегда, когда у полотна вообще есть цвета), тогда как зеркало и остекление — опциональные исполнения, накладываемые поверх уже выбранного цвета. Итоговый порядок: длина → высота → **цвет** → зеркало → остекление → реверс. Как и у существующих шагов, округление происходит после каждого шага, поэтому порядок влияет на итоговую сумму в пограничных случаях.

Это встраивается по уже установленному в проекте паттерну: каждое добавление нового вида наценки к цепочке (зеркало, затем остекление) вводило собственное requirement «Место наценки за X в последовательности надбавок», полностью переопределяющее порядок на момент своего появления, не переписывая предыдущие requirements. Новое requirement для цвета продолжает эту цепочку.

### `ColourSurchargeDto` и `colourSurcharges` в `PricingSurchargesDto` — по образцу `GlazingSurchargeDto`/`glazingSurcharges`
Новый DTO `ColourSurchargeDto(Long id, String name, BigDecimal surchargePercent)`, новое поле `List<ColourSurchargeDto> colourSurcharges` в `PricingSurchargesDto`, заполняется из `colourTypeRepository.findAll()` — полный список всех `colour_type`, а не только «нестандартного» цвета (аналогично тому, как `glazingSurcharges` отдаёт все виды остекления, включая «Прозрачное» с 0%).

Фронтенду для отображения наценки требуется двухшаговый lookup (в отличие от зеркала/остекления, где id из ответа `calculate()`/каталога — это сразу id типа): `colourOptionId` (выбран клиентом) → найти в `leafComponent.colourOptions` соответствующий `colourOption.colourType.id` → найти этот id в `pricingSurcharges.colourSurcharges` → взять `surchargePercent`. Это следствие уже существующей, не меняемой этим change структуры `ColourOptionDto`, а не новая асимметрия, вносимая этим change.

### Схема миграций: добавление колонки отдельно от сид-данных
По аналогии с 0090/0091 (`glazing_type`/`glazing_type.surcharge_percent`), но `colour_type` уже существует (в отличие от `glazing_type`, который создавался с нуля), поэтому нужен только шаг, эквивалентный 0091:
1. Новая миграция — добавить nullable `surcharge_percent DECIMAL` в `colour_type`; backfill всех существующих строк в 0; добавить `NOT NULL` constraint (три шага одного changelog, как в 0091).
2. Отдельная миграция сид-данных — вставить новую строку `colour_type` («Другой цвет из коллекции RAL и NCS», код `CT-029`, `surcharge_percent = 20`) и строки `colour_option`, связывающие её с каждым `leaf_type` коллекций LC-001–LC-007 (динамический `INSERT ... SELECT` по `collection.code IN (...)`, как в 0101, а не перечисление конкретных id).

Разделение на два changelog (структура / данные) сделано по прямому прецеденту 0090+0091 и 0100+0101 в этом проекте — упрощает будущий откат/повтор сид-данных отдельно от структуры.

## Risks / Trade-offs

- [Двухшаговый lookup на фронтенде (colourOptionId → colourTypeId → percent) чуть сложнее, чем прямой lookup у зеркала/остекления] → Изолируется в один helper внутри `computeSurchargeBreakdown`, аналогичный уже существующим `matchesStandardDimension`/поиску по `mirrorFinishSurcharges`; риск ограничен читаемостью одной функции, не архитектурой.
- [Новый шаг в `applySequentialSurcharges` меняет итоговую (округлённую) цену в кейсах, где одновременно нестандартны высота и выбран новый цвет, по сравнению с гипотетическим другим порядком] → Порядок закреплён явным requirement с конкретным сценарием округления, так же как для зеркала и остекления; расхождение ожидаемо и тестируется.
- [Данные: наценка 20% должна применяться только к одной конкретной строке `colour_type`, а не по имени/коду на лету] → `surcharge_percent` — атрибут строки в БД, а не логика по имени; ошибиться в резолвинге можно только при неверных сид-данных, что покрывается сценарием «Позиция заведена с наценкой 20%» в specs.
