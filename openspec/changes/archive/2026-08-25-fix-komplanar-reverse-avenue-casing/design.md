## Context

См. proposal.md — Why/What Changes. Ключевые факты из текущей кодовой базы:

- `door_casing_type` — плоский справочник (`id`, `name`, `code`), без ссылки на `frame_type`: совместимость наличника с коробом выражается исключительно наличием соответствующих строк `door_configuration`, а не полем на самом типе.
- Миграция `0028-komplanar-reverse-avenue-casing-configurations.yaml` (уже применена и закоммичена) вставила 13 строк `door_configuration`, связавших все реверс-модели полотна (короб FT-004) с существующим `door_casing_type` «Авеню» (DCT-002, заведён миграцией `0005`, цена — миграцией `0010`).
- Code-префикс `door_casing_type`: DCT- (последний DCT-004, «Онда»).
- Проект запрещает редактировать уже применённые и закоммиченные changeset'ы задним числом — исправление оформляется новой миграцией (см. CLAUDE.md).

## Goals / Non-Goals

**Goals:**
- Завести отдельную каталожную позицию наличника для системы КОМПЛАНАР РЕВЕРС, не смешанную с обычным «Авеню».
- Переключить 13 существующих `door_configuration` (реверс-модели + FT-004) на новый тип наличника вместо DCT-002, сохранив те же id конфигураций и ту же цену.
- Гарантировать, что новый тип наличника не появится ни в одной `door_configuration` с другим коробом (кроме FT-004).

**Non-Goals:**
- Не меняем схему `door_casing_type`/`door_configuration` — используется тот же плоский паттерн, что и для остальных типов наличника.
- Не меняем стоимость — переносится то же значение (3622 ₽ retail / 2070 ₽ dealer при высоте 2100 мм), что фабрика называла для «Авеню».
- Не трогаем существующие связи DCT-002 с обычным коробом КОМПЛАНАР (FT-002, миграция `0011`) и другие её использования — они остаются как есть.

## Decisions

### Новая миграция вместо правки 0028
`0028` уже применена локально и закоммичена в git (коммит `942f427`). Правка задним числом запрещена конвенцией проекта. Новая миграция `0029`:
1. Вставляет новый `door_casing_type` «Авеню для системы КОМПЛАНАР РЕВЕРС \*» (код `DCT-005`).
2. Вставляет для него `liner_dimension_option` (высота 2100 мм) и `configuration_price` (3622/2070) — по образцу того, как это сделано для DCT-002 в `0010`.
3. `UPDATE door_configuration SET door_casing_type_id = <DCT-005> WHERE frame_type_id = <FT-004> AND door_casing_type_id = <DCT-002>` — точечно исправляет только те 13 строк, что были ошибочно заведены `0028` (условие по обоим id гарантирует, что затронутся именно они, а не любые другие связи DCT-002).

Рассмотрен альтернативный вариант — удалить 13 строк из `0028` и вставить заново с новым `door_casing_type_id`. Отклонён: `UPDATE` по точному предикату (`frame_type_id` + старый `door_casing_type_id`) достигает того же результата за один шаг, без риска рассинхронизации id и без даунтайма по внешним ссылкам (если появятся заказы/item-конфигурации на эти door_configuration — их id не меняются).

### Отдельная цена и опция высоты, а не переиспользование строк DCT-002
`configuration_price`/`liner_dimension_option` физически принадлежат ровно одному владельцу (`chk_*_single_owner`) — переиспользовать строки DCT-002 для DCT-005 невозможно на уровне схемы, только дублировать значения с новым `door_casing_type_id`. Значения (2100 мм, 3622/2070) копируются один в один из `0010`.

## Risks / Trade-offs

- **[Trade-off] Дублирование цены между DCT-002 и DCT-005** — если фабрика позже изменит цену «Авеню», её нужно будет обновить в двух местах. Осознанно: это те же две независимые каталожные позиции, что и у фабрики (разные строки прайс-листа), не искусственное дублирование.
- **[Риск] `UPDATE`-миграция должна точно отобрать только 13 ошибочных строк** → Смягчение: предикат по обеим ссылкам (`frame_type_id = FT-004 AND door_casing_type_id = DCT-002`) однозначно совпадает с тем, что вставила `0028`, и ни с чем другим (DCT-002 больше нигде не пересекается с FT-004).
