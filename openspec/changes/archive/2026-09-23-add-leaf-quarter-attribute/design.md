## Context

`door_configuration` (`backend/src/main/java/com/example/furniturecalculator/domain/DoorConfiguration.java`) сейчас — leaf_type (обязателен) + опциональные frame_type/edge_type/door_casing_type/frame_extensions_type + `is_reverse` (boolean, `reverse` в Java). Уникальность обеспечивает индекс `uk_door_configuration_combination` на (leaf_type_id, COALESCE(frame_type_id,0), COALESCE(edge_type_id,0), COALESCE(door_casing_type_id,0), COALESCE(frame_extensions_type_id,0), is_reverse) — NULL-safe через `COALESCE(...,0)`.

До этого change вид кромки жёстко соответствовал `is_reverse` (миграция из `refine-catalog-and-edge-reverse-rule`: ET-001 «Прямая» только при `is_reverse=false`, ET-002 «С четвертью» только при `is_reverse=true`) — эта связь удалена самим бизнес-запросом (см. proposal.md).

Текущее состояние каталога (снято перед началом работы, для оценки миграции):
- Всего строк `door_configuration`: 5734. `is_reverse=true`: 2318, `is_reverse=false`: 3416. Различных leaf_type: 44.
- edge_type: ET-001 — 1597 строк, ET-002 — 1159 строк, без кромки (edge_type IS NULL) — 2978 строк.
- 33 leaf_type имеют каталожную опцию толщины 59 мм (см. `add-leaf-thickness-59mm-option`); их строки с frame_type «НЕО» (FT-003, id=4): 870 (все — `is_reverse=false`, ни одной с `is_reverse=true`/ET-002). Всего строк с FT-003 в каталоге: 1230.
- Проверено: ни одна существующая строка не сочетает `is_reverse=false` с ET-002, и ни одна — `is_reverse=true` с ET-001 (следствие прежнего правила) — это гарантирует отсутствие коллизий уникального индекса при переносе кромки ET-001→ET-002 в новых копиях (см. Decisions).

`configuration_price` НЕ ссылается на `door_configuration` — цена ищется отдельно по (владелец, длина, высота, толщина, цвет). Копирование строк `door_configuration` не требует копирования `configuration_price`.

## Goals / Non-Goals

**Goals:**
- Ввести `has_quarter` как явный, самостоятельный атрибут `door_configuration`, не выводимый из `is_reverse`.
- Корректно заполнить его для всех существующих строк и материализовать «отсутствующий» вариант (без четверти → с четвертью) для конфигураций, где он ещё не существует, без потери и без задваивания данных на уникальном индексе.
- Отвязать выбор кромки от `is_reverse`, привязав его к `has_quarter`.
- Исключить короб «Нео» из каталога 33 моделей с толщиной 59 мм.
- Показать `has_quarter` на фронтенде как read-only индикатор.

**Non-Goals:**
- Не меняется цена и её резолвинг — `has_quarter` не участвует ни в одной наценке, `configuration_price` не затрагивается.
- Не вводится собственный переключатель «Четверть» в каскаде выбора (в отличие от «Реверс») — значение только отображается, отдельного шага/фильтра не создаётся (см. Decisions).
- Не трогаются строки без кромки (`edge_type IS NULL`, 2978 шт.) в части соответствия кромки атрибуту — правило применимо только там, где кромка участвует.

## Decisions

### `has_quarter` — новая колонка, а не производное значение
Хотя для строк с заданной кромкой `has_quarter` теперь 1:1 соответствует `edge_type` (ET-001↔false, ET-002↔true), для строк без кромки (`edge_type IS NULL`) вывести значение неоткуда — оно определяется правилами заполнения (реверс/толщина 59мм/остальное), а не кромкой. Поэтому `has_quarter` — обычная материализованная колонка (`BOOLEAN NOT NULL`), как и `is_reverse`, а не вычисляемое поле.

### Расширение uk_door_configuration_combination вместо нового индекса
Копия «остальной» (`has_quarter=false`) строки получает `has_quarter=true`; если исходная кромка была ET-001, у копии она становится ET-002 (другое значение edge_type — уже само по себе не даёт коллизии со старым индексом). Но у строк без кромки (`edge_type IS NULL`, эту часть тоже нужно копировать per proposal — весь `is_reverse=false`-набор «остальных» leaf_type копируется независимо от текущей кромки) копия сохраняет `edge_type IS NULL` неизменным — тогда без изменения индекса новая строка была бы идентична исходной по всем шести существующим колонкам и отклонена как дубликат. Поэтому `uk_door_configuration_combination` пересобирается (DROP + CREATE UNIQUE INDEX) с добавлением `has_quarter` в конец списка колонок — по прецеденту `0054-3-rebuild-door-configuration-unique-index`.

### Дополнение по факту реализации: перенос кромки нужен не только у копий, но и у существующих строк моделей с толщиной 59мм
Обнаружено при проверке на реальных данных (задача 1.8): у строк, чей `has_quarter` стал `true` по правилу «leaf_type имеет опцию толщины 59мм» (а не через копирование), кромка осталась прежней — унаследованной от старого инварианта `is_reverse=false → ET-001`. Шаг копирования (0105-5) ремапит кромку только в НОВЫХ строках-копиях; уже существующие строки этих 33 моделей он не касается. Добавлен отдельный changeset (0105-7) — `UPDATE ... SET edge_type_id = ET-002 WHERE has_quarter = true AND edge_type_id = ET-001`, покрывающий все такие строки одним общим предикатом (независимо от того, стал ли `has_quarter=true` через реверс, толщину 59мм или копирование — само правило одно и то же). Симметричный фикс (has_quarter=false, но edge=ET-002) не нужен: до этого change такой комбинации не существовало ни при каких обстоятельствах.

### Перенос кромки в копии: ET-001→ET-002, всё остальное (включая NULL) не трогается
Рассмотрены два варианта для копий, у которых исходная кромка не ET-001 (то есть NULL — других значений у `is_reverse=false` строк «остальных» leaf_type не бывает, см. Context): (а) принудительно проставить ET-002 в копии; (б) оставить `edge_type` копии равным исходному (NULL остаётся NULL).
Выбран (б). Проставление ET-002 в строку, у которой раньше не было кромки вовсе, — это не «копия существующей конфигурации с другой кромкой», а добавление нового факта каталога (кромка становится применимой там, где раньше не была вовсе), не запрошенного явно. Правило соответствия кромки и `has_quarter` (см. specs, door-configuration-catalog) уже сформулировано так, что применяется только там, где кромка участвует, — что согласуется с этим решением, а не противоречит ему.
Для строк, где исходная кромка — ET-001 (1597 строк, из которых часть относится к 33 leaf_type с толщиной 59мм и не копируется вовсе, см. ниже), копия получает ET-002 — это и есть материализация «доступна кромка с четвertью» для соответствующей модели/короба/наличника/добора, как явно запрошено.

### Дополнение №2 по факту реализации: правило «толщина 59мм ⇒ Четверть=true» отменено (обратная связь после первого прогона на фронте)
Правило (2) в исходной версии («leaf_type с опцией толщины 59мм ⇒ has_quarter=true независимо от is_reverse», см. «Какие строки копируются» выше) на практике жёстко закрепляло has_quarter=true без альтернативы для ВСЕХ 33 моделей — включая целые коллекции без остеклённых моделей (Вертикаль: все 7 моделей входят в этот список, поэтому ни одна не могла быть выбрана «без четверти» при обычном открывании). Это противоречило самой заявленной цели change (толщина и четверть — независимые опции, см. proposal.md, «Why») и было замечено пользователем через реальное поведение фронтенда, а не через анализ данных.

Исправлено новым changeset `0105-8` (и его H2-аналогом): для строк `is_reverse=false`, чей leaf_type входит в список 33 моделей с толщиной 59мм, и у которых has_quarter уже true (из-за отменённого правила 2) — создаётся отсутствующая копия с has_quarter=false (кромка ET-002→ET-001 в копии, NULL остаётся NULL) — тем же способом, что и 0105-5, но в обратную сторону и только для этого предиката (1438 строк на реальных данных). Итоговое правило заполнения теперь симметрично для ЛЮБОЙ модели полотна: `is_reverse=true` ⇒ только «Четверть=true»; `is_reverse=false` ⇒ доступны оба варианта, независимо от толщины. Короб «Нео» для этих 33 моделей остаётся исключённым (0105-6) — это отдельное, не затронутое этой правкой решение фабрики.

### Какие строки копируются: не по leaf_type-фильтру, а по итоговому has_quarter=false
Копированию подлежат строки, для которых итоговое (после применения правил реверс/толщина-59мм) `has_quarter=false` — то есть автоматически все строки `is_reverse=false`, чей `leaf_type` не входит в список 33 моделей с толщиной 59мм (эти 33 модели после заполнения правил вообще не имеют строк с `has_quarter=false`, поэтому явный leaf_type-фильтр в INSERT избыточен, но SQL-запрос строится через сам предикат `has_quarter=false`, а не через отдельное перечисление/исключение leaf_type — так корректность не зависит от того, полон ли список 33 моделей).

### Удаление короба «Нео»: DELETE, не пропуск при генерации
870 строк с FT-003 у 33 моделей толщины 59мм удаляются explicit DELETE (а не «просто не создаём копий») — они и не должны бы попасть в копирование (все они `is_reverse=false`, но их leaf_type имеет толщину 59мм → `has_quarter` для них уже `true` по правилу (2), они не в бакете `has_quarter=false`); DELETE выполняется отдельным шагом до или после копирования — порядок не важен, поскольку предикат DELETE (`leaf_type` из списка 33 AND `frame_type`=FT-003) не пересекается с предикатом копирования (`has_quarter=false`).

### Дополнение №3 по факту реализации: короб «Нео» несовместим с «Четверть», а не с толщиной 59мм (обратная связь: «для Четверть=false невозможно выбрать короб Нео»)
Правило выше («0105-6») удалило ВСЕ строки FT-003 у 33 моделей безусловно. На момент, когда оно писалось, у этих моделей вообще не было строк `has_quarter=false` (правило (2), уже отменённое в «Дополнении №2», делало их все `true`) — поэтому вопрос «а должен ли Нео быть доступен при Четверть=false» тогда не мог даже возникнуть содержательно. После отмены правила (2) и восстановления варианта «без четверти» (0105-8) выяснилось на практике, что фабрика ДОПУСКАЕТ короб «Нео» именно при `has_quarter=false` — то есть реальная несовместимость короба «Нео» — с исполнением «с четвертью» (`has_quarter=true`), а не с толщиной 59мм как таковой (два факта ошибочно были слиты в одно правило изначально).

Исправлено новым changeset (`0105-9`): восстанавливает удалённые строки, но только для `has_quarter=false` — `has_quarter=true` для этих 33 моделей остаётся без короба «Нео» (эта часть правила подтверждена, не отменяется). Поскольку исходные удалённые строки уже не восстановить напрямую (это были конкретные строки, не выводимые из текущего состояния), они регенерируются по шаблону: у 12 «прочих» leaf_type (вне списка 33), где короб «Нео» никогда не трогался, для `has_quarter=false` существует ОДИН одинаковый набор из 30 сочетаний (наличник × добор × кромка — 15 пар наличник/добор × 2 значения кромки: «Прямая» и без кромки) — проверено на реальных данных перед реализацией (все 12 leaf_type дают одинаковое количество и состав). Новые строки для 33 моделей строятся `CROSS JOIN` этого шаблона на список 33 leaf_type, без переиспользования конкретных id старых (удалённых) строк. Итог на реальных данных: 33 × 30 = 990 новых строк (7410 → 8400).

### UI: самостоятельный переключатель каскада, а не индикатор (пересмотрено по прямому запросу)
Первая версия показывала `hasQuarter` как read-only тег рядом с шагом «Кромка», выводимый из уже сделанного выбора кромки — рассуждение было в том, что `has_quarter` тесно связан с этим шагом через 1:1-правило, и превращать его в отдельный переключатель означало бы дублировать уже имеющийся выбор кромки другим виджетом. По прямому запросу («свитч должен быть кликабельным и менять конфигурацию») это пересмотрено: «Четверть» реализован как самостоятельный шаг каскада, полностью симметричный «Реверс» (`resolveHasQuarterStep`, зеркалит `resolveReverseStep`) — оценивается сразу после «Реверс», по каталогу, уже суженному по его значению, до шага выбора типа полотна и коллекции. Дублирования с шагом «Кромка» на практике не возникает: он лишь становится следствием уже сделанного (на этом более раннем шаге) выбора «Четверть» — для суженного набора кромка автоматически предлагает только один совместимый вариант (см. specs, door-configuration-catalog, «Соответствие вида кромки и атрибута «Четверть»»), а не два независимых способа выбрать одно и то же.

### UI: «Четверть» оценивается по полному каталогу, а не по уже суженному «Реверс» (ещё одна правка после проверки)
Версия из предыдущего пункта оценивала `resolveHasQuarterStep` по `reverseFilteredConfigurations` (уже суженному текущим значением «Реверс») — по аналогии с тем, как остальные шаги каскада (тип полотна, коллекция и т.д.) сужаются последовательно, один за другим. Это дало неверный побочный эффект: при включённом «Реверс» среди суженного набора остаются только строки с `has_quarter=true` (альтернативы «без четверти» для реверса не существует, см. выше) — значит `hasQuarterValues.size === 1`, и переключатель «Четверть» ПРОПАДАЛ (замечено пользователем: «нажал на свитч реверс и свитч четверть пропал»).

Исправлено: `resolveHasQuarterStep`, как и `resolveReverseStep`, теперь вызывается на ПОЛНОМ, нефильтрованном `configurations` — оба переключателя оцениваются как независимые сиблинги одного уровня, а не последовательно один через другой. Согласованный набор для последующих шагов фильтруется одновременно по обоим текущим значениям (`configuration.reverse === resolvedReverse && configuration.hasQuarter === resolvedHasQuarter`) одним выражением, а не через промежуточную `reverseFilteredConfigurations`.

Поскольку «Реверс»=true физически совместим только с «Четверть»=true (а не с обоими значениями), два переключателя ДОЛЖНЫ синхронизироваться, чтобы не оказаться в невозможной комбинации — иначе после этой правки пользователь мог бы поставить «Реверс»=true и «Четверть»=false одновременно, для которой в каталоге просто нет строк (пустой, «сломанный» результат каскада). Синхронизация — не через скрытие/блокировку виджета (как раньше), а через взаимное принудительное переключение, приоритет — у переключателя, который клиент трогает последним:
- `handleReverseChange(true)` → дополнительно `setHasQuarterSelection(true)`.
- `handleHasQuarterChange(false)`, когда `resolvedReverse === true` → дополнительно `setReverseSelection(false)`.
- Обратные направления (`handleReverseChange(false)`, `handleHasQuarterChange(true)`) ничего принудительно не меняют — обе позиции «Четверть» совместимы с «Реверс»=false, и обе позиции «Реверс» здесь не участвуют, когда «Четверть»=true.

Это тот же принцип, что уже применялся для толщины 59мм (`setHasQuarterSelection(true)` при выборе 59мм) — но здесь синхронизация двусторонняя и явно описана как отдельное поведение обоих хендлеров, а не одностороннее автоматическое включение.

### Толщина 59мм ↔ «Четверть»: правило запроса, а не каталога (пересмотрено по обратной связи после проверки на реальных данных)
Изначальная (уже отменённая, см. «Дополнение №2» выше) версия пыталась выразить связь толщины 59мм и четверти через каталог — жёстко фиксируя `has_quarter=true` для leaf_type, у которых ЕСТЬ опция толщины 59мм, независимо от того, выбрал ли клиент её в конкретном запросе. Это была категориальная ошибка: толщина — атрибут, выбираемый клиентом отдельно при расчёте (`thicknessOptionId`), а не свойство самой строки `door_configuration`; связывать её с `has_quarter` на уровне каталога значило бы либо неверно ограничивать ВСЕ конфигурации подходящего leaf_type (что и произошло), либо требовать почти двойного числа door_configuration (по одной паре на каждую комбинацию толщины) — оба варианта хуже, чем правило уровня запроса.

Правильная модель (подтверждена пользователем): толщина 59мм физически требует четверть, но это проверяется В МОМЕНТ, когда клиент ВЫБИРАЕТ 59мм — не заранее, на уровне каталога. Реализовано:
- **Backend**: `DoorConfigurationPricingService.validateThicknessRequiresQuarter(leafSelection, hasQuarter)` — при `hasQuarter=false` и толщине 59мм — 400. `hasQuarter` резолвится по-разному в зависимости от эндпоинта: `calculate()` — прямо из `configuration.isHasQuarter()` (всегда известно); `calculateForLeaf()`/`resolveSpecificationComponents()` — из явно переданного `edgeTypeId` через новый `hasQuarterFromEdgeTypeId(edgeTypeId)` (код ET-002 ⇒ true, иначе false); если кромка не передана вовсе — `null` («неизвестно»), проверка пропускается, а не блокирует запрос (у отдельного полотна без кромки нет способа определить «Четверть» точно, и блокировать по умолчанию было бы неверно строже, чем того требует бизнес-правило).
- **Frontend**: селектор толщины полотна скрывает опцию 59мм, когда `resolvedHasQuarter === false` (точно известно и выключено); выбор 59мм вызывает `setHasQuarterSelection(true)` напрямую — НЕ через `handleHasQuarterChange` (который сбрасывает весь каскад, как и положено при явном клике по независимому переключателю более раннего уровня). Прямой `setHasQuarterSelection(true)` не трогает `cascadeSelection`/выбранную коллекцию/полотно — только меняет фильтр по «Четверть», из-за чего уже выбранная (несовместимая) кромка естественным образом становится невалидной в `applyCascadeStep` (её id пропадает из `availableTypes`) и требует повторного явного выбора — без необходимости писать отдельную логику инвалидации.

### Наценка за «Четверть»: +10%, но не задваиваясь с реверсом/толщиной 59мм
Прямой запрос пользователя: «за опцию четверть +10% к стоимости полотна, если ранее не была применена наценка за толщина 59 мм или реверс». Реализовано как ещё один фиксированный процент-множитель уровня кода (`QUARTER_SURCHARGE_MULTIPLIER = 1.10`), тем же способом, что и `REVERSE_SURCHARGE_MULTIPLIER`/`DOUBLE_SIDED_PAINTING_SURCHARGE_MULTIPLIER` — не строка в БД.

Условие неприменения — не «has_quarter=false», а именно «has_quarter=true, но уже подразумевается другой применённой наценкой»: `resolveQuarterSurchargeMultiplier(type, hasQuarter, applyReverseSurcharge, thicknessMultiplier)` возвращает `ONE`, если `hasQuarter` не точно `true`, ИЛИ `applyReverseSurcharge` истинен, ИЛИ `thicknessMultiplier != ONE` (толщина 59мм уже дала наценку). Только когда `hasQuarter=true` и ни одно из двух условий-исключений не выполнено, применяется 1.10.

**Почему через `hasQuarter`, переданный в `addComponentIfPresent`, а не вычисленный только из `applyReverseSurcharge`/`thicknessMultiplier`**: наценка должна применяться и тогда, когда четверть выбрана явно (клиентом, без реверса и без толщины 59мм) — для этого нужно знать сам факт `has_quarter=true`, а не только «не сработали ли исключения». Источник `hasQuarter` — тот же, что уже был у `validateThicknessRequiresQuarter` (см. выше): `configuration.isHasQuarter()` для `calculate()`, `hasQuarterFromEdgeTypeId(edgeTypeId)` для `calculateForLeaf()`/`resolveSpecificationComponents()`. Поскольку валидация и наценка используют один и тот же источник и одно и то же значение за один вызов, добавлен новый параметр `Boolean hasQuarter` в `addComponentIfPresent` (нужен только для leaf; для остальных 4 типов владельца — всегда `null`, наценка для них не считается: `resolveQuarterSurchargeMultiplier` возвращает `ONE` для `!(type instanceof LeafType)` до проверки самого `hasQuarter`).

**Место в последовательности наценок**: сразу после толщины, до цвета — рядом с толщиной, так как обе наценки описывают одну смысловую категорию («структурные» свойства самого полотна, а не его отделку), и это единственное место, где взаимное «не задваивание» с толщиной естественно читается по соседству в коде и в specs.

## Risks / Trade-offs

- [Расширение уникального индекса — операция DROP+CREATE на таблице с ~5700+ строками] → Выполняется как отдельный changeset (по прецеденту 0054), без даунтайма приложения (Liquibase-миграция при старте, до открытия трафика).
- [Массовое копирование строк может неожиданно сильно увеличить размер каталога, если оценка «остальных» строк неверна] → Оценка предиката копирования — `has_quarter=false` после backfill, а не оценка на глаз; фактическое количество проверяется в рамках задачи миграции по факту (`SELECT count(*)` до/после).
- [Строки без кромки (edge_type IS NULL) при копировании тоже дублируются, хотя видимого эффекта на выбор кромки не дают] → Явное решение (см. Decisions, «Перенос кромки в копии») — так и должно быть, раз речь именно про «конфигурации», а не только про «конфигурации с кромкой»; при этом такие копии безопасны для уникального индекса благодаря добавлению `has_quarter` в его состав.
- [Отмена прежнего инварианта «кромка↔реверс» — потенциально влияет на любой код/тесты, которые полагались на него неявно] → Проверить существующие тесты `DoorConfigurationCatalogService`/каталога на прямые ожидания вида «is_reverse=true ⇒ только ET-002» и обновить их вместе с этим change (см. tasks.md).
- [Новый параметр `Boolean hasQuarter` в `addComponentIfPresent` затрагивает все 14 мест вызова этого приватного метода, хотя нужен только 3 из них (leaf)] → Остальные 11 передают `null` явно — тот же уже установленный в проекте паттерн, что и у `applyReverseSurcharge` (передаётся `false` для всех не-leaf вызовов); не новая асимметрия, а продолжение существующей.
