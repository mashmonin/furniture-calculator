## Context

В каталоге уже есть один прецедент «независимой от door_configuration» позиции — фурнитура (hardware-catalog, hardware-standalone-pricing): собственная 3-уровневая иерархия (категория → тип → цветовой вариант с ценой), собственный REST-эндпоинт каталога и собственный эндпоинт расчёта стоимости списка позиций, который также можно подмешать в основной расчёт по `door_configuration` и в расчёт отдельного полотна. Декоративные элементы (плинтус) повторяют этот же общий паттерн, но без цветовой оси (у плинтуса нет цветовых вариантов — только фиксированные длина и цена на тип) и с дополнительным измерением, которого у фурнитуры нет: допустимость декоративного элемента зависит от коллекции выбранного полотна (недоступно для «Фантом»).

Существующая генерик-система `liner_dimension_option`/`configuration_price` с закрытым списком владельцев (leaf_type, frame_type, edge_type, door_casing_type, frame_extensions_type — см. door-configuration-catalog, «Владение liner_dimension_option» и «Владение configuration_price») не рассматривается как место для длины/цены плинтуса — добавление шестого владельца в этот закрытый список было бы инвазивным изменением центральной структурной сущности каталога ради позиции, которая и так задумана как независимая от door_configuration, по образцу фурнитуры.

## Goals / Non-Goals

**Goals:**
- Ввести декоративные элементы как полноценный, независимый от door_configuration каталожный пласт — по образцу фурнитуры, но с собственной моделью данных, отражающей отсутствие цвета и наличие ограничения по коллекции.
- Обеспечить сквозную интеграцию (каталог → расчёт → конфигуратор → корзина → выгрузка), без «половинчатой» реализации, которую нельзя реально заказать.
- Оставить расширяемым под будущие декоративные элементы, не являющиеся плинтусом (категория как отдельный уровень).

**Non-Goals:**
- Не вводится цветовая вариативность декоративных элементов (у плинтуса её нет; если понадобится в будущем — отдельное расширение схемы).
- Backend не проверяет допустимость decorative_element_type для конкретной коллекции/leaf_type при расчёте стоимости (ни в основном расчёте по door_configuration, ни в расчёте отдельного полотна, ни в собственном standalone-эндпоинте) — как и для фурнитуры, эта проверка выполняется только на фронтенде по каталогу; backend принимает любой существующий decorative_element_type независимо от контекста. Это сознательное упрощение, симметричное существующему поведению фурнитуры.
- Наличник/добор/наценки за нестандартный погонаж к декоративным элементам не применяются — они не участвуют в семействе «короб и обрамление» и не имеют своего pogonazh_surcharge_rule.

## Decisions

**Схема данных — 3 новые таблицы, без изменения существующих:**
- `decorative_element_category` (id, name, code) — группировка, по образцу `hardware_category`; на старте — одна строка «Плинтус».
- `decorative_element_type` (id, decorative_element_category_id, name, code, length_mm, retail_price, dealer_price) — готовая позиция целиком, включая цену; в отличие от `hardware_type`/`hardware_option`, здесь только один уровень под категорией, так как цветовой вариативности нет. Две строки на старте: «Плинтус Модо», «Плинтус Модо облегчённый» — обе 2400 мм, 2611 ₽ розница / 1492 ₽ дилер.
- `decorative_element_option` (id, decorative_element_type_id, leaf_type_id, unique(decorative_element_type_id, leaf_type_id)) — допустимость типа для конкретного leaf_type, по образцу `colour_option`/`mirror_finish_option`. Заполняется для обоих типов плинтуса и всех leaf_type всех коллекций, кроме «Фантом» (`LC-009`).

Альтернатива — переиспользовать `hardware_option`-подобный 3-уровневый шаблон с фиктивным «единственным цветом» — отклонена: добавляла бы лишнюю сущность без смысла (плинтус в принципе не имеет цвета, а не «имеет один цвет»).

**Backend — три новых эндпоинта:**
- `GET /api/decorative-elements-catalog` — полная иерархия категория → тип, по образцу `GET /api/hardware-catalog`.
- `POST /api/decorative-elements/price` — расчёт списка позиций {decorative_element_type_id, quantity?}, по образцу `POST /api/hardware/price`.
- Существующие `POST /api/door-configurations/{id}/price` и `POST /api/leaf-types/{id}/price` дополняются необязательным полем списка позиций декоративных элементов — по тому же образцу, что и уже существующее поле позиций фурнитуры.

Допустимость decorative_element_type для leaf_type (owned by leaf_type в `decorative_element_option`) используется только каталогом конфигураций (`GET /api/door-configurations`, поле `decorativeElements` у leaf-компонента) — фронтенд строит список выбора по этому полю. Ни один из трёх расчётных эндпоинтов эту связь не проверяет (см. Non-Goals) — так же, как и для фурнитуры.

**Frontend — переиспользование паттерна блока фурнитуры:**
Блок «Декоративные элементы» реализуется тем же компонентом-паттерном, что и блок фурнитуры (каскад категория → тип, количество, запрет повторного выбора одного типа в двух позициях), но с одним уровнем каскада меньше (нет цвета) и с дополнительным условием доступности — коллекция выбранного полотна должна быть определена и отлична от «Фантом». Этап расчёта «Декоративные элементы» — четвёртый независимый debounced-этап, наравне с «Полотно», «Короб и обрамление», «Фурнитура»; условие запуска мирроит «Фурнитуру» (тип полотна определён + есть завершённая позиция), с добавлением условия по коллекции.

## Risks / Trade-offs

- [Backend не валидирует допустимость decorative_element_type для коллекции при расчёте] → Осознанно принято как симметрия с фурнитурой; ограничение — чисто фронтенд-уровня. Риск: прямой вызов API в обход UI может добавить плинтус к конфигурации «Фантом». Митигация не требуется — это тот же класс риска, что уже существует для фурнитуры, и не считается проблемой в текущей архитектуре системы.
- [Расширение под будущие некатегоризированные декоративные элементы] → Наличие уровня `decorative_element_category` уже закладывает расширяемость; если будущий декоративный элемент потребует цветовую вариативность, потребуется отдельное расширение схемы (добавление уровня, аналогичного `hardware_option`) — не блокирует текущую реализацию.
- [Объём изменений — 9 capability] → Осознанно принято пользователем (подтверждена «полная паритет с фурнитурой»); задачи в tasks.md разбиты по слоям (схема → backend API → frontend конфигуратор → корзина → выгрузка), чтобы реализация могла идти последовательно и проверяться на каждом слое отдельно.
