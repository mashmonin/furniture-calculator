## Why

Фабрика хочет предложить клиентам полотно нестандартной высоты 2800 мм и 2900 мм с наценкой 80% — для всех моделей, кроме «СИБИРЬ 03» (угловая модель коллекции «Сибирь», не может быть такой высоты по конструктивным причинам). Сейчас произвольная высота полотна (`customHeightValueMm`) принимается только если для неё есть строка `dimension_surcharge_rule` для оси высоты (`liner_dimension_type` с кодом «ВЫСОТА»); иначе запрос отклоняется с 400 («фабрика не производит полотно с размером X мм для этой оси»). Значений 2800/2900 сейчас в `dimension_surcharge_rule` нет — высота недоступна вообще ни для одной модели.

## What Changes

- **Расширение модели `dimension_surcharge_rule`**: справочник сейчас сознательно не привязан к владельцу (см. требование «Независимость от каталога допустимых конфигураций» в dimension-surcharge-rules) — одно правило одинаково для всех моделей полотна. Это перестаёт быть верным: добавляется опциональная ссылка на `leaf_type` (`leaf_type_id`, nullable) — `NULL` сохраняет старое поведение (правило действует для всех моделей, все существующие строки не меняются), заданное значение делает правило специфичным для одной конкретной модели. Уникальность (`liner_dimension_type_id`, `value`) дополняется владельцем по тому же приёму, что уже применялся для `pogonazh_surcharge_rule`/`liner_dimension_option` (generated-колонка `leaf_type_key`, схлопывающая `NULL` в уникальное отрицательное значение), чтобы новые строки с разными `leaf_type_id` не конфликтовали друг с другом.
- **Новые данные**: для оси высоты (`liner_dimension_type` с кодом «ВЫСОТА») заводятся строки `value = 2800` и `value = 2900`, `surcharge_percent = 80`, по одной на каждую модель полотна (`leaf_type`), кроме «СИБИРЬ 03» (`leaf_type` с кодом LT-041) — она не получает строк для этих значений, поэтому высота 2800/2900 мм для неё останется недоступной (запрос будет отклонён с тем же 400, как и сегодня для любого неподдерживаемого размера).
- **Backend**: поиск применимого правила при разрешении произвольной высоты/длины полотна (`DoorConfigurationPricingService`) сначала ищет правило, специфичное для конкретного `leaf_type` запрошенного компонента, и только при его отсутствии — общее правило без владельца (`leaf_type_id IS NULL`), чтобы не потерять уже существующие общие правила (1900–2700 мм). `GET /api/pricing-surcharges` (`DimensionSurchargeRuleDto`) дополнительно отдаёт `leafTypeId` (`null` — правило общее, иначе — конкретная модель). **BREAKING** (аддитивное расширение контракта ответа, не ломающее существующих полей): элементы `dimensionSurchargeRules` теперь могут иметь непустой `leafTypeId`.
- **Frontend**: разбивка наценки за нестандартную высоту полотна (`App.tsx`, `computeSurchargeBreakdown`) учитывает `leafTypeId` правила — раньше поиск шёл только по (тип оси, значение), теперь предпочитается правило текущей модели, затем общее; без этого для «СИБИРЬ 03» на 2800/2900 мм в разбивке ошибочно показался бы процент 80%, хотя расчёт стоимости эту высоту отклонит.

## Capabilities

### Modified Capabilities
- `dimension-surcharge-rules`: требование «Независимость от каталога допустимых конфигураций» переформулируется — правило может (но не обязано) ссылаться на конкретный `leaf_type`; добавляется требование о наценке 80% за высоту 2800/2900 мм для всех моделей, кроме «СИБИРЬ 03».
- `door-configuration-api`: резолв наценки за нестандартный размер полотна учитывает специфичные для модели правила; `GET /api/pricing-surcharges` дополнительно отдаёт `leafTypeId` у правил наценки за размер полотна.
- `door-configurator-ui`: разбивка наценки за нестандартную высоту полотна учитывает `leafTypeId` правила, а не только значение.

## Impact

- Backend: новый Liquibase changelog (`ALTER TABLE dimension_surcharge_rule` — nullable `leaf_type_id` + FK, generated-колонка `leaf_type_key`, пересозданный unique-индекс; `INSERT` строк 2800/2900 для всех `leaf_type`, кроме LT-041); новый метод в `DimensionSurchargeRuleRepository`; правка `DoorConfigurationPricingService.resolveAxisSurchargeMultiplier` (сначала специфичное правило, потом общее); расширение `DimensionSurchargeRuleDto`/`PricingSurchargesService`.
- Frontend: расширение типа `DimensionSurchargeRuleDto` в `api/types.ts`, правка `computeSurchargeBreakdown()` в `App.tsx` (передаётся `leafTypeId`, поиск правила предпочитает совпадение по модели).
- Desktop (H2): `ALTER TABLE ... ADD COLUMN` (в т.ч. generated-колонка) и пересборка unique-индекса — тот же приём, что и в 0006/0062/0065/0069 для H2-совместимости; проверить, нужен ли desktop-override (в отличие от 0096, здесь колонка `leaf_type_key` — generated, а не просто DDL, поэтому по аналогии с `changes-desktop-overrides/0006-door-configuration-catalog.yaml` может не потребоваться отдельный override, так как generated-колонки одинаково работают в PostgreSQL и H2 — уточняется в design.md).
