## Context

`dimension_surcharge_rule` (см. dimension-surcharge-rules) сейчас принципиально не знает о владельце: одна строка = (liner_dimension_type, value, surcharge_percent), уникальная по (liner_dimension_type_id, value), и применяется одинаково к любому leaf_type — это явно закреплено требованием «Независимость от каталога допустимых конфигураций». `DoorConfigurationPricingService.resolveAxisSurchargeMultiplier` использует эту таблицу как whitelist произвольных значений длины/высоты полотна: если для значения нет ни каталожной liner_dimension_option, ни строки dimension_surcharge_rule — запрос отклоняется 400 («фабрика не производит полотно с размером X мм для этой оси»).

Новое требование фабрики — высота 2800/2900 мм должна стать доступной (с наценкой 80%) для всех моделей полотна (leaf_type), КРОМЕ «СИБИРЬ 03» (LT-041, угловая модель коллекции «Сибирь» — конструктивно не может быть такой высоты). Это прямо противоречит текущему принципу «одинаково для всех» — обсуждено с пользователем, выбран вариант «явно перечислить владельцев» (см. proposal.md), а не вводить отдельный механизм исключений.

## Goals / Non-Goals

**Goals:**
- Позволить dimension_surcharge_rule как раньше описывать общие правила (leaf_type не указан), и вместе с этим — правила, специфичные для одной конкретной модели полотна.
- Реализовать «доступно всем, кроме одной модели» через явное перечисление владельцев (по одной строке на каждый leaf_type, кроме LT-041) — без строки для LT-041 запрос для неё естественно отклоняется существующим кодом (whitelist), без специальной логики исключения.
- Не трогать существующие 19 общих строк (1900–2700 мм) — они продолжают действовать одинаково для всех моделей.

**Non-Goals:**
- Не вводим отдельную таблицу/механизм "исключений" — решение принято явно в пользу перечисления (см. proposal.md, обсуждение с пользователем).
- Не меняем ось длины (liner_dimension_type «ДЛИНА») — запрос касается только высоты; привязка к leaf_type в схеме — общая возможность (для обеих осей), но новые данные заводятся только для высоты.
- Не вводим отдельный desktop-override для H2 — изменения (ADD COLUMN, generated-колонка, пересборка НЕ partial unique-индекса) синтаксически одинаковы в PostgreSQL и H2, тот же подход, что и в 0096 (см. changes/0096-pogonazh-surcharge-rule-70-100-percent-tiers.yaml), без partial/functional-индексов, которые H2 не поддерживает.

## Decisions

### Owner-скоуп — nullable `leaf_type_id`, а не отдельная таблица правил-переопределений
Добавляем `leaf_type_id` (nullable FK на leaf_type) прямо в dimension_surcharge_rule: NULL — как сейчас, общее правило; заданное значение — правило только для этой модели. Специфичное правило имеет приоритет перед общим с тем же значением (на практике сейчас конфликтов не будет — общих строк для 2800/2900 не заводится, — но приоритет нужен как общее правило резолва на будущее).

**Альтернатива (отклонена пользователем)**: оставить dimension_surcharge_rule полностью глобальным, добавить отдельный список исключений (leaf_type + ось + значение), который блокирует иначе разрешённое общее правило для конкретной модели. Меньше данных (2 строки вместо 88), но вводит новую, ранее не существовавшую в проекте концепцию «глобально разрешено, но с точечным запретом», требующую дополнительной проверки-исключения в резолвере. Пользователь выбрал явное перечисление владельцев — тот же принцип, что уже используется для pogonazh_surcharge_rule (наличие строки = разрешено, отсутствие = недопустимо), без нового понятия «запрет».

### Уникальность — тот же generated-key приём, что и в 0006/0062/0065/0069
Плоский составной unique-индекс `(liner_dimension_type_id, value, leaf_type_id)` не подошёл бы: в SQL NULL не равен другому NULL, поэтому такой индекс НЕ помешал бы вставить вторую общую (leaf_type_id = NULL) строку с тем же (type, value) — регресс по сравнению с текущим строгим индексом `(liner_dimension_type_id, value)`. Вместо этого — тот же приём, что уже применялся для pogonazh_surcharge_rule/liner_dimension_option/door_configuration: generated-колонка `leaf_type_key = CASE WHEN leaf_type_id IS NOT NULL THEN leaf_type_id ELSE -id END`, unique-индекс на `(liner_dimension_type_id, value, leaf_type_key)`. Для строк с конкретным leaf_type_id это даёт строгую уникальность (конкретная модель + тип + значение не может повториться) — то, что нам реально нужно для 88 новых строк. Для общих строк (leaf_type_id = NULL) индекс, как и в 0006/0062/0065/0069, не защищает от дублей (каждая получает свой -id) — то же самое, уже принятое в проекте, ограничение; новых рисков не добавляет.

### Резолвер — специфичное правило, затем общее (а не объединённый список)
`DimensionSurchargeRuleRepository` получает два метода: `findByLinerDimensionTypeIdAndValueAndLeafTypeId(...)` (специфичное) и `findByLinerDimensionTypeIdAndValueAndLeafTypeIsNull(...)` (общее, замена текущего `findByLinerDimensionTypeIdAndValue`). `resolveAxisSurchargeMultiplier` сначала пробует первый, при пустом результате — второй. Явные Spring Data derived queries, без @Query — оба случая однозначны (не пересекаются: одна строка не может быть одновременно с leaf_type_id и без него).

### DTO и фронтенд — `leafTypeId` как дополнительное nullable-поле, тот же приём, что и `ownerId` у pogonazh
`DimensionSurchargeRuleDto` получает `leafTypeId` (nullable). Фронтенд (`computeSurchargeBreakdown` в App.tsx) получает leafTypeId текущего компонента и при поиске правила высоты предпочитает совпадение по (value, leafTypeId), при отсутствии — по (value, leafTypeId == null). Без этой правки для «СИБИРЬ 03» на 2800/2900 мм разбивка ошибочно нашла бы чужую (другой модели) строку с тем же value и показала 80%, хотя сам расчёт эту высоту отклонит (несогласованность UI и реального результата, а не просто "красиво/некрасиво").

## Risks / Trade-offs

- **Ломает задокументированный принцип «dimension_surcharge_rule не знает о владельце»** → требование в specs/dimension-surcharge-rules прямо переформулировано (MODIFIED, не ADDED) — не тихая точечная лазейка, а явный пересмотр инварианта, зафиксированный в спеке.
- **88 новых строк (44 модели × 2 значения) для одного изменения** → каждая — тривиальный `INSERT ... SELECT ... WHERE code <> 'LT-041'`, не ручное перечисление; при добавлении новой модели полотна в будущем её придётся отдельно добавить в подобный INSERT, если её тоже нужно включить в это правило (не автоматично, в отличие от отклонённой альтернативы с исключениями) — принятая цена za простоту и согласованность с уже принятым в проекте паттерном.
- **Общие строки (leaf_type_id NULL) не защищены от дублей на уровне БД** (как и в 0006/0062/0065/0069) — тот же, уже принятый в проекте риск, не новый.
