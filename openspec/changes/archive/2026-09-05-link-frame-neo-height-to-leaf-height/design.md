## Context

См. proposal.md — «Why» и «What Changes».

Ключевые технические факты о текущем состоянии, важные для решения:

1. **Ветка `FrameType` в `DoorConfigurationPricingService.addComponentIfPresent` сегодня не трогает height/length опции вообще.** Код:
   ```java
   if (type instanceof FrameType frameType) {
       ColourOption colourOption = validatedColourOption(componentName, frameType, selection.colourOptionId());
       components.add(framePostPrice(componentName, frameType, colourOption));
       return;
   }
   ```
   `return` происходит раньше вызовов `validatedDimensionOption(...)` для length/height. Стоимость короба (`framePostPrice`) считается как сумма `frame_post` плюс, опционально, цена по цвету — высота на цену никак не влияет и нигде не проверяется. Ни один существующий `frame_type_id` сегодня не имеет строк `liner_dimension_option` (ни длины, ни высоты) — фича добавляет первые такие данные.
2. **У кромки поле `value` совпадает и с физической высотой опции, и с верхней границей диапазона высоты полотна** — это не общий принцип, а частное совпадение данных кромки. Для короба «НЕО» физическая высота (2170/2400/2700 мм) не совпадает с верхней границей диапазона высоты полотна (2100/2250/2300/2550 мм), поэтому `value` нельзя переиспользовать как границу диапазона.
3. **Уникальный индекс** `uk_liner_dimension_option_frame_type (frame_type_id, liner_dimension_type_id, value) WHERE frame_type_id IS NOT NULL` (0006-7) не позволяет вставить две строки с одинаковым `value` для одного `frame_type_id` — а по бизнес-данным короба «НЕО» значению 2400 соответствуют два непересекающихся диапазона высоты полотна: 2150–2250 и отдельно ровно 2300 (между ними — «дыра» 2250–2300, где короб «НЕО» недоступен).
4. Фронтенд уже рендерит группу «Высота» для любого шага generically через `component.dimensionOptions.filter(code === HEIGHT_TYPE_CODE)` (`frontend/src/App.tsx:616`), кроме `edge`, у которого свой `edgeHeightOptions()`. Раз для короба сейчас нет данных высоты, эта группа для `frame` сейчас пустая и скрыта (`OptionGroup` не рендерит пустой список).

## Goals / Non-Goals

**Goals:**
- Позволить хранить для `door_casing`-независимого владельца `frame_type_id` диапазон высоты полотна, отдельно от физической высоты опции.
- Ограничить выбор высоты короба «НЕО» (`FT-003`) диапазоном высоты полотна, не затрагивая другие типы короба.
- Переиспользовать существующий механизм валидации (`validateHeightWithinLeafRange`), обобщив его без изменения текущего поведения для кромки.
- Разрешить неконтигуальные (непересекающиеся, с разрывом) диапазоны для одного и того же значения высоты компонента.

**Non-Goals:**
- Не меняется формула стоимости короба — выбор высоты остаётся не влияющим на цену (как и раньше для frame), только гейтит допустимость выбора.
- Не создаются новые типы короба/наличника.
- Не переносится существующая логика кромки на общий, полностью абстрактный механизм валидации диапазонов «на все компоненты сразу» — расширяется только под явно описанный кейс `FrameType` с кодом `FT-003`.

## Decisions

### 1. Новое поле `max_value` вместо переиспользования `value` как верхней границы

Добавляем в `liner_dimension_option` новую nullable-колонку `max_value` (тип `DECIMAL`, как у `min_value`). Семантика:
- `value` — физическая высота компонента (то, что показывается и выбирается пользователем, что уходит в `heightOptionId`).
- `min_value`/`max_value` — необязательные границы диапазона высоты полотна, для которого эта опция допустима. Обе колонки `NULL` (как сейчас у всех опций, кроме кромки) означают «диапазон не ограничен, для родительской высоты полотна проверка не выполняется».

Для короба «НЕО»: `min_value`/`max_value` заполняются реальными границами диапазона (например, `value=2170, min_value=1900, max_value=2100`).

Для кромки данные и код не меняются: `min_value` заполнен, `max_value` остаётся `NULL` для всех существующих строк кромки.

**Альтернатива (отклонена):** переиспользовать `value` как верхнюю границу для короба, как это сделано для кромки. Отклонено, потому что для короба «НЕО» физическая высота компонента и верхняя граница диапазона — разные числа; переиспользование `value` в этой роли исказило бы отображаемое/выбираемое значение высоты короба.

### 2. Обобщение `validateHeightWithinLeafRange`

Метод обобщается: верхняя граница диапазона вычисляется как `option.getMaxValue() != null ? option.getMaxValue() : option.getValue()` — для кромки (`maxValue == null` всегда) поведение не меняется (используется `value`, как сейчас), для короба «НЕО» используется явный `maxValue`. Нижняя граница — по-прежнему `option.getMinValue()` (`NULL` = не ограничена снизу), без изменений.

### 3. Валидация применяется к `FrameType` только по коду `FT-003`

В `addComponentIfPresent`, в ветке `if (type instanceof FrameType frameType)`, добавляется:
- получение и валидация (существование + принадлежность) `heightOption` через существующий `validatedDimensionOption(componentName, frameType, selection.heightOptionId())` — сегодня этот вызов там отсутствует;
- если `heightOption != null` и `"FT-003".equals(frameType.getCode())`, вызывается обобщённый `validateHeightWithinLeafRange(componentName, heightOption, leafHeightValue)`.

Именно проверка по коду типа (а не «если у опции заполнены границы»), потому что код — явный, стабильный бизнес-ключ (используется по всему сервису так же, как `HEIGHT_TYPE_CODE`/`LENGTH_TYPE_CODE`), и делает намерение читаемым: «это правило специфично для короба Neo», а не побочный эффект того, заполнены ли у опции границы диапазона. Другие типы короба (`FT-001` Фантом, `FT-002` Компланар, `FT-004` реверс-полотна — если получат `frame_type_id`) не затрагиваются, даже если для них в будущем появятся строки `liner_dimension_option` с высотой без диапазона.

Валидированный `heightOption` короба **не передаётся** в `findMostSpecificPrice`/`framePostPrice` — стоимость короба, как и раньше, не зависит от высоты (см. Non-Goals). Это сознательно ограничивает изменение только гейтингом допустимости, без побочных эффектов на прайсинг.

### 4. Расширение уникального индекса `uk_liner_dimension_option_frame_type`

Существующий индекс `(frame_type_id, liner_dimension_type_id, value) WHERE frame_type_id IS NOT NULL` заменяется на:
```sql
CREATE UNIQUE INDEX uk_liner_dimension_option_frame_type ON liner_dimension_option (
  frame_type_id, liner_dimension_type_id, value, COALESCE(min_value, -1), COALESCE(max_value, -1)
) WHERE frame_type_id IS NOT NULL
```
`COALESCE(..., -1)` — потому что PostgreSQL считает `NULL <> NULL` в уникальных индексах (несколько строк с одинаковыми `NULL` не конфликтуют), а нам нужно однозначно различать «одна опция без диапазона» и «две опции с разными диапазонами»; `-1` как санитайзер невозможен для реальных высот (всегда положительные), что уже используется в проекте как паттерн (`COALESCE(leaf_type_id, 0)` в `uk_configuration_price_combination`, 0008-3).

Итоговая уникальность для короба «НЕО»: `(FT-003, HEIGHT, 2400, 2150, 2250)` и `(FT-003, HEIGHT, 2400, 2300, 2300)` — два разных ключа, обе строки сохраняются. Для всех остальных `frame_type_id` (сегодня нет данных, `min_value`/`max_value` всегда `NULL`) поведение индекса не меняется: как и раньше, `value` не может повторяться в рамках одного `frame_type_id` и оси размера.

**Альтернатива (отклонена):** смоделировать диапазон 2150–2300 одной строкой (`min_value=2150, max_value=2300`), закрыв глаза на разрыв 2250–2300. Отклонено — прямо противоречит явному требованию пользователя, что в диапазоне 2250–2300 короб «НЕО» должен быть недоступен.

### 5. Frontend: фильтрация высоты короба

Добавляется `frameNeoHeightOptions(component, leafHeightValue)` — по образцу `edgeHeightOptions`, с той же формулой диапазона (`minValue`/`maxValue` вместо `minValue`/`value`). Рендер группы «Высота» в `App.tsx` (сейчас строка ~614) получает третью ветку:
```
step.key === 'edge'
  ? edgeHeightOptions(component, leafHeightValue)
  : step.key === 'frame' && component.type.code === 'FT-003'
    ? frameNeoHeightOptions(component, leafHeightValue)
    : component.dimensionOptions.filter((option) => option.dimensionType.code === HEIGHT_TYPE_CODE)
```
Сброс `selection.frame.heightOptionId` при смене высоты полотна добавляется в `updateSelection` рядом с уже существующим сбросом `next.edge.heightOptionId` (по тому же условию `isLeafHeightChange`).

`LinerDimensionOptionDto`/`types.ts` дополняются полем `maxValue: number | null`, параллельно уже существующему `minValue`.

### 6. Высота обязательна для короба «НЕО» (закрытие дыры в проверке)

Обнаружено при ручной проверке уже реализованной части: сейчас проверка совместимости вызывается только когда `heightOption != null` (см. Decision 3). Если клиент вообще не передаёт `heightOptionId` для frame-компонента с кодом `FT-003`, `validateHeightWithinLeafRange` не вызывается вовсе, и короб «НЕО» считается по цене (`framePostPrice`) без какой-либо проверки высоты. Из-за этого для высоты полотна, не покрытой ни одним диапазоном короба «НЕО» (2600–2850, 2900–2950 и любые будущие «дыры»), можно было получить успешный расчёт с этим коробом вообще без выбранной высоты — то есть именно та комбинация, которую вся эта фича должна была сделать невозможной, проходила через единственную лазейку: «не выбирать высоту вообще».

Решение: в ветке `if (type instanceof FrameType frameType)`, до вызова `validateHeightWithinLeafRange`, добавляется проверка — если `NEO_FRAME_TYPE_CODE.equals(frameType.getCode())` и `selection.heightOptionId() == null`, эндпоинт отвечает 400 («для короба «НЕО» необходимо выбрать высоту»). Существующая проверка `if (heightOption != null && ...)` остаётся без изменений для случая, когда высота передана. Для других типов короба (`FT-001`, `FT-002`) высота остаётся необязательной, как раньше.

**Альтернатива (отклонена):** считать отсутствие `heightOptionId` эквивалентным «высота вне диапазона» внутри самого `validateHeightWithinLeafRange`. Отклонено — это смешало бы два разных по смыслу условия (высота не выбрана / высота выбрана, но не подходит) в одном методе и потребовало бы менять сигнатуру вызова для кромки, где отсутствие высоты кромки по-прежнему допустимо.

### 7. Frontend: исключение короба «НЕО» из каскада при известной несовместимой высоте полотна

Шаг каскадного выбора короба (`CASCADE_ORDER`, ключ `frame`) вычисляет `availableTypes` в `applyCascadeStep` (App.tsx:175-208) — список типов короба, присутствующих хотя бы в одном из `candidates` (строк `door_configuration`, уже суженных предыдущими шагами `leaf`/`edge`). Эта функция ничего не знает о `leafHeightValue` и о `dimensionOptions` компонента — только о `door_configuration.frame.type`.

Осложняющий момент: `leafHeightValue` в `App.tsx` сейчас вычисляется ИЗ результата `buildCascadeSteps` (`cascadeSteps.find(...'leaf')?.resolvedComponent`, затем `leafComponent.dimensionOptions.find(...)`, App.tsx:387-392) — то есть высота полотна становится известна только ПОСЛЕ того, как каскад уже построен. Чтобы отфильтровать шаг `frame` по этой высоте, нужно знать её ДО построения этого шага.

Решение — двухпроходное построение каскада:
1. `buildCascadeSteps` вызывается первый раз без изменений (как сейчас) — из результата берётся `leafComponent`/`leafHeightValue`. Резолюция шага `leaf` не зависит от `leafHeightValue`, поэтому от второго прохода она не изменится.
2. `buildCascadeSteps` получает новый необязательный параметр `leafHeightValue: number | undefined`. Внутри цикла по `CASCADE_ORDER`, непосредственно перед `applyCascadeStep('frame', candidates, manualSelection)`, из `candidates` убираются конфигурации, где `configuration.frame?.type.code === NEO_FRAME_TYPE_CODE` и ни одна из опций высоты `configuration.frame.dimensionOptions` не покрывает `leafHeightValue` (если оно задано; если `leafHeightValue === undefined`, фильтр не применяется — «НЕО» остаётся в списке, как раньше). Формула диапазона переиспользуется из `frameNeoHeightOptions`, вынесенная в общий предикат (например, `neoFrameCoversHeight(component, leafHeightValue)`), чтобы не дублировать логику `min_value`/`max_value`/`value`-фолбэка.
3. Второй вызов подставляется на место текущего единственного вызова (App.tsx:387) — его результат (`cascadeSteps`, `selectedConfiguration`) используется дальше по коду вместо первого.

**Альтернатива (отклонена):** вынести резолюцию шага `leaf` в отдельную лёгкую функцию (`applyCascadeStep('leaf', collectionFilteredConfigurations, cascadeSelection)`) вместо повторного вызова всего `buildCascadeSteps`. Отклонено ради минимальности диффа — `buildCascadeSteps` уже дёшева (перебор небольшого списка конфигураций каталога), самостоятельная узкая функция добавила бы код без ощутимой выгоды.

**Риск, специфичный для этого decision:** если для конкретной пары leaf+edge короб «НЕО» — единственный доступный тип короба (нет альтернативного короба и нет варианта «без короба»), то после фильтрации `candidates` для шага `frame` станет пустым, `availableTypes.length === 0`, и, по уже существующей логике `applyCascadeStep` («Ни у одного кандидата нет этого компонента — выбирать нечего, шаг пропускается»), шаг короба просто исчезнет из UI — вместо явного сообщения «короб «НЕО» недоступен для этой высоты полотна» пользователь увидит так, будто короба у этой конфигурации вообще не предусмотрено. Это принятый риск (см. Risks ниже) — реализация более точного «заблокированного» состояния шага потребовала бы расширения типа `CascadeStep` и вынесена за рамки этой доработки; backend (Decision 6) в любом случае не даст оформить такую конфигурацию.

## Risks / Trade-offs

- **[Риск]** Разрыв 2250–2300 и разрывы 2600–2850, 2900–2950 не выражаются отдельными строками «недоступности» — они возникают неявно, как отсутствие подходящей опции. → Это тот же принцип, что уже используется для кромки (разрывы между диапазонами кромки тоже никак явно не помечены) — консистентно с прецедентом, риск принят.
- **[Риск]** Расширение уникального индекса — операция на существующей таблице; на проде это `DROP INDEX` + `CREATE UNIQUE INDEX`, требует блокировки на запись на короткое время. → Таблица `liner_dimension_option` небольшая (справочник, не транзакционные данные), простой краткий; выполняется в отдельном changeset.
- **[Риск]** Добавление валидации/`validatedDimensionOption` вызова в ветку `FrameType` меняет поведение для *любого* `heightOptionId`, ранее присланного для frame-компонента (раньше он тихо игнорировался, теперь будет проверяться на существование и принадлежность). → Осознанно: раньше это было просто нереализованной проверкой (данных для проверки не было), нового `heightOptionId` для frame ранее в принципе не могло быть валидным, так как опций не существовало — риска регрессии для существующих клиентов нет.
- **[Риск]** Обязательность высоты для `FT-003` (Decision 6) — потенциально breaking для клиента API, который раньше мог не передавать `heightOptionId` для короба «НЕО» и получать расчёт без проверки. → Осознанно принято: до этого change у короба «НЕО» вообще не было опций высоты в БД, поэтому ни один существующий клиент не мог полагаться на «короб «НЕО» без высоты» как на рабочий сценарий — опции появляются в рамках этого же change.
- **[Риск]** Двухпроходный `buildCascadeSteps` (Decision 7) и связанный с ним риск исчезновения шага «короб» из UI, если «НЕО» — единственный вариант для данной пары leaf+edge при несовместимой высоте полотна. → См. разбор в конце Decision 7; смягчается тем, что backend (Decision 6) не даст завершить такую конфигурацию расчётом в любом случае — риск чисто UX-овый, не функциональный.

## Migration Plan

1. Liquibase-миграция №1: `addColumn max_value` в `liner_dimension_option` (nullable, без данных).
2. Liquibase-миграция №2: `DROP INDEX` + `CREATE UNIQUE INDEX` для `uk_liner_dimension_option_frame_type` с новыми колонками.
3. Liquibase-миграция №3: вставка данных высоты короба «НЕО» (`frame_type_id` = id `FT-003`, `liner_dimension_type_id` = id `DT-002`) — 4 строки с `value`/`min_value`/`max_value` по бизнес-данным, `is_standard = true`.
4. Backend-код: обобщение `validateHeightWithinLeafRange`, изменение ветки `FrameType`, обновление DTO/маппинга.
5. Frontend-код: `frameNeoHeightOptions`, изменение рендера группы «Высота», сброс выбора при смене высоты полотна, обновление типов.
6. Тесты: новые кейсы в `DoorConfigurationPricingServiceTest` по аналогии с кейсами кромки (внутри диапазона / вне диапазона / выбрана высота короба без высоты полотна / разрыв между диапазонами / точка 2300 отдельно от диапазона 2150–2250).
7. Backend-код (доп. правка): обязательность `heightOptionId` для `FrameType` с кодом `FT-003` (Decision 6) + тест.
8. Frontend-код (доп. правка): вынесение предиката диапазона в переиспользуемую функцию, двухпроходный `buildCascadeSteps` с фильтрацией шага `frame` по `leafHeightValue` (Decision 7).

Откат — стандартный (новые миграции — новые changeset'ы, откат через Liquibase `rollback`, если потребуется; данные короба «НЕО» и код валидации откатываются вместе, не затрагивая остальные типы).
