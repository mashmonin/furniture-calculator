## Context

См. proposal.md - Why. API уже отдаёт `panelType` в leaf-компоненте (`backend/.../dto/ComponentCatalogDto.java`, добавлено в change `add-leaf-panel-type`). На фронте `frontend/src/api/types.ts` описывает `ComponentCatalogDto`, но без этого поля (лишний JSON-ключ сейчас просто игнорируется). Карточка «Параметры выбранного полотна» рендерится в `renderCascadeStep` (frontend/src/App.tsx, ветка для `step.key === 'leaf'`) через `component = step.resolvedComponent`.

## Goals / Non-Goals

**Goals:**
- Показать тип полотна текущего выбранного leaf-компонента человекочитаемой подписью.
- Согласовать TS-тип каталога с фактическим API-контрактом.

**Non-Goals:**
- Фильтрация каталога/коллекций по типу полотна (в отличие от коллекции и исполнения зеркала, тип полотна не сужает последующие шаги — см. proposal.md).
- Любые изменения запроса расчёта стоимости.
- Отображение типа полотна где-либо, кроме карточки параметров полотна (например, в разбивке итоговой цены).

## Decisions

- **Тип на фронте**: `panelType: 'BLIND' | 'GLAZED' | 'MIRRORED' | null` в `ComponentCatalogDto` — зеркалит Java enum `LeafPanelType`, сериализуемый Jackson как строка; `null` для компонентов, отличных от leaf (как и на backend).
- **Словарь подписей и визуальный стиль (пересмотрено по макету Figma)**: константа `LEAF_PANEL_TYPE_OPTIONS` (код → синтетический id → подпись: «Глухое», «С остеклением», «Зеркальное» — формулировки и порядок взяты из макета, node `#6:57`) вместо изначального `LEAF_PANEL_TYPE_LABELS`. Отображается через существующий `OptionGroup` (variant `buttons`, т. е. `Radio.Group block` + `Radio.Button`) — тот же визуальный компонент, что уже используют «Кромка», «Короб», «Толщина полотна», и который в точности соответствует сегментированному переключателю на макете. Интерактивность отключена не через `disabled` (это увело бы цвет выбранной кнопки от макета — antd гасит акцентный синий у disabled-радио), а через `onChange={() => {}}`: `selectedId` остаётся производным от `component.panelType`, поэтому клик по другой кнопке не меняет подсветку — реально ничего не выбирается, как и требует spec.md.
- **Место отображения (пересмотрено по явному указанию пользователя)**: в одном ряду с `OptionGroup` «Коллекция» (`flex` row, `gap: 16`, оба элемента `flex: 1` — тот же паттерн, что уже используется для парных полей, например в секции «Фурнитура»), а не внутри `Card` «Параметры выбранного полотна». Значение по-прежнему читается из `leafComponent` (та же переменная, что уже вычисляется в компоненте на основе первого прохода `buildCascadeSteps` для `leafHeightValue`, — resolvedComponent шага `leaf` идентичен в первом и втором проходах, так как сам шаг `leaf` от `leafHeightValue` не зависит). Пока конкретная модель полотна не выбрана (`leafComponent` не определён), второй элемент ряда не рендерится — ряд временно состоит из одной «Коллекции», растянутой на всю ширину; как только модель выбрана, «Тип полотна» появляется рядом.
  - Альтернатива (отклонена, был первоначальный выбор): внутри карточки «Параметры выбранного полотна» — визуально корректно, но не совпадало с раскладкой макета (там переключатель в верхнем ряду рядом с «Коллекция», до блока «Модель»); пользователь явно попросил разместить его там же, где на макете.
  - Альтернатива (отклонена): `Tag` в `extra` заголовка `Card` — не соответствует макету, где тип полотна показан как сегментированный переключатель, а не бейдж.

## Risks / Trade-offs

- [Пользователь может не понять смысл подписи без контекста] → короткая подпись рядом с остальными техническими атрибутами полотна (длина/высота/толщина/цвет) читается как ещё один параметр модели, что соответствует остальной карточке.
