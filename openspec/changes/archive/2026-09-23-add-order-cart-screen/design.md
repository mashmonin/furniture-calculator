## Context

См. proposal.md — почему нужна корзина заказа. Здесь — как она устроена технически.

Сейчас `frontend/src/App.tsx` — единственный компонент (~2200 строк), без роутинга (в зависимостях только `antd`/`react`/`react-dom`, `react-router` нет и не добавляется по CLAUDE.md — только antd-компоненты, других UI/навигационных библиотек не вводим). Экран — три колонки (`app-sidebar`/`app-main`/`app-pricing`), state хранится через `useState` прямо в `App`. Кнопка «Скачать excel спецификацию» (`handleExportSpecification`) уже строит `SpecificationExportRequestDto` из всего текущего состояния выбора и скачивает файл через `exportSpecification()` (см. `frontend/src/api/*`) → `POST /api/specification/export` → `SpecificationExportService.export()` на бэкенде, который использует уже существующий `DoorConfigurationPricingService.resolveSpecificationComponents(request)` для получения посчитанных `ComponentPriceDto`/`HardwarePriceDto` и раскладывает их по листу `.xlsx`.

Макет (Figma, node `43:521`, «Корзина заказа») показывает: общую шапку с постоянной ссылкой «Корзина» + счётчик; левое меню с пунктом «Корзина заказа»; таблицу позиций заказа с раскрываемой по кнопке «Посмотреть» детализацией каждой позиции (та же информация, что уже есть в `pricingResult` конфигуратора); редактируемое количество (шаговый счётчик), сумму = цена за единицу × количество; сводку и панель выгрузки заказа в один excel-файл.

## Goals / Non-Goals

**Goals:**
- Добавить экран «Корзина заказа», переключение на него и обратно без перезагрузки страницы и без новых зависимостей.
- Переиспользовать уже посчitанный на экране конфигуратора `pricingResult` при добавлении в корзину — никаких новых расчётных запросов при просмотре/раскрытии позиции корзины или при изменении количества.
- Один новый backend-эндпоинт для выгрузки всего заказа одним `.xlsx`, переиспользующий существующую построчную логику `resolveSpecificationComponents` без её дублирования.

**Non-Goals:**
- Авторизация, серверное хранение корзины, синхронизация между устройствами/вкладками — корзина живёт только в `localStorage` текущего браузера (см. proposal.md, подтверждено пользователем).
- Пересчёт цены на бэкенде при изменении количества в корзине — сумма позиции считается на фронте как `цена_за_единицу × количество`, без нового запроса (см. «Количество и сумма позиции» ниже).
- Новый общий роутинг/история браузера (`history.pushState`, deep-link на `/cart`) — просто переключение видимого экрана в памяти приложения; при обновлении страницы всегда открывается экран конфигуратора (сама корзина при этом не теряется — она в `localStorage`, теряется только текущий «какой экран открыт»).
- Отдельная категория «входная дверь»/«межкомнатная дверь» для статус-тега позиции — в приложении сейчас единственный вид изделия (межкомнатные двери, сервис «Эмаль и шпон»); статус-тег в таблице корзины показывает фиксированный текст «МЕЖКОМНАТНАЯ ДВЕРЬ» для всех позиций, без нового поля в данных (в макете второй пример — «ВХОДНАЯ ДВЕРЬ» — иллюстративный, реального такого различия в каталоге нет).
- Пункт «Фурнитура» в левом меню (виден в макете рядом с «Корзина заказа») — самостоятельная фурнитура как отдельный сервис не входит в этот change; выбор фурнитуры остаётся частью конфигуратора, как сейчас. Пункт не добавляется.

## Decisions

### Разбиение `App.tsx` на компоненты и переключение экрана
`App.tsx` становится тонкой оболочкой: хранит состояние текущего экрана (`type AppScreen = 'configurator' | 'cart'`, `useState<AppScreen>('configurator')`), состояние корзины (см. ниже) и рендерит общую шапку + левое меню один раз, а внутри — оба экрана как компоненты (`ConfiguratorScreen.tsx` — весь нынешний код `App.tsx`, перенесённый как есть, с добавлением пропа-колбэка добавления в корзину вместо старого `handleExportSpecification`; новый `CartScreen.tsx`), одновременно смонтированные, но видимым остаётся только текущий (`style={{ display: screen === 'configurator' ? undefined : 'none' }}` на обёртке каждого, а не условный рендер `screen === 'x' && <.../>`). Так незавершённый (ещё не добавленный в корзину) выбор в конфигураторе — раскрытый аккордеон, введённые размеры, выбранная кромка и т.д. — не теряется при переходе в корзину и обратно: компонент не размонтируется, локальный `useState` внутри `ConfiguratorScreen` сохраняется как есть. Альтернатива — условный рендер (`{screen === 'configurator' && <ConfiguratorScreen />}`) — отклонена: он бы размонтировал конфигуратор при каждом уходе в корзину, сбрасывая весь его локальный стейт. Альтернатива с `react-router` — тоже отклонена: экрана два, переключение тривиальное, а роутинг добавил бы новую зависимость ради функциональности, которая не нужна (глубокие ссылки, история не требуются по Non-Goals).

### Модель данных корзины и хранение
Корзина — массив позиций в `localStorage` (ключ `door-configurator:cart`, версионированный JSON, как у прочих клиентских настроек в этом приложении — по аналогии с уже существующими паттернами чтения/записи `localStorage`, если такие есть в проекте, иначе — обычный `JSON.parse`/`JSON.stringify` с try/catch на случай повреждённых данных). Одна позиция:

```ts
interface CartItem {
  id: string                 // crypto.randomUUID() — локальный идентификатор строки корзины, не связан с БД
  addedAt: string            // ISO-дата добавления, для сортировки/отображения при желании
  quantity: number           // редактируемое количество, по умолчанию 1
  displayName: string        // например "Вертикаль 01" — имя leaf_type на момент добавления
  dimensionsLabel: string    // например "600 × 2000 × 44 мм" — уже отформатированная строка
  exportRequest: SpecificationExportRequestDto  // тот же объект, что сегодня уходит в /api/specification/export — переиспользуется для выгрузки заказа
  pricingSnapshot: {
    // срез уже посчитанного pricingResult на момент добавления — используется и для цены за единицу
    // в таблице корзины, и для разворачиваемой детализации, без нового запроса к API
    totalRetailPrice: number
    totalDealerPrice: number
    components: ComponentPriceDto[]
    hardware: HardwarePriceDto[]
  }
}
```

`exportRequest` — это в точности то, что сегодня строит `handleExportSpecification` перед вызовом `exportSpecification()`; `pricingSnapshot` — срез уже имеющегося на момент клика `pricingResult` (оба типа уже определены в `frontend/src/api/types.ts`, ничего нового вводить не нужно). Хранить именно снимок цены, а не только `exportRequest`, — чтобы таблица корзины и раскрытая детализация отображались мгновенно, без похода на бэкенд, и не менялись, если каталог/цены изменятся после добавления в корзину (соответствует подсказке в макете: «При изменении конфигурации цены будут пересчитаны» — имеется в виду, что если пользователь ещё раз изменит и добавит ту же конфигурацию заново, будет новая позиция с новым снимком, а не то, что старая позиция сама пересчитывается).

### Добавление в корзину заменяет скачивание файла
`handleExportSpecification` переименовывается в `handleAddToCart` (или аналогично) и вместо вызова `exportSpecification()` формирует `CartItem` (переиспользуя уже существующий код сборки `SpecificationExportRequestDto` из состояния — эта часть не меняется) и добавляет его в состояние корзины (проп/колбэк из `App.tsx`, персистится в `localStorage` сразу же). Кнопка переименовывается в «Добавить в корзину»; `exportError`/`exportLoading` больше не нужны для этого пути (добавление в корзину — синхронная операция, сети не требует) — переименовываются или заменяются на простое состояние подтверждения (например, кратковременное сообщение «Добавлено в корзину»).

### Количество и сумма позиции
Шаговый счётчик (−/+, как в макете) меняет `quantity` в состоянии корзины напрямую; сумма позиции в таблице — `pricingSnapshot.totalRetailPrice × quantity`, вычисляется в рендере, не хранится отдельно. Дилерская цена по позиции с учётом количества нигде в таблице заказа не показывается (как и в макете) — только розничная сумма; дилерская цена видна лишь внутри раскрытой детализации, за одну единицу (как сегодня в `pricingResult.components`).

### Раскрываемая детализация — переиспользование существующего рендера
«Посмотреть»/раскрытие строки в таблице корзины показывает ровно то же самое разбиение по компонентам (наименование, размер, цвет, количество, базовая/итоговая цена розница и дилер), что сегодня показывает разбивка результата расчёта на экране конфигуратора (см. door-configurator-ui, «Отображение базовой цены рядом с ценой компонента», «Разбивка надбавок...», после change `show-surcharges-under-component-price`) — тот же самый `List`/рендер-функция по `pricingSnapshot.components`/`pricingSnapshot.hardware`, вынесенная в переиспользуемую функцию/компонент, чтобы не дублировать разметку. Реализуется через `Table` (`antd`) с `expandable.expandedRowRender` — идиоматичный для antd способ показать раскрываемую вложенную таблицу в строке, вместо кастомного аккордеона.

### Backend: выгрузка всего заказа одним файлом
Новый эндпоинт `POST /api/specification/export-order`, принимающий `List<OrderLineExportRequestDto>` (новый record: `SpecificationExportRequestDto` + `int quantity` + `String displayName` на позицию). Сервис (`OrderExportService`, аналогичен по стилю `SpecificationExportService`) для каждой позиции вызывает уже существующий `DoorConfigurationPricingService.resolveSpecificationComponents(...)` (без изменений в нём) и собирает один `.xlsx`:
- лист «Сводка»: по одной строке на позицию — №, наименование, параметры, цена за единицу, количество, сумма; последняя строка — итог по заказу (совпадает с суммой всех строк);
- по одному листу «N. <наименование>» на каждую позицию — тот же формат строк и колонок, что уже использует `SpecificationExportService` для одиночной выгрузки (переиспользуем приватные методы построения строк напрямую или через общий protected/package-private helper — без копирования логики).

Имя файла — то же соглашение, что и сегодня: `Заказ-от-DD-MM-YY.xlsx` (см. `SpecificationExportController`, уже так называет одиночный файл).

## Risks / Trade-offs

- [Дублирование логики построения строк спецификации между `SpecificationExportService` (одна конфигурация) и новым `OrderExportService` (несколько)] → Новый сервис вызывает существующие приватные/package-private helper-методы построения разделов листа (после рефакторинга их видимости, если нужно), а не копирует код; общий `resolveSpecificationComponents` не меняется.
- [`localStorage` может быть недоступен или переполнен (приватный режим браузера, отключённое хранилище)] → Обёртка чтения/записи корзины оборачивается в try/catch; при ошибке корзина ведёт себя как пустая в текущей сессии (та же деградация, что и у прочих клиентских настроек), без падения приложения.
- [Снимок цены в корзине может разойтись с актуальным прайс-листом, если тот обновится после добавления] → Сознательный trade-off (см. Non-Goals) — корзина хранит цену на момент добавления, как обычная торговая корзина; итоговый пересчёт «по факту» — вне рамок этого change.
- [Перенос текущего содержимого `App.tsx` в `ConfiguratorScreen.tsx` — большой рефакторинг ради малой на вид фичи] → Необходим, так как без него негде разместить переключение экранов и общую шапку/меню без дублирования; ограничиваем рефакторинг чисто механическим переносом (без переписывания логики), чтобы не расширять риск регрессии на не связанную с корзиной функциональность.

## Migration Plan

Изменений схемы БД нет — миграция не требуется. Деплой — обычная выкладка бэкенда (новый эндпоинт, аддитивный, не ломает существующий `/api/specification/export`) и фронтенда. У пользователей, уже открывавших приложение, при первом заходе после обновления `localStorage` ключ корзины отсутствует — считается пустой корзиной, без ошибок.
