## Context

См. `proposal.md` — «Why» и «What Changes». Ключевые факты о текущей реализации, определяющие подход:

- Цена полотна (`leaf`) сейчас — плоская сумма, не зависящая от длины/высоты: все `configuration_price` для `leaf_type` имеют `length_option_id`/`height_option_id` = NULL (например, `0009-vertikal-configuration-prices.yaml`, `0018-atmosfera-leaf-prices.yaml`). Значит, «базовая» цена полотна для наценки за размер — это ровно та же цена, что находится сегодня через `findMostSpecificPrice`, только по цвету (без учёта длины/высоты).
- Стандартные каталожные размеры полотна одинаковы во всех коллекциях: длина 400/600/700/800 мм, высота 2000/2100 мм (`liner_dimension_option`, `leaf_type_id IS NOT NULL`). Ни одно значение из присланной пользователем таблицы наценок (см. proposal) не совпадает со стандартными — пересечений нет.
- `DoorConfigurationPricingService.calculate()` уже применяет один процентный множитель к цене leaf-компонента — надбавку за реверс (`REVERSE_SURCHARGE_MULTIPLIER = 1.10`, `applyReverseSurcharge`). Комментарий в коде уже называет текущий способ временным и предполагает в будущем движок бизнес-правил (Drools) — этот change вводит второй, независимый процентный множитель того же рода, но не трогает существующий механизм реверса и не объединяет их в общую абстракцию.
- `ComponentSelectionDto`/`PricingRequestDto` — простые Java-record'ы без сеттеров, расширяются добавлением новых полей.
- Пользователь описал наценки в сантиметрах; в БД все размеры хранятся в миллиметрах — подтверждено умножение на 10 при заполнении данных.

## Goals / Non-Goals

**Goals:**
- Клиент может задать длину и/или высоту полотна произвольным значением (в мм) вместо выбора из каталожного списка.
- Нестандартные, но известные фабрике размеры дают точно определённую процентную наценку к цене полотна.
- Совсем неизвестные фабрике размеры отклоняются как невалидный ввод (400), а не тихо принимаются без наценки или с произвольной ценой.
- Правила наценки хранятся как явный, обособленный справочник в БД (Liquibase), редактируемый так же, как остальные справочники проекта — без добавления новой библиотеки/движка правил.

**Non-Goals:**
- Не подключается реальный движок Drools — это простой табличный справочник + сервисная логика, воспроизводящая идею «внешних бизнес-правил» без новой инфраструктуры.
- Не объединяется с существующей надбавкой за реверс в общую абстракцию «правил» — они остаются двумя независимыми процентными множителями к цене leaf-компонента. Объединение — естественный следующий шаг, но вне рамок этого change.
- Не распространяется на другие компоненты (кромка, короб, наличник, добор) и не варьируется по коллекции/модели полотна — справочник наценок глобален и зависит только от типа размера (длина/высота) и конкретного значения.
- Не вводится частичная/приближённая наценка для значений между известными точками (например, интерполяция) — только точное совпадение с конкретным значением правила.

## Decisions

**Справочник наценок — плоская таблица (liner_dimension_type, value, surcharge_percent), не связанная с leaf_type/коллекцией.**
Присланная фабрикой таблица не различает коллекции или модели — наценка зависит только от того, какая ось (длина/высота) и какое конкретное значение выбрано. Отдельная сущность `DimensionSurchargeRule`, а не расширение `liner_dimension_option` (которая описывает *допустимые* размеры конкретного владельца), потому что смысл разный: `liner_dimension_option` — «что вообще можно выбрать», `dimension_surcharge_rule` — «сколько это стоит дополнительно», причём последнее не привязано к владельцу.

**Порядок разрешения произвольного значения: сначала стандартный размер, потом правило наценки, иначе — ошибка.**
Если бы произвольное значение, совпадающее со стандартным размером (например, клиент напечатал «600» в поле «Другое» вместо выбора из списка), не проверялось на совпадение со стандартом первым, пришлось бы либо запрещать «случайное» совпадение (плохой UX), либо задавать в таблице наценок ещё и «нулевые» правила для каждого стандартного размера каждого полотна (дублирование данных, которое рассинхронизируется при будущих изменениях каталога). Проверка «сначала стандарт» решает это без дублирования.

**Наценка за длину, наценка за высоту и надбавка за реверс применяются последовательно, каждый раз с округлением промежуточного результата, а не единым перемножением коэффициентов.**
Порядок: (1) к базовой цене полотна применяется наценка за длину → сумма₁ (округление HALF_UP до целого, как и у остальных процентных модификаторов сервиса); (2) к сумме₁ применяется наценка за высоту → сумма₂; (3) если конфигурация реверсивная — к сумме₂ применяется надбавка за реверс → итоговая цена. Шаг для отсутствующей наценки (нет нестандартного размера по оси, конфигурация не реверсивная) пропускается, не влияя на промежуточный результат. Порядок и промежуточное округление на каждом шаге заданы явно по требованию пользователя — это отличается от прежнего решения (единое перемножение коэффициентов без промежуточного округления, где порядок был безразличен) и делает схему применения наценки за размер единообразной с уже существующей схемой округления после каждого умножения на процентный коэффициент (`applyPercentMultiplier`).

**Отклонение полностью неизвестного значения — ошибка 400, а не «цена не найдена» (0 некалькулируемый компонент).**
Для большинства компонентов отсутствие подходящей `configuration_price` — штатная ситуация («компонент без цены», расчёт продолжается по остальным). Здесь другое: неизвестное значение размера — это в принципе невозможный для производства размер, а не просто отсутствие прайса на существующий вариант. Пользователь явно выбрал этот вариант ответа при уточнении.

**Именование новых полей запроса — `customLengthValueMm`/`customHeightValueMm`, не переиспользование `lengthOptionId` с отрицательным/специальным значением.**
Явные отдельные поля читаемее и не создают риска коллизии с реальными id (в отличие, например, от `NONE_OPTION_ID = 0`, который работает, потому что реальные id всегда положительны, но такой трюк для произвольного числового значения непригоден).

**Входное поле на фронтенде — в миллиметрах, не в сантиметрах.**
Вся остальная система (стандартные варианты, отображаемые значения) уже оперирует миллиметрами. Ввод в других единицах именно в этом одном поле был бы источником путаницы; конвертация сантиметров фабрики в миллиметры уже сделана один раз — при заполнении справочника наценок.

## Risks / Trade-offs

- **[Trade-off]** Ошибка 400 на «фабрика не производит такой размер» может показаться пользователю резкой (в отличие от мягкого «цена не найдена» у остальных компонентов). Это осознанный выбор пользователя при уточнении; сообщение на фронтенде должно быть понятным (см. UI-спеку: страница показывает сообщение об ошибке, не теряя введённое значение, чтобы клиент мог его поправить).
- **[Risk]** Значение «45\*» в присланной таблице содержит звёздочку неясного значения (вероятно, сноска из исходного прайс-листа фабрики, не имеющая отношения к числу). Учтено как обычное значение 450 мм с наценкой 20% — если звёздочка означала что-то содержательное (другое условие, другую наценку), нужно будет скорректировать данные отдельным changeset'ом после уточнения с пользователем.
- **[Risk]** Если в будущем наценка должна будет варьироваться по коллекции/модели полотна, текущая плоская структура (без ссылки на leaf_type) потребует пересмотра — осознанно отложено как Non-Goal, добавить владельца можно будет так же, как это сделано у `liner_dimension_option`/`colour_option`/`configuration_price` (опциональная ссылка на владельца).

## Migration Plan

1. Новый changeset: создать таблицу `dimension_surcharge_rule` (id, liner_dimension_type_id FK, value DECIMAL, surcharge_percent DECIMAL, unique(liner_dimension_type_id, value)); заполнить 19 строками наценок (9 — длина, 10 — высота) по присланной таблице, переведёнными из см в мм.
2. Backend: сущность `DimensionSurchargeRule` + репозиторий с поиском по (liner_dimension_type_id, value); `ComponentSelectionDto`/`PricingRequestDto` — новые опциональные поля `customLengthValueMm`/`customHeightValueMm`; `DoorConfigurationPricingService` — валидация (конфликт id/произвольного значения, произвольное значение не для leaf) и разрешение произвольного значения (стандарт → без наценки; правило → наценка; иначе → 400), применение наценки к цене leaf мультипликативно вместе с надбавкой за реверс.
3. Frontend: `ComponentSelectionDto`/`PricingRequestDto` (типы) — новые поля; `App.tsx` — числовое поле «Другое значение» рядом с группами «Длина»/«Высота» компонента «Полотно», взаимоисключающее со стандартным выбором; обработка ошибки 400 в существующем потоке ошибок расчёта.
4. Проверка: unit-тесты `DoorConfigurationPricingService` (совпадение со стандартом, совпадение с правилом, неизвестное значение → 400, конфликт id+значения → 400, значение не для leaf → 400, перемножение с надбавкой за реверс); `./gradlew test`; ручная/API-проверка нескольких точек таблицы наценок; `npm run build`/`lint`.

Откат — по конвенции проекта: новые компенсирующие changeset'ы, не редактирование уже применённых.
