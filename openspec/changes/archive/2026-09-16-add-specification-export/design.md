## Context

См. proposal.md — «Why». Технический контекст, установленный исследованием перед написанием этого change:

- В проекте нет вообще никакой библиотеки для генерации файлов (Excel/иное) и нет ни одного эндпоинта, отдающего бинарный файл (`Content-Disposition`) — это полностью новая для backend возможность.
- Ответы существующих трёх этапных эндпоинтов расчёта (`ComponentPriceDto`, `HardwarePriceDto` — кроме неё) почти не содержат описательных данных: `ComponentPriceDto` — это `(component: String — просто ключ вида "leaf"/"frame"/..., priced, retailPrice, dealerPrice, baseRetailPrice, baseDealerPrice)`, без наименования выбранного типа, размеров в мм и цвета. `HardwarePriceDto` — исключение, он уже описательный (`category`, `type`: `ReferenceDto`, `colourName`).
- В `DoorConfigurationPricingService.addComponentIfPresent` (и в ветке короба — `framePostPrice`) выбранные `LinerDimensionOption`/`ColourOption`/сам `CatalogType` уже находятся в области видимости именно там, где находится цена (`lengthOption`, `heightOption`, `thicknessOption`, `colourOption`, `type` — все резолвятся раньше `findMostSpecificPrice`) — но `componentPriceFrom`/`framePostPrice` строят `ComponentPriceDto` только из цены и наценок, без этих объектов. Расширять сами `ComponentPriceDto`/эндпоинты не нужно — данные уже рядом, их просто нужно донести до нового кода, не меняя существующий контракт.
- Фронтенд уже держит (как готовое состояние/производные константы) весь набор данных, нужный для комбинированного запроса экспорта: `leafTypeId`, `edgeTypeId`, `frameTypeId`, `doorCasingTypeId`, `frameExtensionsTypeId`, `selection.{leaf,edge,frame,doorCasing,frameExtensions}`, `hardwareLines`, `resolvedReverse`, `leafHeightValue` — эндпоинт экспорта можно собрать из них без нового состояния.
- Кнопка экспорта в Figma-макете (узел `#6:397`) — сплошная синяя (primary) кнопка на всю ширину панели результата, без иконки, текст «Скачать excel спецификацию», расположена в самом низу sticky-панели, после блока «Фурнитура в расчете».

## Goals / Non-Goals

**Goals:**
- Один новый эндпоинт, отдающий `.xlsx`-файл, рассчитывающий цены на backend теми же правилами, что и три существующих этапных эндпоинта (не доверяя ценам с клиента).
- Переиспользовать существующую ценовую логику `DoorConfigurationPricingService`, не дублируя её и не меняя контракты уже существующих эндпоинтов.
- Кнопка на фронте — по месту и виду из макета, без нового постоянного состояния сверх уже имеющегося.

**Non-Goals:**
- Не вводим сохранение сгенerированных файлов (каждый запрос — расчёт и генерация заново, без персистентности).
- Не вводим форматы, отличные от `.xlsx` (PDF и др. — вне скоупа).
- Не меняем существующие эндпоинты расчёта стоимости и их контракты.
- Не создаём отдельный «конструктор» произвольной структуры файла — раскладка на 4 раздела фиксирована кодом, не настраивается через запрос.

## Decisions

### Библиотека генерации Excel — Apache POI (`poi-ooxml`)
Стандартный и единственный де-факто выбор для генерации `.xlsx` на Java/Spring; уже доступен через `mavenCentral()` (единственный репозиторий, уже подключённый в `backend/build.gradle`). Добавляется `implementation 'org.apache.poi:poi-ooxml:5.3.0'` (актуальная стабильная версия на момент разработки — точную версию сверить при реализации).

### Один комбинированный запрос, поля — объединение трёх существующих
Новый DTO `SpecificationExportRequestDto` объединяет поля `PricingRequestDto` (leaf-стадия: `leaf`, `edgeTypeId`, `edge`, `isReverse`) и `FrameGroupPricingRequestDto` (frame-стадия: `frame`, `doorCasingTypeId`, `doorCasing`, `frameExtensionsTypeId`, `frameExtensions`, `leafHeightValue`) плюс `hardware: List<HardwareSelectionDto>` — но, в отличие от них, `leafTypeId` и `frameTypeId` (наравне с `doorCasingTypeId`/`frameExtensionsTypeId`/`edgeTypeId`) становятся полями тела запроса, а не path-параметром: у комбинированного запроса нет единого «владельца» пути, как у трёх раздельных стадий. `leafTypeId` — обязательное поле (без него нечего экспортировать); остальные — опциональны, как и в исходных стадийных запросах.

Альтернатива — эндпоинт, принимающий `door_configuration_id` (как старый комбинированный `/api/door-configurations/{id}/price`) — отклонена: фронтенд с прошлого change (frontend-staged-pricing) больше не оперирует единым `door_configuration_id`, вся сборка идёт по отдельным id компонентов; требовать его обратно означало бы восстанавливать уже убранную логику.

### Переиспользование ценовой логики — общий внутренний метод резолва, а не дублирование
`addComponentIfPresent`/`framePostPrice` рефакторятся так, чтобы резолв (валидация опции + подбор `ConfigurationPrice` + вычисление итоговой цены с наценками) возвращал не только `ComponentPriceDto`, но и достаточно данных, чтобы вызывающий код мог построить описательную строку — либо через новый параллельный приватный метод, разделяющий с `addComponentIfPresent` вызовы `validatedDimensionOption`/`validatedColourOption`/`findMostSpecificPrice`/`applySequentialSurcharges`, либо через небольшой внутренний record-результат (`type`, `lengthOption`, `heightOption`, `thicknessOption`, `colourOption`, итоговая `ComponentPriceDto`), из которого `addComponentIfPresent` берёt только `ComponentPriceDto` (как сейчас), а новый сервис экспорта — все поля. Выбор конкретной формы рефакторинга — на этапе реализации; ключевое ограничение: ценовая арифметика (включая последовательность наценок) не должна существовать в двух местах.

Новый сервис (`SpecificationExportService` или аналогичный) вызывает этот общий резолв для каждого применимого компонента (leaf, edge, frame + его frame_post, doorCasing, frameExtensions) и `priceHardwareSelections` (уже существующий, без изменений — `HardwarePriceDto` уже описательный) для фурнитуры, раскладывая результат по 4 разделам.

### Структура файла — один лист, разделы компонентов + завершающий раздел надбавок, общие колонки
Один Excel-лист (не отдельные вкладки) — читается/печатается как единый документ-спецификация, без переключения вкладок. Разделы компонентов (1–4, см. «Разделы файла спецификации») идут друг за другом с заголовком-разделителем; колонки одинаковы во всех разделах (чтобы не путать структуру при чтении сверху вниз): Наименование, Измерения (мм — применимые оси через `*`, например `900*2400*44`, вместо отдельной колонки на каждую ось), Цвет, Количество, Итоговая цена (₽), Базовая цена розница (₽) — цена без наценок, Цена дилер (₽), Базовая цена дилер (₽) — ячейки, неприменимые для конкретной строки (например, измерения у фурнитуры), остаются пустыми, а не нулевыми/дефисными (кроме специально нулевого случая «цена не найдена» — см. specs, там именно прочерк, сигнализирующий об отсутствии цены, а не о неприменимости поля). Под строкой полотна — строки выбранных опций (тип открывания, если реверс; исполнение зеркала/вид остекления, если выбраны), без собственной цены. Если к цене полотна применены надбавки, файл ДОПОЛНИТЕЛЬНО завершается отдельным разделом «Надбавки к цене полотна» (с той же общей раскладкой колонок, но только наименованием — проценты, без цены) — под всей таблицей расчётов, а не внутри раздела полотна (см. specs, «Надбавки к цене полотна в файле»).

### Скачивание на фронте — без новых npm-зависимостей
Стандартный паттерн: `fetch` → `response.blob()` → `URL.createObjectURL` → синтетический клик по `<a download>` → `URL.revokeObjectURL`. Имя файла берётся из `Content-Disposition` заголовка ответа, если он его содержит, иначе — запасное имя по умолчанию.

## Risks / Trade-offs

- **[Риск]** Рефакторинг `addComponentIfPresent`/`framePostPrice` — уже нетривиальный, много раз изменённый метод с плотной бизнес-логикой (диапазоны высот, реверс, наценки). Ошибка при выделении общей части может незаметно сломать существующий расчёт. → Рефакторинг обязан сохранить 100% существующее поведение трёх этапных эндпоинтов — после рефакторинга обязательный прогон существующего набора тестов `DoorConfigurationPricingServiceTest` (точечно, см. заметку про `--tests`), не только новых.
- **[Риск]** Расхождение цены в Excel с ценой, только что показанной в sticky-панели (например, если между расчётом на экране и нажатием кнопки кто-то поменял прайс-лист в БД — маловероятно для локального демо, но принципиально возможно). → Не устраняется этим change: экспорт всегда пересчитывает на backend в момент запроса, это и есть источник истины, а не «заморозка» ранее показанных чисел с фронта.
- **[Риск]** Новая тяжёлая зависимость (Apache POI) увеличивает время сборки/размер артефакта backend. → Стандартная и ожидаемая цена за нативную генерацию `.xlsx`; альтернатив без соответствующего трейд-оффа на JVM не существует.

## Migration Plan

1. `backend/build.gradle` — добавить `poi-ooxml`.
2. Backend: рефакторинг общего резолва в `DoorConfigurationPricingService`; новый `SpecificationExportRequestDto`; новый сервис генерации Excel; новый контроллер `POST /api/specification/export`.
3. Frontend: `frontend/src/api/doorConfigurations.ts` (новая функция, возвращающая `Blob`/`Response`), `frontend/src/App.tsx` (кнопка, сборка запроса, скачивание, состояние загрузки/ошибки).
4. Точечные backend-тесты на новую логику + весь `DoorConfigurationPricingServiceTest` (проверка отсутствия регрессии после рефакторинга), `compileJava`/`tsc -b`/`lint`.
5. Откат — обычный git-ревёрт; изменения аддитивны для существующих эндпоинтов (рефакторинг должен быть чисто внутренним, без изменения их внешнего поведения).
