## Context

См. proposal.md — «Why» и «What Changes». Механизм «диапазон высоты полотна ограничивает доступную высоту компонента» уже реализован и заархивирован в `2026-09-05-link-frame-neo-height-to-leaf-height`, но сейчас жёстко завязан на один код короба:

- Backend (`DoorConfigurationPricingService.java`): константа `NEO_FRAME_TYPE_CODE = "FT-003"` (строка 54), используется в двух местах ветки `FrameType` внутри `addComponentIfPresent` — проверка обязательности высоты (строка 141) и вызов `validateHeightWithinLeafRange` (строка 146).
- Frontend (`App.tsx`): константа `NEO_FRAME_TYPE_CODE = 'FT-003'` (строка 62), используется в `buildCascadeSteps` (строка 233, фильтрация кандидатов шага `frame`), в `updateSelection`/сбросе высоты при смене высоты полотна (строка 499), и в рендере группы «Высота» (строки 665–666, выбор между `frameNeoHeightOptions` и обычным списком). Функции `frameNeoHeightOptions` (строка 105) и `neoFrameCoversHeight` (строка 116) реализуют формулу диапазона.
- Схема БД уже готова к нескольким типам короба с диапазонами: `max_value` и уникальный индекс `uk_liner_dimension_option_frame_type` (расширенный до `(frame_type_id, liner_dimension_type_id, value, min_value, max_value)`) — оба универсальны, не завязаны на конкретный `frame_type_id`.

Короб «Компланар» (`FT-002`) сейчас не имеет ни одной строки `liner_dimension_option` — как и «НЕО» до предыдущего change.

## Goals / Non-Goals

**Goals:**
- Применить диапазонное ограничение высоты к коробу «Компланар» (`FT-002`), используя существующий механизм, без дублирования кода под второй хардкод-код.
- Обобщить точки, зашитые под один код (`NEO_FRAME_TYPE_CODE`), на набор кодов — так, чтобы добавление третьего типа короба в будущем не требовало снова трогать логику, только данные и список кодов.
- Учесть отличие данных «Компланар» от «НЕО»: диапазон 2600–2850 у «Компланар» **покрыт** (высота 3000 мм), недоступен только 2900–2950 — у «НЕО» недоступны оба диапазона (2600–2850 и 2900–2950). Механизм это уже поддерживает без изменений (просто разное количество строк данных).
- Явно подтвердить (тестами), что правило действует одинаково для обычных и реверсивных `door_configuration` — проверка ключуется по `frame_type.code`, не по `leaf_type`/`is_reverse`.

**Non-Goals:**
- Не меняется формула стоимости короба (высота по-прежнему не влияет на цену).
- Не переносится диапазонное ограничение на короб «Фантом» (`FT-001`) — для него таких данных нет и в этом change не появляется.
- Не меняется схема БД — колонка `max_value` и уникальный индекс уже универсальны.

## Decisions

### 1. Замена `NEO_FRAME_TYPE_CODE` на набор кодов (backend и frontend)

Backend: константа `NEO_FRAME_TYPE_CODE` заменяется на
```java
private static final Set<String> HEIGHT_RANGE_FRAME_TYPE_CODES = Set.of("FT-002", "FT-003");
```
Оба существующих условия (`DoorConfigurationPricingService.java:141,146`) меняются с `NEO_FRAME_TYPE_CODE.equals(frameType.getCode())` на `HEIGHT_RANGE_FRAME_TYPE_CODES.contains(frameType.getCode())`. Логика `validateHeightWithinLeafRange` не меняется — она уже общая (использует `min_value`/`max_value`/`value` опции, не зависит от кода владельца).

Frontend: аналогично, `NEO_FRAME_TYPE_CODE` заменяется на
```ts
const HEIGHT_RANGE_FRAME_TYPE_CODES = ['FT-002', 'FT-003']
```
Использования на строках 233, 499, 665 переходят на `HEIGHT_RANGE_FRAME_TYPE_CODES.includes(code)`. Заодно переименовываются функции, которые сейчас называются в честь «НЕО», хотя после этого change они больше не специфичны для него:
- `frameNeoHeightOptions` → `frameHeightRangeOptions`
- `neoFrameCoversHeight` → `frameCoversHeight`

Это чисто механическое переименование (сигнатуры и поведение не меняются) — без него код и дальше называл бы общий механизм именем одного из двух типов, для которых он теперь используется, что стало бы вводящим в заблуждение.

**Альтернатива (отклонена):** добавить отдельную константу `KOMPLANAR_FRAME_TYPE_CODE` и продублировать оба условия (`NEO_FRAME_TYPE_CODE.equals(...) || KOMPLANAR_FRAME_TYPE_CODE.equals(...)`) без переименования функций. Отклонено — это второй раз, когда добавляется код короба с этим же правилом; при третьем разе такое дублирование само по себе станет источником ошибок (легко забыть добавить условие в одном из мест). Набор кодов в одном месте снимает этот риск на будущее.

### 2. Данные короба «Компланар» — только новые строки, без изменений схемы

Новая Liquibase-миграция (`0064-komplanar-frame-height-configurations.yaml`) вставляет 5 строк `liner_dimension_option` для `frame_type_id` = id `FT-002`, `liner_dimension_type_id` = id `DT-002`, по образцу `0063-neo-frame-height-configurations.yaml`:
- value=2170, min_value=1900, max_value=2100
- value=2400, min_value=2150, max_value=2250
- value=2400, min_value=2300, max_value=2300
- value=2700, min_value=2350, max_value=2550
- value=3000, min_value=2600, max_value=2850

Диапазон 2900–2950 не получает строки — как и разрывы у «НЕО», это выражается отсутствием подходящей опции, а не отдельной пометкой «недоступно» (см. прецедент в `2026-09-05-link-frame-neo-height-to-leaf-height`). Уникальный индекс уже поддерживает повторяющийся `value=2400` с разными диапазонами (2150–2250 и 2300–2300) — конфликта нет, он уже разрешён предыдущим change для любого `frame_type_id`.

### 3. Специфика применимости ко всем моделям дверей и реверсу — не требует кода, только теста

Проверка (`HEIGHT_RANGE_FRAME_TYPE_CODES.contains(frameType.getCode())`) выполняется по коду `frame_type`, полученному из `door_configuration.frame_type` независимо от того, какой `leaf_type` и какое значение `is_reverse` у этой строки — то есть требование «для всех моделей дверей, включая реверс» уже выполняется структурно, без дополнительного кода. Чтобы это не осталось неявным предположением, добавляется тест с реверсивной `door_configuration` (`is_reverse = true`), где frame_type — «Компланар».

## Risks / Trade-offs

- **[Риск]** Переименование `frameNeoHeightOptions`/`neoFrameCoversHeight` и константы `NEO_FRAME_TYPE_CODE` — механический рефактор, затрагивающий уже работающий (заархивированный) код короба «НЕО». → Риск низкий: чисто переименование и замена `===`/`.equals` на `.includes`/`.contains`, поведение для `FT-003` не меняется; покрывается существующими тестами `DoorConfigurationPricingServiceTest` (должны продолжать проходить без изменений) и повторной сборкой frontend.
- **[Риск]** Если в будущем добавится третий тип короба с другим набором диапазонов (не только новые данные, но и другая логика), общий набор кодов перестанет быть достаточным и потребует более сложного механизма (например, флага на самой опции вместо списка кодов в коде). → Не является проблемой сейчас: у обоих типов («НЕО», «Компланар») идентичная семантика диапазона; пересмотр — по факту появления такого случая, не заранее.

## Migration Plan

1. Backend-код: заменить `NEO_FRAME_TYPE_CODE` на `HEIGHT_RANGE_FRAME_TYPE_CODES` (`Set.of("FT-002", "FT-003")`) в `DoorConfigurationPricingService`, обновить оба использования.
2. Liquibase-миграция `0064-komplanar-frame-height-configurations.yaml` с данными высоты короба «Компланар», подключить в `db.changelog-master.yaml`.
3. Frontend-код: заменить `NEO_FRAME_TYPE_CODE` на `HEIGHT_RANGE_FRAME_TYPE_CODES`, переименовать `frameNeoHeightOptions`→`frameHeightRangeOptions`, `neoFrameCoversHeight`→`frameCoversHeight`, обновить все использования (строки 233, 499, 665–666 в текущей нумерации).
4. Тесты: новые кейсы в `DoorConfigurationPricingServiceTest` для `FT-002` — успех/вне диапазона/без высоты/разрыв/точка 2300/диапазон 2600–2850 (специфичный для «Компланар», отсутствующий у «НЕО») — и отдельный кейс с реверсивной `door_configuration`.
5. Прогнать существующие тесты `DoorConfigurationPricingServiceTest` для «НЕО» — убедиться, что переименование/обобщение не изменило их поведение.

Откат — стандартный, новые миграции как отдельные changeset'ы; при необходимости отката кода изменения по FT-002 отделены от уже работающей логики FT-003 только данными набора кодов.
