## Context

См. proposal.md — «Why» и «What Changes». Это очередное применение уже трижды использованного принципа диапазонов (короб «НЕО»/«Компланар» по высоте, добор «ТС» по длине, наличники «Модо»/«Онда» и наличники короба «Компланар» по длине) — вся инфраструктура для этого уже существует и обобщена, задача сводится к данным + расширению набора кодов + генерализации одного сообщения об ошибке. Ключевые факты:

1. **Добор «КОМПЛАНАР» (`FET-008`–`FET-013`) уже сегодня на оси «Длина», с одной опцией на код.** Миграция `0019-dobor-komplanar-frame-extensions.yaml` вводит 6 кодов ширины (100/140/190/400/600/800 мм) и для каждого — ровно одну `liner_dimension_option` (`value=2170`, ось `DT-001` «Длина», без диапазона) и одну строку `configuration_price`, ссылающуюся на неё через `length_option_id`. В отличие от наличников (которым перенос на ось «Длина» потребовал отдельной миграции `0068`), добор «КОМПЛАНАР» уже на нужной оси — переносить нечего.
2. **Backend уже полностью обобщён под этот код-путь.** `requireLengthWithinLeafRange(componentName, ownerCode, lengthRangeCodes, missingLengthMessage, selection, lengthOption, leafHeightValue)` (см. `link-modo-onda-casing-length-to-leaf-height`) не содержит ничего специфичного для добора «ТС» — вся специфика в наборе кодов и тексте сообщения, передаваемых как параметры существующим единственным вызовом в общей (не-`FrameType`) ветке `addComponentIfPresent`:
   ```java
   if (type instanceof FrameExtensionsType frameExtensionsType) {
       requireLengthWithinLeafRange(componentName, frameExtensionsType.getCode(), LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES,
               "для добора «ТС» необходимо выбрать длину", selection, lengthOption, leafHeightValue);
   }
   ```
   Единственный вызов, единственный набор кодов, единственное сообщение — в отличие от `DoorCasingType`, для `FrameExtensionsType` никогда не было двух параллельных вызовов с разными наборами. Добавление добора «КОМПЛАНАР» в тот же набор `LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES` требует лишь того, чтобы сообщение перестало называть конкретно «ТС».
3. **Уникальный индекс `uk_liner_dimension_option_frame_extensions_type` уже расширен диапазонными колонками.** Миграция `0065-frame-extensions-type-length-range-index.yaml` (из `link-dobor-ts-length-to-leaf-height`) добавила `COALESCE(min_value, -1)`/`COALESCE(max_value, -1)` в индекс для ЛЮБОГО `frame_extensions_type_id`, не только добора «ТС» — это уже разрешает несколько строк с одинаковым `value` (например, 2400 у обоих диапазонов [2150,2250] и [2300,2300]) для одного и того же добора «КОМПЛАНАР». Новой миграции по индексу не требуется, как и для добора «ТС».
4. **Frontend уже имеет ось-нейтральную геометрию диапазона, но название константы жёстко привязано к «ТС».** `lengthRangeOptions`/`lengthRangeCoversHeight` (см. `link-modo-onda-casing-length-to-leaf-height`) ни на что не завязаны, кроме чисел и переданного набора кодов. Однако сам набор кодов до сих пор называется `DOBOR_TS_FRAME_EXTENSIONS_TYPE_CODES` — единственная константа в кодовой базе для frame-extensions диапазонов, названная по конкретному владельцу, а не обобщённо (в отличие от `LENGTH_RANGE_DOOR_CASING_TYPE_CODES` на фронтенде, которая с самого начала называлась обобщённо). Расширение этого набора добором «КОМПЛАНАР» без переименования сделало бы название вводящим в заблуждение.
5. **Добор «КОМПЛАНАР» (`FET-008`–`FET-013`) сегодня в каталоге всегда идёт в паре с коробом «Компланар» (`FT-002`).** Проверено по всем миграциям, ссылающимся на эти коды (`0019`, `0020`, `0043`, `0046`, `0049`, `0057`): условие всегда `ft.code = 'FT-002'` (включая реверс-конфигурации после `0054-rework-reverse-mechanism`, где `is_reverse = true` тоже подразумевает `frame_type_id = FT-002`). Как и для наличников короба «Компланар» и для добора «ТС» с коробом «НЕО», это означает, что гейтинг по коду `frame_extensions_type`, без явной проверки короба, эквивалентен по факту ограничению коробом «Компланар».
6. **После этого изменения ВСЕ реально достижимые коды добора попадают в диапазонный набор.** `frame_extensions_type` содержит 13 кодов: `FET-001`–`FET-003` — категорийные заголовки («ДОБОРЫ ДЛЯ КОРОБА КОМПЛАНАР», «…НЕО ТИПОВЫХ РАЗМЕРОВ», «…ОБРАМЛЕНИЯ ПРОЁМОВ НЕО»), ни разу не связанные ни с одной `door_configuration` — недостижимы через каталог ни при каком выборе клиента. `FET-004`–`FET-007` (добор «ТС») и `FET-008`–`FET-013` (добор «КОМПЛАНАР») — единственные реально выбираемые добора. После этого изменения `LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES` покрывает все 10 реально достижимых кодов; `FET-001`–`FET-003` остаются вне набора, но недостижимы через UI, поэтому сценарий «проверка не применяется к коду вне набора» в спецификации формулируется без привязки к конкретному (недостижимому) коду.
7. **Существующая формулировка спецификации использует добор «КОМПЛАНАР» как пример кода ВНЕ диапазонного набора.** Требования «Совместимость диапазона длины добора «ТС» с высотой полотна» и «Обязательность длины для добора «ТС»» в `door-configuration-api`, а также их аналоги в `door-configurator-ui`, явно называют добор «КОМПЛАНАР» примером типа, к которому проверка не применяется. После этого изменения это утверждение становится неверным — эти формулировки корректируются как MODIFIED без изменения остального текста требований (сама проверка для добора «ТС» не меняется, меняется только использованный в тексте пример).

## Goals / Non-Goals

**Goals:**
- Ограничить выбор длины добора «КОМПЛАНАР» (все 6 ширин, `FET-008`–`FET-013`) диапазоном высоты полотна, не затрагивая добор «ТС» или другие компоненты.
- Переиспользовать уже обобщённый механизм (backend: `requireLengthWithinLeafRange`/`validateHeightWithinLeafRange`; frontend: `lengthRangeOptions`/`lengthRangeCoversHeight`) без дублирования логики диапазона.
- Сделать цену добора «КОМПЛАНАР» независимой от выбранной длины — симметрично добору «ТС» и наличникам.
- Скорректировать формулировки существующих требований для добора «ТС», ставшие неверными после этого изменения (пример кода «вне набора»), не меняя описываемое ими поведение.

**Non-Goals:**
- Не переносится диапазонное ограничение на недостижимые коды `FET-001`–`FET-003` — они не встречаются ни в одной `door_configuration` и не могут быть выбраны клиентом ни при каком запросе.
- Не меняется цена добора «КОМПЛАНАР» по сравнению с текущей (2390/1366, 2834/1619, 3253/1858, 8008/4576, 11877/6786, 15843/9053 по кодам) — меняется только то, от чего эта цена формально зависит.
- Не меняется поведение добора «ТС» — константа расширяется, но набор кодов добора «ТС» и его собственные диапазоны не затрагиваются.
- Не меняется схема таблиц — используются уже существующие колонки `min_value`/`max_value`/`length_option_id` и уже расширенный уникальный индекс.

## Decisions

### 1. Один набор кодов на 10 значений, единое обобщённое сообщение об обязательности длины

`LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES` расширяется до `Set.of("FET-004", "FET-005", "FET-006", "FET-007", "FET-008", "FET-009", "FET-010", "FET-011", "FET-012", "FET-013")` — единственный вызов `requireLengthWithinLeafRange` для `FrameExtensionsType` остаётся один, но сообщение об обязательности длины обобщается с «для добора «ТС» необходимо выбрать длину» на «для этого добора необходимо выбрать длину» — по тому же принципу, что и обобщённое с самого начала сообщение «для этого наличника необходимо выбрать длину» у `DoorCasingType`.

**Альтернатива (отклонена):** оставить сообщение для добора «ТС» без изменений и добавить второй вызов `requireLengthWithinLeafRange` с отдельным набором `Set.of("FET-008"..."FET-013")` и отдельным сообщением «для добора «КОМПЛАНАР» необходимо выбрать длину» — по образцу того, как `DoorCasingType` в `link-modo-onda-casing-length-to-leaf-height` изначально получил обобщённое сообщение именно потому, что предвиделась вторая группа наличников. Отклонено — здесь предпосылка симметрична: оба вызова были бы структурно идентичны (одна и та же ветка, одна и та же ось, разница только в наборе кодов и тексте), что уже было признано чистым дублированием в аналогичной ситуации при обобщении наличников (`link-modo-onda-casing-length-to-leaf-height`, Decision 1). Текст сообщения не является частью спецификации (specs описывают код ответа 400, а не точный текст), поэтому обобщение не затрагивает наблюдаемое поведение API.

### 2. Данные: переиспользование существующей опции 2170 мм под первый диапазон

Единственная существующая строка `liner_dimension_option` (`value=2170`, без диапазона) для каждого из 6 кодов обновляется добавлением границ диапазона `[1900, 2100]` — значение `2170` не меняется (оно уже совпадает с требуемым значением первого диапазона, как и в прецеденте добора «ТС», где значение 2170 тоже совпало без изменений). Добавляются новые строки:
- Для всех 6 кодов: `value=2400, min_value=2150, max_value=2250`; `value=2400, min_value=2300, max_value=2300` (диапазон-точка); `value=2700, min_value=2350, max_value=2550`.
- Для `FET-008`, `FET-009`, `FET-010` (ширины 100/140/190 мм): `value=3000, min_value=2600, max_value=2850`.
- Для `FET-011`, `FET-012`, `FET-013` (ширины 400/600/800 мм): `value=2950, min_value=2600, max_value=2850`.

Диапазон `[2900, 2950]` не получает опций ни для одного из 6 кодов — добор в этом диапазоне недоступен для всех ширин одинаково (в отличие от диапазона `[2600, 2850]`, где недоступности нет — только разное значение длины по группам ширин).

**Альтернатива (отклонена):** `DELETE` старой строки + `INSERT` новых. Отклонено по той же причине, что и во всех предыдущих подобных изменениях — переиспользование строки через `UPDATE` не создаёт зависимости от предварительного обнуления `configuration_price.length_option_id`.

### 3. Цена добора «КОМПЛАНАР» перестаёт зависеть от length_option_id

`UPDATE configuration_price SET length_option_id = NULL WHERE frame_extensions_type_id IN (id для каждого из 6 кодов)` — по тому же приёму, что и в `link-dobor-ts-length-to-leaf-height` (Decision 3). Без этого шага добавление новых опций длины без соответствующих строк `configuration_price` привело бы к тому, что выбор любой длины, кроме исходной 2170, возвращал бы «цена не найдена» для добора «КОМПЛАНАР» — бизнес-требование касается только допустимости длины, а не цены. `matchesDimension`/`findMostSpecificPrice` не меняются — `priceOption == null` уже трактуется как «подходит для любого выбора».

### 4. Frontend: переименование `DOBOR_TS_FRAME_EXTENSIONS_TYPE_CODES` в осе-нейтральное имя

Константа переименовывается в `LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES` (по аналогии с `LENGTH_RANGE_DOOR_CASING_TYPE_CODES`) и расширяется до 10 кодов. Все три места использования (рендер группы «Длина», `buildCascadeSteps`, сброс выбора в `updateSelection`) переименовываются вместе с константой — тело этих мест не меняется, они уже параметризованы набором кодов, а не привязаны к добору «ТС» по смыслу.

**Альтернатива (отклонена):** оставить имя `DOBOR_TS_FRAME_EXTENSIONS_TYPE_CODES` без изменений, чтобы минимизировать диф. Отклонено — имя константы, охватывающей теперь оба семейства добора, вводило бы в заблуждение любого, кто в будущем будет читать код добора «КОМПЛАНАР» и увидит, что он гейтится набором с «ТС» в названии; переименование — механическая правка без изменения поведения.

### 5. Спецификация: точечная правка примеров в требованиях для добора «ТС»

Требования «Совместимость диапазона длины добора «ТС» с высотой полотна» и «Обязательность длины для добора «ТС»» (`door-configuration-api`), а также «Условное отображение длины добора «ТС» по высоте полотна» (`door-configurator-ui`) содержат сценарии, использующие добор «КОМПЛАНАР» как пример кода ВНЕ диапазонного набора. Эти сценарии копируются как MODIFIED с заменой примера на нейтральную формулировку «код вне обоих наборов (добора «ТС» и добора «КОМПЛАНАР»)», без изменения остального текста требований. Само поведение добора «ТС» не меняется — меняется только то, какой пример спецификация использует для описания уже существующего исключения.

**Замеченное, но не исправляемое в этом изменении:** аналогичная спецификация для наличников («Совместимость диапазона длины наличников «Модо»/«Онда» с высотой полотна», сценарий «Проверка не применяется к другим наличникам и компонентам») использует наличник «Эво» (`DCT-001`) как пример кода вне набора — начиная с `link-komplanar-casing-length-to-leaf-height` это утверждение тоже стало неверным (Эво теперь тоже в диапазонном наборе), но не было исправлено в том изменении. Это отдельная, не связанная с добором область (`door-configuration-catalog`/наличники) — вне рамок этого изменения; упоминается здесь для осведомлённости, без исправления.

## Risks / Trade-offs

- **[Риск]** Обобщение сообщения об обязательности длины (Decision 1) технически меняет текст ошибки для уже работающей проверки добора «ТС», хотя и без изменения кода ответа. → Спецификация не фиксирует точный текст сообщения (только код 400), и ни один существующий тест не проверяет текст явно (проверено: тесты добора «ТС» используют только `ex.getStatusCode().value()`); митигируется регрессионным прогоном существующих тестов добора «ТС».
- **[Риск]** Переименование `DOBOR_TS_FRAME_EXTENSIONS_TYPE_CODES` → `LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES` на фронтенде затрагивает уже существующий код добора «ТС» в трёх местах. → Низкий риск: чисто механическое переименование, поведение не меняется; проверяется сборкой (`npm run build`).
- **[Риск]** Как и для предыдущих подобных изменений, при несовместимой высоте полотна и отсутствии альтернативного добора шаг «Добор» может исчезнуть из UI вместо явного сообщения о недоступности — особенно заметно в диапазоне [2900, 2950], где недоступны все 6 ширин добора «КОМПЛАНАР» одновременно. → Тот же принятый риск: backend в любом случае не даст завершить такую конфигурацию расчётом.
- **[Риск]** Расширение `LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES` до всех 10 реально достижимых кодов `frame_extensions_type` делает правило «длина обязательна» действующим для каждого реально выбираемого добора в каталоге. → Смягчается тем, что набор кодов — явный перечисляемый `Set`, а не «все существующие коды» по определению; при добавлении нового типа добора в будущем потребуется явное решение, входить ли в этот набор (то же соглашение, что и для предыдущих наборов кодов).

## Migration Plan

1. Liquibase-миграция №1 (`0074-komplanar-dobor-length-range-configurations.yaml`): данные диапазона длины добора «КОМПЛАНАР» — `UPDATE` существующей строки (добавление диапазона [1900,2100] к value=2170) для каждого из 6 кодов; `INSERT` общих для всех 6 кодов диапазонов (2400/[2150,2250], 2400/[2300,2300], 2700/[2350,2550]); `INSERT` раздельно по значению для группы ширин 100/140/190 (3000/[2600,2850]) и группы 400/600/800 (2950/[2600,2850]).
2. Liquibase-миграция №2 (`0075-komplanar-dobor-configuration-price-length-decouple.yaml`): `UPDATE` строк `configuration_price` добора «КОМПЛАНАР» — `length_option_id = NULL`.
3. Backend-код: расширение константы `LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES` шестью кодами; обобщение текста сообщения об обязательности длины в существующем вызове `requireLengthWithinLeafRange`; логика метода не меняется.
4. Тесты backend: новые кейсы в `DoorConfigurationPricingServiceTest` — высота внутри/вне диапазона, точка 2300, разрыв между диапазонами, разные длины для двух групп ширин в диапазоне 2600–2850, недоступность в 2900–2950, обязательность длины, цена не зависит от длины; регрессионная проверка, что существующие тесты добора «ТС» по-прежнему проходят после обобщения сообщения (тесты проверяют только код 400, не текст).
5. Frontend-код: переименование `DOBOR_TS_FRAME_EXTENSIONS_TYPE_CODES` → `LENGTH_RANGE_FRAME_EXTENSIONS_TYPE_CODES` во всех использованиях, расширение состава кодов; остальной код не меняется.
6. Спецификации: точечная правка примеров в существующих требованиях для добора «ТС» (Decision 5) как MODIFIED; новые требования для добора «КОМПЛАНАР» как ADDED.
7. Проверка: `npm run build` (из `frontend/`); backend — компиляция и точечный прогон `DoorConfigurationPricingServiceTest` (не полный `./gradlew test`); ручная проверка в браузере — выбор добора «КОМПЛАНАР» разных ширин с высотой полотна в разных диапазонах, включая границы и разрывы между ними, и сравнение поведения ширин 100/140/190 против 400/600/800 в диапазоне 2600–2850.

Откат — стандартный: новые миграции — новые changeset'ы, откат через Liquibase `rollback`, если потребуется; данные и код добора «КОМПЛАНАР» откатываются вместе, не затрагивая добор «ТС» и остальные компоненты.
