## Context

`frontend/` — нетронутый шаблон Vite + React 19 + TypeScript с уже подключённым `antd` (см. `frontend/package.json`), без API-клиента, роутинга или state-менеджера. Backend уже реализует `GET /api/door-configurations` и `POST /api/door-configurations/{id}/price` (capability `door-configuration-api`) и слушает `localhost:8080`. См. `proposal.md` — «Why» и «What Changes» — для мотивации; см. `specs/door-configurator-ui/spec.md` — для контракта поведения.

## Goals / Non-Goals

**Goals:**
- Один экран, целиком заменяющий содержимое `App.tsx`, реализующий мастер-поток «конфигурация → опции → цена» из specs.
- Минимум зависимостей и абстракций: без роутера, без стейт-менеджера (Redux/Zustand) — состояние мастера умещается в несколько `useState` в одном компоненте.

**Non-Goals:**
- Адаптивная/продуманная вёрстка, брендинг, анимации — только рабочий минимальный UI на компонентах `antd`.
- Поддержка нескольких одновременных расчётов, истории расчётов, сохранения выбора между сессиями.
- Прод-конфигурация API base URL (переменные окружения, разные бэкенды по стендам) — только локальная разработка через один backend на `localhost:8080`.

## Decisions

### Dev-прокси вместо CORS
`frontend/vite.config.ts` получает `server.proxy: { '/api': 'http://localhost:8080' }`. Фронтенд обращается к `/api/...` относительными путями. Альтернатива — включить CORS на backend и обращаться к `http://localhost:8080/api/...` напрямую с фронтенда — отклонена: потребовала бы правки backend (вне impact этого изменения, см. proposal.md) и захардкоженного абсолютного URL на фронтенде.

### Состояние мастера — простые React-хуки в одном компоненте
Состояние (загруженный каталог, выбранная конфигурация, выбор опций по осям, результат расчёта, статусы загрузки/ошибок) живёт в `useState`/`useEffect` внутри `App.tsx` (или одного корневого компонента, если разбить на файлы ради читаемости). Выбор опций по осям хранится как map «ключ компонента → { lengthOptionId?, heightOptionId?, thicknessOptionId?, colourOptionId? }», которая при отправке расчёта напрямую сериализуется в тело `POST .../price` (форма запроса уже зафиксирована в design.md capability `door-configuration-api`: поля `leaf`/`frame`/`edge`/`doorCasing`/`frameExtensions`, каждое — `ComponentSelectionDto`). Отдельный стейт-менеджер не нужен: состояние не расшаривается вне этого экрана.

### UI-примитивы — antd `Radio.Button` в `Radio.Group`, а не произвольные `Button`
И для выбора конфигурации, и для выбора значения внутри оси используется `Radio.Group` с `optionType="button"` — это даёт ровно семантику «выбор не более одного значения в группе» из specs (взаимоисключающее выделение, снятие через повторный выбор — если backend допускает пустой выбор оси, группа снабжается неявным «пустым» состоянием через `allowClear`-подобное поведение, реализуемое сбросом значения в `undefined` при повторном клике на уже выбранную кнопку). Требование пользователя «динамическая отрисовка кнопок» выполняется визуально (это kнопки, `Radio.Button` рендерится как `<button>` с видом кнопки antd), при этом не приходится вручную реализовывать логику взаимоисключающего выбора, которую `Radio.Group` даёт из коробки — самостоятельная реализация через голые `Button` с ручным состоянием `selected` была рассмотрена и отклонена как ненужное дублирование существующего компонента antd (запрещено CLAUDE.md).

### Запрос расчёта — только по клику, без автопересчёта при каждом изменении опции
Изменение выбора опции только обновляет локальное состояние; запрос `POST .../price` уходит исключительно по нажатию «Рассчитать стоимость» (см. specs: «Повторный расчёт после изменения выбора»). Альтернатива — автоматический пересчёт при каждом изменении выбора — отклонена: для минимального UI это лишняя сложность (дебounce, гонки запросов), а specs явно описывают модель «explicit calculate action».

### Типы ответов API дублируются на фронтенде вручную
Поскольку в репозитории нет общей генерации типов из backend (OpenAPI/схемы), TypeScript-интерфейсы под `DoorConfigurationDto`, `PricingResponseDto` и т.д. на фронтенде объявляются вручную по образу DTO из `backend/src/main/java/com/example/furniturecalculator/dto/`. Расхождение полей — известный риск ручного дублирования, см. Risks.

## Risks / Trade-offs

- [Риск] Ручное дублирование формы DTO между backend (Java-record) и frontend (TS-интерфейс) может разойтись при будущих изменениях API → Оба места явно перечислены в tasks.md; при следующем изменении API их нужно менять синхронно (кодогенерация — за рамками этого минимального UI).
- [Риск] `Radio.Group` со сброшенным значением при повторном клике не входит в стандартное поведение antd «из коробки» и потребует небольшой ручной обработки `onChange`/повторного клика → Изолировано в одном переиспользуемом месте (компонент/хук выбора оси), не размножается по всей странице.
- [Trade-off] Прокси на фиксированный `http://localhost:8080` в `vite.config.ts` работает только для локальной разработки одного разработчика на дефолтном порту backend → Приемлемо: proposal.md ограничивает impact только фронтендом для локальной разработки, продовая конфигурация — Non-Goal.
