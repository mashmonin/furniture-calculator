## Why

Сейчас конфигуратор двери — это два разделённых блока: сначала клиент проходит каскад выбора типов компонентов («1. Соберите конфигурацию» — реверс, коллекция, полотно, кромка, короб, наличник, добор), и только когда конкретная `door_configuration` однозначно определена, появляется второй блок («2. Выберите опции»), где для каждого уже выбранного компонента разом показываются его длина/высота/толщина/цвет. Это разносит логически связанный ввод («выбрал полотно» → «указал его размеры и цвет») на два визуально далёких этапа и заставляет реверс определяться только после выбора полотна и кромки, хотя по факту это первый вопрос, которым руководствуется продавец при подборе двери. Также в расчёте стоимости клиент видит только итоговую цену полотна, но не то, из чего складывается доплата (нестандартная ширина, нестандартная высота, реверс — независимо или все вместе), что затрудняет объяснение цены покупателю. Наконец, для реверсивных дверей сейчас невозможно оформить конфигурацию без короба (только полотно) — это ограничение каталога, не продуктовое решение.

## What Changes

- Слить блоки «1. Соберите конфигурацию» и «2. Выберите опции» в один непрерывный поток «Введите данные двери»: тип компонента и его опции (длина/высота/толщина/цвет) вводятся сразу друг за другом, не откладываясь до полного разрешения конфигурации.
- Переставить порядок шагов потока: реверс (да/нет) → серия (коллекция) → модель полотна → длина/высота/толщина/цвет полотна → кромка (реальный вариант или «без кромки», как сейчас) → короб (реальный вариант или «без короба») → наличник → добор. Переключатель «Реверс» становится первым шагом потока (оценивается по всему каталогу, а не только по кандидатам, оставшимся после выбора полотна и кромки), вместо теперешнего появления между кромкой и коробом.
- Механизм сужения кандидатов `door_configuration` по выбору типа компонента не меняется (тот же алгоритм, что и сейчас) — меняется только порядок и способ отображения: ввод опций размера/цвета конкретного компонента показывается сразу после выбора его типа, до перехода к следующему компоненту.
- Ввод длины/высоты полотна остаётся как сейчас — кнопки стандартных каталожных значений плюс отдельное числовое поле «Другое значение» для нестандартного размера; толщина и цвет остаются кнопками из каталога, без изменений.
- В блоке расчёта стоимости добавить разбивку применённых надбавок к цене полотна в процентах — отдельно: за нестандартную ширину, за нестандартную высоту, за реверс — показывая все, что применились одновременно, если применилось несколько.
- Добавить новый read-only эндпоинт, отдающий проценты надбавок (таблицу `dimension_surcharge_rule` и надбавку за реверс), чтобы фронтенд мог сопоставить введённые клиентом значения с наценкой и показать проценты в разбивке. Контракт запроса эндпоинта расчёта стоимости (`POST /api/door-configurations/{id}/price`) не меняется.
- В разбивке по компонентам результата расчёта, рядом с ценой каждого компонента, показать его базовую цену — без применённых к этому компоненту надбавок — визуально менее заметно (светлее/мельче), чем итоговая; показывается только для компонента, к которому реально применилась хотя бы одна надбавка (на практике — только leaf). Базовая цена приходит новыми полями в объекте компонента ответа того же эндпоинта расчёта стоимости (аддитивное расширение контракта ответа — существующие поля не меняются и не удаляются).
- Разрешить «без короба» для реверсивных конфигураций: ослабить проверку БД `chk_door_configuration_reverse_requires_frame` (сейчас реверс обязательно требует короб) и добавить в каталог для каждой существующей комбинации реверс+полотно+кромка новую строку `door_configuration` без короба/наличника/добора — по тому же принципу, по которому «без короба» уже работает для нереверсивных конфигураций.

## Capabilities

### New Capabilities

(нет)

### Modified Capabilities

- `door-configurator-ui`: единый поток ввода данных двери вместо двух разделённых блоков; реверс — первый шаг потока; отображение процентной разбивки надбавок к цене полотна.
- `door-configuration-api`: новый read-only эндпоинт, отдающий проценты надбавок (`dimension_surcharge_rule` + надбавка за реверс), для использования фронтендом при построении разбивки; в объекте каждого компонента ответа расчёта стоимости появляются новые поля с базовой (до надбавок) ценой этого компонента — аддитивно, без изменения существующих полей запроса/ответа.
- `door-configuration-catalog`: для реверсивных конфигураций разрешается отсутствие короба (и, соответственно, наличника/добора) — ослабляется CHECK-ограничение и добавляются соответствующие строки каталога.

## Impact

- **Frontend**: `App.tsx` — полная переработка структуры рендера (единый поток вместо двух блоков), перестановка шага реверса в начало каскада, список процентной разбивки доплат и отображение базовой цены рядом с ценой каждого компонента в разбивке результата расчёта; `api/types.ts`/`api/doorConfigurations.ts` — новый клиентский метод под новый read-only эндпоинт, новые поля в типе компонента ответа расчёта стоимости.
- **Backend**: новый контроллер/DTO для эндпоинта надбавок (читает `DimensionSurchargeRuleRepository` и константу надбавки за реверс из `DoorConfigurationPricingService`); `ComponentPriceDto` — два новых поля с базовой ценой компонента (до надбавок); сам метод `calculate()` — без изменения математики надбавок, только базовая цена компонента передаётся в его же DTO наряду с итоговой.
- **БД**: новый Liquibase changeset — снятие/ослабление `chk_door_configuration_reverse_requires_frame`, добавление строк `door_configuration` без короба для существующих реверсивных leaf+edge комбинаций.
- Контракт запроса эндпоинта расчёта стоимости (`POST /api/door-configurations/{id}/price`) не меняется; контракт ответа расширяется аддитивно (два новых поля в объекте каждого компонента).
