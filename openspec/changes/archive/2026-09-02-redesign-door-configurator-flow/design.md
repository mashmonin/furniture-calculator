## Context

См. `proposal.md` — «Why» и «What Changes». Ключевые факты о текущей реализации, определяющие подход:

- `App.tsx` сейчас строит выбор в два разнесённых визуальных блока: `selectedCollectionId` (state, вне каскада) → `buildCascadeSteps(collectionFilteredConfigurations, cascadeSelection, reverseSelection)` вычисляет шаги `CASCADE_BEFORE_REVERSE = [leaf, edge]`, затем `reverseStep` (видим только если среди кандидатов, оставшихся после leaf+edge, есть оба значения `is_reverse`), затем `CASCADE_AFTER_REVERSE = [frame, doorCasing, frameExtensions]`. Опции размеров/цвета (`OptionGroup` для длины/высоты/толщины/цвета) рендерятся отдельным блоком «2. Выберите опции» только когда `selectedConfiguration` — единственный оставшийся кандидат.
- `ComponentCatalogDto` (длина/высота/толщина/цвет, посты короба) принадлежит **типу** компонента, а не конкретной строке `door_configuration` — у всех кандидатов с одинаковым `leaf.type.id` (или `edge.type.id` и т.д.) объект `ComponentCatalogDto` для этого ключа идентичен. Это уже используется для `edgeHeightOptions`/`leafHeightValue` до полного разрешения конфигурации.
- БД: `chk_door_configuration_reverse_requires_frame` (`0054-2`) — `is_reverse = false OR frame_type_id IS NOT NULL`. Все существующие `is_reverse = true` строки поэтому обязаны иметь `frame_type_id`. Небольшой набор коллекций (Вертикаль и т.п.) уже имеет non-reverse строки только с `leaf_type_id` (без короба) — `0007-vertikal-leaf-configurations.yaml` и аналогичные, показывая, что «без короба» — штатный паттерн каталога, не требующий отдельного механизма в UI.
- `door_casing_type`/`frame_extensions_type` уже требуют `frame_type_id` через отдельный (не меняемый этим change) constraint — это правило действует независимо от `is_reverse` и остаётся в силе.
- `DoorConfigurationPricingService` хранит надбавку за реверс как приватную константу `REVERSE_SURCHARGE_MULTIPLIER = new BigDecimal("1.10")` и разрешает произвольные размеры полотна через `DimensionSurchargeRuleRepository` (см. change `add-dimension-surcharge-rules`, метод `resolveAxisSurchargeMultiplier`). Ни то, ни другое сейчас не доступно фронтенду отдельно от расчёта — только в применённом виде, внутри итоговой цены компонента.
- `DoorConfigurationController` — единственный контроллер, `@RequestMapping("/api/door-configurations")`, два метода: `GET` (каталог) и `POST /{id}/price` (расчёт). Контракт запроса `calculate()`/`POST .../price` не меняется; контракт ответа расширяется аддитивно двумя новыми полями с базовой (до надбавок) ценой — по прямому запросу пользователя после первичного согласования non-goal'а (см. proposal.md).

## Goals / Non-Goals

**Goals:**
- Единый непрерывный поток «Введите данные двери» вместо двух блоков; реверс — первый шаг, оцениваемый по всему каталогу, до коллекции.
- Опции размеров/цвета каждого компонента вводятся сразу после определения его типа, не дожидаясь полного разрешения конфигурации.
- Разрешить «без короба» для реверсивных конфигураций на уровне БД и каталога, чтобы существующий универсальный механизм «без компонента» в UI сработал для реверса так же, как для обычных конфигураций — без специального кода в UI под этот случай.
- Показать в результате расчёта проценты применённых надбавок (ширина/высота/реверс) через новый read-only эндпоинт, не меняя эндпоинт расчёта стоимости.

**Non-Goals:**
- Не меняется контракт запроса `POST /api/door-configurations/{id}/price` и математика надбавок в `DoorConfigurationPricingService.calculate()` — контракт ответа расширяется только аддитивно (см. Decisions, «Базовая цена в ответе calculate()»).
- Не меняется механика ввода толщины/цвета (остаются кнопками из каталога) и механика ввода длины/высоты полотна (кнопки стандартных значений + отдельное поле «Другое значение», как сейчас).
- Не вводится отдельный переключатель «нужна ли кромка» — используется тот же общий механизм «без компонента» (`NONE_OPTION_ID`), что и для остальных опциональных компонентов.
- Не затрагиваются другие капабилити (`item-configuration-schema`, `frame-post-catalog`, `dimension-surcharge-rules`).

## Decisions

**Реверс вычисляется как отдельный, самый первый шаг — над полным каталогом, а не внутри `buildCascadeSteps`.**
Сейчас `buildCascadeSteps` сама решает, когда показать `reverseStep`, разбивая `CASCADE_ORDER` на «до» и «после». Раз реверс переезжает перед коллекцией (которая уже сегодня вычисляется отдельно от `buildCascadeSteps`, в самом `App`), симметрично выносим и реверс наружу: `reverseStep` вычисляется первым, из полного `configurations`; результат (`resolvedReverse`) фильтрует `configurations` в `reverseFilteredConfigurations`; `collectionOptions`/`collectionFilteredConfigurations` считаются уже от `reverseFilteredConfigurations` (а не от полного каталога, как сейчас); `buildCascadeSteps` вызывается как раньше, но получает на вход уже дважды отфильтрованный список и **без** внутреннего разделения на `CASCADE_BEFORE_REVERSE`/`CASCADE_AFTER_REVERSE` — просто единый `CASCADE_ORDER = [leaf, edge, frame, doorCasing, frameExtensions]`. Это не усложняет, а упрощает `buildCascadeSteps`: убирается вся ветка вычисления `reverseStep` внутри неё.

**Альтернатива (отклонена): оставить реверс внутри `buildCascadeSteps`, просто передвинуть на первое место списка типов.**
Не подходит, потому что реверс — не тип-компонент (`ComponentKey`), а булев признак самой строки `door_configuration`, как и было решено в `rework-door-reverse-mechanism` (см. архивный design.md, раздел Decisions). Тот же принцип, по которому коллекция уже вычисляется отдельно от каскада типов компонентов, естественно распространяется и на реверс.

**Опции компонента получаются из «любого подходящего кандидата», а не только из `selectedConfiguration`.**
Чтобы показать длину/высоту/толщину/цвет полотна сразу после выбора его модели (когда кромка/короб ещё не выбраны, `selectedConfiguration` ещё не единственен), нужен `ComponentCatalogDto` для уже выбранного `leaf.type.id` до полного разрешения. Поскольку этот объект идентичен у всех кандидатов с этим `type.id` (см. Context), берём его через `candidates.find(c => c[key]?.type.id === selectedId)?.[key]` в момент, когда шаг `key` разрешён (`selectedId !== undefined`) — не дожидаясь, пока `candidates.length === 1`. Это единственное новое обращение к данным; сама структура `DoorConfigurationDto`/`ComponentCatalogDto` не меняется.

**Рендер — один линейный список шагов вместо двух `<Space>`-блоков.**
Вместо `cascadeSteps.filter(before)` / переключателя / `cascadeSteps.filter(after)` / отдельного блока «2. Выберите опции» — один проход по `[reverseStep, collectionStep, ...cascadeSteps]`, где после каждого разрешённого шага с типом компонента сразу рендерится его `OptionGroup`-набор (длина/высота/толщина/цвет), если это применимо (для реверса и коллекции — нет). Секция «Расчёт стоимости» остаётся как есть, просто использует финальный `selectedConfiguration`, как сейчас.

**Новый эндпоинт — отдельный ресурс `GET /api/pricing-surcharges`, не метод существующего `DoorConfigurationController`.**
Не привязан к конкретной `door_configuration` (в отличие от `GET /api/door-configurations` и `POST .../price`), поэтому не вкладывается в `@RequestMapping("/api/door-configurations")`. Новый контроллер `PricingSurchargesController`, читает `DimensionSurchargeRuleRepository.findAll()` и процент надбавки за реверс.

**Надбавка за реверс становится читаемой константой, а не только внутренним множителем.**
`DoorConfigurationPricingService` получает публичный метод (например, `reverseSurchargePercent()` → `BigDecimal`, вычисляемый из уже существующего `REVERSE_SURCHARGE_MULTIPLIER`), которым пользуется только новый контроллер/сервис. `calculate()` не трогается — только добавляется независимый метод-геттер рядом.

**Разбивка процентов на фронтенде вычисляется локально из уже загруженных данных, не из ответа `calculate()`.**
Проценты не запрашиваются заново при расчёте: на старте страницы вместе с каталогом загружается список правил наценки и надбавка за реверс (см. `GET /api/pricing-surcharges`); при показе результата фронтенд сам сопоставляет `selection.leaf.customLengthValueMm`/`customHeightValueMm` со значением правила той же оси (точное совпадение, по коду `DT-001`/`DT-002`) и добавляет надбавку за реверс, если `selectedConfiguration.reverse === true`. Это следствие ограничения «эндпоинт расчёта не меняется» — альтернатива (возвращать разбивку из `calculate()`) была бы проще, но прямо запрещена.

**DB: `chk_door_configuration_reverse_requires_frame` не заменяется более слабым constraint'ом, а снимается полностью.**
После этого change `is_reverse = true` не накладывает на `frame_type_id` никаких требований, отличных от обычной строки (только общее правило «наличник/добор требуют короба», которое уже есть отдельно и не зависит от `is_reverse`). Дополнительное более узкое правило не нужно — реверс должен вести себя как обычная конфигурация в этой части.

**Каталог: для каждой существующей пары (leaf_type_id, edge_type_id) среди `is_reverse = true` строк добавляется одна новая строка без короба/наличника/добора, если такой ещё нет.**
`INSERT ... SELECT DISTINCT ... WHERE is_reverse = true AND NOT EXISTS (...)`, сравнение через `COALESCE(edge_type_id, 0)` — тем же способом, каким уже построен `uk_door_configuration_combination` (`0054-3`), чтобы не полагаться на точное поведение `NULL = NULL` в SQL и не вставить дубликат, если для какой-то пары строка без короба уже почему-то существует.

**Базовая цена — поля на уровне каждого компонента (`ComponentPriceDto`), а не агрегат на уровне всего ответа.**
Пользователь сначала попросил базовую (до надбавок) цену рядом с итоговой на уровне всего расчёта (сумма по всем компонентам), затем явно скорректировал: базовая цена должна относиться к каждому элементу разбивки, а не только к сумме. Поскольку надбавки применяются только к leaf, разница видна только у него, но поля добавлены на уровне `ComponentPriceDto` (`baseRetailPrice`/`baseDealerPrice`), а не как `totalRetailPriceBeforeSurcharges`/`totalDealerPriceBeforeSurcharges` у `PricingResponseDto` (эти два поля из первой итерации решения удалены). Значения точные, вычисленные из уже читаемой `ConfigurationPrice.retailPrice/dealerPrice` — не приближены делением. Обратное восстановление базовой цены из итоговой и известных процентов было бы неточным: `applySequentialSurcharges` округляет после каждого шага (длина → высота → реверс, см. change `add-dimension-surcharge-rules`), а деление не инвертирует округление. Точное значение уже вычисляется на backend — это именно `price.getRetailPrice()`/`getDealerPrice()` строки `ConfigurationPrice`, найденной для компонента, ДО применения `applySequentialSurcharges`; для frame (никогда не наценивается) базовая цена равна `postsRetailPrice/postsDealerPrice [+ price...]` — той же сумме, что и итоговая. Это меняет **контракт ответа** `PricingResponseDto` (два новых поля в `ComponentPriceDto`) — аддитивно, существующие поля не меняются; контракт запроса и сама математика надбавок в `calculate()` не затрагиваются.

**Альтернатива (отклонена): вычислять базовую цену на фронтенде через деление итоговой цены на известные проценты.**
Не даёт точного значения из-за округления на каждом шаге backend-формулы (см. выше) — расхождение было бы небольшим, но необъяснимым для пользователя, читающего рядом стоящие числа. Раз ответ `calculate()` и так строится из `ConfigurationPrice` до наценок, точное значение получить на backend дешевле и надёжнее, чем приближать на фронтенде.

**Альтернатива (отклонена после уточнения пользователя): агрегированные `totalRetailPriceBeforeSurcharges`/`totalDealerPriceBeforeSurcharges` на уровне `PricingResponseDto`.**
Первая реализация добавляла именно эти два поля и суммировала базовые цены компонентов на backend. Пользователь отклонил этот вариант: базовая цена должна относиться к каждому элементу (компоненту) разбивки, а не быть только агрегатом. Поля на уровне `ComponentPriceDto` делают то же самое, что и total-поля, более гранулярно — общую сумму при необходимости фронтенд может посчитать сам, суммируя `baseRetailPrice`/`baseDealerPrice` по компонентам, поэтому отдельные total-поля избыточны и удалены.

## Risks / Trade-offs

- **[Risk]** Восстановление `App.tsx` — большой рефакторинг рендера в одном файле. → Логика сужения candidates (`buildCascadeSteps`, `applyCascadeStep`) переиспользуется почти без изменений; меняется в основном порядок вызовов и структура JSX, а не алгоритм.
- **[Trade-off]** Проценты в разбивке вычисляются на фронтенде независимо от `calculate()`, а не берутся из его ответа — при гипотетическом расхождении данных между загрузкой каталога/правил и моментом расчёта (например, правило наценки изменили между двумя запросами) разбивка теоретически может разойтись с фактически применённой ценой на доли секунды окна между запросами. Осознанный трейд-офф — прямое следствие требования не менять эндпоинт расчёта; для внутреннего конфигуратора-калькулятора это приемлемо.
- **[Risk]** Снятие `chk_door_configuration_reverse_requires_frame` — необходимо явно проверить на локальной БД, что вставка `is_reverse = true` без `frame_type_id` больше не отклоняется, и что общий constraint «наличник/добор требуют короба» по-прежнему отклоняет реверс с наличником, но без короба (сценарий в specs). → Ручная проверка перед архивированием, как и в предыдущих change с миграциями (см. tasks.md).
- **[Risk]** `NOT EXISTS`-вставка новых `door_configuration` строк с `NULL` в `edge_type_id`/`frame_type_id` — нужна аккуратная NULL-safe формулировка сравнения (через `COALESCE`), иначе на PostgreSQL `NULL = NULL` не совпадёт и защита от дублей не сработает. → Использовать ровно тот же `COALESCE(...,0)` паттерн, что уже применяется в `uk_door_configuration_combination`.

## Migration Plan

1. **БД**: новый Liquibase changeset — `ALTER TABLE door_configuration DROP CONSTRAINT chk_door_configuration_reverse_requires_frame`; затем `INSERT` новых строк без короба для существующих реверсивных пар (leaf_type_id, edge_type_id), NOT EXISTS-guard. Прогнать локально, проверить вручную (нет ошибки NULL-констрейнта, старые данные не задеты, новые строки видны в `GET /api/door-configurations`).
2. **Backend**: `DoorConfigurationPricingService` — добавить `reverseSurchargePercent()` (не трогая `calculate()`); новый `PricingSurchargesDto`/`DimensionSurchargeRuleDto`; новый `PricingSurchargesController` (`GET /api/pricing-surcharges`); `ComponentPriceDto` — два новых поля `baseRetailPrice`/`baseDealerPrice`, заполняются в `componentPriceFrom`/`framePostPrice` (цена компонента до наценок), не меняя математику самих надбавок.
3. **Frontend**: `App.tsx` — вынести вычисление `reverseStep` перед коллекцией, над полным каталогом; убрать `CASCADE_BEFORE_REVERSE`/`CASCADE_AFTER_REVERSE`, оставить единый `CASCADE_ORDER`; функция получения `ComponentCatalogDto` компонента из первого подходящего кандидата (не только из `selectedConfiguration`); единый линейный рендер потока с опциями сразу после каждого типа; загрузка `GET /api/pricing-surcharges` вместе с каталогом; локальное вычисление и отображение разбивки надбавок после расчёта; в списке компонентов результата расчёта — отображение базовой цены компонента (`baseRetailPrice`/`baseDealerPrice`) рядом с его итоговой ценой, менее заметно (вторичный текст меньшего размера), только для компонента, у которого базовая цена отличается от итоговой. `api/types.ts`/`api/doorConfigurations.ts` — новые типы и клиентский метод.
4. **Проверка**: точечный прогон затронутых backend-тестов (не полный `./gradlew test` — см. предпочтение пользователя в этой сессии); `npm run build`/`lint`; ручная проверка в браузере — единый поток от реверса до расчёта, реверс + «без короба» доступен и считается, разбивка процентов появляется и совпадает с ожидаемой (например, длина 950мм → +20% отдельной строкой).

Откат — по конвенции проекта: новые компенсирующие changeset'ы, не редактирование уже применённых.
