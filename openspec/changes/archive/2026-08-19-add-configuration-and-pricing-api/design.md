## Context

Схема БД (`door_configuration`, `liner_dimension_option`, `colour_option`, `configuration_price` и связанные `*_type` справочники) уже существует (changelog'ы `0004`–`0009`), но в `backend/` нет ни одной JPA-сущности, репозитория или контроллера — только точка входа Spring Boot приложения. Это первый прикладной код поверх схемы, поэтому решения ниже задают базовый паттерн (пакеты, слои, именование DTO) для будущих эндпоинтов, а не только для этих двух. См. `proposal.md` — «Why» и «What Changes» — для мотивации; см. `specs/door-configuration-api/spec.md` — для контракта.

## Goals / Non-Goals

**Goals:**
- Дать клиенту (в первую очередь frontend) единый способ получить каталог допустимых конфигураций с опциями и рассчитать стоимость изделия по выбору клиента.
- Заложить слоистую структуру (controller/service/repository), которой project CLAUDE.md требует для backend, в масштабе, достаточном для этих двух эндпоинтов, без избыточной инфраструктуры.

**Non-Goals:**
- Расчёт стоимости зеркала (leaf_mirror) — оно не входит в door_configuration catalog и не имеет configuration_price; остаётся вне этой фичи.
- Создание/редактирование конфигураций или цен через API (только чтение и расчёт).
- Кэширование, пагинация каталога — объём справочных данных мал (десятки строк), не требуется на данном этапе.
- Аутентификация/авторизация — не входит в это изменение.

## Decisions

### Слой доступа к данным: Spring Data JPA поверх существующих таблиц
Используем `spring-boot-starter-data-jpa` (уже подключён) с `@Entity`-классами, размеченными `@Table` на существующие имена таблиц, и `JpaRepository`. Альтернатива — прямой JDBC/`NamedParameterJdbcTemplate` без ORM — отклонена: JPA даёт декларативные `@ManyToOne` для читаемого построения ответов каталога и меньше ручного маппинга, а схема уже спроектирована с обычными FK, что хорошо ложится на JPA без специальных ухищрений.

### Один сервис на каждый эндпоинт, общий слой репозиториев
`DoorConfigurationCatalogService` (сборка каталога с опциями) и `DoorConfigurationPricingService` (расчёт стоимости) — отдельные сервисы, оба используют одни и те же репозитории (`DoorConfigurationRepository`, `LinerDimensionOptionRepository`, `ColourOptionRepository`, `ConfigurationPriceRepository`). Разделение по эндпоинту, а не один общий "God service", — т.к. логика подбора наиболее специфичной цены (pricing) существенно отличается по сложности от простой сборки каталога.

### Поиск наиболее специфичной цены — в памяти после выборки кандидатов
Для каждого компонента запрашиваем из `configuration_price` все строки данного владельца (`*_type_id`), у которых непустые ссылки на length/height/thickness/colour, если заданы, входят в множество { выбранная клиентом опция ИЛИ NULL } — то есть потенциальных кандидатов, — затем в Java-коде фильтруем те, чьи непустые ссылки совпадают с выбором клиента, и выбираем строку с максимальным числом непустых ссылок; при неоднозначности (несколько строк с одинаковым максимумом) считаем компонент некалькулируемым. Альтернатива — закодировать приоритет полностью в SQL (`ORDER BY` по числу непустых столбцов) — отклонена как менее прозрачная для последующих изменений правил и не сильно быстрее при таком объёме данных (справочные строки, не транзакционные).

### DTO уровня API отделены от JPA-сущностей
Ответы контроллеров строятся через отдельные record-DTO (например, `DoorConfigurationDto`, `PricingResponseDto`), а не отдают JPA-сущности напрямую — чтобы не тянуть в JSON служебные поля/ленивые прокси и не завязывать контракт API на структуру таблиц.

### Разбор входа: id конфигурации в пути, выбор опций в теле
`GET /api/door-configurations` — список без параметров. `POST /api/door-configurations/{id}/price` — id конфигурации в пути, тело запроса содержит выбор опций по компонентам (`leaf`, `frame`, `edge`, `doorCasing`, `frameExtensions` — только те, что присутствуют в данной конфигурации). REST-путь и форма тела фиксируются здесь, а не в спеке, т.к. это техническая деталь контракта; наблюдаемое поведение (что обязательно, что возвращается) описано в specs.

## Risks / Trade-offs

- [Риск] Правило "наиболее специфичная цена" при неоднозначности молча исключает компонент из суммы (частичный расчёт) → Компонент явно перечисляется в ответе как некалькулируемый, чтобы клиент мог показать это пользователю, а не терял информацию молча.
- [Риск] Валидация "опция принадлежит компоненту" требует на каждый выбор дополнительной проверки владельца (`leaf_type_id`/`frame_type_id`/...) у `liner_dimension_option`/`colour_option` → Реализуется как простая проверка в сервисе перед подбором цены, не требует изменений схемы.
- [Trade-off] Выборка кандидатов "опция ИЛИ NULL" может вернуть больше строк, чем нужно, при большом числе `configuration_price` на один тип компонента → Приемлемо при текущем объёме справочных данных; если объём вырастет на порядки, можно перенести фильтрацию в SQL позже без изменения внешнего контракта.
