## Context

См. `proposal.md` — «Why» и «What Changes». Ключевые факты о текущей схеме и коде, определяющие подход:

- `colour_option` и `configuration_price` уже поддерживают `frame_type` как одного из пяти владельцев (наравне с `leaf_type`/`edge_type`/`door_casing_type`/`frame_extensions_type`) — схема БД для этого менять не нужно (`openspec/specs/door-configuration-catalog/spec.md`, «Структура colour_option», «Владение colour_option», «Структура configuration_price»).
- Каталог (`door-configuration-api`, «Допустимые опции размеров и цвета для каждого компонента конфигурации») и UI (`door-configurator-ui`, «Динамический выбор опций компонентов») уже сформулированы обобщённо для всех типов компонентов, включая frame — они автоматически подхватят цвета короба, как только у `frame_type` появятся строки `colour_option`. Менять эти два требования не нужно.
- Единственное место, которое жёстко исключает frame из цветового ценообразования, — `DoorConfigurationPricingService`: специальный `if (type instanceof FrameType) { framePostPrice(...); return; }` в методе, добавляющем компонент к расчёту (`addComponentIfPresent`), и метод `framePostPrice`, который суммирует **все** записи `frame_post` по `frame_type_id`, не глядя на переданный `colourOptionId`. Это соответствует уже существующему требованию спеки, которое эта задача меняет.
- Готовый прецедент того же паттерна цвета (5 позиций: Хром матовый/Бронза/Черный/Золото матовое/Покраска по RAL как `colour_type`, `colour_option` + `configuration_price` с ценой) уже есть для кромки: `0025-vertikal-edge-configurations.yaml`. Новая миграция для ФАНТОМ следует этому же образцу, только с владельцем `frame_type` вместо `edge_type` и без оси размера (высоты).
- КОМПЛАНАР/НЕО/КОМПЛАНАР РЕВЕРС остаются как есть: у их `frame_type` нет строк `colour_option`, поэтому новое условие в сервисе не меняет их поведение — стоимость короба для них по-прежнему равна сумме `frame_post`.

## Goals / Non-Goals

**Goals:**
- Короб ФАНТОМ (`FT-001`) появляется в каскадном выборе конфигуратора и корректно рассчитывает стоимость по выбранному клиентом цвету комплекта стоек.
- Механизм цветового выбора для короба переиспользует существующую инфраструктуру `colour_option`/`configuration_price`/`findMostSpecificPrice`, не вводя новых таблиц/колонок и не трогая `frame_post`.
- Поведение расчёта для уже активных коробов (КОМПЛАНАР, НЕО, КОМПЛАНАР РЕВЕРС) не меняется.

**Non-Goals:**
- Не активируется коллекция полотна `LC-009` «Фантом» (полотно LT-045) — она остаётся неактивной, как и до этого change.
- Не вводится общий механизм «выбор одного варианта из нескольких `frame_post`» — для ФАНТОМ `frame_post` не используется вовсе, комплект описывается только через цвет.
- Не меняется UI-код и не добавляется новый компонент отображения — общий рендеринг групп опций уже покрывает этот случай (см. Context).

## Decisions

**Цена короба ФАНТОМ — через `colour_option`/`configuration_price`, а не через новые `frame_post`-строки с ценой на цвет.**
Рассматривались два варианта: (а) добавить nullable `colour_option_id` в `frame_post` и хранить 4 строки-варианта прямо там; (б) не трогать `frame_post` вовсе, завести цвет и цену через уже существующий генерик-механизм `colour_option`/`configuration_price`, как это сделано для кромки. Выбран (б): он не требует миграции схемы (`frame_post` не меняется), переиспользует уже реализованный и специфицированный путь «наиболее специфичная цена по цвету» и не создаёт второй, отдельный способ хранить «выбираемую» цену компонента. `frame_post` для ФАНТОМ просто остаётся пустым (0 строк) — этот случай уже предусмотрен структурой (`frame-post-catalog`: «Короб одним комплектом» / «Короб без записей frame_post»), а спецификация расчёта после этого change трактует «нет frame_post» + «есть выбранный цвет» как базовую сумму 0 плюс цена цвета.

**Формула стоимости короба: `sum(frame_post) + цена по выбранному цвету`, а не «либо-либо».**
Альтернатива — если у frame_type есть `colour_option`, полностью игнорировать `frame_post`. Выбрана аддитивная формула, потому что она строго обобщает старое поведение (для коробов без цвета сумма по цвету равна нулю по построению — цветовых строк нет) и оставляет теоретическую возможность в будущем комбинировать «база + отделка» для другого короба, если бизнес это попросит, без повторного изменения спеки.

**Отсутствие выбора цвета при наличии `colour_option` → некалькулируемый компонент, а не «сумма frame_post без надбавки».**
Если у короба есть цветовые варианты, но клиент не выбрал ни один, компонент считается некалькулируемым целиком (см. delta-спеку). Это соответствует уже действующему для остальных компонентов правилу «нет подходящей строки — компонент из расчёта исключается, а не молча получает частичную цену» (`door-configuration-api`, «Частичный расчёт при отсутствии цены компонента»). Не показывать ФАНТОМ по цене 0 рублей, если цвет не выбран, — иначе итоговая сумма будет вводить в заблуждение.

**Новый `colour_type` «Золото/бронза» вместо переиспользования «Бронза»/«Золото матовое».**
Пользователь описал один вариант отделки с одной ценой, отличной от существующих «Бронза» (CT-024) и «Золото матовое» (CT-026), используемых для кромки. Переиспользование любого из них исказило бы название видимого клиенту варианта. Заведён отдельный `colour_type` с новым кодом (следующий свободный в последовательности CT-xxx — `CT-028`).

## Risks / Trade-offs

- **[Риск]** Формула «`frame_post` + цвет» при `colour_option` пуст, а `frame_post` не пуст (гипотетический будущий короб) молчаливо сведётся к старому поведению — это ожидаемо и безопасно, но стоит явно проверить тестом при реализации, чтобы не создать регрессию для КОМПЛАНАР/НЕО/РЕВЕРС. → Митигация: тест-кейсы из delta-спеки покрывают оба режима (с цветом и без).
- **[Риск]** Общий рендеринг UI уже, по спецификации, обязан показывать группу цвета для frame, но код мог никогда не быть исполненным для этого пути (frame ещё ни разу не имел цветов) — есть шанс, что в `DoorConfigurationCatalogService`/`buildFrameComponent` цвет для frame на практике не собирается, несмотря на спецификацию. → Митигация: при реализации явно проверить это сборкой каталога с тестовыми данными перед тем, как полагаться на «уже работает»; если сборка не включает `colourOptionsFor(FrameType)`, это баг соответствия существующему требованию, а не новая спека — исправляется без delta.
- **[Trade-off]** Аддитивная формула (`frame_post` + цвет) чуть сложнее, чем «либо-либо», но выбрана ради обратной совместимости и единообразия с остальными компонентами, где размерные и цветовые совпадения тоже складываются в одну наиболее специфичную строку, а не выбираются взаимоисключающе на уровне разных таблиц.

## Migration Plan

1. Liquibase-миграции (в `backend/src/main/resources/db/changelog/changes/`, подключить в master changelog, по образцу `0025-vertikal-edge-configurations.yaml` и `004х-*-frame-configurations.yaml`):
   - `door_configuration`: `FT-001` × полотно всех уже активных коллекций (`LC-001`–`LC-008`), без `door_casing_type`/`frame_extensions_type`, затем отдельным шагом — с `edge_type` (`ET-001`, `ET-002`), по аналогии с `0043`/`0044`.
   - `colour_type`: новая строка «Золото/бронза», код `CT-028`.
   - `colour_option`: 4 строки для `frame_type_id = FT-001` × `colour_type` в (`CT-023`, `CT-025`, `CT-027`, `CT-028`).
   - `configuration_price`: 4 строки с `frame_type_id = FT-001` и соответствующим `colour_option_id` — цены (дилер/розница): Хром матовый 9903/16850, Черный 11003/18722, Покраска по RAL 19806/33700, Золото/бронза 19806/33700.
2. Backend: в `DoorConfigurationPricingService` убрать безусловный ранний выход для `FrameType`; посчитать сумму `frame_post`, и если для `frame_type` есть `colour_option`, дополнительно найти цену по выбранному цвету через существующий `findMostSpecificPrice` и прибавить (или пометить компонент некалькулируемым при отсутствии/неоднозначности выбора).
3. Проверить (не переписывая, если уже работает) сборку каталога — что `colourOptionsFor` включает `FrameType` при построении frame-компонента; если нет, поправить как исправление соответствия уже действующей спеке каталога.
4. Ручная проверка через UI: короб ФАНТОМ выбирается в каскаде, показывает 4 цвета, расчёт стоимости корректен для каждого; КОМПЛАНАР/НЕО/РЕВЕРС считаются как раньше.

Откат — обычный для этого проекта: новые changeset'ы не редактируются задним числом; при необходимости отката добавляется новый компенсирующий changeset (не удаляет предыдущий), а откат кода — обычный revert коммита.
