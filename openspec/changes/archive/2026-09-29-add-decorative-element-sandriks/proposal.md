## Why

Фабрика хочет продавать «сандрики» (Левия, Арно, Адела) как новую категорию декоративных элементов для коллекций «Элегант» и «Гармония». В отличие от «Блока и базы» у сандрика ширина зависит от длины выбранного полотна (три диапазона на каждый дизайн) — текущая модель decorative_element_type хранит только одну фиксированную ширину на тип и этого не покрывает.

## What Changes

- Новая категория decorative_element_category «Сандрики» (`DEC-003`) с тремя decorative_element_type: «Сандрик Левия» (длина 200 мм, толщина 67 мм, дилер 9574 ₽, розница 16755 ₽), «Сандрик Арно» (длина 188 мм, толщина 64,5 мм, дилер 6237 ₽, розница 10915 ₽), «Сандрик Адела» (длина 93 мм, толщина 59 мм, дилер 5237 ₽, розница 9166 ₽). Applicability — decorative_element_option для leaf_type коллекций «Элегант» (`LC-003`) и «Гармония» (`LC-004`), тем же принципом, что и «Блок и база».
- Новая структура decorative_element_width_option: для типа декоративного элемента — диапазон длины полотна (min/max, по образцу уже существующего liner_dimension_option) → ширина элемента в этом диапазоне. Для трёх типов сандриков заполняется по три строки (диапазоны длины полотна ≤800 / 801–900 / 901–1200 мм — см. таблицу в спецификации). decorative_element_type.width_mm для сандриков остаётся NULL — фиксированной ширины у них нет, она полностью определяется диапазоном.
- Расчёт стоимости декоративных элементов (по `door_configuration`, по отдельному полотну `leaf-standalone-pricing`, и в новом виде — по отдельному запросу `POST /api/decorative-elements/price`) при формировании разбивки для типа с диапазонами ширины ДОЛЖЕН резолвить фактическую ширину по длине полотна: в двух первых эндпоинтах длина полотна уже есть в запросе; в независимом эндпоинте `POST /api/decorative-elements/price` появляется новое необязательное поле длины полотна (`leafLengthMm`) специально для этого резолва. Если длина полотна не передана/неизвестна или не попадает ни в один диапазон — ширина остаётся неопределённой (не показывается), сама позиция не отклоняется. Для типов без диапазонов (плинтус, блок, база) поведение не меняется — ширина остаётся фиксированной из decorative_element_type.width_mm.
- На экране конфигуратора независимый этап расчёта декоративных элементов начинает передавать в `POST /api/decorative-elements/price` длину уже выбранного на этом же экране полотна — только для того, чтобы сандрики корректно показывали подобранную ширину в результате и в дальнейшей выгрузке; никаких новых полей ввода в UI не добавляется.
- Каталог длины полотна коллекций «Элегант»/«Гармония» не меняется (сейчас 600–800 мм у «Элегант», 400–800 мм у «Гармония») — диапазоны 801–900 и 901–1200 мм заводятся в данных заранее (по значениям, предоставленным фабрикой), но при сегодняшних каталожных длинах полотна практически недостижимы; это осознанное решение, а не ошибка.

## Capabilities

### New Capabilities
_(нет)_

### Modified Capabilities
- `decorative-element-catalog`: новая категория «Сандрики» с тремя типами; новая структура decorative_element_width_option (диапазон длины полотна → ширина) как альтернатива фиксированному width_mm.
- `decorative-element-standalone-pricing`: запрос расчёта получает необязательное поле длины полотна (`leafLengthMm`), используемое для резолва ширины позиций с диапазонами.
- `door-configuration-api`: расчёт стоимости декоративных элементов резолвит ширину по диапазону, используя уже известную в запросе длину полотна.
- `leaf-standalone-pricing`: аналогично — резолв ширины по уже известной длине полотна.
- `door-configurator-ui`: независимый этап расчёта декоративных элементов передаёт длину выбранного полотна в запрос расчёта (см. выше) — без новых элементов ввода.

## Impact

- Backend: новая таблица `decorative_element_width_option` (Liquibase) + новые данные (категория, 3 типа, 9 строк диапазонов, decorative_element_option для Элегант/Гармония). Сервис расчёта стоимости декоративных элементов резолвит эффективную ширину по длине полотна там, где она известна; `DecorativeElementPricingRequestDto` получает новое необязательное поле; `DecorativeElementPriceDto.widthMm` теперь означает «эффективная (резолвленная) ширина», без изменений в его использовании на стороне экспорта (уже существующий формат `длина × ширина × толщина` подхватывает это без изменений).
- Frontend: один новый параметр в уже существующем запросе расчёта декоративных элементов (передаётся длина уже выбранного полотна); видимых изменений UI нет.
- Данные: наименования, длина, толщина и таблица «диапазон длины полотна → ширина» — по значениям, указанным пользователем; границы диапазонов — включительно (≤800 / 801–900 / 901–1200).
