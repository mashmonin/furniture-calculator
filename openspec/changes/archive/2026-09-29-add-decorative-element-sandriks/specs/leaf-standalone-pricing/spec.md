## MODIFIED Requirements

### Requirement: Расчёт стоимости отдельного полотна по его типу
Система ДОЛЖНА (SHALL) предоставлять эндпоинт расчёта стоимости, принимающий id существующего `leaf_type` и набор выбранных клиентом опций полотна: id `liner_dimension_option` для длины и высоты (либо произвольное значение для соответствующей оси, как и при расчёте по `door_configuration`), id `liner_dimension_option` для толщины (у толщины нет режима произвольного значения — только выбор из каталожных опций, как и при расчёте по `door_configuration`, см. door-configuration-api, «Наценка за выбранную толщину полотна»), id `colour_option` (фронтальный цвет), id `mirror_finish_type`, id `glazing_type`, явный признак реверса (булево значение; отсутствие ДОЛЖНО (SHALL) трактоваться как false) — и, независимо от полотна, список позиций фурнитуры и список позиций декоративных элементов (см. decorative-element-catalog). Эндпоинт ДОЛЖЕН (SHALL) также принимать признак двусторонней покраски и id второго (заднего) `colour_option`, по тем же правилам приёма и валидации, что и в расчёте по `door_configuration` (см. door-configuration-api, «Второй цвет и признак двусторонней покраски полотна в запросе расчёта»): задний цвет допустим только при установленном признаке двусторонней покраски, и оба цвета должны принадлежать указанному `leaf_type`. Дополнительно эндпоинт МОЖЕТ (MAY) принимать id вида кромки (`edge_type`) и опции кромки (id `liner_dimension_option` для высоты, id `colour_option`) — кромка считается и добавляется в разбивку результата наравне с полотном. Указанный id `edge_type` ДОЛЖЕН (SHALL) ссылаться на вид кромки, для которого существует хотя бы одна строка `door_configuration` с этим `leaf_type` и этим `edge_type` (т.е. кромка допустима для этого полотна, независимо от короба/наличника/добора этой строки); иначе — ошибка 400. Короб, наличник и добор эндпоинтом не рассматриваются, даже если присутствуют в запросе (см. frame-group-standalone-pricing). Если для полотна определена длина (выбранная опция либо произвольное значение), для позиций декоративных элементов, чей decorative_element_type имеет строки decorative_element_width_option (см. decorative-element-catalog, «Ширина сандрика по диапазону длины полотна»), ширина в разбивке ДОЛЖНА (SHALL) резолвиться по этой длине — тем же принципом, что и в расчёте по `door_configuration` (см. door-configuration-api, «Учёт декоративных элементов в расчёте стоимости изделия»); если длина полотна не определена или не попадает ни в один диапазон, ширина такой позиции остаётся неопределённой.

#### Scenario: Расчёт стоимости полотна без дополнительных опций
- **WHEN** отправляется запрос расчёта с id существующего `leaf_type` без выбранных опций размеров, цвета, исполнения зеркала, вида остекления и кромки
- **THEN** эндпоинт возвращает результат с найденной (если есть подходящая строка `configuration_price`) или не найденной ценой полотна, без ошибки

#### Scenario: Несуществующий тип полотна
- **WHEN** отправляется запрос расчёта с id `leaf_type`, которого не существует
- **THEN** эндпоинт отвечает ошибкой 404 и не выполняет расчёт

#### Scenario: Опция не принадлежит указанному полотну
- **WHEN** в запросе id выбранной `liner_dimension_option` (длины, высоты или толщины) или `colour_option` (фронтального или, при двусторонней покраске, заднего) ссылается на компонент, отличный от указанного `leaf_type`
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Надбавки за размер и исполнение зеркала применяются так же, как при расчёте по конфигурации
- **WHEN** в запросе указано произвольное значение длины или высоты полотна, совпадающее с правилом наценки, и/или id допустимой для этого полотна опции толщины, и/или id допустимого для этого полотна исполнения зеркала, и/или (см. добавленную наценку за остекление) id допустимого для этого полотна вида остекления
- **THEN** итоговая цена полотна включает соответствующие надбавки, рассчитанные по тем же правилам и в том же порядке, что и в расчёте стоимости по `door_configuration`

#### Scenario: Наценка за толщину применяется так же, как при расчёте по конфигурации
- **WHEN** в запросе указан id опции толщины 59 мм, допустимой для этого `leaf_type`
- **THEN** итоговая цена полотна включает наценку 20% за толщину, применённую на том же месте в последовательности надбавок, что и при расчёте стоимости по `door_configuration` (см. door-configuration-api, «Место наценки за толщину полотна в последовательности надбавок»)

#### Scenario: Наценка за цвет и надбавка за двустороннюю покраску применяются так же, как при расчёте по конфигурации
- **WHEN** в запросе для полотна установлен признак двусторонней покраски и указаны фронтальный и задний цвет, каждый из которых ссылается на colour_type с ненулевым surcharge_percent
- **THEN** итоговая цена полотна включает наценку за цвет, вычисленную как сумма процентов обеих сторон (а не последовательное перемножение), и отдельную надбавку 50% за двустороннюю покраску — по тем же правилам и в том же порядке, что и в расчёте стоимости по `door_configuration` (см. door-configuration-api, «Наценка за выбранный цвет полотна», «Наценка за двустороннюю покраску полотна», «Место надбавки за двустороннюю покраску в последовательности надбавок»)

#### Scenario: Задний цвет без двусторонней покраски отклоняется
- **WHEN** в запросе для полотна указан задний цвет, но признак двусторонней покраски не установлен (или равен false)
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Надбавка за реверс применяется по явному признаку в запросе
- **WHEN** в запросе передан явный признак реверса со значением true
- **THEN** к цене полотна применяется та же надбавка за реверс, что и при расчёте по `door_configuration` с `is_reverse = true`, по тем же правилам последовательного применения надбавок

#### Scenario: Без явного признака реверса надбавка не применяется
- **WHEN** в запросе признак реверса не передан либо передан со значением false
- **THEN** к цене полотна надбавка за реверс не применяется

#### Scenario: Признак реверса не влияет на расчёт по door_configuration
- **WHEN** признак реверса передан в запросе к эндпоинту расчёта по `door_configuration` (а не к расчёту отдельного полотна)
- **THEN** он игнорируется — надбавка за реверс для этого эндпоинта по-прежнему определяется исключительно значением `is_reverse` самой `door_configuration`

#### Scenario: Позиции фурнитуры учитываются так же, как при расчёте по конфигурации
- **WHEN** запрос содержит одну или несколько позиций фурнитуры (см. hardware-catalog)
- **THEN** их стоимость рассчитывается и суммируется с ценой полотна так же, как при расчёте стоимости по `door_configuration`

#### Scenario: Позиции декоративных элементов учитываются так же, как при расчёте по конфигурации
- **WHEN** запрос содержит одну или несколько позиций декоративных элементов (см. decorative-element-catalog)
- **THEN** их стоимость рассчитывается и суммируется с ценой полотна так же, как при расчёте стоимости по `door_configuration` (см. door-configuration-api, «Учёт декоративных элементов в расчёте стоимости изделия»)

#### Scenario: Ширина сандрика резолвится по длине этого полотна
- **WHEN** в запросе указана длина полотна 700 (выбранная опция или произвольное значение) и позиция декоративного элемента с decorative_element_type «Сандрик Левия»
- **THEN** запись этой позиции в разбивке содержит ширину 1150 (диапазон ≤800)

#### Scenario: Кромка принимается и считается вместе с полотном
- **WHEN** в запросе указан id вида кромки, для которого существует door_configuration с этим leaf_type и этим edge_type, и (опционально) её опции цвета и высоты
- **THEN** запрос обрабатывается без ошибки валидации формата запроса, и кромка учитывается в расчёте по тем же правилам, что и при расчёте по door_configuration (включая проверку высоты кромки в диапазоне высоты полотна)

#### Scenario: Без указанного вида кромки кромка не считается
- **WHEN** в запросе id вида кромки не указан
- **THEN** расчёт выполняется без кромки, как и до появления этой возможности — в разбивке результата запись о кромке отсутствует

#### Scenario: Кромка, недопустимая для указанного полотна, отклоняется
- **WHEN** указанный id вида кромки существует, но не существует ни одной строки door_configuration с этим leaf_type и этим edge_type
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Несуществующий вид кромки недопустим
- **WHEN** указанный id вида кромки не существует ни в одной строке edge_type
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт
