## Context

`decorative_element_type` (см. decorative-element-catalog) хранит одну фиксированную длину/ширину/толщину на тип — этого достаточно для плинтуса и «Блока и базы», но не для сандрика, у которого ширина зависит от длины полотна (три диапазона на дизайн).

Расчёт стоимости декоративных элементов происходит в трёх местах: по `door_configuration` и по отдельному полотну (`leaf-standalone-pricing`) — оба знают длину полотна; и независимый эндпоинт `POST /api/decorative-elements/price` (decorative-element-standalone-pricing) — он принципиально не привязан ни к какому полотну (по аналогии с hardware-standalone-pricing) и сейчас не получает никакого измерения.

В кодовой базе уже есть устоявшийся паттерн для «значение зависит от диапазона другого измерения» — таблица `liner_dimension_option` (min_value/max_value + FK на конкретный тип компонента), используемая для длины добора/наличника в зависимости от высоты полотна (см. changes 0066, 0074, 0068–0072).

## Goals / Non-Goals

**Goals:**
- Хранить для сандрика три варианта ширины, каждый — для своего диапазона длины полотна, без потери существующей фиксированной ширины у прочих типов (плинтус, блок, база).
- Резолвить фактическую ширину сандрика в разбивке результата (и, как следствие, в выгрузке — она уже показывает `длина × ширина × толщина`, если ширина задана) там, где длина полотна известна.
- Не ломать decorative-element-standalone-pricing как независимый от `door_configuration` эндпоинт — длина полотна становится необязательным дополнительным параметром, а не обязательной привязкой к каталогу полотна.

**Non-Goals:**
- Не переносить и не меняем каталог длины полотна «Элегант»/«Гармония» — сейчас он не превышает 800 мм, диапазоны 801–1200 мм у сандрика вводятся заранее и сегодня недостижимы. Расширение каталога длины — отдельная возможная задача, не в этом change.
- Не добавляем никакого нового поля ввода на экране конфигуратора — длина полотна там уже выбрана до открытия блока «Декоративные элементы»; фронт просто передаёт уже известное значение в уже существующий запрос.
- Не проверяем и не ограничиваем выбор сандрика по длине полотна (блок «Декоративные элементы» остаётся полностью ручным — тип и количество); резолв ширины влияет только на то, что показывается в результатах/выгрузке, а не на то, что можно выбрать.

## Decisions

### Новая таблица decorative_element_width_option вместо фиксированного width_mm
По аналогии с `liner_dimension_option`: `decorative_element_width_option(id, decorative_element_type_id, min_value, max_value, width_mm)`, `min_value`/`max_value` — nullable (NULL с одной стороны = без ограничения с этой стороны), диапазон включительный. Для сандриков заполняется 3 строки на тип (9 всего); `decorative_element_type.width_mm` для них остаётся NULL. Для типов без строк в этой таблице (плинтус, блок, база) поведение не меняется — используется их собственный `width_mm`.

Альтернатива — заводить отдельный decorative_element_type на каждую комбинацию дизайн×диапазон (9 типов с шириной в названии, полностью вручную выбираемых), как уже сделано для «Блок А»/«Блок В». Отклонено пользователем в пользу автоматического резолва — иначе продавцу пришлось бы вручную сверяться с диапазоном при каждом подборе.

### Резолв ширины — на уровне сервиса расчёта, не в каталог-эндпоинте
`GET /api/decorative-elements-catalog` (каталог) по-прежнему отдаёт типы без резолва ширины — он не зависит от door_configuration/leaf (см. decorative-element-catalog, «Получение каталога декоративных элементов», не меняется). Резолв происходит там, где строится `DecorativeElementPriceDto` для конкретного расчёта — доступная длина полотна (из door_configuration/leaf-standalone запроса, либо из нового необязательного поля независимого эндпоинта) ищется среди строк `decorative_element_width_option` этого типа; при совпадении диапазона `widthMm` в DTO заполняется найденным значением, иначе — значением `decorative_element_type.width_mm` (для типов без диапазонов) либо остаётся NULL (для типов с диапазонами, если совпадения нет или длина не передана).

### decorative-element-standalone-pricing получает leafLengthMm, а не leafTypeId
Проще было бы принимать id `leaf_type` и брать его длину из каталога, но независимый эндпоинт принципиально не валидирует позиции по каталогу дверей (см. текущий текст спецификации: «список позиций принимается как есть») и не должен обрастать зависимостью от leaf_type. Достаточно одного необязательного числового поля — конкретное значение длины, которое фронт и так уже знает на экране (выбрано пользователем или введено произвольно, как и остальные размеры полотна в этом калькуляторе).

## Risks / Trade-offs

- **Диапазоны 801–1200 мм сегодня недостижимы** (каталог длины полотна этих коллекций не превышает 800 мм) → пока всегда будет резолвиться только первый диапазон. Осознанно принято пользователем; данные заводятся заранее.
- **Несовпадение диапазона не считается ошибкой** (ширина просто не резолвится, позиция не отклоняется) — соответствует принципу, что декоративные элементы уже сегодня не валидируются по применимости в этих расчётных эндпоинтах («их допустимость... этим эндпоинтом не проверяется», decorative-element-catalog/door-configuration-api). Компромисс: пользователь, использующий калькулятор API напрямую без UI, может не заметить, что ширина не резолвилась, если забыл передать `leafLengthMm`.
