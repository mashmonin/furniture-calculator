## Context

См. `proposal.md` — «Why» и «What Changes». Ключевые факты о текущей реализации, определяющие подход:

- `is_reverse` сейчас — колонка `frame_type` (`0026-reverse-leaf-catalog.yaml`), `true` только у одной строки — `FT-004` «КОМПЛАНАР РЕВЕРС (в проем)». `FrameType.java`: `@Column(name = "is_reverse") private boolean reverse;`, без сеттера.
- `DoorConfigurationPricingService.calculate()` читает `configuration.getFrameType().isReverse()` и передаёт это как `applyReverseSurcharge` только для leaf-компонента (+10%, `REVERSE_SURCHARGE_MULTIPLIER`).
- Реверс-конфигурации существуют для всех 8 активных коллекций, заведены через FT-004 в миграциях 0026–0029, 0032, 0034–0035, 0040–0041, 0043, 0046, 0049 — плюс Гармония получила их «бесплатно» через клонирование коллекции по шаблону Элегант в 0037 (эта миграция копирует door_configuration шаблонного leaf_type целиком, включая уже существовавшие на тот момент строки с FT-004). Подтверждено по факту в БД после применения 0054: у Гармонии 18 leaf+edge комбинаций с is_reverse=true, включая наличники DCT-005 «Авеню-реверс» и DCT-007 «Аура-реверс» (последнее — не совсем свой наличник Гармонии, а унаследованный артефакт того же клонирования; не относится к этому change, не трогаем).
- Три door_casing_type существуют только для FT-004: DCT-005 «Авеню для системы КОМПЛАНАР РЕВЕРС \*» (Вертикаль/Атмосфера/Геометрия), DCT-007 «Аура для системы КОМПЛАНАР РЕВЕРС \*» (Элегант), DCT-009 «Ария для системы КОМПЛАНАР РЕВЕРС \*» (Свобода). У Сияние и Сибирь реверс-конфигурации вообще без наличника (`door_casing_type_id IS NULL` в обоих режимах) — это единственный случай, когда обычная и реверсивная строка door_configuration совпадают по всем ссылкам, кроме признака реверса.
- `frame_post` у FT-004 (`0027`) дублирует цены FT-002 один в один (PT-001/PT-002, те же суммы) — реальной ценовой разницы в стойках короба между режимами нет.
- Frontend (`App.tsx`): `CASCADE_ORDER = ['leaf', 'edge', 'frame', 'doorCasing', 'frameExtensions']`, `buildCascadeSteps()` на каждом шаге вычисляет `availableTypes` из текущего списка `candidates` (уже отфильтрованного предыдущими шагами) и сужает `candidates` после выбора — единый универсальный механизм для всех шагов-типов компонентов.
- `door_configuration` уже имеет уникальный индекс по (leaf, frame, edge, casing, extensions) с `COALESCE(...,0)` для необязательных ссылок (`0006-3`), и check-констрейнт «наличник/добор требуют короба» (`0006-2`).

## Goals / Non-Goals

**Goals:**
- Один короб (frame_type) КОМПЛАНАР обслуживает и обычные, и реверсивные конфигурации; отдельный код короба для реверса не нужен.
- Признак реверса — явное свойство конкретной строки door_configuration, а не типа короба.
- В UI реверс — явный, понятный пользователю переключатель, а не скрытый смысл одного из вариантов в списке коробов.
- Полностью убрать короб FT-004 и связанные с ним данные из БД (не оставлять мёртвых записей).

**Non-Goals:**
- Не меняется величина или механизм надбавки за реверс (+10% к цене полотна) — только источник признака, из которого она вычисляется.
- Не меняются сами реверс-наличники (DCT-005/007/009) и их цены — только владелец связывающих их door_configuration (FT-002 вместо FT-004).
- Не расширяется охват реверса на новые коллекции и не вводится реверс для короба НЕО — сохраняется текущий охват (только КОМПЛАНАР, только те коллекции, где реверс уже был, включая Гармонию — см. Context).
- Не переносится логика надбавки в движок бизнес-правил (Drools) — уже отмечено как отдельная будущая задача в комментарии кода, не в этом change.

## Decisions

**Признак реверса — новая колонка `is_reverse` на `door_configuration`, а не на `door_casing_type`.**
Рассматривался вариант пометить реверс-наличники (DCT-005/007/009) флагом и выводить реверс-статус конфигурации из выбранного наличника. Отклонён, потому что для Сияние/Сибирь наличника нет вообще ни в одном из режимов — вывести реверс из наличника там нечем. Явная колонка на самой строке конфигурации работает одинаково для всех коллекций независимо от того, есть у них выделенный реверс-наличник или нет.

**Уникальный индекс door_configuration расширяется до `is_reverse` включительно.**
Без этого для Сияние/Сибирь обычная и реверсивная строки (одинаковые leaf/frame/edge, оба без наличника) физически совпадали бы и не могли сосуществовать. Индекс `uk_door_configuration_combination` пересоздаётся с добавлением `COALESCE(is_reverse::int, 0)` (либо просто `is_reverse`, т.к. колонка NOT NULL — COALESCE не нужен для неё самой, нужен только для остальных, как сейчас).

**FT-004 и его данные удаляются физически (DELETE/DROP), а не архивируются как мёртвый справочник.**
Короб-дубликат создавался только ради флага реверса; после переноса флага на door_configuration он не несёт больше никакой уникальной информации (цены frame_post идентичны FT-002, наличники переиспользуются). Хранить пустой/неиспользуемый frame_type без единой ссылающейся строки — источник путаницы при дальнейшей разработке. Порядок удаления в новом changeset: сначала `door_configuration`/`frame_post` со ссылкой на FT-004, затем сам `frame_type` (FK `ON DELETE RESTRICT` по умолчанию не позволит удалить родителя раньше потомков).

**Переключатель «Реверс» встраивается в тот же общий механизм `buildCascadeSteps`, что и остальные шаги, но как отдельная булева псевдо-ось, а не через `CASCADE_ORDER`/`ComponentKey`.**
`ComponentKey`/`CASCADE_ORDER` заточены под типы-справочники (`ReferenceDto` с id/name) — реверс не такой: у него нет каталожной сущности, только `boolean` на самой конфигурации. Поэтому переключатель реализуется отдельной вставкой в цепочку вычисления `candidates` между шагами `edge` и `frame` (не через типовой цикл `CASCADE_ORDER`), но по тем же принципам: доступность считается от текущих `candidates`, выбор сужает `candidates` для последующих шагов, смена значения сбрасывает более поздние шаги.

**Переключатель по умолчанию выключен, если оба режима доступны — отступление от правила «явный клик даже при единственном варианте».**
Для типовых шагов (короб, наличник, добор) любой шаг с ровно одним вариантом всё равно требует явного клика — так исключается неявное угадывание намерения пользователя среди именованных альтернатив. Для булева переключателя это правило неприменимо буквально: «не трогать переключатель» — это осмысленное, самодостаточное действие «оставить обычную комплектацию», а не пропущенный шаг. Считаем выключенное положение полноценным явным состоянием по умолчанию, не требующим дополнительного клика — это соответствует ожидаемому поведению переключателя как UI-паттерна и продуктовой логике (обычная комплектация — более частый случай).

## Risks / Trade-offs

- **[Риск]** Пересборка уникального индекса `door_configuration` и добавление колонки — на таблице с уже нетривиальным объёмом строк (200+ конфигураций). Миграция полностью аддитивна и быстра (ALTER TABLE + пересоздание индекса), но требует аккуратной последовательности: сначала добавить колонку с default false, затем обновить перенесённые реверс-строки на true, затем пересобрать индекс. → Порядок шагов зафиксирован в tasks.md.
- **[Риск]** Прямое DELETE справочной строки frame_type (FT-004) — необычная операция для этого проекта (обычно только INSERT/UPDATE). Ошибка в порядке DELETE уронит миграцию на FK-констрейнте. → Явный порядок (потомки → родитель) в одном changeset, проверка на локальной БД перед архивированием (как и в предыдущих change).
- **[Trade-off]** Логика реверс-переключателя во frontend не переиспользует `buildCascadeSteps` дословно (отдельная ветка вычисления), что немного увеличивает сложность `App.tsx` по сравнению с полностью единообразным циклом по `CASCADE_ORDER`. Альтернатива — искусственно завести псевдо-`ComponentKey` "reverse" с двумя "типами" (true/false) — отклонена, т.к. усложнила бы `ComponentCatalogDto`/`ComponentKey` ради одного булева случая и не отражала бы, что у реверса нет каталожной сущности.

## Migration Plan

1. Backend/БД (один блок изменений, несколько changeset'ов подряд):
   - Добавить `door_configuration.is_reverse` (BOOLEAN NOT NULL DEFAULT false); расширить `chk_door_configuration_casing_extensions_require_frame`-подобной проверкой «is_reverse=true ⇒ frame_type_id IS NOT NULL»; пересобрать `uk_door_configuration_combination` с учётom `is_reverse`.
   - Для каждой существующей комбинации, которая раньше шла через FT-004: INSERT новых `door_configuration` под FT-002 с `is_reverse = true`, сохраняя те же leaf_type/edge_type/door_casing_type (DCT-005/007/009 либо NULL для Сияние/Сибирь).
   - DELETE всех `door_configuration` и `frame_post` с `frame_type_id = FT-004`; DELETE строки `frame_type` FT-004; DROP COLUMN `frame_type.is_reverse`.
2. Backend-код: `FrameType.java` — убрать поле `reverse`; `DoorConfiguration.java` — добавить `boolean reverse` (`@Column(name = "is_reverse")`); `DoorConfigurationPricingService` — заменить `configuration.getFrameType().isReverse()` на `configuration.isReverse()`; `DoorConfigurationDto`/`DoorConfigurationCatalogService.toDto()` — добавить поле `reverse`.
3. Frontend: добавить в `App.tsx` вычисление доступности/сужения по `is_reverse` между шагами `edge` и `frame`; UI-переключатель (antd `Switch`) с лейблом «Реверс»; сброс `frame`/`doorCasing`/`frameExtensions` выбора при его изменении — по аналогии с существующим сбросом при смене более раннего шага.
4. Проверка: `./gradlew test` (обновить/добавить unit-тесты `DoorConfigurationPricingService` под чтение `is_reverse` с конфигурации), ручная/API-проверка каскада для одной коллекции с выделенным реверс-наличником (Элегант) и одной без него (Сияние/Сибирь), `npm run build`/`lint`.

Откат — по конвенции проекта: новые компенсирующие changeset'ы, не редактирование уже применённых.
