## Why

Для добора «ТС» (`FrameExtensionsType`, коды `FET-004`–`FET-007`, ширины 100/140/190/400 мм) длина физически зависит от выбранной высоты полотна: одному диапазону высоты полотна соответствует ровно одна допустимая длина добора, а для некоторых диапазонов высоты полотна добор «ТС» вообще недоступен. Сейчас в каталоге у всех четырёх типов добора «ТС» есть только одна опция длины (2170 мм) без какой-либо привязки к высоте полотна, поэтому клиент может собрать физически невозможную конфигурацию (например, добор длиной 2170 мм при полотне высотой 2700 мм). Аналогичная проблема уже решена для короба «НЕО» (`2026-09-05-link-frame-neo-height-to-leaf-height`) и короба «Компланар» (`2026-09-05-link-komplanar-height-to-leaf-height`) — этот change переносит тот же принцип на длину добора «ТС», используя ось «Длина» вместо оси «Высота».

## What Changes

- Валидация «размер компонента совместим с высотой полотна» на бэкенде (`validateHeightWithinLeafRange`) обобщается так, чтобы работать не только с высотой (ось `DT-002`), но и с длиной (ось `DT-001`) — вызывающий код сам указывает ожидаемую ось размера, а не полагается на внутреннюю проверку, жёстко привязанную к высоте. Так же, как раньше в этом методе не менялось поведение для кромки при обобщении под короб «НЕО», здесь не меняется поведение существующих вызовов (кромка, короб «НЕО»/«Компланар») при добавлении добора «ТС».
- Для добора «ТС» (`FrameExtensionsType` с кодом из `FET-004`, `FET-005`, `FET-006`, `FET-007`) длина становится обязательной и ограничивается диапазоном высоты полотна:
  - 1900–2100 → длина 2170 мм
  - 2150–2250 → длина 2400 мм
  - 2300 (точка) → длина 2400 мм
  - 2350–2550 → длина 2700 мм
  - 2600–2850 и 2900–2950 → добор «ТС» недоступен (опций нет)
- Новая Liquibase-миграция: существующие 4 строки `liner_dimension_option` (value=2170, по одной на каждый код `FET-004`–`FET-007`) дополняются границами диапазона `min_value=1900, max_value=2100`; добавляются новые строки для value=2400 (диапазон [2150, 2250]), value=2400 (диапазон-точка [2300, 2300]) и value=2700 (диапазон [2350, 2550]) — по одной на каждый из 4 кодов.
- Существующий уникальный индекс `uk_liner_dimension_option_frame_extensions_type` расширяется дополнительными колонками диапазона (по аналогии с `uk_liner_dimension_option_frame_type` из `link-frame-neo-height-to-leaf-height`), чтобы разрешить две опции добора с одинаковой длиной (2400 мм), но непересекающимися диапазонами высоты полотна (2150–2250 и отдельно 2300).
- Цена добора «ТС» перестаёт зависеть от выбранной длины (сейчас формально зависит — единственная опция длины 2170 мм жёстко привязана к строке `configuration_price` через `length_option_id`, из-за чего добавление новых опций длины без изменения цены потребовало бы дублировать строку цены на каждую новую длину). Новая миграция обнуляет `length_option_id` в 4 существующих строках `configuration_price` для добора «ТС» — так же, как выбор высоты никогда не влиял на цену короба «НЕО»/«Компланар» (см. Non-Goals в `link-frame-neo-height-to-leaf-height`). Это не затрагивает добор «КОМПЛАНАР» (`FET-008`–`FET-013`) и другие компоненты.
- Frontend: список доступных длин добора «ТС» фильтруется по высоте полотна (аналог `frameHeightRangeOptions`), выбор длины сбрасывается при смене высоты полотна; добор «ТС» дополнительно исключается из списка доступных типов добора на шаге каскадного выбора, если высота полотна уже выбрана и не покрывается ни одним его диапазоном длины (аналог исключения короба «НЕО» из каскада).
- Backend: длина становится обязательной для добора «ТС» — если `lengthOptionId` не передан, эндпоинт расчёта стоимости отвечает 400, а не тихо пропускает проверку диапазона (закрывает ту же дыру, что и обязательность высоты для короба «НЕО»).

### Modified Capabilities

- `door-configuration-api`: добавляется требование о совместимости диапазона длины добора «ТС» с высотой полотна и требование об обязательности длины для добора «ТС» (по аналогии с существующими требованиями для короба «НЕО»/«Компланар»).
- `door-configurator-ui`: добавляется требование об условной фильтрации длины добора «ТС» по высоте полотна и исключении добора «ТС» из каскада при несовместимой высоте полотна (по аналогии с существующим требованием для короба «НЕО»/«Компланар»).

`door-configuration-catalog` не меняется на уровне спецификации: требования «Атрибуты liner_dimension_option» (диапазоны min_value/max_value, повтор value с непересекающимися диапазонами для одного владельца) и «Структура configuration_price» (необязательность ссылки на длину) уже сформулированы универсально для любого владельца — новые данные добора «ТС» и обнуление length_option_id укладываются в уже описанное поведение без изменения текста требований.

## Impact

- **Backend**: `DoorConfigurationPricingService` — обобщение `validateHeightWithinLeafRange` (переименование параметра/добавление ожидаемого кода оси), новая ветка проверки для `FrameExtensionsType` с кодом из `FET-004`–`FET-007` (обязательность и диапазон длины) в общей (не-`FrameType`) ветке `addComponentIfPresent`.
- **БД**: обновление существующих строк `liner_dimension_option` (диапазон для value=2170) и `configuration_price` (`length_option_id = NULL`) для добора «ТС»; новые строки `liner_dimension_option` для value=2400 (×2) и value=2700; изменение уникального индекса `uk_liner_dimension_option_frame_extensions_type`; для desktop-профиля (H2) — отдельная параллельная миграция по аналогии с `changes-desktop-overrides/0062-frame-type-height-range-index.yaml`.
- **Frontend**: `frontend/src/App.tsx` (фильтрация длины добора «ТС» по высоте полотна, сброс выбора при смене высоты полотна, исключение добора «ТС» из каскада выбора при несовместимой высоте полотна — расширение существующего двухпроходного `buildCascadeSteps`).
- **Тесты**: `DoorConfigurationPricingServiceTest` — новые кейсы по аналогии с кейсами короба «НЕО»; `TestEntities` — новый оверлоад `frameExtensionsType(id, code)` по аналогии с `frameType(id, code)`.
- Добор «КОМПЛАНАР» (`FET-008`–`FET-013`) и другие компоненты (leaf, frame, edge, doorCasing) не меняют поведение.
