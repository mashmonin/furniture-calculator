## Context

`dimension_surcharge_rule` для высоты полотна сейчас содержит 12 точек с шагом 50мм: 1900, 1950, 2050, 2150, 2200, 2300, 2400, 2500, 2600, 2700 (общие) и 2800, 2900 (по каждой модели отдельно, кроме «СИБИРЬ 03» — см. change `add-leaf-height-2800-2900-except-sibir-03`). Между многими из них есть «дыры» сетки (2250, 2350, 2450, 2550, 2650, 2750, 2850, 2950 и выше) — сегодня такая высота отклоняется 400, потому что `resolveAxisSurchargeMultiplier` (см. `DoorConfigurationPricingService`) — чисто lookup-резолвер: либо точное совпадение с каталожной опцией/строкой `dimension_surcharge_rule`, либо отказ.

Фабрика хочет закрыть эти дыры не построчным перечислением (которое здесь принципиально невозможно — каскад открыт вверх без потолка), а формулой: наценка = наценка ближайшего меньшего значения сетки + 20 п.п.

## Goals / Non-Goals

**Goals:**
- Разрешить произвольную высоту полотна на сетке 50мм от 1900мм, для которой нет точной строки, с наценкой, вычисляемой каскадно от ближайшего меньшего определённого значения той же сетки.
- Корректно остановить каскад там, где конкретная модель полотна физически не может иметь такую высоту (сейчас — «СИБИРЬ 03» на 2800/2900мм), не открывая её случайно через промежуточное меньшее значение.
- Не потребовать верхнего предела — правило должно работать для любой высоты на сетке, сколь угодно большой.

**Non-Goals:**
- Не затрагиваем ось длины — каскад в этом change только для высоты (`HEIGHT_TYPE_CODE`), как и было прямо указано в запросе.
- Не вводим сетку с шагом 10мм — отдельное будущее change.
- Не перезаписываем существующие точки (1900...2900) — они остаются точными строками, каскад их не касается (используется только как якоря для промежуточных значений).

## Decisions

### Каскад — вычисляется в резолвере, а не хранится строками
В отличие от диапазонного правила `pogonazh_surcharge_rule` (два предвычисленных диапазона на весь change), здесь путь от 1900мм вверх без потолка — заранее перечислить все возможные значения невозможно. `resolveAxisSurchargeMultiplier` для оси высоты, не найдя точной строки, спускается по сетке с шагом 50мм (сначала −50, потом −100 и т.д.), на каждом шаге ищет точную строку (leaf-специфичную, затем общую — та же логика, что уже есть для точного совпадения); как только находит — берёт её `surcharge_percent` и добавляет 20 п.п. за каждый пройденный шаг. Итеративный (не рекурсивный вызов метода) цикл с защитным потолком в 200 шагов (соответствует высоте почти на 10 метров больше 1900мм — заведомо за пределами любого реалистичного запроса) — чтобы аномально большое клиентское значение не создавало неограниченный цикл запросов к репозиторию.

### Блокировка — новый вид строки dimension_surcharge_rule, а не побочный эффект отсутствия строки
До этого change отсутствие строки для (leaf_type, value) означало «недопустимо» безусловно. Теперь отсутствие строки означает «попробовать каскад» — поэтому для «СИБИРЬ 03» на 2800/2900мм понадобилась явная блокирующая строка, иначе каскад откроет их через 2750мм (2700мм @ 50% + 20 + 20 = 90%, что неверно — фабрика прямо сказала, что 2800/2900 для этой модели недоступны, а 2750 — доступно и наследует от 2700). Строка получает `unavailable = true` (новая nullable-колонка, по умолчанию false) и `surcharge_percent = NULL`; CHECK-констрейнт гарантирует ровно одно из двух — обычная строка (surcharge_percent задан) либо блокирующая (unavailable = true, привязана к конкретному leaf_type — глобальная блокировка бессмысленна).

Резолвер на каждом шаге каскада, найдя строку, проверяет: если это блокирующая строка — сразу отклоняет запрос (400), не продолжая спуск дальше (не откатывается к 2700мм). Тот же самый прямой lookup (без каскада) уже отклоняет 2800/2900 для «СИБИРЬ 03» напрямую, если их запросили точно, а не как часть каскада для более высокого значения — единая логика на оба случая.

### Блокирующие строки не попадают в GET /api/pricing-surcharges
`PricingSurchargesService` фильтрует их при построении списка `dimensionSurchargeRules` — это внутренний резолверский концепт («это значение для этой модели недопустимо»), а не «правило наценки», которое имеет смысл показывать клиенту. Заодно это устраняет необходимость передавать признак `unavailable`/nullable `surchargePercent` во фронтенд-тип и обрабатывать его там.

### Фронтенд дублирует ровно ту же каскадную логику, без блокирующих строк
`computeSurchargeBreakdown()` получает такую же функцию спуска по сетке 50мм для оси высоты. Поскольку блок «Надбавки к цене за нестандарт» рендерится только после УСПЕШНОГО расчёта (`leafPricingResult` уже получен), а любая высота, которую backend отклонил бы (в том числе упирающаяся в блокировку), просто не доходит до этой точки — фронтенду не нужно знать о блокирующих строках вообще: он гарантированно вызывается только для высот, которые backend уже принял. Это тот же принцип дублирования, что уже применён для диапазонов `pogonazh_surcharge_rule` и leaf_type-специфичных правил `dimension_surcharge_rule` — расхождение между двумя копиями логики возможно только при будущей правке одной стороны без другой (принятый в проекте риск, не новый).

## Risks / Trade-offs

- **Дублирование каскадного алгоритма между Java и TypeScript** — тот же уже принятый риск, что и для диапазонов/leaf-scoping; каскад чуть сложнее (цикл, а не одно сравнение), поэтому риск рассинхронизации выше, чем у предыдущих дублирований. Митигация — не техническая (нет общего рантайма), а организационная: оба места явно ссылаются друг на друга в комментариях.
- **Защитный потолок в 200 шагов** — техническое ограничение, не бизнес-требование; если фабрика когда-нибудь захочет полотно на 12+ метров, потолок нужно будет поднять. Указано в коде явным комментарием, не константой без объяснения.
- **Блокировка обрывает весь каскад выше себя, а не только точное значение** — для «СИБИРЬ 03» это означает, что и 2850, 2950, 3000мм и выше тоже станут недоступны (каскад для 2850 упрётся в блокировку на 2800), хотя явно перечислены как недоступные только 2800/2900. Это соответствует физическому смыслу (у модели есть потолок высоты), и явно проговорено с пользователем для 2750/2800/2900; более высокие значения им не обсуждались, но вывод — единственный логически согласованный при выбранной семантике блокировки.
