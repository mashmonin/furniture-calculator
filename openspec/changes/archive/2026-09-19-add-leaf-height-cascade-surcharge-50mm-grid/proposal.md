## Why

В `dimension_surcharge_rule` для оси высоты полотна («ВЫСОТА») сейчас есть «дыры» в сетке 50мм между уже заведёнными точками (1900, 1950, 2050, 2150, 2200, 2300, 2400, 2500, 2600, 2700, 2800, 2900 мм) — например, 2250, 2350, 2450, 2550, 2650, 2750, 2850, 2950 мм и выше вообще не заведены, поэтому такая высота полотна сегодня просто отклоняется (400 «фабрика не производит полотно с размером...»). Фабрика хочет разрешить эти промежуточные значения без необходимости заводить каждое точкой вручную: наценка = наценка ближайшего меньшего уже определённого значения + 20 процентных пунктов, и так каскадно вверх без верхнего предела.

## What Changes

- **Новая категория правила — вычисляемый каскад, а не точка/диапазон**. В отличие от уже существующих способов задать `dimension_surcharge_rule`/`pogonazh_surcharge_rule` (точное значение, диапазон), это правило не хранится построчно — оно вычисляется резолвером на лету: для высоты полотна, отсутствующей в справочнике, но лежащей на сетке 50мм от 1900мм (`value = 1900 + 50×n`, n ≥ 0), наценка равна наценке ближайшего МЕНЬШЕГО уже определённого значения этой же модели полотна (с учётом её собственных leaf_type-специфичных правил, если есть, иначе общих) + 20 процентных пунктов; если этот меньший сосед тоже не заведён, а тоже является таким промежуточным значением, наценка берётся у него (рекурсивно/каскадно), пока не найдётся заведённая точка. Значения ниже 1900 мм по-прежнему отклоняются (нижней границы каскада нет — 1900мм уже наименьшая заведённая точка). Значения не на сетке 50мм (например, 2013 мм) по-прежнему отклоняются — эта сетка отдельная от возможного будущего шага 10мм (не входит в это изменение).
- **Новый вид строки `dimension_surcharge_rule` — явная блокировка**, отдельно от «нет строки» (что теперь означает «каскадное промежуточное значение», а не автоматический отказ). Модель полотна «СИБИРЬ 03» (`leaf_type` LT-041) физически не может иметь высоту 2800/2900 мм (см. change `add-leaf-height-2800-2900-except-sibir-03`) — раньше это выражалось просто отсутствием строки для нее, но при введении каскада отсутствие строки на 2800мм привело бы к тому, что она вычислилась бы через промежуточное 2750мм (2700мм + 20% + 20% = 90%), что неверно. Поэтому для (leaf_type=«СИБИРЬ 03», value=2800) и (leaf_type=«СИБИРЬ 03», value=2900) заводятся явные блокирующие строки (`unavailable = true`, `surcharge_percent = NULL`) — резолвер, дойдя до такой строки при каскадном спуске, ДОЛЖЕН (SHALL) немедленно отклонить запрос, не продолжая спуск дальше. Промежуточное значение 2750мм для «СИБИРЬ 03» блокировкой не затронуто — оно по-прежнему наследует наценку от 2700мм (50% + 20% = 70%), так как в цепочке спуска для него встречается только заведённая точка 2700мм, а не блокировка.
- **Backend**: `dimension_surcharge_rule` дополняется nullable-колонкой `unavailable` (BOOLEAN, по умолчанию false) и CHECK-констрейнтом «ровно одно из: задан surcharge_percent (обычное правило), либо unavailable = true (блокировка, только для leaf_type-специфичных строк)». `DoorConfigurationPricingService.resolveAxisSurchargeMultiplier` для оси высоты, если точного правила (каталожного размера или точной строки dimension_surcharge_rule) не нашлось, а значение лежит на сетке 50мм и ≥ 1900мм — пробует каскадный спуск с шагом 50мм; при встрече блокирующей строки — отклоняет запрос как недопустимое значение (тот же 400, что и сейчас для неизвестных значений).
- **Frontend**: разбивка наценки за нестандартную высоту (`computeSurchargeBreakdown` в App.tsx) дублирует ту же каскадную логику (по аналогии с уже продублированным матчингом диапазонов `pogonazh_surcharge_rule` и leaf_type-специфичных правил `dimension_surcharge_rule`), чтобы бейдж «За нестандартную высоту» показывал верный процент и для промежуточных (не заведённых построчно) значений.

## Capabilities

### Modified Capabilities
- `dimension-surcharge-rules`: добавляется требование о каскадной наценке для промежуточных значений сетки 50мм (высота полотна) и требование о блокирующих строках, отдельных от отсутствия строки.
- `door-configuration-api`: резолв наценки за нестандартную высоту полотна дополняется каскадным вычислением и обработкой блокирующих строк.
- `door-configurator-ui`: разбивка наценки за нестандартную высоту учитывает каскадные значения.

## Impact

- Backend: новый Liquibase changelog (`ALTER TABLE dimension_surcharge_rule` — колонка `unavailable`, CHECK-констрейнт; `INSERT` двух блокирующих строк для «СИБИРЬ 03» на 2800/2900мм); новый метод/логика каскадного резолва в `DoorConfigurationPricingService` (ограничен осью высоты — на длину не распространяется, в запросе явно не упоминалась); поле `unavailable` в `DimensionSurchargeRule` (используется только внутри резолвера, наружу в DTO не отдаётся — блокирующие строки не являются «правилами наценки» для отображения).
- Frontend: `computeSurchargeBreakdown()` в `App.tsx` дублирует каскадный алгоритм для оси высоты.
- Данные: 2 новые блокирующие строки (СИБИРЬ 03 × {2800, 2900}); ни одна из уже существующих строк не меняется.
- Риск: каскадный спуск в худшем случае выполняет O((H−1900)/50) шагов для запрошенной высоты H — для реалистичных значений это единицы-десятки шагов; в design.md рассматривается защитный потолок на случай абсурдно большого H.
