## Context

См. proposal.md — «Why». Текущее состояние фронтенда (`frontend/src/App.tsx`), установленное исследованием перед написанием этого change:

- Один debounce-эффект (строки ~761-843) на каждое изменение отправляет ровно один запрос: `calculatePrice(selectedConfiguration.id, request)`, если каскад уже определил единственную согласованную `door_configuration`, иначе `calculateLeafPrice(leafTypeId, request)`. Фурнитура всегда едет внутри этого же запроса (`request.hardware`).
- Три раздела аккордеона (`leafPanelContent`, `frameGroupPanelContent`, `hardwarePanelContent`, ~1370-1497) уже разбиты по тем же границам, что и новые backend-эндпоинты: `LEAF_PANEL_STEP_KEYS = ['leaf', 'edge']`, `FRAME_GROUP_PANEL_STEP_KEYS = ['frame', 'doorCasing', 'frameExtensions']` (строки 58-59).
- `leafHeightValue` (строки 652-654) уже вычисляется локально из `leafComponent` (resolvedComponent шага `leaf`) и `selection.leaf` — независимо от какого-либо запроса к backend; именно это значение нужно будет передавать явно новому `/api/frame-types/{id}/price`.
- `frameComponent`/`doorCasingComponent`/`frameExtensionsComponent` (строки 677, 713, 734) уже вычисляются через `cascadeSteps.find(...).resolvedComponent` — из них уже сегодня доступны `.type.id`, просто не извлекаются в именованные переменные и не используются нигде, кроме `.type.code`.
- Единственный `pricingResult`/`pricingLoading`/`pricingError` (строки 525-527) и единственный `requestSeqRef` (531) — весь sticky-панель рендерится из этой одной тройки состояния (~1559-1656).
- Backend-контракты трёх этапов уже существуют и не меняются этим change (см. change add-staged-pricing-endpoints): `POST /api/leaf-types/{id}/price` (расширен `edgeTypeId`), `POST /api/frame-types/{id}/price` (новый), `POST /api/hardware/price` (новый).

## Goals / Non-Goals

**Goals:**
- Подключить все три новых/расширенных эндпоинта, сохранив внешне идентичный пользовательский опыт (единая sticky-панель, единый итог, единая разбивка) — см. решения пользователя при планировании: «один общий итог как сейчас» + «3 независимых debounce-эффекта».
- Убрать больше не используемый вызов комбинированного `POST /api/door-configurations/{id}/price` и связанную с ним ветвление-логику.
- Дать каждому этапу собственный, независимый триггер пересчёта — правка фурнитуры не должна вызывать сетевой запрос к этапам «Полотно»/«Короб и обрамление», и наоборот.

**Non-Goals:**
- Не менять backend — все три эндпоинта уже реализованы и не меняются.
- Не менять визуальную структуру sticky-панели, аккордеона или каскада — только механизм получения данных для sticky-панели.
- Не вводить частичное/прогрессивное отображение результата по мере готовности каждого этапа — по выбору пользователя, итог остаётся «всё или ничего» (ожидание всех применимых этапов), как и сегодня.
- Не реализовывать сам change — этот документ описывает подход, реализация — в отдельном шаге `/opsx:apply`.

## Decisions

### Три независимых debounce-эффекта, один объединённый результат для отображения
Каждый из трёх этапов получает собственную тройку состояния (`leafPricing{Result,Loading,Error}`, `frameGroupPricing{...}`, `hardwarePricing{...}`) и собственный `useEffect` с собственным debounce и собственным `requestSeqRef` (race-guard) — по образцу существующего единственного эффекта, просто утроенного и с независимыми зависимостями. Для отображения sticky-панель вычисляет производное объединённое состояние:
- «применим» этап — тот, для которого выполнено условие запуска (leaf: `leafTypeId !== undefined`; frame group: `frameTypeId !== undefined`; hardware: `leafTypeId !== undefined && есть хотя бы одна завершённая позиция`);
- если у любого применимого этапа есть ошибка — показывается ошибка (как сегодня, для единственного запроса);
- иначе если любой применимый этап ещё не завершён (`loading` или ещё не начат) — показывается состояние ожидания (как сегодня);
- иначе — объединённый результат: сумма трёх `totalRetailPrice`/`totalDealerPrice`, `components` — конкатенация `leafResult.components` и `frameGroupResult.components`, отсортированная по `COMPONENT_ORDER` (чтобы сохранить привычный порядок полотно→короб→кромка→наличник→добор, поскольку в отдельных ответах порядок внутри этапа: `[leaf, edge]` и `[frame, doorCasing, frameExtensions]` — при простой конкатенации кромка оказалась бы перед коробом), `hardware` — из `hardwareResult.hardware`.

Альтернатива — прогрессивное отображение (показывать этап сразу по готовности, не дожидаясь остальных) — отклонена пользователем при планировании в пользу «один общий итог как сейчас»: минимизирует визуальные отличия от текущего поведения и не требует переосмысления структуры sticky-панели.

### Условия запуска каждого этапа
- «Полотно»: как и сегодня, `leafTypeId !== undefined` (без ожидания кромки — она добавляется в запрос по готовности, не блокируя сам факт запроса).
- «Короб и обрамление»: `frameTypeId !== undefined` (независимо от готовности «Полотно» — этому этапу нужен только явно переданный `leafHeightValue`, не сам факт резолва полотна как сетевой сущности).
- «Фурнитура»: `leafTypeId !== undefined` И есть хотя бы одна завершённая позиция — сохраняет действующее правило «фурнитура не считается до определения типа полотна» (см. существующий сценарий «Расчёт фурнитуры без определённого типа полотна не запускается»), несмотря на то, что технически новый `/api/hardware/price` от leaf вообще не зависит; это сознательное сохранение прежнего пользовательского поведения, а не техническое ограничение backend.

### `frameTypeId`/`doorCasingTypeId`/`frameExtensionsTypeId` — именованные производные значения
Сегодня из `resolvedComponent` шагов извлекается только `.type.code` (для проверок вхождения в `*_TYPE_CODES`). Этот change добавляет явные `frameComponent?.type.id`, `doorCasingComponent?.type.id`, `frameExtensionsComponent?.type.id` как именованные значения (аналогично уже существующему `leafTypeId` на строке 665) — переиспользуются и для существующей логики, и для тела нового запроса.

### `calculatePrice` и ветвление по `selectedConfiguration` удаляются
`selectedConfiguration` остаётся (он по-прежнему нужен для сужения каталога/каскада — это не ценовая логика), но перестаёт использоваться для выбора «какой запрос расчёта отправить». Клиентская функция `calculatePrice` (`frontend/src/api/doorConfigurations.ts`) удаляется как более не вызываемый код — backend-эндпоинт `/api/door-configurations/{id}/price`, который она вызывала, не трогается (может использоваться другими клиентами в будущем).

### Новые типы и клиентские функции
`frontend/src/api/types.ts`: `edgeTypeId?: number` — новое поле верхнего уровня `PricingRequestDto` (не внутри `ComponentSelectionDto`, по образцу backend, где `edgeTypeId` — отдельное поле `PricingRequestDto`, в отличие от `mirrorFinishTypeId`/`glazingTypeId`, вложенных в `ComponentSelectionDto` полотна); `FrameGroupPricingRequestDto`/`FrameGroupPricingResponseDto`; `HardwarePricingRequestDto`/`HardwarePricingResponseDto` — зеркально backend-DTO.
`frontend/src/api/doorConfigurations.ts`: `calculateFrameGroupPrice(frameTypeId, request)` → `POST /api/frame-types/${frameTypeId}/price`; `calculateHardwarePrice(request)` → `POST /api/hardware/price`.

## Risks / Trade-offs

- **[Риск]** Утроение debounce-эффекта увеличивает количество сетевых запросов при одновременном изменении входов нескольких этапов (например, сброс каскада при смене коллекции влияет и на «Полотно», и на «Короб и обрамление» одновременно) — раньше это был один запрос, теперь до трёх параллельных. → Приемлемо: каждый запрос лёгкий (тот же объём данных, что раньше передавался одним запросом, просто разделённый), а полезный эффект (фурнитура не блокирует полотно/короб) перевешивает.
- **[Риск]** Логика объединения результатов (сортировка `components` по `COMPONENT_ORDER`, суммирование трёх итогов, комбинирование ошибок/loading трёх источников) — новая, ранее не существовавшая на фронтенде область для ошибок. → Специфицирована явно в specs/door-configurator-ui/spec.md («Объединение результатов трёх этапов расчёта») с конкретными сценариями; реализация переиспользует уже существующий `COMPONENT_ORDER`.
- **[Риск]** Удаление `calculatePrice` — если какой-то другой код (вне App.tsx) на неё ссылается, потребуется дополнительная правка. → Проверяется на этапе apply простым поиском по репозиторию перед удалением.

## Migration Plan

1. `frontend/src/api/types.ts` — новые DTO, `edgeTypeId`.
2. `frontend/src/api/doorConfigurations.ts` — новые клиентские функции, удаление `calculatePrice`.
3. `frontend/src/App.tsx` — именованные `frameTypeId`/`doorCasingTypeId`/`frameExtensionsTypeId`; три независимых debounce-эффекта с тремя тройками состояния; функция объединения результатов для sticky-панели; обновление зависимых мест рендера (`pricingResult` → производный объединённый результат).
4. `npx tsc -b` и `npm run lint` — без ошибок.
5. Ручная проверка в браузере (см. tasks.md) — поскольку это чисто фронтенд-change без изменений backend, полноценная проверка требует поднятого backend.
6. Откат — обычный git-ревёрт; backend не менялся, откат безопасен.
