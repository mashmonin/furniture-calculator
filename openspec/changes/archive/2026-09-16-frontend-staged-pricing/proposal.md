## Why

Backend уже умеет считать стоимость тремя независимыми этапными эндпоинтами, ровно соответствующими трём разделам аккордеона на фронтенде («Полотно» с кромкой, «Короб и обрамление», «Фурнитура» — см. change add-staged-pricing-endpoints), но фронтенд их ещё не использует: он по-прежнему вызывает либо старый комбинированный `POST /api/door-configurations/{id}/price`, либо старую версию `POST /api/leaf-types/{id}/price` без кромки. Нужно подключить фронтенд к новым эндпоинтам, сохранив текущий пользовательский опыт.

## What Changes

- Три раздела аккордеона получают по независимому debounce-запросу расчёта стоимости вместо одного общего:
  - «Полотно» (+ кромка) — `POST /api/leaf-types/{id}/price`, расширенный полем `edgeTypeId` и опциями кромки; запускается, как только определён тип полотна (кромка добавляется в запрос, когда определена, но не блокирует расчёт полотна).
  - «Короб и обрамление» — новый `POST /api/frame-types/{id}/price`; запускается, как только определён тип короба (наличник/добор добавляются в запрос по мере определения, каждый — по своему id типа); высота полотна передаётся явно значением, уже известным фронтенду.
  - «Фурнитура» — новый `POST /api/hardware/price`; запускается, как только определён тип полотна и есть хотя бы одна завершённая позиция фурнитуры.
- Sticky-панель результата внешне не меняется: итоговая розничная/дилерская цена — сумма итогов трёх этапов (клиентское сложение), разбивка по компонентам — объединённый список из ответов «Полотно» и «Короб и обрамление» (в привычном порядке: полотно, короб, кромка, наличник, добор), разбивка по фурнитуре — из ответа «Фурнитура». Как и сейчас: результат целиком скрывается, пока определён не весь набор применимых на данный момент этапов; ошибка любого применимого этапа заменяет собой весь результат (без частичного отображения).
- Старый комбинированный `POST /api/door-configurations/{id}/price` фронтендом больше не вызывается; клиентская функция `calculatePrice` и связанная с ней ветка выбора запроса по `selectedConfiguration` удаляются как неиспользуемый код. Backend-эндпоинт не трогается (используется другими потенциальными клиентами/сохраняется для обратной совместимости — вне скоупа этого change).
- Добавляются фронтенд-типы и клиентские функции для двух новых эндпоинтов (`FrameGroupPricingRequestDto`/`ResponseDto`, `HardwarePricingRequestDto`/`ResponseDto`, `calculateFrameGroupPrice`, `calculateHardwarePrice`) и поле `edgeTypeId` в существующий `PricingRequestDto`.
- Backend не меняется.

## Capabilities

### New Capabilities

_(нет)_

### Modified Capabilities

- `door-configurator-ui`: автоматический расчёт стоимости переходит с одного комбинированного запроса на три независимых этапных запроса (полотно+кромка, короб+обрамление, фурнитура), каждый со своим условием запуска; способ объединения трёх результатов в единую sticky-панель описывается явно; прежняя модель «расчёт отдельного полотна до определения door_configuration, затем переключение на расчёт по door_configuration» упраздняется — вместо неё три этапа всегда независимы друг от друга.

## Impact

- **Frontend**: `frontend/src/App.tsx` (дебаунс-эффект разделяется на три; вычисление `frameTypeId`/`doorCasingTypeId`/`frameExtensionsTypeId` как именованных значений; объединение результатов для sticky-панели), `frontend/src/api/types.ts` (новые DTO, `edgeTypeId`), `frontend/src/api/doorConfigurations.ts` (новые клиентские функции, удаление `calculatePrice`).
- **Backend**: не затрагивается.
- **Удаляется**: использование `POST /api/door-configurations/{id}/price` фронтендом (сам эндпоинт остаётся в backend).
