## Context

Сборка `.dmg` идёт через существующий Gradle-таск `desktopAppImage` (`backend/build.gradle`) — он сам вызывает сборку фронтенда, jlink-рантайм и jpackage, и не может собрать чужую архитектуру (см. proposal.md, Why). Результат кладётся в `backend/build/desktop/<arch>/dmg/Я-Конфигуратор-<version>-<arch>.dmg`, где `<arch>` — `aarch64` или `x86_64` (архитектура определяется самим Gradle-скриптом по `os.arch` JDK, на которой он запущен).

Репозиторий сейчас — приватный на GitHub (см. предыдущий change в этой сессии), без ранее настроенного CI. Встроенный `GITHUB_TOKEN` у GitHub Actions по умолчанию имеет права на создание Releases в собственном репозитории — отдельный PAT не нужен.

## Goals / Non-Goals

**Goals:**
- Один ручной запуск workflow добавляет один GitHub Release с двумя `.dmg` (arm64 + x86_64) под явно указанную версию.
- Использовать существующий Gradle-таск как есть — CI не должен становиться вторым местом, где живёт логика сборки.

**Non-Goals:**
- Windows/Linux-сборка — отдельный change, когда понадобится (см. proposal.md).
- Автоматическое версионирование (semver bump) в CI — версия остаётся ручным вводом, как и в локальном скилле `macos-arm64-release`; вопрос, должны ли CI и скилл в будущем использовать общую логику вычисления версии, не входит в этот change.
- Обновление файла `VERSION` в репозитории — CI ничего не коммитит.
- Настройка `app.update-check.url` (`UpdateCheckService`, см. `desktop-app-packaging`) на реальный манифест, указывающий на GitHub Releases — сама возможность публикации становится доступна этим change, но подключение уведомлений о новой версии к ней — отдельная, самостоятельная задача.

## Decisions

**Три отдельных job вместо одного.** `check-version` (дешёвый `ubuntu-latest`) → `build` (matrix: `macos-14` для arm64, `macos-15-intel` для x86_64) → `publish` (`ubuntu-latest`, `needs: build`). Разделение даёт нужную гарантию «нет частичного релиза» бесплатно, без ручной логики: если один из двух прогонов matrix-job'а `build` падает, весь job `build` считается упавшим, и `publish` (который его `needs`) не запускается вообще — GitHub Actions делает это сам.

**`gh` CLI вместо стороннего action для проверки версии и публикации релиза.** Альтернатива — готовые community-actions (`softprops/action-gh-release` и т.п.). Отклонено: `gh` уже предустановлен на всех GitHub-hosted раннерах и уже аутентифицирован через `GITHUB_TOKEN` — не нужно добавлять внешнюю зависимость (сторонний action, которому нужно доверять и обновлять) там, где всё нужное уже есть из коробки. `check-version` — `gh release view "v${VERSION}"`, ненулевой exit code (релиза нет) — ожидаемый успешный путь, нулевой — ошибка «уже существует». `publish` — `gh release create "v${VERSION}" <файлы> --title "v${VERSION}"`.

**Передача файлов между job через `actions/upload-artifact`/`download-artifact`.** `build` выполняется на двух разных macOS-раннерах — файлы с диска одного раннера недоступны другому job напрямую. Каждая нога matrix заливает свой `.dmg` под уникальным именем артефакта (`dmg-aarch64`/`dmg-x86_64`, по `matrix.arch`), `publish` скачивает оба перед вызовом `gh release create`.

**Раннеры `macos-14` (arm64) и `macos-15-intel` (x86_64).** Это стандартные GitHub-hosted образы с нужной архитектурой «из коробки» (см. proposal.md, Why) — не нужны self-hosted раннеры ради этого. Изначально для x86_64 был выбран `macos-13` по общему правилу «номер версии = архитектура», но он оказался выведен из эксплуатации 4 декабря 2025 — GitHub в этом случае не отклоняет job с таким label, а молча держит его в очереди без раннера навсегда, без явной ошибки (обнаружено при первом реальном прогоне). `macos-15-intel` — явный label для последнего доступного x86_64-образа (живёт до августа 2027, дальше GitHub Actions перестаёт поддерживать x86_64 на macOS вовсе) — более надёжный выбор, чем полагаться на то, что номер версии совпадёт с архитектурой: этот label не зависит от будущих сдвигов линейки hosted-раннеров так, как зависел `macos-13`.

**`workflow_dispatch` с обязательным текстовым input `version`.** Валидация формата (semver) — best-effort шагом в начале `check-version` (простая проверка регуляркой), не полноценный semver-парсер — ошибка в формате версии должна быть заметна сразу, до траты минут раннера на сборку, но не обязана покрывать все edge-case'ы semver.

## Risks / Trade-offs

[GitHub-hosted macOS-раннеры дороже Linux-раннеров по биллингу минут (multiplier у приватных репозиториев)] → приемлемо: триггер только ручной (`workflow_dispatch`), не на каждый push/PR — минуты тратятся только при осознанном релизе, не на каждый коммит.

[Ручной ввод версии — опечатка в самой версии (не дублирование, а просто неверное число) ничем не ловится] → тот же риск уже существует в локальном скилле `macos-arm64-release` (там тоже ручной ввод через AskUserQuestion) — не хуже статус-кво, отдельно не решается в этом change.

[Между `check-version` и фактической публикацией в `publish` проходит время сборки (десятки минут) — теоретическая гонка, если кто-то опубликует релиз с тем же тегом вручную в этом окне] → маловероятный сценарий при однопользовательском/малокомандном release-процессе; `gh release create` в этом случае просто упадёт с понятной ошибкой (тег уже занят) — не тихая порча данных, а видимый провал `publish`, который можно перезапустить с новой версией.
