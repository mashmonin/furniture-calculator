## Context

См. proposal.md — Why/What Changes. Ключевые факты из текущей кодовой базы:

- `LeafType` — плоская JPA-сущность (`id`, `name`, `code`), реализует общий маркерный интерфейс `CatalogType`; такой же паттерн у `FrameType`, `EdgeType`, `DoorCasingType`, `FrameExtensionsType`, `ColourType`, `LinerDimensionType`. Ни один справочник сейчас не ссылается FK на другой справочник — связь `leaf_type → collection` будет первым таким случаем в схеме.
- Liquibase-таблицы справочников создаются в два шага (`createTable` только с `id`, затем `addColumn` с `name`/`code`), но это исторический паттерн для таблиц, изначально пустых. `leaf_type` уже содержит 45 строк, поэтому для `collection_id` потребуется отдельная последовательность: добавить nullable-столбец → задать значения существующим строкам → перевести в `NOT NULL`.
- Все существующие 45 строк `leaf_type` сгруппированы по `code`-диапазонам на 9 коллекций (см. `0004-item-configuration-reference-data.yaml`): LT-001…007 — Вертикаль, LT-008…013 — Атмосфера, LT-014…019 — Элегант, LT-020…025 — Гармония, LT-026…033 — Свобода, LT-034…037 — Геометрия, LT-038 — Сияние, LT-039…044 — Сибирь, LT-045 — Фантом.
- Каталог отдаётся одним эндпоинтом `GET /api/door-configurations`; данные `leaf_type` попадают в ответ через `ComponentCatalogDto`/`ReferenceDto` (`DoorConfigurationCatalogService`). Отдельного эндпоинта под справочники нет.
- Фронтенд строит каскад в `App.tsx` (`buildCascadeSteps`, `CASCADE_ORDER`), рендерит шаги через `OptionGroup` (`Radio.Group`/`Radio.Button` из antd) на основе плоского списка `ReferenceDto` из загруженного каталога.

## Goals / Non-Goals

**Goals:**
- Нормализовать группировку моделей полотна по коллекции в схеме БД, без изменения существующей группировки (9 коллекций, те же 45 моделей).
- Сделать коллекцию обязательным атрибутом каждого `leaf_type` (нет полотна без коллекции).
- Добавить шаг выбора коллекции в конфигуратор строго перед шагом выбора модели полотна, не меняя поведение остальных шагов каскада.

**Non-Goals:**
- Не переименовывать и не менять текстовые `name` существующих `leaf_type` (уже содержат название коллекции текстом — оставляем как есть, дублирование name с collection.name допустимо).
- Не вводим отдельный REST-эндпоинт под справочник коллекций — коллекция отдаётся как часть существующего ответа каталога (вместе с leaf_type), фронтенд выводит список коллекций из уже загруженных данных.
- Не меняем структуру `door_configuration`, `configuration_price`, `liner_dimension_option`, `colour_option` — коллекция не становится самостоятельным "владельцем" этих таблиц, она атрибут только `leaf_type`.

## Decisions

### Имя JPA-сущности — `LeafCollection`, а не `Collection`
`java.util.Collection` — базовый интерфейс JDK; сущность с именем `Collection` в `domain`-пакете создаёт постоянную неоднозначность импортов и код-ревью риск. Имя таблицы в БД остаётся `collection` (соответствует остальным справочникам и proposal.md), но Java-класс называется `LeafCollection implements CatalogType`. Альтернатива — `DoorCollection`: отклонена, т.к. коллекция сейчас относится именно к полотну (`leaf_type`), а не ко всей двери.

### Двухшаговая миграция обязательного FK на непустую таблицу
Т.к. `leaf_type` уже содержит 45 строк, нельзя добавить `collection_id BIGINT NOT NULL` одним `addColumn`. Последовательность changeset'ов:
1. `createTable: collection` (id) + `addColumn` (name, code с unique-constraint) — по образцу существующих справочников.
2. `insert` 9 строк collection (по одной на каждую коллекцию из proposal.md).
3. `addColumn: leaf_type.collection_id` как nullable BIGINT с inline FK (`foreignKeyName`, `references: collection(id)`), без `NOT NULL` на этом шаге.
4. Серия `sql`/`update`-changeset'ов, проставляющих `collection_id` всем 45 строкам `leaf_type` по `code`-диапазону (по образцу `0018-atmosfera-leaf-prices.yaml`, где `UPDATE ... WHERE code IN (...)`), один changeset на коллекцию либо один общий с несколькими `UPDATE`.
5. `addNotNullConstraint` на `leaf_type.collection_id` — последним шагом, после того как все строки заполнены.

Это стандартный безопасный паттерн для добавления обязательной колонки в непустую таблицу и не требует ручных правок схемы мимо Liquibase.

### Защита от удаления связанной collection
В проекте уже есть требование "не удалять справочную строку, пока на неё ссылается запись" (item-configuration-schema, для item_type/leaf_type/mirror_type и др.) — вероятно, реализовано через `ON DELETE RESTRICT` (поведение по умолчанию для FK без явного `onDelete`). Для `leaf_type.collection_id` используем такой же default (без `onDelete: CASCADE`), это даёт нужное поведение "нельзя удалить collection, пока на неё ссылается leaf_type" без дополнительного кода.

### DTO: коллекция как вложенный `ReferenceDto` внутри leaf-компонента
`ReferenceDto` уже используется для любого `CatalogType` (id/code/name). Расширяем `ComponentCatalogDto` (или сам `ReferenceDto`, используемый для типа leaf) необязательным полем `collection: ReferenceDto`, заполняемым только для leaf-компонента (у остальных компонентов конфигурации коллекции нет). Отдельный DTO под коллекцию не создаём — переиспользуем `ReferenceDto.from(leafCollection)`.

### Фронтенд: коллекция как отдельный шаг перед `leaf`, не как элемент `CASCADE_ORDER`
Коллекция не является полем `door_configuration` (в отличие от leaf/frame/doorCasing/edge/frameExtensions, которые сужают набор `DoorConfigurationDto`-кандидатов). Поэтому шаг выбора коллекции реализуется как отдельный этап перед существующим каскадом: он не участвует в `handleCascadeStepChange`/`buildCascadeSteps` напрямую, а лишь предварительно фильтрует список моделей полотна, показываемых на первом шаге текущего каскада (`leaf`). Выбор/смена коллекции сбрасывает выбор `leaf` и всех последующих шагов — так же, как сегодня смена более раннего шага каскада сбрасывает более поздние.

## Risks / Trade-offs

- **[Риск] Ошибка в распределении 45 моделей по 9 коллекциям при backfill-миграции** (например, полотно попадёт не в свою коллекцию) → Смягчение: диапазоны `code` для каждой коллекции однозначно видны в исходном сид-changeset'е (`0004-item-configuration-reference-data.yaml`) и в имени (`name`), backfill-changeset должен фильтровать по `code IN (...)` точными списками, а не по префиксу `name` (текст `name` менее надёжен для матчинга, чем `code`).
- **[Trade-off] Дублирование "коллекции" в тексте `name` полотна и в новом справочнике `collection`** (например, `name = "ВЕРТИКАЛЬ 01"` при `collection.name = "Вертикаль"`) → Осознанно принято: переименование 45 существующих `name` не входит в scope этого изменения (см. Non-Goals); визуально на фронтенде это не мешает, т.к. второй шаг покажет только модели уже выбранной коллекции.

## Migration Plan

1. Применить новые Liquibase changeset'ы (создание `collection`, сид 9 строк, `addColumn` nullable FK, backfill, `NOT NULL`) через обычный процесс `./gradlew bootRun`/деплой — изменения полностью прямые (forward-only), без отдельного отката данных.
2. Откат при необходимости — новый changeset, отменяющий `NOT NULL` и/или удаляющий столбец/таблицу (по конвенции проекта — не редактировать уже применённые changeset'ы задним числом).
3. Backend и frontend разворачиваются вместе с миграцией: до появления `collection_id` у `leaf_type` и обновлённого DTO фронтенд с новым шагом выбора коллекции работать не может — деплой backend (миграция + API) должен предшествовать деплою обновлённого frontend либо выполняться одновременно.
