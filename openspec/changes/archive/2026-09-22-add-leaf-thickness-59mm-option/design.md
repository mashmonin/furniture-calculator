## Context

`liner_dimension_type` «ТОЛЩИНА» (`DT-003`) существует с самого начала каталога, но фактически используется только как справочная/валидируемая ось: у каждого leaf_type заведена ровно одна `liner_dimension_option` (value=44, is_standard=true), `configuration_price.thickness_option_id` во всех сид-данных равен NULL, а метод подбора цены (`matchesDimension`) матчит толщину как «подходит всегда», когда у строки цены эта ссылка не задана. Транспортный слой уже полностью готов: `ComponentSelectionDto.thicknessOptionId`, каталог отдаёт опции толщины в общем списке `dimensionOptions` компонента, а фронтенд уже показывает селектор «Толщина» для полотна (`App.tsx`, `THICKNESS_TYPE_CODE = 'DT-003'`) — выбор толщины 59 мм уже можно отправить в запросе расчёта, только сервер пока не резолвит по нему никакой наценки, и в каталоге такой опции пока нет ни для одной модели.

В отличие от длины и высоты, у толщины нет режима «произвольное значение» (`customLengthValueMm`/`customHeightValueMm`) — только выбор из каталожных опций по id. Это меняет то, как для неё резолвится наценка: не через ветку «произвольное значение размера» (см. door-configuration-api, «Разрешение произвольного значения размера полотна»), а напрямую по значению выбранной каталожной опции.

Наценки к цене leaf-компонента уже применяются как цепочка последовательных множителей с округлением после каждого шага (см. `applySequentialSurcharges`/аналог, текущий порядок: длина → высота → цвет → двусторонняя покраска → зеркало → остекление → реверс). Каждое добавление нового вида наценки в этом проекте добавляло собственный requirement «Место наценки за X в последовательности надбавок», переопределяющий полный порядок на момент своего появления, без переписывания предыдущих requirements — этот change продолжает ту же цепочку.

## Goals / Non-Goals

**Goals:**
- Завести толщину 59 мм как каталожную опцию для нужных leaf_type и наценку 20% за неё, не создавая новых таблиц и не меняя схему БД — переиспользовать существующую структуру `liner_dimension_option`/`dimension_surcharge_rule`.
- Встроить наценку за толщину в уже существующую последовательную цепочку наценок к цене leaf-компонента, на обоих путях расчёта (по `door_configuration` и по отдельному полотну), без изменения контракта запроса (поле `thicknessOptionId` уже существует).
- Отразить наценку за толщину в разбивке надбавок на фронтенде, переиспользуя уже загружаемый список `dimension_surcharge_rule` (эндпоинт `GET /api/pricing-surcharges` не меняется).

**Non-Goals:**
- Не вводится режим произвольного (custom) значения толщины — только выбор из каталожных опций, как сейчас.
- Не меняется структура `configuration_price`/подбор наиболее специфичной цены — толщина остаётся вне ценообразующих строк `configuration_price` (её `thickness_option_id` продолжает быть NULL везде), наценка идёт отдельным множителем, а не через отдельную цену для 59 мм.
- Не вводятся блокирующие (`unavailable = true`) строки `dimension_surcharge_rule` для остеклённых моделей — их исключение достигается тем, что для них просто не заводится сама каталожная опция 59 мм (см. «Решения» ниже).

## Decisions

### Общее (не per-leaf_type) правило dimension_surcharge_rule для толщины 59 мм
Рассматривались два варианта: (а) одна общая строка `dimension_surcharge_rule` (ТОЛЩИНА, 59, surcharge_percent=20, без leaf_type) — по аналогии с тем, как задаются глобальные правила по умолчанию; (б) отдельная строка на каждый из ~33 подходящих leaf_type — по аналогии с тем, как заведена наценка за высоту 2800/2900мм (привязанная к каждой модели отдельно, кроме «СИБИРЬ 03»).

Выбран вариант (а). Причина: наценка за высоту привязывается per-leaf_type, потому что высота принимает *произвольное* значение — клиент может отправить 2800мм для любой модели, включая ту, для которой это должно быть недопустимо (поэтому нужна была явная блокирующая строка для «СИБИРЬ 03»). У толщины нет произвольного ввода: клиент может выбрать значение 59мм только через id существующей `liner_dimension_option`, а такая опция физически создаётся (этим же change) только для тех leaf_type, для которых она должна быть доступна. Остеклённые модели этой опции просто не получают — им нечего выбирать, и общее правило для них никогда не резолвится. Одна строка проще 33 и не требует отдельной миграции на каждую модель.

Альтернатива (б) отклонена как избыточная: она копировала бы паттерн, оправданный только для оси с произвольным вводом.

### Наценка резолвится по значению выбранной опции толщины, а не по отдельному запросу
`ComponentSelectionDto.thicknessOptionId` уже валидируется (`validatedDimensionOption`) и участвует в подборе цены. Новый шаг читает `value` уже резолвленной `LinerDimensionOption` (44 или 59) и ищет применимую `dimension_surcharge_rule` для оси «ТОЛЩИНА» и этого значения (сперва специфичную для leaf_type, затем общую) — тем же методом, что уже используется для точных (не каскадных) правил длины/высоты, без нового параметра запроса и без веток «произвольное значение»/каскад (у толщины их нет).

Если правило не найдено (это будет типичный случай для 44мм, у которого правила нет вовсе) — наценка просто не применяется, это НЕ ошибка 400, в отличие от отсутствия правила для произвольного значения длины/высоты. Это отличие явно зафиксировано в specs (door-configuration-api, «Наценка за выбранную толщину полотна»), чтобы не спутать с логикой «недопустимая величина».

### Место в последовательности наценок: сразу после высоты, до цвета
Толщина — такая же «размерная» ось, как длина и высота (использует тот же механизм dimension_surcharge_rule), поэтому логично сгруппировать её со шагами длины/высоты, до более специфичных для полотна наценок (цвет, двусторонняя покраска, зеркало, остекление). Итоговый порядок: длина → высота → **толщина** → цвет → двусторонняя покраска → зеркало → остекление → реверс. Как и у всех предыдущих добавлений, округление происходит после каждого шага, поэтому порядок влияет на итоговую сумму в пограничных случаях — это зафиксировано отдельным requirement с конкретным сценарием (door-configuration-api, «Место наценки за толщину полотна в последовательности надбавок»), не переписывающим более ранние requirements о размещении цвета/зеркала/остекления/реверса.

### Границы каталога: «не остеклённое», а не строго «глухое»
См. proposal.md, раздел «Уточнение формулировки задачи» — среди перечисленных заказчиком коллекций у большинства не остеклённых моделей уже есть `mirror_finish_option`, поэтому их `panel_type = «с зеркалом»`, а не «глухое». Условие для заведения опции 59 мм — `panel_type ≠ «остеклённое»` (т.е. включает и «глухое», и «с зеркалом»), в пределах перечисленных 9 коллекций. Динамический `INSERT ... SELECT` по `collection.code IN (...) AND lt.panel_type <> 'GLAZED'` (или эквивалент через отсутствие строки в подзапросе glazing) — без перечисления конкретных id leaf_type, по прецеденту 0101/0103.

### Схема миграций: только сид-данные, без изменения структуры
В отличие от `glazing_type.surcharge_percent`/`colour_type.surcharge_percent` (которые требовали добавления новой колонки), обе используемые таблицы (`liner_dimension_option`, `dimension_surcharge_rule`) уже имеют все нужные колонки. Нужна одна миграция сид-данных (вставка `liner_dimension_option` для 59мм по нужным leaf_type + одна строка `dimension_surcharge_rule`), без отдельной структурной миграции.

## Risks / Trade-offs

- [Общее правило dimension_surcharge_rule без привязки к leaf_type может неожиданно сработать для другого компонента (frame/edge/casing/extensions), если у него когда-нибудь появится своя опция толщины со значением 59] → Наценка применяется только к цене leaf-компонента (как и цвет/зеркало/остекление) — для остальных типов компонентов шаг наценки за толщину не вызывается вовсе, независимо от их опций размера.
- [Толкование «глухие» как «не остеклённые» (включая «с зеркалом») — интерпретация, а не буквальная формулировка заказчика] → Явно зафиксировано в proposal.md и specs с указанием точного критерия (`panel_type ≠ «остеклённое»`) и списком коллекций/моделей, чтобы заказчик мог поправить до архивации, если толкование неверное.
- [Новый шаг в цепочке наценок меняет итоговую (округлённую) цену в кейсах, где одновременно нестандартна высота и выбрана толщина 59мм, по сравнению с порядком, где толщина была бы после цвета] → Порядок закреплён явным requirement с конкретным сценарием округления, как и для всех предыдущих добавлений; расхождение ожидаемо и покрывается тестом.
