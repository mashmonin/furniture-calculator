## Context

См. proposal.md — «Why» и «What Changes». Это четвёртое применение одного и того же принципа диапазонов (после короба «НЕО»/«Компланар» по высоте, добора «ТС» по длине, наличников «Модо»/«Онда» по длине) — вся инфраструктура уже существует и обобщена, задача сводится к данным + расширению набора кодов. В отличие от предыдущего применения (наличники «Модо»/«Онда»), здесь у разных кодов внутри одного набора — разные допустимые длины в одних и тех же диапазонах высоты, и набор явно включает реверс-варианты как отдельные каталожные коды. Ключевые факты:

1. **Механизм диапазонов уже полностью обобщён и код-агностичен.** `requireLengthWithinLeafRange`/`validateHeightWithinLeafRange` (backend) и `lengthRangeOptions`/`lengthRangeCoversHeight` (frontend), введённые в `link-dobor-ts-length-to-leaf-height` и обобщённые в `link-modo-onda-casing-length-to-leaf-height`, не содержат ничего специфичного для конкретного набора кодов — вся специфика (какие коды входят в правило) живёт в константе `LENGTH_RANGE_DOOR_CASING_TYPE_CODES` (backend и frontend) и в данных `liner_dimension_option`. Задача сводится к: (а) расширить константу 7 новыми кодами, (б) добавить данные диапазонов на уровне Liquibase-миграций. Ни строчки новой логики не требуется.
2. **Каждый из 7 кодов уже имеет ровно одну опцию длины (value=2100, диапазон не задан) на оси «Длина».** Как и «Модо»/«Онда», наличники «Эво» (DCT-001), «Авеню» (DCT-002), «Авеню-реверс» (DCT-005), «Аура» (DCT-006), «Аура-реверс» (DCT-007), «Ария» (DCT-008), «Ария-реверс» (DCT-009) перенесены на ось «Длина» миграцией `0068-door-casing-length-axis.yaml` (см. `general-fixes-leaf-step-colour-casing-length`) — у каждого кода отдельная строка `liner_dimension_option` (владение по `door_casing_type_id`, как и у всех прочих наличников), и соответствующая строка `configuration_price` уже ссылается через `length_option_id`.
3. **Уникальный индекс `uk_liner_dimension_option_door_casing_type` уже включает колонки диапазона.** Миграция `0069-door-casing-type-length-range-index.yaml` (из `link-modo-onda-casing-length-to-leaf-height`, ещё не закоммичена в этой ветке, но уже применена к рабочему дереву) расширила индекс до `(door_casing_type_id, liner_dimension_type_id, value, COALESCE(min_value, -1), COALESCE(max_value, -1))` — это уже разрешает несколько строк с одинаковым value, но непересекающимися диапазонами для одного и того же `door_casing_type_id`, что нужно для группы «Авеню/Ария/Аура» (три диапазона со значением 2700). Новой миграции по индексу не требуется.
4. **Каждый из 7 кодов сегодня в каталоге всегда идёт в паре с коробом «Компланар» (FT-002).** Проверено по всем миграциям, ссылающимся на эти коды через `door_casing_type_id`/`dct.code` (`0010`, `0011`, `0020`, `0028`, `0029`, `0035`, `0040`, `0043`, `0046`, `0049`, `0054`, `0055`): условие всегда `ft.code = 'FT-002'` (для реверс-вариантов — исторически `ft.code = 'FT-004'`, после `0054-rework-reverse-mechanism` эти строки перенесены на `frame_type_id = FT-002` с `is_reverse = true`). Ни разу эти коды не встречаются с «НЕО» (FT-003) или «ФАНТОМ» (FT-001). Как и для наличников «Модо»/«Онда» с коробом «НЕО» (design.md того change, п. 5), это означает, что гейтинг по коду `DoorCasingType`, без явной проверки короба/реверса, эквивалентен по факту ограничению коробом «Компланар» — при этом правило не привязывается к этому факту явно и продолжит работать корректно, даже если это фактическое соответствие в будущем изменится (в этом случае потребуется отдельное решение, а не тихая деградация: набор кодов конечен и явно перечислен).
5. **Внутри набора — две группы с разными длинами в одних и тех же диапазонах.** «Эво» (DCT-001) отличается от «Авеню»/«Ария»/«Аура» (DCT-002, DCT-005, DCT-006, DCT-007, DCT-008, DCT-009) в диапазоне [2150, 2250] (2400 мм против 2700 мм) и в диапазоне [2600, 2850] (доступен только для «Эво», 3000 мм). Механизм не требует различения групп на уровне кода — обе группы гейтятся одной и той же константой `LENGTH_RANGE_DOOR_CASING_TYPE_CODES`, а разница выражается исключительно данными `liner_dimension_option` (у каждого кода — свой набор строк).
6. **Реверс-вариант — это отдельный каталожный код `DoorCasingType`, а не флаг.** В отличие от «Модо»/«Онда» (где реверс-конфигурация недостижима и потому не рассматривалась), здесь у «Авеню», «Ария» и «Аура» есть отдельные реверс-коды (DCT-005, DCT-007, DCT-009) с собственными строками `liner_dimension_option`/`configuration_price`. Правило пользователя «одна и та же длина для наличника независимо от реверса» реализуется тем, что обычный и реверс-код получают идентичный набор диапазонов длины — это решение о данных (Decision 2), а не о логике.

## Goals / Non-Goals

**Goals:**
- Ограничить выбор длины наличников короба «Компланар» — «Эво», «Авеню», «Ария», «Аура», включая их реверс-варианты (DCT-001, DCT-002, DCT-005, DCT-006, DCT-007, DCT-008, DCT-009) — диапазоном высоты полотна, не затрагивая другие наличники.
- Переиспользовать уже обобщённый механизм (backend: `requireLengthWithinLeafRange`/`validateHeightWithinLeafRange`; frontend: `lengthRangeOptions`/`lengthRangeCoversHeight`) без изменения кода — только расширением константы кодов и данными.
- Сделать цену этих наличников независимой от выбранной длины — симметрично добору «ТС» и наличникам «Модо»/«Онда».
- Обеспечить одинаковые допустимые длины для обычного и реверс-варианта одного и того же наличника («Авеню» и «Авеню-реверс» и т. д.).

**Non-Goals:**
- Не переносится диапазонное ограничение на наличники «Модо»/«Онда» (уже ограничены отдельным изменением) — их коды не входят в новый набор.
- Не меняется цена наличников «Эво»/«Авеню»/«Ария»/«Аура» по сравнению с текущей — меняется только то, от чего эта цена формально зависит (перестаёт зависеть от length_option_id).
- Не вводится явная проверка «короб = Компланар» или проверка `is_reverse` в правиле — гейтинг остаётся по коду `DoorCasingType`, как и для «Модо»/«Онда» (см. Context, п. 4).
- Не меняется схема таблиц — используются уже существующие колонки `min_value`/`max_value`/`length_option_id` и уже расширенный уникальный индекс.

## Decisions

### 1. Один набор кодов на 7 значений, без разделения на «группу Эво» и «группу остальных» на уровне кода

`LENGTH_RANGE_DOOR_CASING_TYPE_CODES` расширяется до `Set.of("DCT-001", "DCT-002", "DCT-003", "DCT-004", "DCT-005", "DCT-006", "DCT-007", "DCT-008", "DCT-009")` (backend) и аналогично во frontend-массиве. Разница в допустимых длинах между «Эво» и «Авеню»/«Ария»/«Аура» не требует отдельного под-набора в коде — `requireLengthWithinLeafRange`/`validateHeightWithinLeafRange` проверяют только диапазон конкретной выбранной `liner_dimension_option`, которая уже привязана к конкретному `door_casing_type_id`; какая именно длина доступна для какого кода — целиком вопрос данных.

**Альтернатива (отклонена):** ввести отдельную константу `LENGTH_RANGE_EVO_DOOR_CASING_TYPE_CODES = Set.of("DCT-001")` рядом с общей, чтобы явно отразить в коде особые диапазоны «Эво». Отклонено — единственное, что отличается, это строки `liner_dimension_option`, а не проверяемая логика; отдельная константа ничего не гейтила бы (обе используются в одной и той же проверке) и добавила бы код без функциональной необходимости.

**Итог:** после этого изменения `LENGTH_RANGE_DOOR_CASING_TYPE_CODES` включает все 9 существующих кодов `door_casing_type` (DCT-001–DCT-009) — то есть правило «длина обязательна + совместима с высотой полотна» становится действующим для абсолютно всех наличников каталога. Это не выходит за рамки задачи (правило по-прежнему применяется только там, где для этого есть данные диапазонов, а для будущих новых кодов потребуется отдельное решение — по аналогии с тем, как и раньше набор кодов расширялся явным перечислением), но стоит зафиксировать явно: любой новый `door_casing_type`, добавленный без опций длины с диапазоном, автоматически потребует явной длины (обязательность длины гейтится тем же набором) — если это когда-либо понадобится сделать иначе, потребуется отдельное решение.

### 2. Данные: реверс-вариант получает тот же набор диапазонов, что и обычный наличник

Для каждой из трёх пар (DCT-002/DCT-005, DCT-006/DCT-007, DCT-008/DCT-009) вставляются идентичные по value/min_value/max_value строки `liner_dimension_option` — по одной на каждый код в паре, а не общая строка на пару (владение `liner_dimension_option` — по одному `door_casing_type_id`, как и у всех прочих наличников; общей строки на два кода в схеме не предусмотрено, см. `chk_liner_dimension_option_single_owner`). Это соответствует прочтению исходного запроса пользователя («Эво, Авеню, Ария и Аура, в том числе для дверей поддерживающих реверс») как «одна и та же длина для наличника независимо от того, обычная это конфигурация или реверс» — а не как отдельное требование к реверс-исполнению.

**Альтернатива (отклонена):** запросить у пользователя отдельно длины для реверс-вариантов. Отклонено — формулировка запроса явно перечисляет 4 наличника без разделения на реверс/не-реверс и отдельно уточняет «в том числе для дверей поддерживающих реверс», что читается как «не забыть про реверс-коды», а не как «у реверса другие числа»; технической причины для разных чисел тоже нет (реверс не влияет физически на длину наличника, только на геометрию короба).

### 3. Данные: переиспользование существующей опции 2100 мм под первый диапазон, раздельно по 7 кодам

По тому же приёму, что и в `link-dobor-ts-length-to-leaf-height`/`link-modo-onda-casing-length-to-leaf-height`: для каждого из 7 кодов существующая строка `liner_dimension_option` (value=2100, без диапазона) обновляется на `value=2250, min_value=1900, max_value=2100`, а не удаляется. Затем добавляются новые строки:
- Для DCT-001 («Эво»): value=2400 [2150,2250]; value=2700 [2300,2300]; value=2700 [2350,2550]; value=3000 [2600,2850].
- Для DCT-002, DCT-005, DCT-006, DCT-007, DCT-008, DCT-009 («Авеню», «Ария», «Аура» и их реверс-варианты): value=2700 [2150,2250]; value=2700 [2300,2300]; value=2700 [2350,2550].

Диапазон [2900,2950] не получает опций ни для одного из 7 кодов — наличник в этом диапазоне недоступен, как и в диапазоне [2600,2850] для «Авеню»/«Ария»/«Аура».

**Альтернатива (отклонена):** `DELETE` старой строки + `INSERT` новых. Отклонено по той же причине, что и в предыдущих изменениях — переиспользование строки через `UPDATE` не создаёт зависимости от предварительного обнуления `configuration_price.length_option_id` (FK), в отличие от `DELETE`.

### 4. Цена наличников «Эво»/«Авеню»/«Ария»/«Аура» перестаёт зависеть от length_option_id

По той же причине и тем же приёмом, что и в `link-dobor-ts-length-to-leaf-height`/`link-modo-onda-casing-length-to-leaf-height`: `UPDATE configuration_price SET length_option_id = NULL WHERE door_casing_type_id IN (id для каждого из 7 кодов)`. `matchesDimension`/`findMostSpecificPrice` не меняются — `priceOption == null` уже трактуется как «подходит для любого выбора».

### 5. Уникальный индекс и backend/frontend-код диапазонов не меняются

Индекс `uk_liner_dimension_option_door_casing_type` уже включает колонки диапазона (см. Context, п. 3) — новой миграции по индексу не требуется ни для основного профиля, ни для desktop/H2 (колонки `door_casing_type_key`/`min_value_norm`/`max_value_norm` уже существуют и уже участвуют в индексе). Backend- и frontend-код (`requireLengthWithinLeafRange`, `validateHeightWithinLeafRange`, `lengthRangeOptions`, `lengthRangeCoversHeight`, рендер группы «Длина», `buildCascadeSteps`, сброс выбора в `updateSelection`) уже гейтится единой константой `LENGTH_RANGE_DOOR_CASING_TYPE_CODES` без перечисления конкретных кодов внутри логики — расширение константы автоматически распространяет всю уже существующую логику на новые 7 кодов, изменений в этих местах не требуется.

### 6. Тестовая инфраструктура: без новых перегрузок

`TestEntities.doorCasingType(id, code)` уже введена в `link-modo-onda-casing-length-to-leaf-height` — новых перегрузок не требуется, новые тесты используют существующую фабрику с кодами DCT-001, DCT-002, DCT-005–DCT-009.

## Risks / Trade-offs

- **[Риск]** Обнуление `length_option_id` в существующих строках `configuration_price` для 7 кодов и переиспользование существующих строк `liner_dimension_option` — изменение данных, вставленных ранее применёнными миграциями (`0010`, `0028`, `0029`, `0035`, `0040`, `0068`). → Новые `UPDATE`-changeset'ы, не редактирующие сами эти миграции; приём уже трижды применён в проекте (`link-dobor-ts-length-to-leaf-height`, `general-fixes-leaf-step-colour-casing-length`, `link-modo-onda-casing-length-to-leaf-height`).
- **[Риск]** Расширение `LENGTH_RANGE_DOOR_CASING_TYPE_CODES` до всех 9 существующих кодов `door_casing_type` делает правило «длина обязательна» действующим для каждого наличника в каталоге — любой новый наличник, добавленный в будущем без диапазонных данных длины, либо должен получить хотя бы одну опцию длины (иначе расчёт с ним станет невозможен), либо должен быть сознательно исключён из набора при добавлении. → Смягчается тем, что набор кодов — явный перечисляемый `Set`, а не «все существующие коды» по определению; при добавлении нового наличника разработчик увидит существующий набор и примет явное решение, входить в него или нет (то же соглашение, что и для предыдущих трёх наборов кодов).
- **[Риск]** Как и для «Модо»/«Онда», при несовместимой высоте полотна и отсутствии альтернативного наличника шаг «Наличник» может исчезнуть из UI вместо явного сообщения о недоступности — особенно заметно в диапазоне [2900,2950], где недоступны все 4 наличника короба «Компланар» одновременно. → Тот же принятый риск: backend в любом случае не даст завершить такую конфигурацию расчётом.
- **[Риск]** Идентичные диапазоны для обычного и реверс-варианта наличника — решение, сделанное по прочтению запроса пользователя (Decision 2), а не подтверждённое отдельно на уровне физических размеров реверс-исполнения. → Смягчается тем, что реверс не меняет геометрию самого наличника (только направление открывания/установку короба), и явной информации от пользователя о различии нет; при необходимости различить длины для реверс-кодов это отдельная точечная миграция данных без изменения логики или спецификации (спецификация уже сформулирована в терминах кода `door_casing_type`, а не «обычный/реверс»).

## Migration Plan

1. Liquibase-миграция №1: расширение данных диапазона длины для 7 кодов (`liner_dimension_option`) — `UPDATE` существующей строки value=2100 на value=2250/[1900,2100] для каждого из 7 кодов; `INSERT` новых строк по Decision 3, раздельно для DCT-001 и для группы DCT-002/005/006/007/008/009.
2. Liquibase-миграция №2: `UPDATE configuration_price SET length_option_id = NULL` для 7 кодов (Decision 4).
3. Backend-код: расширение константы `LENGTH_RANGE_DOOR_CASING_TYPE_CODES` семью кодами (Decision 1); логика не меняется.
4. Тесты backend: новые кейсы в `DoorConfigurationPricingServiceTest` — высота внутри/вне диапазона для «Эво» и для «Авеню»/«Ария»/«Аура», разные допустимые длины в одном диапазоне высоты для «Эво» и остальных, точка 2300, разрыв между диапазонами, отсутствие выбранной длины, реверс-код проверяется по тому же диапазону, что и обычный, цена не зависит от длины, регрессия для «Модо»/«Онда» и добора «ТС» не затронута.
5. Frontend-код: расширение константы `LENGTH_RANGE_DOOR_CASING_TYPE_CODES` семью кодами; остальной код не меняется.
6. Проверка: `npm run build` (из `frontend/`); backend-тесты — точечно через `--tests` на класс `DoorConfigurationPricingServiceTest`, не полный `./gradlew test`; ручная проверка в браузере — выбор каждого из наличников «Эво», «Авеню», «Ария», «Аура» (и их реверс-вариантов через переключатель «Реверс») с высотой полотна в разных диапазонах, включая границы (1900, 2100, 2150, 2250, 2300, 2350, 2550, 2600, 2850, 2900, 2950) и разрывы между ними.

Откат — стандартный: новые миграции — новые changeset'ы, откат через Liquibase `rollback`, если потребуется; данные и расширение набора кодов откатываются вместе, не затрагивая «Модо»/«Онда», добор «ТС» и остальные компоненты.
