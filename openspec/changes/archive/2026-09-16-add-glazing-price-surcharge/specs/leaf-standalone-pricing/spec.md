## MODIFIED Requirements

### Requirement: Расчёт стоимости отдельного полотна по его типу
Система ДОЛЖНА (SHALL) предоставлять эндпоинт расчёта стоимости, принимающий id существующего `leaf_type` и набор выбранных клиентом опций полотна: id `liner_dimension_option` для длины и высоты (либо произвольное значение для соответствующей оси, как и при расчёте по `door_configuration`), id `colour_option`, id `mirror_finish_type`, id `glazing_type`, явный признак реверса (булево значение; отсутствие ДОЛЖНО (SHALL) трактоваться как false) — и, независимо от полотна, список позиций фурнитуры. Компоненты, не являющиеся полотном (короб, кромка, наличник, добор), эндпоинтом не рассматриваются, даже если присутствуют в запросе.

#### Scenario: Расчёт стоимости полотна без дополнительных опций
- **WHEN** отправляется запрос расчёта с id существующего `leaf_type` без выбранных опций размеров, цвета, исполнения зеркала и вида остекления
- **THEN** эндпоинт возвращает результат с найденной (если есть подходящая строка `configuration_price`) или не найденной ценой полотна, без ошибки

#### Scenario: Несуществующий тип полотна
- **WHEN** отправляется запрос расчёта с id `leaf_type`, которого не существует
- **THEN** эндпоинт отвечает ошибкой 404 и не выполняет расчёт

#### Scenario: Опция не принадлежит указанному полотну
- **WHEN** в запросе id выбранной `liner_dimension_option` или `colour_option` ссылается на компонент, отличный от указанного `leaf_type`
- **THEN** эндпоинт отвечает ошибкой 400 и не выполняет расчёт

#### Scenario: Надбавки за размер и исполнение зеркала применяются так же, как при расчёте по конфигурации
- **WHEN** в запросе указано произвольное значение длины или высоты полотна, совпадающее с правилом наценки, и/или id допустимого для этого полотна исполнения зеркала, и/или (см. добавленную наценку за остекление) id допустимого для этого полотна вида остекления
- **THEN** итоговая цена полотна включает соответствующие надбавки, рассчитанные по тем же правилам и в том же порядке, что и в расчёте стоимости по `door_configuration`

#### Scenario: Надбавка за реверс применяется по явному признаку в запросе
- **WHEN** в запросе передан явный признак реверса со значением true
- **THEN** к цене полотна применяется та же надбавка за реверс, что и при расчёте по `door_configuration` с `is_reverse = true`, по тем же правилам последовательного применения надбавок

#### Scenario: Без явного признака реверса надбавка не применяется
- **WHEN** в запросе признак реверса не передан либо передан со значением false
- **THEN** к цене полотна надбавка за реверс не применяется

#### Scenario: Признак реверса не влияет на расчёт по door_configuration
- **WHEN** признак реверса передан в запросе к эндпоинту расчёта по `door_configuration` (а не к расчёту отдельного полотна)
- **THEN** он игнорируется — надбавка за реверс для этого эндпоинта по-прежнему определяется исключительно значением `is_reverse` самой `door_configuration`

#### Scenario: Позиции фурнитуры учитываются так же, как при расчёте по конфигурации
- **WHEN** запрос содержит одну или несколько позиций фурнитуры (см. hardware-catalog)
- **THEN** их стоимость рассчитывается и суммируется с ценой полотна так же, как при расчёте стоимости по `door_configuration`
