## Context

См. proposal.md — «Why». Технически наценка за исполнение зеркала (`mirror_finish_type.surcharge_percent`, `MirrorFinishOption`, `resolveMirrorFinishMultiplier` в `DoorConfigurationPricingService`) — уже существующий, работающий образец для ровно той же задачи: глобальный справочник с процентом наценки + таблица владения (`*_option`), связывающая справочник с конкретными `leaf_type`. `GlazingType`/`GlazingOption` (см. миграция `0090-glazing-catalog.yaml`) структурно идентичны `MirrorFinishType`/`MirrorFinishOption`, только без поля наценки и без участия в расчёте — это изменение достраивает симметрию, а не вводит новый паттерн.

## Goals / Non-Goals

**Goals:**
- Добавить `surcharge_percent` к `glazing_type` и задать его для всех шести существующих строк по значениям из proposal.md.
- Провести наценку через тот же конвейер последовательных надбавок, что и наценка за исполнение зеркала, — не вводить отдельный механизм.
- Прокинуть выбор вида остекления с фронтенда в запрос расчёта (сейчас он там осознанно не участвует).

**Non-Goals:**
- Не менять сужение каталога/каскада по виду остекления — оно по-прежнему не сужает `door_configuration` (см. delta door-configurator-ui, «Выбор вида остекления»).
- Не вводить отдельную таблицу бизнес-правил (по образцу `dimension_surcharge_rule`) — наценка остаётся свойством самого `glazing_type`, как и у `mirror_finish_type`, поскольку она не зависит от числового значения, только от выбранного вида.
- Не трогать уже применённый changeset `0090-glazing-catalog.yaml` — новое поле добавляется отдельным changeset'ом (см. CLAUDE.md: заархивированные/выпущенные changeset'ы не редактируются задним числом).

## Decisions

### Место наценки за остекление в последовательности: после исполнения зеркала, до реверса
Порядок надбавок к цене полотна становится: длина → высота → исполнение зеркала → вид остекления → реверс, с округлением после каждого шага (см. `applySequentialSurcharges`). Мирроринг и остекление физически взаимоисключающи для одного и того же `leaf_type` (миграция `0090-5-remove-mirror-finish-for-glazed-models` уже удалила `mirror_finish_option` для остеклённых моделей) — порядок между этими двумя шагами не влияет ни на один реальный расчёт, но фиксируется явно для предсказуемости и на случай появления в будущем полотна, поддерживающего оба варианта.

Альтернатива — вставить наценку за остекление перед исполнением зеркала — отклонена: не даёт никакого практического отличия, а нарушает естественный порядок «сначала уже существующая наценка, потом новая», которому следовали предыдущие изменения этого файла (см. историю добавления зеркала и реверса).

### `surcharge_percent = 0` для «Прозрачное» вместо отдельного признака «базовый вид»
«Прозрачное» — такая же строка `glazing_type`, как и остальные, просто с нулевым процентом; отдельного булева флага «это базовое стекло» не вводится. Это самый простой вариант, согласованный с тем, как `mirror_finish_type` не имеет специальной записи «без зеркала» (сам факт отсутствия выбора эквивалентен нулевой наценке). `resolveGlazingMultiplier` возвращает `BigDecimal.ONE`, если вид остекления не выбран **или** выбрано «Прозрачное» — обе ветки дают одинаковый результат естественным образом, без специального кода под «Прозрачное».

### Наценка применяется только к leaf-компоненту, независимо от способа расчёта
Как и исполнение зеркала, `glazingTypeId` добавляется в `ComponentSelectionDto` (общий для запроса и по `door_configuration`, и по отдельному полотну) и обрабатывается в общей для обоих путей `addComponentIfPresent`/`resolveGlazingMultiplier` — отдельного кода для `calculateForLeaf` не требуется, само устройство сервиса это уже обеспечивает (см. `DoorConfigurationPricingService`).

### Репозиторий: `GlazingOptionRepository.findByGlazingTypeIdAndLeafTypeId`
По образцу `MirrorFinishOptionRepository.findByMirrorFinishTypeIdAndLeafTypeId` — валидирует, что выбранный вид остекления допустим для данного полотна, тем же способом (owned-lookup, а не полный список + фильтрация в памяти).

### Новый Liquibase changeset, не редактирование `0090-glazing-catalog.yaml`
`ALTER TABLE glazing_type ADD COLUMN surcharge_percent NUMERIC(5,2) NOT NULL DEFAULT ...` потребовал бы default для уже существующих строк при добавлении NOT NULL-колонки без явного значения — вместо default он делается как обычно в этом проекте (см. `0060-mirror-finish.yaml`/аналогичные): добавить колонку, затем `UPDATE glazing_type SET surcharge_percent = ... WHERE name = '...'` для каждой из шести строк по имени, отдельными changeset'ами или одним набором `UPDATE`, без default-значения колонки.

## Risks / Trade-offs

- **[Риск]** Будущий `leaf_type`, поддерживающий одновременно исполнение зеркала и остекление (сейчас таких нет), — наценки применятся обе, в порядке зеркало → остекление. → Если/когда такая модель появится, явный порядок в спецификации не потребует пересмотра, только подтверждения, что порядок по-прежнему устраивает бизнес.
- **[Риск]** Фронтенд уже отправляет `glazingTypeId` только как локальное состояние (`glazingTypeId`, не часть `selection.leaf`) — нужно аккуратно включить его в `leafSelection` перед отправкой запроса (по образцу `mirrorFinishTypeId` на строке ~770 `App.tsx`), не забыв про `useEffect`-зависимости debounce-расчёта. → Тестируется вручную через `npm run dev` на реально остеклённой модели (например, `LT-017`).

## Migration Plan

1. Новый Liquibase changeset: добавить `glazing_type.surcharge_percent NUMERIC NOT NULL` + `UPDATE` шести строк по проценту.
2. Backend: `GlazingType.surchargePercent`, `GlazingOptionRepository` (новый метод), `ComponentSelectionDto.glazingTypeId`, `DoorConfigurationPricingService` (резолв + встраивание в последовательность), `GlazingSurchargeDto`, `PricingSurchargesDto.glazingSurcharges`, `PricingSurchargesService`.
3. Frontend: `api/types.ts` (`ComponentSelectionDto.glazingTypeId`, `GlazingSurchargeDto`, `PricingSurchargesDto.glazingSurcharges`), `App.tsx` (включение `glazingTypeId` в запрос расчёта, `computeSurchargeBreakdown`, обновление устаревших комментариев про «ничего не влияет»).
4. Откат — стандартный для Liquibase (down-миграция/новый changeset, отменяющий колонку), код бэкенда/фронтенда откатывается обычным ревертом коммитов; отдельной стратегии отката для данных не требуется (наценка не переписывает уже сохранённые цены, только влияет на новые расчёты).
