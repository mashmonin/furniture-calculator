## Context

См. proposal.md — Why/What Changes. Ключевые факты из текущей кодовой базы:

- `FrameType` — плоская сущность (`id`, `name`, `code`), реализует `CatalogType`. Ни один справочник компонента раньше не имел признаков-флагов такого рода.
- `DoorConfigurationPricingService.pricesFor` резолвит `configuration_price` по `type.getId()` через `switch` по типу компонента; `addComponentIfPresent` уже содержит спецкейсы внутри общего цикла по компонентам: `type instanceof FrameType` (цена короба как сумма `frame_post`, см. archived change `add-frame-post-catalog`) и кросс-компонентная проверка высоты кромки против высоты полотна (см. archived change `link-edge-height-to-leaf-height`). Надбавка за реверс — третий такой кросс-компонентный случай: цена leaf-компонента зависит от того, какой frame_type выбран в этой же конфигурации.
- Code-префиксы: LT- (leaf_type, последний LT-045, не меняется), FT- (frame_type, последний FT-003).
- Коллекции Вертикаль (LC-001, LT-001…007) и Атмосфера (LC-002, LT-008…013) — 13 моделей суммарно, полностью существующие, без изменений.

## Goals / Non-Goals

**Goals:**
- Дать пользователю возможность заказать реверс-исполнение любой модели полотна коллекций Вертикаль/Атмосфера, не создавая для этого отдельных каталожных записей полотна — выбор реверса выражается только выбором короба.
- Применить надбавку за реверс к цене leaf-компонента, когда выбран реверс-короб, изолировав расчёт так, чтобы будущая замена на движок бизнес-правил (Drools) была локальной заменой одной реализации.
- Завести короб «КОМПЛАНАР РЕВЕРС (в проем)» и связать его со всеми 13 существующими моделями полотна Вертикаль/Атмосфера.

**Non-Goals:**
- Не наполняем цены на стойки (`frame_post`) короба «КОМПЛАНАР РЕВЕРС (в проем)» — короб временно остаётся некалькулируемым как компонент «короб», как ранее было с НЕО (см. `0022`/`0023`). Надбавка за реверс не связана с ценой самого короба.
- Не реализуем сейчас движок бизнес-правил (Drools) — надбавка реализуется как простой изолированный расчёт (константа), с очевидной точкой замены.
- Не меняем `leaf_type` — ни новых строк, ни переименований, ни новых полей. Каталог полотна для пользователя выглядит абсолютно так же, как до этого изменения.
- Не вводим отдельный UI-переключатель «требуется реверс» — выбор короба «КОМПЛАНАР РЕВЕРС (в проем)» в уже существующем шаге выбора короба и есть выражение этого выбора.

## Decisions

### is_reverse на frame_type, а не на leaf_type
Первая версия этого изменения помечала реверсивность на `leaf_type` (дублирование 13 строк с суффиксом «РЕВЕРС» в названии). Отклонено по прямому указанию пользователя: реверс не должен порождать отдельные позиции в каталоге полотна — пользователь выбирает ту же самую «Вертикаль 01», реверсивность выражается исключительно выбором короба. Поэтому признак переносится на `frame_type`: `is_reverse` — обычное булево поле, без self-referencing FK и без переиспользования чужих данных (полотно как было, так и осталось единственным источником своих размеров/цветов/цены).

### Надбавка определяется по выбранному frame_type, а не по leaf_type
`DoorConfigurationPricingService.calculate` уже резолвит `configuration.getFrameType()` для конфигурации. Надбавка применяется, если `configuration.getFrameType() != null && configuration.getFrameType().isReverse()` — это булево передаётся в `addComponentIfPresent` только для вызова, строящего leaf-компонент (`applyReverseSurcharge = true`), и `false` для всех остальных компонентов (frame/edge/doorCasing/frameExtensions). Короб при этом продолжает считаться обычным образом (через `frame_post`, либо как некалькулируемый, если цены на стойки нет) — надбавка на его цену не влияет.

### Надбавка — вычисляемая, не хранимая; изолирована в одном месте
Фабрика называет надбавку процентом (+10%) от цены полотна — плавающая величина, которая по решению пользователя будет вынесена в бизнес-правила (Drools) в будущем. Хранить готовую сумму в `configuration_price` было бы неверно: базовая цена уже варьируется по длине/высоте/цвету, хранение потребовало бы дублировать и держать в синхроне N ценовых строк при каждом изменении процента. Вместо этого: `DoorConfigurationPricingService.componentPriceFrom` при `applyReverseSurcharge = true` применяет надбавку через отдельный явно названный метод `applyReverseSurcharge(BigDecimal price)` (константа `REVERSE_SURCHARGE_MULTIPLIER = 1.10`, округление `HALF_UP` до целого), с комментарием, что это временная реализация до появления правил. Замена на Drools в будущем — замена содержимого этого одного метода, остальной код не меняется.

Надбавка применяется только к цене leaf-компонента (retail и dealer — каждая отдельно), не пересчитывает итоговую сумму по конфигурации напрямую — итог по-прежнему просто сумма цен компонентов, поэтому надбавленная цена leaf естественным образом попадает в общую сумму.

### Короб «КОМПЛАНАР РЕВЕРС (в проем)» — обычная новая запись frame_type
Короб для реверс-исполнения физически другой (собирается «в проём»), но по структуре — точно такой же frame_type, как ФАНТОМ/КОМПЛАНАР/НЕО, только с дополнительным флагом `is_reverse`. Совместимость с полотном выражается обычными `door_configuration`-строками — все 13 существующих моделей полотна получают новую пару с этим коробом, без изменений в остальных компонентах пары (наличник/добор/кромка не заданы).

## Risks / Trade-offs

- **[Trade-off] Ответ API не хранит фактическую надбавку явно** — надбавленная цена leaf-компонента — результат вычисления в коде, а не буквальное значение из `configuration_price`. Осознанно принято — таково решение пользователя вынести проценты на уровень бизнес-правил.
- **[Риск] Короб «КОМПЛАНАР РЕВЕРС (в проем)» останется некалькулируемым до данных о стойках** → Смягчение: то же поведение, что уже было с НЕО (см. `0023-neo-frame-post-prices.yaml`) — не регресс, а известный и уже отработанный паттерн «сначала механизм, потом данные».
- **[Риск] Изменение процента надбавки в коде требует деплоя** (до появления Drools) → Смягчение: осознанный компромисс на переходный период, явно задокументированный как временный; процент изолирован в одном методе, поэтому изменение — точечная правка.
