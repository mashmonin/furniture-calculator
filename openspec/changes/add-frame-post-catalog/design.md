## Context

См. proposal.md — Why/What Changes. Ключевые факты из текущей кодовой базы:

- `configuration_price` для frame_type сейчас содержит 0 строк (проверено запросом к БД) — frame-компонент при расчёте стоимости всегда попадает в список некалькулируемых. У frame_type также нет ни одной строки `liner_dimension_option`/`colour_option` — короб сейчас не имеет ни допустимых размеров, ни цветов для выбора клиентом.
- Расчёт стоимости (`DoorConfigurationPricingService.calculate`) для каждого компонента вызывает `addComponentIfPresent`, который валидирует переданные клиентом опции (`validatedDimensionOption`/`validatedColourOption`), затем ищет наиболее специфичную строку `configuration_price` через `findMostSpecificPrice` (фильтрация по совпадению length/height/thickness/colour + выбор строки с максимальным числом непустых ссылок; при неоднозначности — компонент некалькулируем). Эта функция работает одинаково для всех пяти типов компонентов через `pricesFor(CatalogType)` (switch по типу).
- Справочники в проекте (leaf_type, frame_type, edge_type, door_casing_type, frame_extensions_type, colour_type, liner_dimension_type) — плоские id/name/code сущности, реализующие `CatalogType`, без FK друг на друга (кроме недавно добавленной `leaf_type.collection_id`, см. archived change `add-leaf-collection-catalog`).
- Code-префиксы справочников: LT- (leaf_type), FT- (frame_type), ET- (edge_type), DCT- (door_casing_type), FET- (frame_extensions_type), LC- (collection).

## Goals / Non-Goals

**Goals:**
- Дать коробу (frame_type) реальный механизм ценообразования: сумма цен его составных позиций (стоек/комплектов стоек).
- Не ломать существующий алгоритм ценообразования (наиболее специфичная строка configuration_price) для leaf/edge/doorCasing/frameExtensions.
- Наполнить реальными данными пример КОМПЛАНАР из запроса пользователя, чтобы короб этой модели сразу получал корректную цену.
- Показать пользователю в блоке «Короб» состав цены — какие стойки/комплекты в неё входят, с их количеством, длиной (если задана) и ценой.

**Non-Goals:**
- Не вводим выбор клиентом опций размера/цвета для стоек короба — length у frame_post статична (справочная величина конкретной позиции), не выбирается пользователем в запросе на расчёт.
- Не проверяем и не связываем длину боковой стойки (2170) с высотой выбранного пользователем полотна средствами схемы/бэкенда — это просто значение в данных (см. design-решение ниже), без рантайм-валидации между компонентами.
- Не удаляем и не меняем существующий (неиспользуемый для frame_type) механизм `configuration_price.frame_type_id` — схема этой таблицы не трогается.
- Не наполняем данные для короба НЕО (FT-003) — только КОМПЛАНАР (FT-002), по данным, которые дал пользователь.

## Decisions

### post_type — справочник конкретных позиций (SKU), а не абстрактных «сторон» стойки
Рассматривались два варианта: (а) post_type = 2 абстрактных значения («Зарезная стойка» / «Незарезная стойка»), а факт продажи комплектом из нескольких стоек выражается отдельным полем quantity на frame_post; (б) post_type = справочник конкретных продаваемых позиций короба, один-в-один с тем, что называет пользователь («Незарезная стойка», «Комплект зарезных стоек», в будущем — «Комплект короба» и т.п.).

Выбран вариант (б): он точнее соответствует формулировке задачи (пользователь дал два конкретных названия позиций как есть) и не требует придумывать способ описать «комплект короба целиком, включающий оба вида стоек» одной ссылкой на абстрактный тип — при варианте (б) это просто ещё одно значение справочника post_type. Quantity на frame_post остаётся как описательное поле (сколько физических стоек в позиции), не абстрактный тип.

### Цена короба = сумма цен frame_post, а не «наиболее специфичная строка»
Существующий алгоритм `findMostSpecificPrice` подбирает ОДНУ наиболее специфичную строку `configuration_price` на основе совпадения выбранных клиентом опций. Для короба это не подходит: короб не собирается по выбору клиента — он определяется конфигурацией (frame_type) целиком, а его цена — это сумма цен всех его составных позиций (это следует из примера: если пользователь ничего не выбирает у короба, всё равно должна получиться сумма 2027+4027 / 3549+7047). Поэтому для frame-компонента вводится отдельная, более простая ветка расчёта в `DoorConfigurationPricingService`: `sum(dealer_price)`/`sum(retail_price)` по всем `frame_post` данного `frame_type`, без сопоставления с `ComponentSelectionDto`.

### length — простое поле на frame_post, а не переиспользование liner_dimension_option
`liner_dimension_option` — общий полиморфный справочник допустимых ЗНАЧЕНИЙ размера с owner-констрейнтом (ровно один владелец среди 5 типов) и собственным CHECK-ограничением. Заводить frame_post как ещё одного возможного владельца означало бы менять существующее CHECK-ограничение (`chk_liner_dimension_option_single_owner`) — рискованное расширение уже применённого constraint'а ради одной опциональной величины, которая к тому же не выбирается пользователем (см. Non-Goals). Вместо этого `length` — обычный nullable DECIMAL столбец прямо на `frame_post`, по аналогии с тем, как `retail_price`/`dealer_price` уже лежат прямо на строке, а не выносятся в отдельный справочник.

### Уникальность (frame_type_id, post_type_id) на frame_post
Короб не может иметь две разные ценовые записи одного и того же post_type (это было бы неоднозначно — какая из двух цен верна). Уникальный индекс по паре (frame_type_id, post_type_id) предотвращает дублирование, аналогично существующим uk_*_leaf_type индексам на liner_dimension_option/colour_option.

### Код-префикс post_type — `PT-`
Продолжает существующую конвенцию (LT-/FT-/ET-/DCT-/FET-/LC-).

### Список стоек короба — новое поле ComponentCatalogDto.posts, только для frame
`ComponentCatalogDto` уже несёт необязательное поле `collection`, заполняемое только для leaf-компонента (см. archived change `add-leaf-collection-catalog`). По тому же образцу добавляется необязательное поле `posts: List<FramePostDto>` (post_type как `ReferenceDto`, quantity, length, retailPrice, dealerPrice), заполняемое только для frame-компонента — для остальных компонентов остаётся пустым/не задано. Отдельного эндпоинта под frame_post не вводим: это часть того же ответа каталога, что уже отдаёт leaf/frame/edge/doorCasing/frameExtensions. Список чисто информационный — не участвует в `ComponentSelectionDto`/запросе расчёта стоимости; сам расчёт по-прежнему просто суммирует все frame_post данного frame_type на бэкенде (см. «Цена короба = сумма цен frame_post» выше), фронтенд лишь отображает те же записи.

## Risks / Trade-offs

- **[Trade-off] Vestigial `configuration_price.frame_type_id`** — столбец остаётся в схеме, но после этого изменения окончательно перестаёт использоваться приложением для frame_type. Не критично: он и сейчас (0 строк) фактически не используется; убирать его — отдельная, более рискованная миграция вне рамок этой задачи.
- **[Риск] Данные по короба НЕО останутся непосчитанными** (частичный расчёт, как и сейчас) → Смягчение: это то же поведение, что уже есть сегодня для всех коробов — не регресс, а неполное покрытие данными, которое можно закрыть последующим change по образцу этого.
- **[Риск] Длина боковой стойки (2170) верна только при высоте полотна 2000/2100, но система это не проверяет** → Смягчение: явно задокументировано как Non-Goal; если в будущем понадобится валидация, это отдельное расширение схемы (см. design предыдущего change как прецедент послойного наращивания).
