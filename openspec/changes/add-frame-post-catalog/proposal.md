## Why

Короб (frame_type) сейчас не имеет ни одной строки в configuration_price: при расчёте стоимости конфигурации он всегда попадает в список компонентов без найденной цены. Фактически стоимость короба складывается из стоимости составляющих его стоек (боковых «зарезных» и верхней «незарезной», либо всего короба одним комплектом) — эта структура сейчас никак не отражена в модели данных.

## What Changes

- Добавить новый справочник `post_type` (тип позиции короба: например «Незарезная стойка», «Комплект зарезных стоек») — по образцу существующих справочников (leaf_type, frame_type и т.п.).
- Добавить новую таблицу `frame_post`: запись о конкретной стойке/комплекте стоек конкретного короба — ссылается на ровно один frame_type (владелец) и ровно один post_type, хранит quantity (сколько физических стоек в этой позиции — 1, 2 или 3), необязательную length (пока единственное измерение стойки), обязательные retail_price и dealer_price. Короб может состоять из нескольких таких записей (например, отдельно незарезная стойка + отдельно комплект зарезных) либо из одной записи, покрывающей весь короб целиком.
- Изменить расчёт стоимости: для frame-компонента конфигурации стоимость теперь ДОЛЖНА (SHALL) вычисляться как сумма retail_price и сумма dealer_price всех записей frame_post, принадлежащих frame_type этой конфигурации (а не через существующий алгоритм подбора наиболее специфичной строки configuration_price, который остаётся без изменений для leaf/edge/doorCasing/frameExtensions). Короб без ни одной записи frame_post, как и раньше, считается некалькулируемым компонентом.
- Наполнить справочники и данные для короба КОМПЛАНАР (frame_type code `FT-002`): «Незарезная стойка» (1 шт, дилер 2027, розница 3549) и «Комплект зарезных стоек» (2 шт, длина 2170, дилер 4027, розница 7047). Наполнение данных для короба НЕО (`FT-003`) — вне рамок этого изменения.
- Расширить ответ каталога конфигураций (`GET /api/door-configurations`): для frame-компонента дополнительно включить список его записей frame_post (post_type, quantity, length, retail_price, dealer_price), чтобы фронтенд мог показать состав короба, а не только итоговую цену.
- Показать этот список в блоке «Короб» на шаге «Выберите опции» конфигуратора — название позиции, количество, длина (если задана) и цена, вместо пустой карточки без опций.

## Capabilities

### New Capabilities
- `frame-post-catalog`: определяет справочник post_type и структуру frame_post — из каких стоек/комплектов стоек состоит короб и сколько это стоит.

### Modified Capabilities
- `door-configuration-api`: правило подбора наиболее специфичной цены (configuration_price) перестаёт применяться к frame_type-компоненту; для него вводится отдельное правило расчёта стоимости как суммы его записей frame_post; ответ каталога для frame-компонента дополняется списком этих записей.
- `door-configurator-ui`: карточка компонента «Короб» на шаге выбора опций показывает список его стоек/комплектов (название, количество, длина, цена).

## Impact

- **Backend**: новая Liquibase-миграция (таблицы `post_type`, `frame_post`, данные для КОМПЛАНАР); новые JPA-сущности `PostType` и `FramePost`; изменение `DoorConfigurationPricingService` — для frame-компонента источник цены переключается с `ConfigurationPriceRepository` на новый репозиторий `FramePostRepository`, с суммированием вместо подбора наиболее специфичной строки; `DoorConfigurationCatalogService`/DTO каталога дополняются списком frame_post для frame-компонента.
- **Frontend**: типы каталога (`ComponentCatalogDto`) получают новое поле со списком позиций короба; карточка «Короб» на шаге «Выберите опции» отображает этот список.
- **База данных**: новые таблицы `post_type`, `frame_post`. Существующий (нигде не используемый для frame_type) механизм `configuration_price.frame_type_id` не удаляется и не меняется — просто перестаёт использоваться приложением для короба.
