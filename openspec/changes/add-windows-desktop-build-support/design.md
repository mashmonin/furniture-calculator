## Context

`desktopAppImage` (`backend/build.gradle`) сейчас безусловно вызывает `jpackage --type dmg` с macOS-специфичными флагами (`--mac-package-identifier`, иконка `.icns`); переиспользуемые под-таски (`desktopAppLibs`, `desktopFxLibs`, `desktopFrontendAssets`, `desktopJlinkRuntime`) уже платформо-нейтральны — classpath/JavaFX-jar'ы/фронтенд-jar/jlink-рантайм собираются одинаково независимо от ОС (JavaFX Gradle-плагин сам подбирает нужный classifier jar'ов под текущую ОС). `desktopArch` резолвится из `os.arch` текущей JDK в `'x86_64'`/`'aarch64'` — одинаково на Windows и на Intel Mac (то есть значение `'x86_64'` не различает платформу, только архитектуру процессора).

CI (`macos-release.yml`, см. `desktop-release-automation`) сейчас — три job'а: `check-version` → `build` (matrix: две macOS-ноги) → `publish`, с гарантией «нет частичного релиза» через `needs`.

## Goals / Non-Goals

**Goals:**
- Локальная сборка `.msi` под Windows x86_64 через тот же `desktopAppImage`, без дублирования переиспользуемых под-тасков.
- Третья нога в существующей CI matrix, публикующая `.msi` в тот же релиз, что и оба `.dmg`, с сохранением правила «нет частичного релиза» (теперь — на все три сборки).

**Non-Goals:**
- Windows 7 — вне рамок (JDK 21 официально не поддерживает, см. proposal.md).
- Windows ARM64 — отдельная архитектура, не запрошена; не путать с тем, что jpackage/jlink всё равно не смогут собрать её кросс-платформенно с x86_64-раннера, даже если бы потребовалась.
- Подпись кода (code signing) `.msi`/`.exe` — не запрошена, не входит в это изменение; непописанный `.msi` будет вызывать предупреждение SmartScreen у пользователя, это известный и принятый на этом этапе компромисс.

## Decisions

**`--type msi`, не `--type exe`.** `.msi` даёт `--win-upgrade-uuid` — механизм, прямо аналогичный `--mac-package-identifier` на macOS: стабильный идентификатор между сборками, повторная установка заменяет, а не дублирует приложение (см. требование «Замена версии при повторной установке»). UUID генерируется один раз на этапе реализации (`python3 -c "import uuid; print(uuid.uuid4())"` или аналог) и жёстко прописывается в `build.gradle` с комментарием, почему он не должен меняться — смена UUID эквивалентна потере механизма замены версии для уже установивших приложение пользователей.

**Различение имени CI-артефакта от `desktopArch`.** `desktopArch` на Windows-раннере резолвится в `'x86_64'` — то же значение, что и на Intel Mac. Если использовать его напрямую как имя artifact'а в `actions/upload-artifact` (`dmg-${{ matrix.arch }}`, как сейчас), Windows-нога попытается создать артефакт с именем, которое либо совпадёт с существующим (`actions/upload-artifact@v4` требует уникальные имена артефактов в рамках одного workflow run — коллизия), либо потребует отдельного поля. Решение: у каждой ноги matrix — отдельное явное поле `artifactName` (например, `release-macos-aarch64`, `release-macos-x86_64`, `release-windows-x86_64`), не производное от `arch`; `publish` скачивает по паттерну `release-*`. Сам файл на диске (`YaKonfigurator-<version>-x86_64.msi` рядом с `Я-Конфигуратор-<version>-x86_64.dmg`, см. решение о латинском имени ниже) не путается — платформу однозначно определяет расширение.

**Раннер `windows-latest`, не конкретная версия (`windows-2022` и т.п.).** Ровно тот урок, что уже получен с `macos-13` в предыдущем change (см. `desktop-release-automation`) — конкретные версии выводятся из эксплуатации без явной ошибки в job'е, job просто вечно висит в очереди. `windows-latest` — плавающий alias, которым управляет GitHub.

**Явно прописать `PATH` до WiX Toolset в Windows-ноге.** `windows-latest` поставляется с предустановленным WiX Toolset v3 (нужен `jpackage --type msi`), но его `bin`-директория не добавлена в `PATH` по умолчанию (известная особенность образа) — без этого `jpackage` не найдёт `candle.exe`/`light.exe` и упадёт. Путь ищется через glob (`C:\Program Files (x86)\WiX Toolset v3*\bin`), а не хардкодится под конкретную минорную версию (`v3.14` и т.п.) — та же логика, что и с `windows-latest` выше: не привязываться к версии, которую GitHub может обновить.

**Латинское имя приложения на Windows (`YaKonfigurator`), на macOS — прежнее `Я-Конфигуратор`.** WiX собирает MSI-базу в кодовой странице 1252 (Western European), и кириллица в неё физически не помещается: `light.exe` падает с `error LGHT0311` (открытая проблема OpenJDK, JDK-8290471). Поэтому jpackage-имя на Windows — `YaKonfigurator`, итоговый файл — `YaKonfigurator-<version>-x86_64.msi`. Имя задаётся в двух местах, которые нужно менять синхронно: `jpackageName` в `backend/build.gradle` и `matrix.appName` Windows-ноги в `macos-release.yml` (по нему CI находит файл для `upload-artifact`). Название приложения внутри самого окна/меню этим не затрагивается.

**Аргументы jpackage на Windows передаются через `@argfile`.** `ProcessBuilder` на Windows кодирует argv через системную ANSI-кодовую страницу (`sun.jnu.encoding`), а не UTF-8: кириллица в `--name` превращалась в `?` ещё до запуска jpackage (`Invalid Application name`). `@argfile` jpackage читает как UTF-8-текст, минуя это кодирование: все аргументы, кроме пути к `jpackage.exe` (ASCII), пишутся в `build/desktop/<arch>/jpackage-args.txt`, аргументы с пробелами — в кавычках. С переходом на латинское имя исходная причина исчезла, но механизм оставлен как защита от нелатинских символов в путях и прочих аргументах; на macOS команда запускается как раньше, напрямую.

**Платформенные детали Gradle- и CI-сборки на Windows.** (1) `desktopFrontendBuild` вызывает `npm.cmd`, а не `npm`: `Exec` не идёт через shell, и голое `npm` на Windows не находится. (2) В `jlink --module-path` разделитель берётся из `File.pathSeparator` (`;` на Windows, `:` на macOS) — хардкод `:` ломал сборку, так как на Windows двоеточие зарезервировано под букву диска. (3) В workflow Windows-нога — отдельный шаг с `.\gradlew.bat` (`./gradlew` — shell-скрипт), а `"-PappVersion=..."` обязательно в кавычках: без них PowerShell при вызове `.bat` разбивает версию `5.0.1` на части, и вторую Gradle пытается выполнить как имя таска.

**`$APPDIR/../fxlibs` на Windows — рабочее предположение, не подтверждённый факт.** На macOS `--app-content <fxlibs-dir>` кладёт содержимое рядом с `Contents/app` (в `Contents/fxlibs`), поэтому `$APPDIR/..` поднимается из `app/` в `Contents/`. jpackage на Windows кладёт `--app-content` то же самое — рядом с `app/`, в корне инсталляции (`<InstallDir>/fxlibs`), что по структуре аналогично macOS (`$APPDIR` = `<InstallDir>/app`) — поэтому ожидается, что тот же относительный путь `$APPDIR/../fxlibs` сработает без изменений. Это не проверено вживую с этим конкретным проектом — первая локальная сборка на Windows (см. tasks.md, группа 2) и есть проверка этого предположения; если раскладка окажется другой, путь поправляется до перехода к встраиванию в CI (задачи сознательно упорядочены так, чтобы это всплыло раньше).

**CI-веткa добавляется в тот же `macos-release.yml`, без переименования файла на этом этапе.** Название файла отражает историю, а не текущий охват — переименование (например, в `desktop-release.yml`) оставлено отдельным, чисто косметическим шагом по желанию пользователя, не блокирует эту функциональность.

## Risks / Trade-offs

[Пользователь явно выбрал совместить в одном change и Gradle-таск, и CI-интеграцию, без промежуточной остановки на «локально проверено, but CI ещё нет» — значит Windows-ветка в CI окажется впервые протестирована уже в реальном workflow, а не заранее локально на чистой машине] → частично смягчается порядком задач в tasks.md (локальная сборка на Windows-машине — отдельная группа перед CI-веткой, в рамках того же change), но полностью риск не снимается: рассинхрон между локальной Windows-машиной пользователя и `windows-latest`-образом раннера (версия WiX, доступность WiX вообще, отличия PATH) возможен и будет пойман только на реальном CI-прогоне.

[Расширение правила «нет частичного релиза» на три сборки означает, что сломанная Windows-ветка теперь блокирует публикацию уже рабочих macOS-сборок тоже — раньше (при двух macOS-ногах) это было симметрично только между macOS-архитектурами, сейчас цена поломки одной платформы выросла] → осознанный trade-off, тот же принцип, что уже применён и одобрен для macOS (см. `desktop-release-automation`); не блокировать частичный релиз для этого change менять не требовалось.

[`--win-upgrade-uuid` — если будет случайно сгенерирован заново в будущей сборке вместо переиспользования зафиксированного значения, следующая установка создаст вторую копию приложения вместо замены] → митигируется комментарием в `build.gradle` рядом со значением, явно запрещающим его менять (тот же паттерн, что уже используется для `--mac-package-identifier`).
